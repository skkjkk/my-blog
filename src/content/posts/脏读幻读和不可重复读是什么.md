脏读、不可重复读、幻读是并发读取时因隔离级别不够而产生的三类数据异常。一句话区分：脏读读到的是别的事务还没提交的数据，不可重复读是同一行的值被别的事务改掉了，幻读是同一条范围查询前后返回的行数不一样。越靠后的异常越难防，也越需要更严格的隔离级别。

## 脏读：读到了别的事务还没提交的数据

一个事务读到了另一个事务**尚未提交**的数据，就是脏读。之所以叫「脏」，是因为对方随时可能回滚，你手里这份数据可能从未真正存在过。

:::caution
场景：A 事务把余额从 100 改成 0 但**没有提交** → B 事务读到余额 = 0 → A 事务回滚 → B 读到的 0 是**根本不存在的数据**。
最危险的地方在于 B 会拿它做决策：看到余额为 0 就拒绝下单，而真实余额是 100，业务判断直接错了。
:::

## 不可重复读：同一行两次读到的值不一样

一个事务在**两次读取同一行数据**之间，别的事务**修改并提交**了它，导致前后两次读到的值不同。

:::caution
场景：A 事务读余额 = 100 → B 事务改成 50 并提交 → A 事务再读同一行 = 50。
关键限定：针对的是 **UPDATE**（修改已存在的行），变的是**单行数据的值**，结果集的行数并没有变。
:::

## 幻读：两次相同的范围查询，行数不一样

一个事务在**两次执行相同的范围查询**之间，别的事务**插入或删除**了符合条件的行，导致前后两次查询返回的**行数**不同。

:::caution
场景：A 事务执行 `SELECT * FROM orders WHERE amount > 100` 查到 10 行 → B 事务插入一条 `amount = 200` 的订单并提交 → A 事务再查变成 **11 行**，多出来的那行就是「幻影行」。
关键限定：针对的是 **INSERT / DELETE**，变的是**结果集的行集合**，而不是某一行里的值。
:::

## 一张表看清三者的本质区别

| | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| **读到了什么** | 别的事务**未提交**的数据 | 别的事务**已提交**的修改 | 别的事务**已提交**的新增行 |
| **触发操作** | 读 | **UPDATE**（改值） | **INSERT / DELETE**（改行数） |
| **影响对象** | 值的**正确性** | 同一行的**值不一致** | 结果集的**行数不一致** |
| **严重程度** | 最高（读到根本不存在的值） | 中 | 中，但影响面最广 |

排序要分两个维度看：按「数据错得有多离谱」，脏读最严重，它读到的是根本不存在的值；按「需要多严格的隔离级别才挡得住」，排序是脏读 < 不可重复读 < 幻读，一步比一步难防。

## 四种隔离级别分别挡住了哪一种

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| **读未提交（RU）** | 可能 | 可能 | 可能 |
| **读已提交（RC）** | 已避免 | 可能 | 可能 |
| **可重复读（RR）** | 已避免 | 已避免 | **基本避免**（有例外） |
| **串行化（Serializable）** | 已避免 | 已避免 | 完全避免 |

规律很整齐：**每提高一级，就多挡住一种异常**。RU 什么都不挡；RC 只挡住脏读；RR 挡住脏读和不可重复读；Serializable 靠事务串行执行把三种全挡住，代价是并发度最低。

## MySQL 的 RR 并没有完全消除幻读

InnoDB 在 RR 下靠 **MVCC + 间隙锁 + 临键锁** 挡住了大部分幻读，但仍有两个必须记住的例外。

例外一：**当前读依旧会看到别的事务新提交的行。**

- **快照读**（普通 `SELECT`）读的是 MVCC 快照版本 → 看不到别的事务新插入的行 → 不幻读
- **当前读**（`SELECT ... FOR UPDATE`、`LOCK IN SHARE MODE`、`UPDATE`、`DELETE`）读的是**最新版本并加锁** → 会看到新插入的行 → **可能幻读**

```sql
-- RR 下同一事务里混用两种读，就会「看见」那条本来不存在的新行
SELECT * FROM orders WHERE id = 5;        -- 快照读：不存在（用的是事务首读时的快照）
-- 此时别的事务插入了 id = 5 并提交
UPDATE orders SET status = 'paid' WHERE id = 5;  -- 当前读：读的是最新版本，命中了这条新行
SELECT * FROM orders WHERE id = 5;        -- 本事务自己的修改可见 → 这条「幻影行」冒出来了
```

例外二：**MVCC 的快照是在事务第一次快照读时建立的**，同一事务后续的快照读都复用这个快照，所以别的事务后来提交的修改一概看不见——这正是「可重复读」的实现方式。

:::tip
因此「RR 里已经查过了，所以别人插不进来」这个推断只在锁得住的前提下成立；当前读与快照读混用，或者语句没走索引、锁范围退化时，都不能指望它。
:::

## 间隙锁与临键锁：RR 防幻读的底层机制

InnoDB 在 RR 下对**范围查询加锁**时用的是**临键锁（Next-Key Lock）= 记录锁 + 间隙锁**。记录锁锁住已有的行，间隙锁锁住「记录与记录之间的空隙」，于是**别的事务无法往这个空隙里插入新行**，幻读从源头被消掉。

:::caution
间隙锁是双刃剑：它靠**阻塞插入**来防幻读，高并发下会显著抬高锁等待与死锁概率。这也是很多系统改用 RC、用更小的锁范围换并发的原因——InnoDB 在 RC 下对普通范围扫描基本不再加间隙锁（外键约束与唯一性检查时仍会加）。
:::

## 解决幻读的三个务实选项

- **选项一：降到 RC 隔离级别。** 放弃一部分一致性，换更高的并发和更少的死锁，是互联网高并发场景的常见选择；不可重复读那部分风险交给业务层的条件更新与唯一索引去兜。
- **选项二：保持 RR，接受当前读的幻读，在业务层做唯一性约束兜底。** 典型做法是用唯一索引防重复下单，让数据库的约束而不是隔离级别来保证不重。
- **选项三：真的需要严格一致时上 Serializable。** 三种异常都能避免，但性能代价大，基本只在极少数场景用。

## 实战里最常踩的其实不是幻读

真实系统里最常出问题的，是**不可重复读带来的业务错误**，而不是教科书反复强调的幻读。

- **读-改-写**：先查库存再扣减，两步之间被别人改掉了 → 超卖
- **判断-执行竞态**：`if (containsKey) put` 这种写法，并发下会重复插入

```sql
-- 错的：查和改是两条语句，中间隔着的这段时间谁都能改掉这一行
SELECT stock FROM product WHERE id = 1;   -- 读到 100
UPDATE product SET stock = 99 WHERE id = 1; -- 别人已经扣过，你把它覆盖了

-- 对的：把判断和修改合并成一条原子语句
UPDATE product SET stock = stock - 1 WHERE id = 1 AND stock >= 1;
-- 影响行数为 0 就代表库存不足，完全不需要依赖隔离级别
```

:::tip
这类问题的正解不是把隔离级别往上调，而是**条件更新、唯一索引、乐观锁版本号**——靠数据库的原子操作保证正确性，而不是靠隔离级别。
:::

## 常见追问

**Q：不可重复读和幻读的界线到底在哪？**
A：看变的是什么。同一行被 UPDATE 改了值，你两次读到不同的数，是不可重复读；符合条件的行被 INSERT / DELETE 改了数量，你两次查出不同的行数，是幻读。

**Q：RR 能彻底解决幻读吗？**
A：不能。快照读靠 MVCC 快照看不到新行，但当前读读的是最新版本，同一事务里两类读混用仍会冒出「幻影行」，还需要唯一索引这类约束兜底。

**Q：为什么很多互联网系统宁可用 RC？**
A：RC 下范围扫描基本不加间隙锁，锁范围小、并发高、死锁少；代价是可能出现不可重复读，通常用条件更新、唯一索引、乐观锁在业务层解决，而不是靠隔离级别。

**Q：MVCC 凭什么能实现可重复读？**
A：快照在事务第一次快照读时建立，之后同一事务的普通 SELECT 都读这个快照对应的一致性视图，别人后来提交的修改一概看不见，所以两次读到的值一样。

## 易错点

- **把幻读说成「同一行读到了不同的值」。** 那是不可重复读。幻读变的是结果集的行数与行集合，值本身可能一个字都没改。
- **以为 RR 已经彻底消除幻读。** 普通快照读看不到新行，但 `FOR UPDATE`、`UPDATE`、`DELETE` 这类当前读看得到最新数据，两类读混用就会「多出行来」。
- **以为提高隔离级别能解决所有并发写错。** 先查后改、判断再执行这类竞态，加锁换来的只是锁等待和死锁，正解是条件更新、唯一索引与乐观锁。
- **把间隙锁当成纯粹的好东西。** 它靠阻塞插入防幻读，高并发下锁等待和死锁概率都会上升，这是选 RR 还是 RC 时必须权衡的代价。

## 一句话记住

:::tip
脏读读到不存在的数据；不可重复读是同一行被改；幻读是同一范围的行数被增删。
:::
