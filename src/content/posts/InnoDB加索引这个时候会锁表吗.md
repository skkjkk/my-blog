**答案分两层：加索引时锁的是"元数据"，不是"数据行" —— 但元数据锁（MDL）仍可能阻塞你的业务。** MySQL 5.7 之前 DDL 是"拷数据 + 锁表"，5.7 之后改为 **inplace 算法**（尽量不拷贝数据），8.0 支持 **INSTANT**（只改元数据）。

## 先分清两种"锁"

- **MDL（元数据锁）**：保护**表结构**（表是否存在、列定义、索引信息）→ **DDL 操作必然要拿**（通常是 X 锁）
- **数据锁（行锁/表锁）**：保护**数据行** → **加索引不需要**

:::tip
**所以准确说法是：加索引不锁数据行，但会拿元数据锁。**
:::

## MDL 的真正危险：读写请求会被"排队阻塞"

MDL 是**读读共享、读写/写写排斥**的，且**请求按队列排队（不能插队）**。也就是说普通 SELECT 之间互不干扰，可一旦有 DDL 在队首等写锁，后面来的读锁请求也只能排在它后面等——业务查询的耗时不再取决于自己，而取决于前面那个 DDL 要等多久。

:::tip
**经典故障场景**：

```
① 长事务 A 正在执行 SELECT（持有 MDL 读锁）
② DDL 加索引（申请 MDL 写锁）→ 排在队列中等待
③ 此时新的 SELECT/BEGIN 申请 MDL 读锁 → **排到 DDL 后面！**
④ DDL 等 A 结束、A 又等队列前面的 DDL → **所有业务请求全部堵死**

```
**这是"加索引把整个库拖垮"的经典成因，也是最值得记住的答案。**
:::

## 加索引的具体算法（决定锁多久）

| 算法 | 版本 | 是否需要锁表 | 说明 |
|---|---|---|---|
| **COPY** | 所有版本 | ❌ | **建临时表 + 拷贝全表 + 加索引 + 改名** → **期间允许读，但写被阻塞** |
| **INPLACE** | 5.6+ | ⚠️ **部分** | **不拷贝数据**，直接在原表上加索引；**期间允许读写**，但**⚠️ 需要短暂 MDL 排他锁**（元数据切换瞬间） |
| **INSTANT** | 8.0+ | ✅ 只改元数据 | 仅支持**加列、改列名、改默认值、加虚拟列**等操作；⚠️ **加索引仍走 INPLACE** |

## 关键限制：INPLACE 加索引仍有两个"卡点"

- **① 开头与结尾需要短暂 MDL 排他锁**（准备阶段与提交阶段各一次）→ **这两个瞬间会阻塞读写**
- **② ⚠️ 中途必须持有 MDL 共享锁** → 期间**新来的 DDL 会被阻塞**（同一张表上排队），但**普通读写不受影响**
- **③ ⚠️ 若有长事务持有 MDL 读锁**（如一个跑了 10 分钟的事务），**DDL 会一直等** → 而后面的新查询又排在 DDL 后面 → **触发第 2 点描述的全面阻塞**

:::tip
**所以"INPLACE 不锁表"不等于"加索引毫无影响"。**
:::

## 在线 DDL 工具（真正避免阻塞的方案）

| 工具 | 原理 | 特点 |
|---|---|---|
| **gh-ost**（GitHub） | **影子表**，读 binlog 异步同步变更（**不用触发器**），再原子切换 | 不阻塞读写、支持限流、MySQL 5.6+ |
| **pt-online-schema-change**（Percona） | 触发器 + 影子表 | 成熟稳定、支持限流 |
| **MySQL 8.0 `ALGORITHM=INSTANT`** | 直接改元数据 | **仅加列等少数操作**，不支持加索引 |

:::tip
**大表加索引的生产标准做法 = gh-ost / pt-osc。**
:::

## 生产操作清单（可直接照做）

- **① 选低峰期 + 确认无长事务** —— 先查 `SELECT * FROM information_schema.innodb_trx WHERE trx_started < NOW() - INTERVAL 10 SECOND`（**长事务是头号杀手**）
- **② 大表用在线 DDL 工具**（gh-ost / pt-osc），小表直接 `ALTER TABLE`
- **③ 限流**：gh-ost 用 `--max-load`、`--chunk-size`、`--max-lag-millis` 保护主库
- **④ ⚠️ 评估磁盘空间** —— 影子表需要**约等于原表大小的额外空间**
- **⑤ 评估主从延迟** —— DDL 产生大量 binlog → **从库回放延迟飙升**
- **⑥ ⚠️ 避开备份窗口 / 大事务期间 / 主从切换期间**

## 其他必须知道的 DDL 特性

- **MySQL 8.0 的原子 DDL** —— DDL 要么完全成功要么完全失败，**不会留下"改了一半"的表**（5.7 之前崩溃可能留下损坏的表）
- **⚠️ DDL 会隐式提交** —— DDL 之前的事务会被提交 → **DDL 前确认事务边界**
- **⚠️ `ALTER TABLE` 一次加多个列/索引只重建一次** —— **把多个 DDL 合并成一条语句**，避免多次全表重建

## 易错点

- **直觉是"加索引必然锁表、业务全停"** → 正确说法：加索引不加任何数据锁，只拿 MDL；真正致命的是 MDL **按队列排队**，把后续普通查询一起挡在后面。
- **直觉是"INPLACE 就等于完全无锁"** → 正确说法：INPLACE 仍要在**准备阶段和提交阶段各拿一次短暂的 MDL 排他锁**，中途还持 MDL 共享锁，期间新 DDL 只能排队。
- **直觉是"8.0 有 INSTANT，加索引也能秒完成"** → 正确说法：INSTANT 只覆盖**加列、改列名、改默认值、加虚拟列**等操作，**加索引仍然走 INPLACE**。
- **直觉是"DDL 出错可以跟着事务一起回滚"** → 正确说法：**DDL 会隐式提交**，它前面的事务先被提交掉，执行前就得确认好事务边界。

## 常见追问

**问：加索引到底锁不锁表？**
**答：** 锁的是元数据不是数据行——DDL 必然要拿 MDL（通常是 X 锁），但不会给数据加行锁/表锁，所以"锁住整张表的数据"这个说法是错的。

**问：那真正的风险在哪？**
**答：** MDL 请求按队列排队、不能插队。长事务持 MDL 读锁时 DDL 在后面等，之后新来的 SELECT 又排到 DDL 后面，DDL 等长事务、后到的查询等 DDL，整表请求全部堵死，这是"加索引把库拖垮"的经典成因。

**问：算法是怎么演进的，INPLACE 又卡在哪？**
**答：** COPY 建临时表拷贝全表、期间写被阻塞；INPLACE（5.6+）不拷贝数据、期间允许读写，但首尾各需一次短暂 MDL 排他锁、中途持 MDL 共享锁挡住新 DDL；INSTANT（8.0+）只改元数据，但加索引仍走 INPLACE。

**问：大表加索引，生产上你具体怎么操作？**
**答：** 先查 `innodb_trx` 确认没有长事务、选低峰期，再上 gh-ost / pt-osc 用影子表异步同步 + 原子切换，配 `--max-load`、`--chunk-size`、`--max-lag-millis` 限流，并提前评估磁盘空间和主从延迟。

## 一句话记住

:::tip
**加索引不锁数据行，真正能堵死整表的是 MDL 排队。**
:::
