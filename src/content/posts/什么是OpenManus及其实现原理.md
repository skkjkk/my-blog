OpenManus 是一个开源的通用 AI Agent 框架，它的实现原理可以浓缩成三件事：多角色分工、文件即外部记忆、计划显式落盘。它出现在 2025 年，由 Manus 社区的开源复现项目发起，目标是在开源环境下复现 Manus 那类「通用任务执行 + 交付成品」的 Agent 形态。所以理解它最好的方式是把它与 Manus 对照着看，而它的核心贡献是把「多角色 + 沙箱 + 长程任务」这套工程设计公开化。

## 它是什么：开源复现 Manus 的通用 Agent 框架

Manus 本身是闭源商业产品，社区拿不到它的代码。OpenManus 的做法是在分析 Manus 公开演示的行为特征之后，独立实现了一套等价的架构，因此两者的关系是**复现**而不是抄袭，代码是社区自己写的。

这个定位决定了它的价值所在：把 Manus 那类「多角色 + 沙箱 + 长程任务」的工程设计公开化，变成可学习、可改造的源码。闭源产品上你看不到角色怎么切、上下文怎么隔离、长任务怎么兜住记忆，这些在 OpenManus 里全部摊开。

## 核心是多 Agent 角色分工

它把任务拆给若干专门角色，每个角色的职责边界都很清楚：

| 角色 | 职责 |
| --- | --- |
| 规划者（Planner） | 整体理解任务、做任务分解，产出可执行的步骤计划 |
| 执行者（Executor） | 按计划逐步调用工具推进任务 |
| 浏览器操作者（Browser） | 页面访问、交互与信息抽取 |
| 报告者（Reporter） | 把过程与结果汇总成最终交付物 |
| 程序员（Coder） | 编写并运行代码，处理需要编程的环节 |

角色之间通过**结构化消息交接**，而不是共用一个上下文。这是整套设计的关键：每个角色有独立的提示词、上下文与工具集，规划者不必背着浏览器抓回来的大段网页，执行者也不继承规划者的全部推理痕迹，上下文因此不会互相污染。

工具与执行环境是这套分工的支撑：内置代码执行器（写 Python 并真实运行，做数据分析、绘图、文件处理）、浏览器自动化（页面访问、交互、抽取）、文件系统操作，以及多模型接入——可以给不同角色配置不同模型，用强模型做规划、用便宜模型做执行。

## 文件即外部记忆：计划和产物都外置

长程任务必然超出上下文窗口，OpenManus 的做法是**把中间产物写入工作区的文件**，上下文里只保留**文件路径与摘要**，需要时再读回。这和 Manus 的思路一致，也是长程 Agent 应对上下文限制最有效的通用手段之一。

**计划本身也要落盘**。规划者写出的计划不是留在内存里，而是作为可读可改写的文件放在工作区，带来两层好处：一是人可以审阅和干预，改计划就等于改任务走向；二是计划不会因为上下文被压缩或截断而丢失，执行到很后面时仍能回到原版计划对照。

和「压缩摘要」相比，文件的优势是能精确回读：摘要是有损的，读十次还是那份摘要；文件是原始产物，需要哪一段就精确打开哪一段。

## 一次任务是怎么跑完的

典型链路是：接收任务 → 规划者拆解并写出计划（写入 plan 文件）→ 执行者按步骤调用工具 → 产出物落盘 → 报告者汇总生成最终交付物（报告 / 网页 / 表格）。展开成步骤就是：

1. 规划者理解目标，把任务拆成可执行步骤
2. 计划写入 plan 文件，形成可审阅的显式计划
3. 执行者按步骤调用工具，需要资料时交给浏览器操作者抓取，需要计算和跑数据时交给程序员
4. 每一步的产出物落盘到工作区，数据文件、中间文档、截图都留在那里
5. 报告者读取这些产物，汇总成最终交付物

工作区大致是下面这样的结构（示意）：

```text
workspace/
├── plan.md            # 规划者写出的步骤计划，可读可改
├── notes/             # 检索到的资料与中间摘要
├── outputs/           # 代码执行、绘图产生的中间产物
└── deliverables/      # 报告者汇总出的最终交付物
```

plan 文件里通常是一份带状态的清单，执行者按它推进，也按它判断还剩什么没做（示意）：

```markdown
- [x] 明确任务目标，确认交付物形态
- [x] 收集资料，摘要写入 notes/
- [ ] 清洗数据并生成对比表，产出 outputs/
- [ ] 汇总成结论文档，产出 deliverables/
```

这条链路还有一个容易被忽略的设计：它是**交付物导向**的。任务的终点不是「模型觉得做完了」，而是一份具体产物（报告 / 网页 / 表格）落在工作区，于是「完成」有了客观标准，可以被人直接检查。

## 与主流框架的定位差异

| 框架 | 强项 |
| --- | --- |
| LangGraph | 可控的图式编排 |
| AutoGen / CrewAI | 角色对话 |
| ADK | 协议互操作与企业级能力 |
| OpenManus | 把 Manus 式通用 Agent 的完整形态摊开给你看 |

所以它的竞争点不在「跑得更好」，而在教学价值与参考价值极高：想知道一个通用 Agent 产品内部大概长什么样、角色怎么切、长程任务靠什么兜住上下文，读它的源码比读任何架构文档都快。选型时如果需求是稳定可控的流程编排，LangGraph 更合适；要快速搭角色协作，AutoGen / CrewAI 更直接；OpenManus 更适合当参考实现和学习基线。

## 它的局限

- **多 Agent 带来显著成本**：每个角色独立上下文、独立调用，token 消耗与延迟都会明显上升。
- **长程可靠性仍不足**：错误会随步骤累积，前面一步的偏差会被后面的步骤继承并放大。
- **没有生产级的治理**：预算守卫、权限隔离、审计、优雅停机这些能力，在开源复现项目里通常较弱。
- **评测与可复现性不足**：缺少稳定的评测口径，很难证明改动之后到底变好还是变坏。

**结论是它更像一个很好的学习与实验基线，而不是可以直接上生产的框架。**

## 常见追问

**Q：OpenManus 和 Manus 到底是什么关系？**
A：复现关系。Manus 是闭源商业产品，OpenManus 是社区分析它公开演示的行为特征后独立实现的等价架构，不是拿它的代码改出来的。

**Q：计划为什么一定要写成文件，放内存里不行吗？**
A：内存里的计划会随上下文压缩、截断而失真，也没法被人直接编辑。落盘之后计划变成可读可改的产物，既能人工干预，也能在执行到后期时回读原版对照。

**Q：为什么不干脆用一个 Agent、一个大上下文把活干完？**
A：上下文会互相污染，工具集也会膨胀到模型选不准。角色分离让每个角色只背自己需要的上下文和工具，本质是用隔离换稳定与成本可控。

**Q：能直接上生产吗？**
A：不建议。预算守卫、权限隔离、审计、优雅停机这类治理能力较弱，评测也不足。它更适合当学习基线或内部实验框架，生产要在它上面自己补齐治理层。

## 易错点

- 说成「OpenManus 抄了 Manus 的代码」。Manus 闭源，拿不到代码，它是基于公开演示的行为特征做独立实现，属于复现。
- 把多 Agent 当成免费的性能优化。角色越多，上下文与调用次数越多，成本和错误累积都会上升，分工是为了隔离与可控，不是白拿的收益。
- 把「文件即外部记忆」理解成「顺手把日志存下来」。它的关键动作是上下文里只留路径与摘要、需要时精确回读，文件是上下文的替代品，不是附属日志。
- 只答「它是一个多 Agent 框架」就收尾。面试要答到计划落盘、产物外置这两条长程机制，缺了就等于没讲实现原理。
