最左前缀匹配是**联合索引的使用规则**：联合索引 `(a, b, c)` 中，查询条件必须**从最左列开始连续匹配**才能命中索引，否则后续列失效。原因在于索引在 B+ 树里按 `(a, b, c)` 的字典序排列，只有前缀连续，后面的列才在同一个连续区间内全局有序、才能被继续定位。

## 底层原理：B+ 树的有序性

联合索引 `(a, b, c)` 在 B+ 树中的**排序规则是字典序**：先按 `a` 排，`a` 相同再按 `b` 排，`a` 和 `b` 都相同再按 `c` 排。

:::tip
**所以整个索引有序的前提是 `a` 有值**。如果 `a` 不确定（范围查询或没传），后面的 `b`、`c` 就**无法定位** —— 因为它们只在 `a` 相同的那个连续区间内有序。
:::

换句话说，索引的「有序」是**全局的**还是**局部的**，取决于前缀是否固定：`a` 用等值条件定死，剩下的 `(b, c)` 就是一段全局有序的数据；`a` 一旦变成一段区间，`b`、`c` 的有序性就碎成了很多小段，每段只在各自区间内有效。

## 四种匹配情况（`(a, b, c)` 为例）

| 查询条件 | 命中情况 | 说明 |
|---|---|---|
| `WHERE a=?` | ✅ a | 索引定位 |
| `WHERE a=? AND b=?` | ✅ a, b | 索引定位 |
| `WHERE a=? AND b=? AND c=?` | ✅ a,b,c | **完全命中，可覆盖** |
| `WHERE a=? AND c=?` | ⚠️ **仅 a** | **b 断链，c 失效** |
| `WHERE b=?` | ❌ **完全失效** | 无法定位 |
| `WHERE b=? AND c=?` | ❌ **完全失效** | 同上 |
| `WHERE a=? AND b>? AND c=?` | ⚠️ **仅 a, b** | **范围查询之后 c 失效** |

## 为什么"范围查询之后的列失效"

B+ 树在 `b` 上是**区间扫描**（`b > 10`），扫过多个不同的 `b` 值 → 这些区间内的 `c` **不再全局有序** → 无法用 `c` 继续缩小范围。

:::tip
**这是最常被问的细节。** 结论：**联合索引中，等值条件列要放在范围条件列前面。**
:::

## 为什么"跳过中间列"会失效

索引按 `(a, b, c)` 排序 → 已知 `a` 之后，`b` 的值在**连续的 a 区间内**有序；此时要查 `c`，但 `c` 只在 `(a,b)` 都相同的区间内有序 —— **跳过 b 就无法定位 c**。

:::tip
**类比字典：按"省份-城市-区县"排序，知道省份能定位，知道城市能定位，但只知道区县无法定位。**
:::

## "最左前缀"指的是索引列顺序，不是 SQL 里 WHERE 的书写顺序

```sql
-- 索引 (a, b, c)
WHERE b=? AND a=?          -- ✅ 一样能用（优化器会重排）

```

很多人把「最左」误读成「WHERE 里先写谁」，其实优化器会把等值条件按索引列顺序重排，`WHERE b=? AND a=?` 与 `WHERE a=? AND b=?` 是完全等价的执行计划；真正决定前缀的是**建索引时写的列顺序**，与 SQL 文本的书写顺序无关。

:::tip
**SQL 条件的书写顺序不影响索引命中**，只有**索引定义的列顺序**决定前缀。
:::

## 范围查询也能"部分使用"后续列（覆盖索引仍可生效）

⚠️ **重要区分**："失效"指的是**无法用于索引查找（定位）**，但**仍会存进索引** → 所以仍可以用于**覆盖索引**。

```sql
-- 索引 (a, b, c)
SELECT a, b, c FROM t WHERE a=? AND b>?;   -- c 无法定位，但 c 在索引里 → 不回表

```

:::tip
**这是"索引失效但查询仍很快"的原因**，很多人在这点上混淆。**区分两个概念：能否用于"查找" vs 能否用于"覆盖"。**
:::

## ORDER BY / GROUP BY 也遵循最左前缀

```sql
-- 索引 (a, b, c)
WHERE a=? ORDER BY b, c      -- ✅ 利用索引有序性，无需 filesort
WHERE b=? ORDER BY a         -- ❌ 无法利用

```

原因和查询定位是同一件事：索引本身已经按 `(a, b, c)` 排好序，`a` 定值后取出的记录天然按 `b, c` 有序，直接顺着索引读就是结果顺序；反过来 `b` 定值时 `a` 在索引里是乱序的，只能把数据捞出来再额外排序（`Using filesort`）。同理，`ORDER BY` 的列顺序和方向要跟索引一致，普通升序索引上写 `ORDER BY b DESC, c ASC` 这种方向混排也用不上（除非专门按这个方向建了降序索引）。

:::tip
**这是"建索引时把排序列也考虑进去"的依据** —— 把排序列接到等值条件列之后，就能消除 `Using filesort`。
:::

## 实践建议

- **建联合索引时，按"等值条件 → 范围/排序条件"的顺序排列**
- **最左列要是高频查询条件**，否则索引的绝大部分都用不上
- **覆盖索引设计时，把 SELECT 列按同样顺序追加** → 既能定位又能免回表
- ⚠️ **不要以为"我把 WHERE 条件按索引顺序写"就够了** —— **必须真的有这个联合索引**，单个列上的索引无法拼接

## 常见追问

**问：为什么跳过了中间的列，后面的列就用不上了？**
**答：** 索引按 `(a, b, c)` 字典序排列，`c` 只在 `(a, b)` 都相同的连续区间内有序；`b` 没定值，区间就被打散成很多段，无法再用 `c` 定位，本质是「局部有序不等于全局有序」。

**问：最左前缀指的是 SQL 里 WHERE 条件的书写顺序吗？**
**答：** 不是。优化器会把等值条件重排，`WHERE b=? AND a=?` 和 `WHERE a=? AND b=?` 的执行计划一样；决定前缀的只有**索引定义的列顺序**。

**问：范围查询后面的列真的"失效"了吗？**
**答：** 只是**无法用于索引查找定位**；这些列仍然存在索引里，查询只用到索引中已有的列时依旧能走覆盖索引、不回表 —— 这就是「索引失效但查询仍然快」的原因。

**问：那实际建联合索引该怎么排列？**
**答：** 先等值条件列、再范围或排序列（等值定死的列越多，后面列的有序性保持得越完整）；最左列必须是高频且能定值的查询条件，否则索引绝大部分用不上。

## 易错点

- **错的直觉：把 WHERE 条件按索引列顺序写就能命中。** 正确说法：必须**真的存在这个联合索引**，单列索引之间无法拼接成前缀顺序，写得多整齐也没用。
- **错的直觉：`WHERE a=? AND c=?` 里 `c` 完全没贡献。** 正确说法：`a` 仍能定位，只是 `b` 断链让 `c` 无法继续缩小范围，是「部分命中」不是「完全失效」。
- **错的直觉：说某列失效就等于它在索引里白存了。** 正确说法：「失效」只针对查找定位，列值仍在索引叶子节点里，覆盖索引、`ORDER BY` 排序都可能用得上。
- **错的直觉：只要 `ORDER BY` 的列都在索引里就能免排序。** 正确说法：得先让最左列等值定值，且排序列的顺序、方向与索引一致，否则照样出现 `Using filesort`。

## 一句话记住

:::tip
**联合索引整体有序，从最左列连续匹配才定位得到；「失效」只谈查找，不谈覆盖。**
:::
