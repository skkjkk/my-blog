`String` 被声明为 `final` 是为了**保证不可变性**，而不可变性是 Java 语言层面刻意设计的核心特性。它带来的收益远大于"子类化 String"这个几乎没人真正需要的能力。

## 安全性的根本保障

。String 被大量用作**共享常量**（配置项、类路径、URL、SQL、文件路径、锁对象）。如果 String 可变，任何拿到引用的代码都能改它的内容，程序将无法推理"这个值是什么"。**不可变让"引用即内容"成立** —— 你可以放心把 String 传给任何方法而不担心它被偷偷改掉。

## 哈希码可缓存，这是 HashMap 能用的前提

。String 在计算完 hashCode 后会缓存到 `hash` 字段。因为内容不可变，缓存永不过期。**如果 String 可变，键放进 HashMap 后内容被改，hashCode 变化就会导致在 HashMap 里"查不到自己"** —— 这是不可变带来的最实际的工程收益。

## 线程安全天然免费

。不可变对象没有可变状态，**不需要同步、不需要锁、不可被并发写坏**，可以安全地在多线程间共享。这直接避免了 StringBuffer 那种"为了线程安全而付出每次操作加锁"的代价。

## 常量池与 intern 机制成立

。JVM 的**字符串常量池**会缓存字面量字符串供复用，`intern()` 会把字符串放进池中并返回池内唯一实例。**只有内容不可变，"同一个字符串就是同一个对象"这个前提才成立**，否则常量池毫无意义，会出现两个"内容相同但引用不同"的字符串，破坏 `==` 的语义。

## 可安全作为锁对象

。`synchronized` 依赖对象头的 monitor，而 monitor 的状态存在对象本身里 —— **如果被锁对象的内容能变，它的 hashCode 就可能变化**，导致哈希相关的查找失效。不可变对象是天然的锁对象。

## 为什么不用"可变 String + 防御性拷贝"来替代

。这正是 `StringBuilder` 与 `StringBuffer` 的设计：需要可变场景就用它们。**Java 的选择是"两种类型各司其职"，而不是让一个类型既可变又不可变。** 而 `final` 类还额外阻止了子类破坏不可变契约 —— 如果 String 可被继承，子类完全可以重写 `length()`、`charAt()`、`equals()`、`hashCode()` 让行为不一致，**不可变性就只是"约定"而非"保证"**。

## `final` 的两层含义要分清

。**类被 final 修饰** = 不可被继承（保证类型本身不可变）；**方法被 final 修饰** = 不可被重写（`String` 的 `equals`、`hashCode`、`length`、`charAt` 等都是 final 方法，这叫**在编译期把"不可变契约"钉死**）。

## 代价与权衡

。不可变意味着**每次"修改"都要产生新对象**，连续拼接会产生大量中间对象并带来 GC 压力。**Java 的应对是"编译器 + 单字符优化"** —— 编译期常量拼接直接折叠成常量、循环内拼接 javac 自动优化为 `StringBuilder`；**运行期高频拼接则应显式使用 `StringBuilder`**。所以"String 不可变"在日常开发中几乎不会成为性能问题，**除非你在循环里用 `+`**。

## 面试怎么答

1. 给三点就够：
2. 安全性（共享常量、引用即内容）
3. hashCode 可缓存 → HashMap 可用 + 线程安全天然免费 + 常量池成立
4. final 类与方法共同把不可变契约钉死，防子类破坏。 第四点可以补"代价是拼接产生新对象，用 StringBuilder 应对"，这样回答既完整又不啰嗦
