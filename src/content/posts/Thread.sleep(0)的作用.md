Thread.sleep(0) 传入 0 表示不进行任何实质的等待，它的作用是让当前线程主动放弃 CPU 时间片，从运行态退回到就绪态，由操作系统重新调度，使那些优先级与它相同或者更高的线程有机会拿到 CPU 执行。在长时间占用 CPU 而不主动让出的循环里插入一次 sleep 零，可以避免单个线程把其它线程饿死。

## 它到底做了什么

计时参数是 0，说明不需要真的睡一段时间，方法几乎立刻返回。关键点在于它仍然走了「请求操作系统重新调度」这条路径：当前线程从运行态转回就绪态，把 CPU 交还给调度器，再由调度器决定下一个跑谁。所以它的效果不是「等待」，而是「主动让出一次执行机会」。

这次让出不改变线程的任何状态标志，也不影响线程已经持有的资源，因此它比「睡 1 毫秒」轻得多，比纯空转又多了让出动作。

## 为什么需要它：解决什么问题

当一个线程在循环里持续计算、忙等某个标志位时，它会一直占着 CPU。抢占式调度虽然会定期打断它，但在优先级差别明显、或者线程数远多于核数的场景下，低优先级线程可能长时间拿不到时间片，表现为「卡住不动」。

在循环体里插一次 sleep(0)，等于主动给调度器一个重新选择的时机：单线程空转带来的 CPU 浪费被压低，高优先级线程的饥饿也得到缓解。代价是每轮循环多了一个调度点，吞吐会略有下降，所以它只适合放在本来就该让出的地方。

## 和 yield、wait 的区别

| 对比项 | Thread.sleep(0) | Thread.yield() | Object.wait() |
| --- | --- | --- | --- |
| 是否真的等待 | 否，立刻返回 | 否，立刻返回 | 是，直到被唤醒或超时 |
| 是否释放已持有的锁 | **不释放** | **不释放** | **释放**该对象的监视器 |
| 让出后线程去哪 | 就绪态，等再次被调度 | 就绪态，等再次被调度 | 进入该对象的等待集 |
| 唤醒条件 | 调度器选中即可 | 调度器选中即可 | notify / notifyAll 或超时 |
| 是否保证发生切换 | 不保证 | 不保证 | 不涉及，一定会阻塞 |
| 调用前提 | 无 | 无 | 必须持有该对象的监视器 |

可以看出 sleep(0) 与 yield 在语义上非常接近，都只是让出 CPU 的提示；而 wait 是完全不同的一类操作，它把线程挂到对象的等待集上并发起通知等待，因此必须写在 synchronized 块里。

## 代码示例

```java
public class SpinWaitDemo {
    private static volatile boolean ready = false;

    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            while (!ready) {
                // 忙等：每轮插一次 sleep(0)，把时间片让给其它线程
                try {
                    Thread.sleep(0);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt(); // 恢复中断标志后退出
                    return;
                }
            }
            System.out.println("worker 看到 ready = true");
        });
        worker.start();

        Thread.sleep(100);   // 模拟准备工作
        ready = true;
        worker.join();
    }
}
```

这段代码里 sleep(0) 并没有缩短等待，它的作用是让 worker 在每一轮没看到 ready 时都把 CPU 交出去，避免它在单核上把主线程饿到无法执行 `ready = true` 那一行。catch 里恢复中断标志是必须的，吞掉中断会让上层无法感知停止请求。

## 关键要点

- **只是提示，不是保证**：是否真正切换、切换给谁，都由操作系统的调度策略决定，当前线程完全可能在下一轮被调度时马上又拿到 CPU，表现为继续执行。
- **不释放任何锁**：sleep 系列只让出 CPU，已经持有的 synchronized 监视器或者 Lock 照旧握在手里，这一点与 wait 完全不同。
- **没有同步语义**：它无法保证被让出的线程真的运行过，用 sleep(0) 做线程间的顺序控制或协作，时序一变逻辑就可能出错。
- **定位是经验性技巧**：主要用于降低单线程空转的 CPU 浪费、缓解高优先级线程饥饿，而不是可靠的线程协调手段。
- **签名要处理中断**：sleep 声明了 InterruptedException，sleep(0) 同样需要 try/catch 或者向上抛出。

## 常见追问

**Q：sleep(0) 和 yield() 到底该用哪个？**
A：两者语义接近，都是让出 CPU 的提示、都不释放锁、都不保证切换。yield 是专门的让出方法，表达意图更清楚；sleep(0) 借的是「睡眠 0 毫秒」的路径，行为还要看具体平台实现，所以能选就选 yield。

**Q：那 sleep(0) 会释放锁吗？wait 会不会？**
A：sleep(0) 不会，任何时长的 sleep 都不会释放锁。wait 会释放它所在对象的监视器并进入等待集，被唤醒后还要重新竞争这把锁，把两者说混是高频错误。

**Q：为什么不用 sleep(1)，或者干脆纯空转？**
A：sleep(1) 至少要真的让出 1 毫秒，而实际唤醒时间受系统时钟粒度影响，往往明显长于 1 毫秒，在需要快速响应的自旋里太钝；纯空转则把核打满、白白耗电。sleep(0) 介于两者之间。JDK 另外还提供了 onSpinWait 一类的自旋提示，用来告诉 CPU 自己正在自旋。

**Q：生产代码里能用 sleep(0) 吗？**
A：可以作为降低空转的经验手段，但不要用它实现线程间的等待与唤醒。真正需要「等某个条件成立」时，用 wait/notify、LockSupport.park、阻塞队列或者 CompletableFuture 这类有明确唤醒语义的机制。

## 易错点

- **以为 sleep(0) 一定发生切换**：不保证。凡是「让出之后别人肯定已经跑了」的推断都是错的，这也正是它不能当同步原语用的根本原因。
- **以为 sleep 会释放锁**：错。睡眠期间锁一直握在手里，别的线程照样进不来；只有 wait 才会释放监视器。
- **用固定睡眠代替条件等待**：写「睡一会儿它应该就好了」的代码，机器一慢、负载一高就翻车，正确做法是轮询条件本身或者用带通知的阻塞原语。
- **吞掉 InterruptedException**：catch 之后什么都不做，线程就无法响应停止请求，至少要像示例那样恢复中断标志。

## 一句话记住

:::tip
**sleep(0) 是一次「让出 CPU」的提示：不等待、不释放锁、不保证切换。**
:::
