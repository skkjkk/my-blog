这四种引用是 JVM 对**对象可达性**的分级表示，决定了 **GC 在什么条件下可以回收该对象**：强弱顺序是 **强 > 软 > 弱 > 虚**，每降一级，GC 就更容易回收它。回答这道题的关键是把「回收时机」和「典型用途」一一对上——强引用只要可达就永不回收、软引用内存不足时才回收、弱引用 GC 一有机会就回收、虚引用拿不到对象、只能感知它被回收。

## 强引用：默认的引用，只要可达就永不回收

`new` 出来的对象、赋给变量的引用，默认都是强引用。**只要从 GC Root 出发还能走到它，它就绝不会被回收**，哪怕内存即将耗尽，JVM 也宁可抛 `OutOfMemoryError` 而不动它。这也是 Java 内存泄漏最常见的成因：**一个对象被某个集合、静态变量、`ThreadLocal`、监听器强引用着，而那个持有者自己又长期存活**，整条引用链上的对象就都回收不掉。所以内存泄漏的排查思路基本就是一句话——**找出谁还强引用着它**。

## 软引用：内存不足时才回收，适合做内存敏感缓存

`SoftReference` 在**强引用不存在、且 JVM 内存紧张**时会被清理；内存充裕时它**不会**被回收，`get()` 仍能拿到对象。**典型用途**是缓存大对象（图片、反序列化后的数据）：内存吃紧时这些缓存能被回收掉，内存充足时又能提升命中率。

:::tip
软引用的清理**不是即时的**，清理时机**依赖 JVM 实现与 GC 策略**，HotSpot 倾向于在内存压力下结合类似 LRU 的年龄策略来清理，而不是无脑清空。因此它**不适合当作"可预测释放"的机制**；如果只是想让缓存可回收，**优先用 Caffeine、Guava 这类有明确淘汰策略和容量上限的缓存**。
:::

## 弱引用：GC 一有机会就回收，跟着别人的生命周期走

弱引用**完全不阻止回收**：对象只剩弱引用时，任何一次 GC 都可能把它回收，**与内存是否紧张无关**。它几乎没有抵抗力，GC 一有机会就会动手，回收之后 `get()` 立刻返回 null。

:::tip
**典型用途**是**解决内存泄漏，以及"让引用跟随被引用对象的生命周期"**。经典例子是**监听器 / 回调**：用 `WeakReference` 持有监听目标，目标被回收时引用自动失效，不会阻止回收。另一个经典场景是 **`WeakHashMap`**——它的 key 是弱引用，**key 被回收后对应 entry 会被自动移除**，很适合做"以对象为键的临时映射"。
:::

## 虚引用：拿不到对象，只能"感知"回收

虚引用是最弱的一级。它**不会阻止对象被回收**，而且 `PhantomReference.get()` **永远返回 null**——这是设计如此，虚引用的 referent 不可访问，不存在"回收前还能读到对象"这回事。它**唯一的作用是配合 `ReferenceQueue` 做"回收后回调"**：对象被回收后（更准确地说，是在它进入 phantom-reachable 状态、对象自身的清理动作执行完之后），对应的 `PhantomReference` 会被放入引用队列，程序据此得知"这个对象没了"，再去释放 native 资源、清理外部缓存、关闭文件句柄。注意 `PhantomReference` 的构造器**必须**传入一个 `ReferenceQueue`，否则这个虚引用没有任何可观察效果。

## ReferenceQueue 是关键配套机制

所有引用类（`SoftReference`、`WeakReference`、`PhantomReference`）都可以关联一个 `ReferenceQueue`。当对象被 GC 回收后，**对应的引用对象本身会被放进队列**。程序通常起一个后台线程，用 `queue.remove()` 阻塞地取出这些引用，再执行清理逻辑。

:::tip
这是"引用不阻止回收、但能感知回收"的关键机制——虚引用的价值几乎全部集中在这里。
:::

## 一个最小示例：弱引用 + 引用队列

```java
ReferenceQueue<byte[]> queue = new ReferenceQueue<>();
WeakReference<byte[]> ref = new WeakReference<>(new byte[1024], queue);

System.out.println(ref.get() != null); // true：对象还在
System.gc();                            // 只是"建议"回收，时机由 GC 决定

Reference<? extends byte[]> cleared = queue.remove(1000); // 最多等 1 秒
System.out.println(cleared == null ? "还没被回收" : "已被回收，引用已入队");
```

这段代码演示的就是"引用不阻止回收、但能感知回收"的最小闭环：创建时把 `ReferenceQueue` 传给引用对象，之后对象是否被回收、何时被回收都由 GC 决定，我们只负责在队列上等待通知。`remove()` 返回非 null，说明对象确实被回收了，并且这个 `WeakReference` 已经被放进队列；如果对象还活着，`remove(1000)` 会超时返回 null。把 `WeakReference` 换成 `PhantomReference`、把 `byte[]` 换成一个持有 native 句柄的包装类，就是虚引用做资源清理的标准写法。

## 四种引用的对比表

| | 引用强度 | 何时被回收 | 能否 get 到对象 | 典型用途 |
|---|---|---|---|---|
| **强引用** | 最强 | **永不回收**（只要强引用存在） | ✅ | 默认引用、内存泄漏排查 |
| **软引用** | 强 | **内存不足时**回收 | ✅（可能已被清空） | 内存敏感缓存 |
| **弱引用** | 弱 | **GC 一有机会就回收** | ✅（可能已被清空） | 监听器、`WeakHashMap`、防泄漏 |
| **虚引用** | 最弱 | 回收后进入引用队列 | ❌ **永远 null** | 回收后回调、释放 native 资源 |

## 引用对象本身也是强引用

`Reference` 对象（`WeakReference` 等实例）就是普通对象：**只要它自己被引用队列或某个变量强引用着，它就不会被回收**，但它**已经引用不到目标对象**（目标被回收后 `get()` 返回 null）。所以**不要把 `Reference` 对象长期强引用住**，否则目标早被回收了，一堆空的 `Reference` 对象却越堆越多——**内存泄漏只是从目标对象转移到了包装对象上**。正确做法是**把 `Reference` 也放进队列，或者定期清理**。

## 软引用与弱引用的关键差别在"时机"

两者都能 `get()` 到对象、都不阻止 GC，区别只在**回收时机**：软引用是"内存扛不住了才让我走"，弱引用是"GC 一有机会就让我走"（更准确地说，对象只剩弱引用时，任何一次 GC 都可能回收它，与内存压力无关）。由此推出选型结论：**内存敏感的缓存用软引用，需要跟随被引用对象生命周期的场景用弱引用**。同时要清楚，两者的回收时点都不可预测，都不能当作可靠的释放信号。

## finalize 废弃之后，虚引用更重要了

对象被回收前的"清理钩子"过去靠 `finalize()`，现在这条路基本堵死：**JDK 9 起 `finalize()` 被标记为废弃，JDK 18 起进一步标记为"将来移除"（JEP 421）**，官方明确不建议再依赖它。**替代方案之一就是"虚引用 + `ReferenceQueue`"**——这也是虚引用在现代 JDK 中更重要的原因。不过更推荐的做法是用 **`Cleaner`（JDK 9 引入）或 try-with-resources 显式管理资源**，把释放时机握在自己手里，而不是交给 GC 去猜。

## 实践建议

- **不要用引用类型"手动管理内存"**：GC 行为不可预测，性能问题应交给有明确淘汰策略的缓存框架。
- **排查内存泄漏**：用 `jmap -histo:live` 看对象分布，用 MAT 的 Dominator Tree 顺**强引用链**从 GC Root 往回找持有者。
- **需要感知回收时机**：虚引用 + `ReferenceQueue`，或者直接用 `Cleaner`。
- **需要跟随被引用对象的生命周期**：弱引用，或直接用 `WeakHashMap`。

## 常见追问

**Q：软引用和弱引用都能 `get()` 到对象，为什么缓存不统一用软引用？**
A：软引用的回收取决于 JVM 内存压力判断，时点不可预测，缓存命中率也就不可控；要可控就用带容量上限和淘汰策略的缓存框架。

**Q：`WeakHashMap` 的 key 被回收后，entry 会立刻消失吗？**
A：不会立刻。它是在下一次操作（`get`、`put`、`size` 等）时顺带清理失效 entry，所以 `size()` 反映的是清理过的视图，不是绝对实时的。

**Q：虚引用能把对象"复活"吗？**
A：不能。`PhantomReference.get()` 永远返回 null，referent 完全不可访问，没有任何入口把对象救回来。

**Q：`System.gc()` 能保证对象马上被回收吗？**
A：不能。它只是向 JVM 提建议，是否回收、何时回收由 GC 决定，打开 `-XX:+DisableExplicitGC` 时它甚至会直接失效。

## 易错点

- **把"永不回收"理解成"变量还在作用域里就回收不了"**：判定依据是**从 GC Root 出发的可达性**，不是变量名有没有出作用域；对象提前不可达，照样能被回收。
- **以为软引用"内存一紧就立刻清空"**：清理由 GC 策略决定且不即时，别拿它当可靠的释放信号。
- **只顾目标对象，忘了 `Reference` 自身也是普通强引用**：包装对象堆积起来，泄漏只是换了个地方住。
- **以为虚引用在回收前还能读到对象**：它任何时候 `get()` 都是 null，连"最后一瞥"都没有。

## 面试怎么答

1. 强弱顺序与回收时机：强引用永不回收、软引用内存不足时回收、弱引用 GC 一有机会就回收、虚引用拿不到对象、回收后入队。
2. 典型用途对应：软引用=内存敏感缓存，弱引用=监听器与 `WeakHashMap`，虚引用=回收后回调配 `ReferenceQueue`。
3. 两个易错点：`Reference` 对象本身是强引用，包装对象堆积也是泄漏；`finalize` 已废弃，"虚引用 + 队列"或 `Cleaner` 才是替代方案。
4. 实践建议：优先用 Caffeine 这类有明确淘汰策略的缓存，引用类型不适合手动管内存。

第 3 点最能体现你读过源码级细节。

## 一句话记住

:::tip
软引用等内存告急才走，弱引用下一轮 GC 就走，虚引用只会通知你它已经走了。
:::
