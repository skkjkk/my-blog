这四种引用是 JVM 对**对象可达性**的分级表示，决定了**GC 在什么条件下可以回收该对象**。强弱顺序是：**强 > 软 > 弱 > 虚**，每降一级，GC 就更容易回收它。

## 强引用（Strong Reference）

—— **默认的引用类型**。只要强引用存在，**对象就绝不会被回收**。这是 Java 内存泄漏最常见的成因：**一个对象被某个集合、静态变量、ThreadLocal、监听器持有，而那个持有者自己又不可达**，于是整条引用链上的对象都回收不掉。**内存泄漏的排查思路基本就是"找出谁还强引用着它"。**

## 软引用（Soft Reference）

—— **内存不足时才回收，适合做内存敏感缓存**。`SoftReference` 在**强引用不存在、且 JVM 内存紧张**时会被清理；内存充裕时它**不会**被回收。**典型用途**：缓存大对象（图片、序列化数据），内存吃紧时能被回收，内存充足时提升命中。

:::tip
**重要特性**：软引用的清理**不是即时的**，且**清理时机依赖 JVM 实现与 GC 策略**（HotSpot 倾向于在内存压力下、并结合 LRU 风格的年龄策略来清理，而不是无脑清空）。
**实践建议**：软引用**不适合用作"可预测释放"的机制**；如果只是想让缓存可回收，**优先用 Caffeine/Guava 这类有明确淘汰策略与容量上限的缓存**，而不是软引用。
:::

## 弱引用（Weak Reference）

—— **只要发生 GC 就可能被回收，无论内存是否紧张**。它完全"没有抵抗力"，GC 一有机会就会回收。

:::tip
**典型用途**：**解决内存泄漏与"对象生命周期跟随别人"的场景**。经典例子是**监听器/回调**：`WeakReference` 持有被监听者，被监听者被回收时引用自动失效，不会阻止回收。**另一个经典场景是 `WeakHashMap`** —— 它的 key 是弱引用，**key 被回收后，对应的 entry 会被自动移除**，非常适合做"以对象为键的临时映射"。
:::

## 虚引用（Phantom Reference）

—— **最弱的引用，几乎不可能被访问到**。它**不会阻止对象被回收**，`get()` 永远返回 null（**对象在被回收前就已经被"复活"进引用队列**）。**唯一作用是配合 `ReferenceQueue` 实现"回收后回调"** —— 在对象被回收后，系统会把对应的 `PhantomReference` 放入引用队列，程序可以从中得知"这个对象被回收了"从而执行清理（如释放 native 资源、清理外部缓存、关闭文件句柄）。

## ReferenceQueue 是关键配套机制

。所有引用类（`SoftReference`/`WeakReference`/`PhantomReference`）都可以关联一个 `ReferenceQueue`。当对象被 GC 回收后，**对应的引用对象会被放入队列**。程序可以起一个后台线程 `queue.remove()` 不断取出被回收的引用，执行清理逻辑。

:::tip
**这是"引用不阻止回收，但能感知回收"的关键机制** —— 虚引用几乎全部价值都在这里。
:::

## 四种引用的对比表

| | 引用强度 | 何时被回收 | 能否 get 到对象 | 典型用途 |
|---|---|---|---|---|
| **强引用** | 最强 | **永不回收**（只要强引用存在） | ✅ | 默认引用、内存泄漏排查 |
| **软引用** | 强 | **内存不足时**回收 | ✅（可能已被清空） | 内存敏感缓存 |
| **弱引用** | 弱 | **GC 一有机会就回收** | ✅（可能已被清空） | 监听器、`WeakHashMap`、防泄漏 |
| **虚引用** | 最弱 | 回收后进入引用队列 | ❌ **永远 null** | 回收后回调、释放 native 资源 |

## 一个必须知道的细节：引用对象本身是强引用

**`Reference` 对象（`WeakReference` 等）是普通对象，被 ReferenceQueue 或变量强引用时，它自己不会被回收** —— 但它**引用不到目标对象**（目标被回收后 `get()` 返回 null）。所以**不要把 `WeakReference` 对象本身长期强引用住**，否则虽然目标被回收了，这些 `Reference` 对象却会堆积 —— **内存泄漏从目标转移到了包装对象上**。

:::tip
**正确做法**：把 `Reference` 对象也放进队列或定期清理。
:::

## 软引用与弱引用的关键差别在"时机"

一句话记忆：**软引用是"内存扛不住了才让我走"，弱引用是"GC 一有机会就让我走"**。所以：**内存敏感的缓存用软引用；需要跟随对象生命周期的用弱引用。**

## JDK 8 之后 `finalize` 被废弃带来的变化

对象被回收前的"清理钩子"过去靠 `finalize()`，现在已废弃（**JDK 9 废弃、JDK 18 移除**）。**替代方案就是"虚引用 + ReferenceQueue"** —— 这也是虚引用在现代 JDK 中更重要的原因。**推荐用 `Cleaner`（JDK 9+）或 try-with-resources 管理资源**，而非依赖引用机制。

## 实践建议

- **不要用引用类型来"手动管理内存"** —— GC 的行为不可预测，性能问题应交给缓存框架
- **内存泄漏排查**：用 `jmap -histo:live` + **MAT 的 Dominator Tree** 找**强引用链**，从 GC Root 出发看谁在持有
- **需要感知回收时机**：用**虚引用 + ReferenceQueue**
- **需要"跟随被引用对象生命周期"**：用**弱引用**（或直接用 `WeakHashMap`）

## 面试怎么答

1. 强弱顺序与回收时机（强=永不、软=内存不足、弱=GC 有机会、虚=回收后入队）
2. 典型用途对应（软=内存敏感缓存、弱=监听器与 WeakHashMap、虚=回收后回调配 ReferenceQueue）
3. 两个易错点（`Reference` 对象本身是强引用，包装对象堆积也是泄漏；`finalize` 已废弃，虚引用+队列是其替代）
4. 实践建议（优先用 Caffeine 等有明确淘汰策略的缓存，引用类型不适合手动管内存）。 第三点最能体现你读过源码级细节
