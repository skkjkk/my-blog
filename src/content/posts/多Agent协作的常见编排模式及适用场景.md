多 Agent 编排模式可按"**谁决策、怎么串、怎么并行**"三个维度划分，每种模式在稳定性、延迟与成本上各有取舍。

## Supervisor（主管式 / 中心编排）

。一个 Supervisor Agent 接收任务、拆解、**分派给各专业 Agent**、收集结果并汇总。**优点**是流程可控、易调试、结果一致性好，**适合任务类型固定、需要稳定产出的场景**（如流水线式报告生成、客服工单分派）。**缺点**是主管成为**单点瓶颈与单点故障**，且它自己的上下文会越来越长。

## Sequential / Pipeline（顺序链式）

。Agent 依次接力，前一个的输出是后一个的输入。**优点**是**上下文隔离最好**（每个 Agent 只见自己该看的）、成本可控、**非常适合流水线任务**（检索 → 分析 → 写作 → 审核）。**缺点**是**无法并行**，且**前序错误会逐级放大**、难以回溯重跑。生产中常在链上插入校验节点来缓解。

## Parallel（并行式）

。同一任务拆成若干互不依赖的子任务，**同时执行**后汇总。**优点**是**延迟最低**、单点风险分散。**缺点**是**成本上升**（每个分支都要独立读上下文）、**需要解决结果冲突与去重**。适合信息收集、多方案生成、多角度评审。

## Router（路由式）

。一个分类器或模型判断请求类型，**路由到对应的专用 Agent**。**优点**是简单高效、上下文干净、**适合意图明确的分类场景**（客服分流、代码审查分派给不同语言专家）。**缺点**是分类错误会直接导致完全错误的结果，**对路由准确率要求高**。

## Debate（辩论式）

。多个 Agent 持不同立场互相质证，直到收敛。**优点**是**提升正确率与发现盲区**，适合需要严谨验证的判断类任务（方案评审、事实核查）。**缺点**是**成本随轮数线性甚至超线性增长**，且存在**收敛到错误共识**的风险（共享盲区）—— 此时比单人更自信。

## Voting / Ensemble（投票集成式）

。多个 Agent 独立作答，按多数投票或加权投票收敛。**优点**是**简单、鲁棒、可靠**（相当于自一致性采样）。**缺点**是**成本是 k 倍**，且当 Agent 同源时**错误高度相关**，投票的收益会大打折扣。

## Hierarchical（层级式）

。多级 Supervisor，上级管下级。**优点**是**可扩展、支持大规模**，错误能在层级内隔离。**缺点**是**深度增加时延迟与误差累积**。适合大型任务的分层规划。

## Blackboard / Shared State（共享黑板式）

。各 Agent 不直接通信，而是**读写共享状态**（工作区、任务板、记忆库），谁有能力谁就上。**优点**是**耦合低、适合开放式问题**、中断后可从共享状态恢复。**缺点**是**状态一致性难保证**、可能出现"抢同一个任务"。适合研究型、探索型任务。

## Handoff（交接式）

。Agent 在识别出该转交时，**把控制权直接移交给另一个 Agent**，后者接管对话。**优点**是**用户体验连贯**、责任边界清晰。**缺点**是**交接处的上下文可能丢失**。适合客服场景的跨部门转接。

## 选型判据

。看**任务是否可预先分解**（可分解 → 顺序或并行；不可 → 主管式或黑板）、看**子任务是否独立**（独立 → 并行；相互依赖 → 链式或层级）、看**是否需要多角度验证**（需要 → 辩论或投票）、看**路由是否清晰**（清晰 → 路由式）、看**延迟要求**（紧 → 并行与路由）。

## 通用工程建议

。**能用确定性代码编排就不要用多 Agent 编排** —— 多 Agent 的复杂度与故障面远大于收益。**默认用 Supervisor + Pipeline 的混合**（主管决策、链上执行）性价比最高。同时必须为编排层配齐**预算守卫、超时熔断、循环检测与统一追踪**。
