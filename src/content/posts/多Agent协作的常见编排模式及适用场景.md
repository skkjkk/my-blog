多 Agent 编排共有九种常见模式——主管式、顺序链式、并行、路由、辩论、投票、层级、黑板、交接，它们的分野可以用"**谁决策、怎么串、怎么并行**"三个维度一次看清：主管式与层级式把决策权收在编排者手里，顺序链式与交接按时间顺序串起来，并行、路由、辩论、投票、黑板则在不同程度上放开并发，代价分别体现在延迟、成本、结果一致性与可解释性上。

## 九个模式一张表

先把决策方式和代价固定下来，后面几节按"中心编排 / 分流 / 冗余"三类展开。

| 模式 | 决策与推进方式 | 主要优点 | 主要代价 | 适合场景 |
| --- | --- | --- | --- | --- |
| 主管式 Supervisor | 主管拆解、分派、汇总 | 流程可控、易调试、一致性好 | 主管是单点瓶颈与单点故障 | 任务类型固定、要求稳定产出 |
| 顺序链式 Pipeline | 前一环输出即后一环输入 | 上下文隔离最好、成本可控 | 无法并行、错误逐级放大 | 检索、分析、写作、审核流水线 |
| 并行 Parallel | 互不依赖子任务同时跑 | 延迟最低、单点风险分散 | 成本上升、需处理冲突与去重 | 信息收集、多方案生成、多角度评审 |
| 路由 Router | 先分类再交给专用 Agent | 简单高效、上下文干净 | 分类错则结果全错 | 意图明确的分类分流 |
| 辩论 Debate | 多立场互相质证到收敛 | 提升正确率、暴露盲区 | 成本随轮数增长、可能收敛到错误共识 | 方案评审、事实核查 |
| 投票 Voting | 独立作答后多数或加权投票 | 简单、鲁棒、可靠 | 成本是 k 倍、同源错误高度相关 | 答案可判优劣的采样场景 |
| 层级 Hierarchical | 多级主管，上级管下级 | 可扩展、支持大规模、错误在层级内隔离 | 深度增加带来延迟与误差累积 | 大型任务的分层规划 |
| 黑板 Blackboard | 读写共享状态，谁有能力谁上 | 耦合低、中断后可恢复 | 状态一致性难保证、可能抢同一任务 | 研究型、探索型任务 |
| 交接 Handoff | 识别出该转交时移交控制权 | 用户体验连贯、责任边界清晰 | 交接处上下文可能丢失 | 客服的跨部门转接 |

## 中心编排：主管式、顺序链式、层级式

这三种模式的共同点是**执行前就定好了结构**，运行时不做拓扑变化，因此可预测性最强。**主管式（Supervisor）**由一个 Supervisor Agent 接收任务、拆解、分派给各专业 Agent，再收集结果并汇总；优点是流程可控、易调试、结果一致性好，适合任务类型固定、需要稳定产出的场景，比如流水线式报告生成、客服工单分派；缺点是主管既是**单点瓶颈**也是**单点故障**，而且它自己的上下文会越来越长。

**顺序链式（Pipeline）**里 Agent 依次接力，前一个的输出就是后一个的输入。它的**上下文隔离最好**（每个 Agent 只见自己该看的），成本可控，非常适合流水线任务（检索 → 分析 → 写作 → 审核）；代价是**无法并行**，且**前序错误会逐级放大**、难以回溯重跑，所以生产中常在链上插入校验节点来缓解。

**层级式（Hierarchical）**就是多级 Supervisor，上级管下级。它可扩展、支持大规模，错误能在层级内隔离；但**深度增加时延迟与误差会累积**，因此适合大型任务的分层规划，而不是把简单任务层层套起来。

## 分流型：并行、路由、交接

这三种模式的共同点是**先把请求或子任务分开，再交给不同的执行者**，区别在于分开的依据和分开之后是否还合流。**并行式（Parallel）**把同一任务拆成若干互不依赖的子任务同时执行、最后汇总，**延迟最低**、单点风险分散；代价是**成本上升**（每个分支都要独立读上下文），还要**解决结果冲突与去重**，适合信息收集、多方案生成、多角度评审。

**路由式（Router）**由一个分类器或模型判断请求类型，**路由到对应的专用 Agent**。它简单高效、上下文干净，适合意图明确的分类场景（客服分流、代码审查分派给不同语言专家）；缺点是分类错误会直接导致完全错误的结果，**对路由准确率要求很高**。

**交接式（Handoff）**更进一步：Agent 识别出该转交时，**把控制权直接移交给另一个 Agent**，由后者接管对话，交接之后通常不再合流。它让**用户体验连贯**、责任边界清晰，适合客服场景的跨部门转接；风险是**交接处的上下文可能丢失**，所以移交时要显式带上必要背景。

## 冗余型：辩论、投票与共享黑板

这三种模式都**不靠单个 Agent 的一次判断**，而是用多份判断或共享状态换可靠性，代价以成本为主。**辩论式（Debate）**让多个 Agent 持不同立场互相质证，直到收敛，能**提升正确率并发现盲区**，适合需要严谨验证的判断类任务（方案评审、事实核查）；但**成本随轮数线性甚至超线性增长**，还存在**收敛到错误共识**的风险——共享盲区会让它们比单人更自信。

**投票集成式（Voting / Ensemble）**由多个 Agent 独立作答，再按多数投票或加权投票收敛，优点是**简单、鲁棒、可靠**，相当于自一致性采样；代价是**成本是 k 倍**，且当多个 Agent 同源时**错误高度相关**，投票的收益会大打折扣。

**黑板式（Blackboard / Shared State）**里各 Agent 不直接通信，而是**读写共享状态**（工作区、任务板、记忆库），谁有能力谁就上。它耦合低、适合开放式问题，中断后还能从共享状态恢复；但**状态一致性难保证**，也可能出现多个 Agent "抢同一个任务"的情况，适合研究型、探索型任务。

## 选型判据：五个问题定模式

选型不必背模式清单，按下面五个问题依次问一遍，答案就把候选集缩到一两种：

1. **任务能否预先分解**？能分解就走顺序或并行；不能分解就用主管式或黑板式。
2. **子任务是否独立**？相互独立就并行；彼此依赖就走链式或层级。
3. **是否需要多角度验证**？需要就用辩论或投票，不需要就别为冗余付成本。
4. **路由是否清晰**？意图明确、边界清楚就走路由式。
5. **延迟要求是否严格**？紧就优先并行与路由，愿意等再上辩论。

## 通用工程建议

最重要的一条是：**能用确定性代码编排就不要用多 Agent 编排**——多 Agent 的复杂度与故障面远大于它带来的收益。实践中的默认答案是**用 Supervisor + Pipeline 的混合**：主管负责决策与汇总，具体的执行交给一条链，性价比最高。

编排层还必须配齐四件基础设施，否则一旦跑起来就无法收敛：

- **预算守卫**：按 token 或调用次数设上限，超了立刻停。
- **超时熔断**：单步和整任务都有超时，避免一个 Agent 卡住整条链路。
- **循环检测**：识别重复调用与死循环，防止 Agent 之间互相推诿。
- **统一追踪**：全链路一个 trace，否则跨 Agent 排障几乎不可能。

## 常见追问

Q：为什么说主管式最容易调试？
A：因为决策点只有一个。所有分派与汇总都经过主管，出问题时看主管的日志就能定位是哪一步拆错或汇总错，而并行、黑板的错误往往散落在多个 Agent 里。

Q：并行式延迟最低，为什么不能默认用它？
A：延迟低是以成本换来的。每个分支都要独立读上下文，任务一多成本迅速上升，而且要额外解决结果冲突与去重，子任务有依赖时并行还会直接失败。

Q：辩论和投票都是多份判断，怎么选？
A：投票要求各 Agent 能独立作答、答案可判优劣，便宜但增益有限；辩论允许相互质证，能暴露盲区，但成本随轮数增长，还可能收敛到错误共识。精度要求高且能接受成本就用辩论。

Q：黑板式为什么强调"可恢复"？
A：因为状态外置在共享工作区里。Agent 中断或重跑时不需要重放对话历史，接着读写共享状态就能续上，代价是要自己保证状态一致性。

## 易错点

- 把"多 Agent"当默认解法：多数需求用一条确定性代码链就能完成，硬上多 Agent 只会放大故障面。
- 忽略主管的上下文膨胀：主管要汇总所有子结果，上下文会越来越长，不做裁剪或摘要迟早会失真。
- 用投票掩盖相关性：多个 Agent 同源时错误高度相关，投票看似严谨，实际只是把同一个错误重复了几遍。
- 交接不带上下文：Handoff 只移交控制权不传背景，用户会被要求重复说一遍需求，体验直接崩掉。

## 一句话记住
