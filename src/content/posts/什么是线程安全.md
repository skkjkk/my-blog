线程安全的定义是：**当多个线程并发访问某个类时，这个类始终能表现出正确的行为，且这份正确性不依赖于任何偶然的执行时序或线程交错顺序**。换句话说，无论线程怎么调度，多线程执行的结果都应当与单线程执行、或某个确定的串行顺序执行一致。它描述的是"结果可预期"这个属性，与实现里用了什么同步手段没有必然关系——没有锁的不可变对象可以完全线程安全，加了锁的代码也可能因为锁错了地方而不安全。

## 判断标准：正确性不依赖时序

判断一个类是否线程安全，不是看它"加没加锁"，而是问：**在不同的线程交错下执行，结果是否都正确**。同一个操作单线程跑一百次都对、多线程跑有时出错，它就不是线程安全的。

这个视角的实用价值在于两条推论。第一条是"能通过的测试不代表线程安全"：并发 bug 依赖特定的交错，本地压测没复现，只说明这次调度没撞上。第二条是"正确性一旦依赖时序就已经不安全"：如果某段代码只在"线程 A 恰好在 B 之前执行"时才对，那它就已经不满足定义，哪怕线上跑了半年没出事。所以**线程安全是一个关于结果的属性，而不是关于实现手段的属性**。

## 要解决的三类问题：原子性、可见性、有序性

并发带来的错误可以归成三类，Java 内存模型的规定也正是围绕这三条：

- **原子性**：操作不可被分割到中途。`count++` 看着是一行，实际是读、加一、写回三步，中间可以被别的线程插进来，两次自增最后只体现一次结果。
- **可见性**：一个线程的修改要能被其他线程及时看到。没有 `volatile` 或 `synchronized` 时，JMM 允许线程一直读自己工作内存里的旧值，于是别人改了标志位它也看不见。
- **有序性**：指令执行顺序要符合预期。编译器与 CPU 都可能重排序，比如 DCL 单例里对 `instance == null` 的检查若被重排，就会读到还没初始化完的对象。

三类问题是并列的，解决手段各管一段：`synchronized` 三条一起管，`volatile` 只管可见性与有序性，CAS 只管一个位置的原子更新。搞清某一手段覆盖哪几条，才不会拿 `volatile` 去修一个自增的竞态。

## 被破坏时的典型表现

落到代码上，线程安全问题通常长成这几种样子：

- **共享可变状态被并发修改**：计数器自增丢失更新；集合一边遍历一边被写，抛 `ConcurrentModificationException`。
- **可见性失效**：一个线程改了标志位，另一个线程在循环里永远看不到，程序卡在那里。
- **"检查-执行"组合不原子**：`if (map.containsKey(k)) map.put(k, v)` 两步单独看都安全，拼成一个复合操作就不安全了。
- **复合操作不原子**：先查库存再扣减，两个线程都通过了检查，结果超卖。
- **DCL 单例不加 `volatile`**：重排序让别的线程拿到半初始化对象。
- **把 `HashMap` 当并发容器用**：并发写会丢数据，扩容时还会互相覆盖，`HashMap` 本身不是线程安全的。

计数器是最小的复现例子，问题全在一行里：

```java
public class Counter {
    private int count = 0;      // 共享可变状态，没有任何同步

    public void increment() {
        count++;                // 读 -> 加一 -> 写回，三步之间可以被抢占
    }
}
```

两个线程各调一千次 `increment()`，结果常常到不了两千：两个线程读到同一个旧值，又各自写回同一个新值，其中一次更新就丢了。丢几次由调度决定，不是固定值——也可能一次都没撞上、结果恰好正确，而"时对时错"本身就说明它的正确性依赖于时序。

## 四类解决手段

按"能不管就不管"的顺序排，成本从低到高：

**① 不可变（Immutability）** —— 最彻底的解法：对象创建后状态不再改变，谁来读都一样，天然线程安全，例如 `String`、`Integer` 这类值对象与 `List.of()` 这类不可变集合。注意别和写时复制混为一谈：`CopyOnWriteArrayList` 内部状态是可变的，只是每次写都新建一个数组快照，读路径因此不用加锁，属于另一种机制。

**② 线程隔离** —— 让数据只属于一个线程，典型是 `ThreadLocal`。但要小心线程池复用线程：上一次任务留下的值没清掉，下一个任务就会读到脏数据；线程长期存活还会让这些值一直回收不掉，形成内存泄漏。

**③ 同步（互斥）** —— `synchronized` / `ReentrantLock` 把临界区串起来，语义最直观，代价是阻塞与上下文切换，锁用不好还会死锁。

**④ 原子类与并发容器** —— `AtomicInteger`、`AtomicReference`、`LongAdder` 用 CAS 完成单变量原子更新；`ConcurrentHashMap` 用 CAS 加桶级锁，`CopyOnWriteArrayList` 用写时复制，把一把大锁拆成细粒度锁或无锁路径。

| 手段 | 靠什么保证 | 代价与边界 |
| --- | --- | --- |
| 不可变 | 状态根本不改，没有竞争 | 每次修改都要新建对象 |
| 线程隔离 | 数据只给一个线程用 | 线程池复用要清理，否则残留、泄漏 |
| 同步 | 临界区互斥，一次只进一个线程 | 阻塞、切换开销，可能死锁 |
| 原子类 / 并发容器 | CAS 与细粒度锁替代大锁 | 只保证单点操作，复合操作仍需自己组合 |

## 边界：容器安全不等于元素安全，还有安全发布

`ConcurrentHashMap` 自身线程安全，**不代表放进去的对象线程安全**——你 put 的那个可变对象，它的字段仍然要你自己保证，容器只保护自己的哈希表结构。**这是最常见的误解**。

另一件常被忽略的事是**安全发布**。构造函数里把字段赋完，不等于别的线程能看到赋好的值：没有同步手段时，其他线程可能看到一个字段还没赋完的对象。所以**"线程安全"包含"安全发布"**。常见的安全发布方式有四种：`volatile` 引用、`final` 字段、静态初始化器（类加载阶段完成，由 JVM 保证可见性）、以及把对象放进并发容器。

## 落地时怎么保证

- 优先设计成不可变：数据通过构造器传入，不提供 setter，需要返回内部集合时给防御性拷贝。
- 明确标识共享状态：哪些字段会被多线程访问，在字段和类注释里写清楚。
- 用最小的同步范围：锁粒度越细、临界区越短越好，别把日志和 IO 塞进 `synchronized` 块。
- 优先用并发工具类而不是手写锁：能用 `ConcurrentHashMap`、`AtomicInteger` 就不自己造轮子。
- 用工具做辅助验证：`JConsole`、JFR 可以看线程状态、死锁与锁竞争，SpotBugs 这类静态检查能发现一部分典型并发缺陷；但工具只能提示风险，不能证明一个类线程安全，最终判据还是回到"结果是否依赖时序"。
- 把结论写下来：用 `@ThreadSafe` / `@NotThreadSafe` 注解，或在类文档里写明"本类线程安全 / 非线程安全，调用方需自行同步"，别让调用方靠猜。

## 常见追问

**Q：加了 `synchronized` 就线程安全了吗？**
A：不是。它只保护被包住的那段代码，方法里访问的外部可变状态、返回的引用所指向的可变对象都不在保护范围内；锁的对象选错（比如锁了 `this` 却被外部拿去当锁）也会失效。

**Q：`volatile` 能不能替代锁？**
A：不能。`volatile` 只保证可见性与有序性，不保证原子性，`count++` 加上 `volatile` 依然是错的。它适合做状态标志位、一次性发布的对象引用。

**Q：局部变量需要担心线程安全吗？**
A：局部变量在栈上、线程私有，本身天然安全；危险的是局部变量引用指向的堆对象——那个对象如果逃逸出去被别的线程拿到，该不安全还是不安全。

**Q：面试官问"什么是线程安全"，答案怎么组织？**
A：先给定义（结果不依赖线程交错与时序），再讲三类问题（原子性、可见性、有序性）并各配一个典型错误（自增丢失更新、DCL 缺 `volatile`、并发写 `HashMap`），然后给解决手段（不可变 > 线程隔离 > 同步 > 并发容器），最后补两个区分点：线程安全的集合不等于里面的对象安全，以及别漏掉安全发布。

## 易错点

- **以为"没加锁就不安全"**：判据是结果，不是实现手段。不可变对象、线程封闭的数据都不需要锁。
- **以为"加了锁就一定安全"**：锁的范围、锁的对象、逃逸出去的引用，任何一处漏了都仍然不安全。
- **以为 `volatile` 能保证原子性**：它只解决可见性与有序性，复合操作（自增、先查后改）必须用锁或原子类。
- **以为用了并发容器就万事大吉**：`putIfAbsent`、`computeIfAbsent` 是原子的，而自己写的"先 get 再 put"不是，复合操作还得自己保证。

## 一句话记住

:::tip
线程安全看结果不看锁：不依赖时序、不乱共享可变状态，才真的安全。
:::
