生产者消费者模型的核心，是让多个生产者线程往共享缓冲区放数据、多个消费者线程从缓冲区取数据，同时满足三条约束：**缓冲区满时生产者阻塞、为空时消费者阻塞、同一时刻只有一个线程能操作缓冲区**。用 `wait`/`notify` 手写时，这三条分别落到 `synchronized` 保证互斥、`wait` 释放锁并挂起、`while` 循环复查条件上：所有对缓冲区的操作都必须在 `synchronized` 块内，判断条件必须用 `while`。

## 三条约束分别落到哪个 API

三条约束不是三件独立的事，而是一套配合关系，缺一条就会出错。

- **互斥**：`put` 和 `take` 都声明为 `synchronized`（或整体包在 `synchronized (buffer)` 块里），保证同一时刻只有一个线程在读改写缓冲区状态。
- **阻塞**：条件不满足时调用 `wait()`，它在挂起当前线程的同时**释放**持有的监视器锁，别的线程才能进来改变条件。
- **复查**：被唤醒不等于条件成立，所以判断写在 `while` 里，醒来后重新检查，不满足就继续 `wait()`。

`wait` 会释放锁这一点是整套方案成立的根基：如果它像 `sleep` 一样占着锁不放，生产者睡着的整段时间里消费者都进不来，缓冲区永远是满的，生产者和消费者谁都推进不了。

## 为什么必须用 while 而不是 if

`if` 只判断一次，而线程从 `wait()` 返回时，等待的条件很可能已经再次不成立，原因有两个。一是**虚假唤醒**：线程可能在没有任何 `notify` 的情况下被唤醒。二是**条件被别的线程抢先改回去**：`notifyAll` 叫醒了一批线程，抢到锁的那个先把元素取走或放满，轮到你看时条件又变了。

用 `if` 就会直接往下执行，消费者从空队列里取元素、生产者往满队列里塞元素，要么抛异常、要么破坏数据。用 `while` 把判断包住，醒来先复查，不满足就再 `wait()`，逻辑才是对的。这是 `wait`/`notify` 最容易写错的一处。

## 为什么用 notifyAll 而不是 notify

`notify` 只从等待队列里挑一个线程唤醒，它并不知道这个线程等的是哪个条件。同一个缓冲区上挂着的等待者，可能既有等「不满」的生产者，也有等「不空」的消费者。

如果 `notify` 恰好唤醒了条件仍不满足的那个，它会复查失败、继续 `wait`，而真正该被唤醒的线程始终没收到信号——表现为**信号丢失，程序卡住不动**。`notifyAll` 唤醒全部等待者，每个线程靠 `while` 自己复查、自行重新排队，代价是一批无效唤醒，但**绝不会丢信号**。结论很直接：只要等待条件不止一种，就必须用 `notifyAll`。

## 单个缓冲区的最小实现

用一个 `ArrayDeque`（或数组）当缓冲区，`put` 在队列满时等待、`take` 在队列空时等待，生产完成后 `notifyAll`，消费完成后同样 `notifyAll`。

```java
class BoundedBuffer<T> {
    private final Deque<T> queue = new ArrayDeque<>();
    private final int capacity;

    BoundedBuffer(int capacity) {
        this.capacity = capacity;
    }

    public synchronized void put(T item) throws InterruptedException {
        while (queue.size() == capacity) {   // 满：用 while 复查，不用 if
            wait();                          // 释放锁并挂起
        }
        queue.addLast(item);
        notifyAll();                         // 状态变了，唤醒所有等待者
    }

    public synchronized T take() throws InterruptedException {
        while (queue.isEmpty()) {            // 空：同样用 while 复查
            wait();
        }
        T item = queue.removeFirst();
        notifyAll();                         // 消费完也要唤醒，否则生产者永远等不到
        return item;
    }
}
```

两个细节值得单独说清：`wait()` 必须在已持有监视器锁时调用，否则抛 `IllegalMonitorStateException`；`notify`/`notifyAll` 只负责把线程移出等待队列，**不会释放锁**，被唤醒的线程要等当前线程退出同步方法之后才真正恢复执行。另外 `put`/`take` 都声明了 `throws InterruptedException`，真正调用它们的生产者、消费者线程捕获之后要补一句 `Thread.currentThread().interrupt()` 恢复中断标记，再把异常向上抛，不能吞掉。

## 多生产者多消费者的代价与替代方案

`notifyAll` 在单生产者单消费者下几乎没有浪费，线程一多就会退化：每次状态变化都叫醒所有等待者，其中大多数复查后发现条件仍不满足，又乖乖回到等待队列，**大量无效唤醒和锁竞争让性能明显低于单生产者单消费者**。也正因为如此，生产环境更倾向直接用 `BlockingQueue`：`ArrayBlockingQueue` 有界、数组实现，`LinkedBlockingQueue` 链表实现、容量可选，它们把同一套等待/通知语义封装好了，还自带超时和阻塞式 API。

| 方案 | 等待条件怎么组织 | 唤醒开销 | 适用场景 |
| --- | --- | --- | --- |
| `wait` / `notifyAll` | 一个监视器只有一条等待队列，所有条件混在一起 | 全量唤醒后靠 `while` 复查 | 教学、线程数少的简单场景 |
| `ReentrantLock` + 两个 `Condition` | 「不满」「不空」各一条队列，分开排队 | 只唤醒对应条件上的线程 | 并发量较大、想自己控制唤醒 |
| `BlockingQueue` | 内部就是锁加条件队列这套，`put`/`take` 已封装 | 精确唤醒，配合原子计数 | 生产环境的默认选择 |

顺着这张表还有两个改进方向：用 `wait(timeout)` 代替无参 `wait`，避免线程无限期挂起，再配合上层的重试或退出逻辑；或者用 `ReentrantLock` 的 `newCondition()` 分别建「不满」和「不空」两个条件队列，把上面那批无效唤醒直接消掉，`BlockingQueue` 内部走的就是这条路。

## 完整实现的检查清单

- 缓冲区状态（队列本身、元素个数）必须由 `synchronized` 保护，读和写在同一把锁内完成。
- 每个 `wait()` 都包在 `while (条件不满足)` 里，且 `wait` 调用前必须已经持有锁。
- 每次改变缓冲区状态后都要 `notifyAll()`，「放入」和「取出」两个方向都要调，只调一侧会留下永久挂起的线程。
- 等待条件写成「满」和「空」两个明确表达式，比如 `queue.size() == capacity`、`queue.isEmpty()`，不要用取反的复合条件，复查时容易写反。
- 捕获 `InterruptedException` 时先 `Thread.currentThread().interrupt()` 恢复中断标记，再把异常向上抛出，不要静默吞掉。
- 别把 `wait` 写成 `sleep`：`sleep` 不释放锁，抱着锁睡会把整个缓冲区卡死。

## 常见追问

**Q：`wait` 和 `sleep` 有什么区别？**
A：`wait` 是 `Object` 的方法，必须在 `synchronized` 内调用，调用时**释放监视器锁**；`sleep` 是 `Thread` 的静态方法，不要求持锁，也**不释放已持有的锁**。所以抱着锁 `sleep`，整个睡眠期间那把锁都占着不放，而 `wait` 期间别的线程可以进来改条件。

**Q：为什么 `wait` 必须在 `synchronized` 里调用？**
A：因为它要操作对象的等待队列，而等待队列是对象监视器的一部分，没持锁就调用直接抛 `IllegalMonitorStateException`。更根本的原因是：`wait` 的语义是「释放锁并挂起」这一个不可分割的动作，如果没持锁也能进入等待，检查条件和真正挂起之间就留出了空隙，信号会在这个空隙里丢掉。

**Q：能不能只用 `notify` 不用 `notifyAll`？**
A：只有确认同一监视器上所有等待者等的是同一个条件时才可以，比如单生产者单消费者、缓冲区上只有一个等待条件。一旦有多个生产者或消费者，`notify` 就可能唤醒条件不满足的线程，真正的等待者收不到信号，程序停在那里不动。

**Q：既然有 `BlockingQueue`，手写这套还有意义吗？**
A：面试考的是「互斥、条件复查、唤醒、中断」这四件事能不能讲明白，`BlockingQueue` 内部就是同一套逻辑。实际写代码时优先用它，手写主要用来理解原理，或用在不好引入队列组件的场景。

## 易错点

- **把 `wait` 当成「不释放锁的睡眠」**——正好相反，`wait` 会释放监视器锁，不释放锁的是 `sleep`，这两个说反了基本等于没掌握。
- **用 `if` 判断等待条件**——被唤醒后条件可能已被别人改回去，或者干脆是虚假唤醒，必须用 `while` 复查。
- **只在 `put` 里 `notifyAll`、忘了在 `take` 里调**——缓冲区被消费空之后再没有线程唤醒消费者，表现为消费线程永久挂起。
- **吞掉 `InterruptedException`**——捕获后不恢复中断标记就继续循环，中断信号被吃掉，线程无法按预期停止；正确做法是 `Thread.currentThread().interrupt()` 后向上抛。

## 一句话记住

:::tip
**一把锁管互斥，while 复查条件，notifyAll 不丢信号。**
:::
