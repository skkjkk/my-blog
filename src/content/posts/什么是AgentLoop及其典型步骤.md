Agent Loop 是驱动 Agent 持续工作的**循环骨架**：模型反复地"感知当前状态 → 思考下一步 → 产生动作 → 观察动作结果 → 更新状态"，直到满足终止条件才退出。一次普通的大模型调用只回答一次，Agent 靠这个循环把"一次性回答"变成"一串可以被真实反馈修正的动作"，它是所有 Agent 框架的公共内核，ReAct、Reflexion、规划-执行等范式都是在它之上做的变体。

## 典型步骤是六步循环

一个完整的 Loop 可以拆成六步，第 6 步判定不终止就回到第 1 步。

| 步骤 | 做什么 | 关键点 |
| --- | --- | --- |
| 1 构建上下文 | 把系统提示、目标、可用工具、相关记忆、近期轨迹组装成提示 | 决定回答质量与成本上限 |
| 2 推理 | 模型生成思考与动作（最终回答，或一次工具调用） | 动作由结构化 `tool_call` 表达，不靠解析自然语言 |
| 3 执行动作 | 调用工具或产生输出 | 权限裁决与参数校验在这一步，模型本身不执行 |
| 4 观察 | 捕获执行结果与错误 | 失败也要回填，模型才有机会自我纠正 |
| 5 更新状态 | 把结果写回消息列表，更新任务状态与预算 | 同时记下耗时、token 消耗 |
| 6 判定终止 | 检查是否完成、是否超限、是否需要重规划 | 不终止则回到第 1 步 |

这六步里最容易写错的是第 3 步和第 6 步：工具执行是安全边界，终止判定决定系统会不会失控，而第 1 步的上下文组装则决定了同样的模型能发挥出多少。下面是骨架的伪代码，重点在于每一步都能被打断、被记录、被预算约束：

```js
while (true) {
  const context = assemble({ system, goal, tools, memory, trace }); // 1 构建上下文
  const step = await model(context);                                // 2 推理：tool_call 或 final
  if (step.final) return step.final;                                // 模型给出最终答案
  const result = await gateway.call(step.toolCall, budget);         // 3 执行动作（校验 + 裁决）
  trace.append(step, result);                                       // 4 观察 + 5 更新状态
  if (shouldStop(trace, budget)) break;                             // 6 判定终止
}
```

## 终止条件是多重的，不是单一

终止条件必须同时设好几层，包括：模型给出最终答案、**验收条件被程序化校验通过**、达到最大步数、达到 token 或时间预算、连续多步无进展、检测到循环（状态重复出现）、或收到外部取消信号。**缺少多重终止条件是 Agent 失控的首要原因**，因为"模型自己说完成了"这一条最不可靠——它对自己的产出往往过于乐观，所以真正的完成判定要交给可执行的外部校验，比如单测通过、schema 校验通过、人工确认。

## 循环的本质是"受控的状态机"

它看起来像 while 循环，但生产实现必须处理**幂等、重试、错误分类、状态持久化、断点恢复**五件事：工具可能被重复调用，所以要幂等；外部服务会抖动，所以要区分可重试错误（超时、限流）与不可重试错误（参数错、权限拒绝）；进程随时会挂，所以状态要落盘才能断点恢复。生产中的 Agent Loop 通常跑在**事件溯源**的引擎上，而不是一个简单的 while——每一步都是一个事件，重放事件就能复现整条轨迹，审计和回滚才有依据。

## 单轮与多轮 Agent 的区别

单轮是"一次调用 → 一次工具 → 一次回答"；多轮 Agent 的循环里，**模型的每一轮输出都只是下一步的输入**，没有哪一轮是最终答案，直到某轮触发了终止条件。所以**不能把某一轮的文本当作结果交付**，尤其是模型中途说"我已经完成了"时，必须经过验收环节确认，否则用户拿到的可能是一段自我感觉良好的过程说明。

## 循环中的"思考"与"行动"要不要分离

ReAct 风格把思考和行动写在同一次输出里（Thought → Action → Observation 交替），实现简单、调试直观，是大多数框架的默认做法。规划-执行分离风格则让规划器与执行器分属不同上下文：规划器只看目标与高层计划，执行器只看当前子任务，上下文互不污染。前者简单、后者在长程任务上更稳，代价是多一层编排与计划失配的风险。

## 循环内指标与人在环

工程上必须监控的循环内指标：每步耗时与 token、工具成功率、**重复动作率**、无进展步数、上下文长度增长曲线、重规划次数。这些是线上定位"Agent 变慢 / 变贵 / 跑偏"的直接依据——重复动作率升高通常意味着模型没读懂观察结果，上下文增长曲线陡峭则预警成本与失真。

循环与"自主程度"也不是绑死的：循环可以完全自主（无人干预直到结束），也可以是**人在环**（关键步骤请求人工确认，如写库、发消息、付款）。生产系统普遍采用人在环，因为完全自主的循环在错误场景下的代价不可控。

## 常见追问

Q：Agent Loop 和工作流（Workflow）的本质区别是什么？
A：工作流的每一步由人预先写死，路径可复现；Agent Loop 的下一步由模型在运行时决定，同一次运行路径不可完全复现，所以更依赖事件溯源与终止条件来兜底。

Q：为什么"模型说完成了"不能作为唯一终止条件？
A：模型对自己的产出偏乐观，容易过早宣布完成或陷入反复修补。所以完成判定要交给程序化验收（单测、schema 校验、断言），模型自述只作为触发验收的信号。

Q：为什么不能直接写一个 while 循环了事？
A：缺幂等会被重复动作搞脏数据，缺错误分类会把限流当致命错，缺状态持久化挂一次就得重跑，缺断点恢复和事件日志则无法审计。工程复杂度都在循环体内，而不在循环本身。

Q：完全自主的 Loop 更"智能"，为什么生产反而用人在环？
A：自主程度越高，错误发生后的代价越大且越难追溯。人在环把高风险动作（写库、付款、对外发送）拦在人工确认上，用很低的成本换到可控性。

## 易错点

- 把某一轮输出当最终答案交付：多轮 Loop 里每一轮都只是下一步的输入，未经验收就交付等于把过程稿当成品。
- 只设"模型说完成"一条终止条件：等于没有兜底，模型一旦自信报完成，循环就带着错误结果退出。
- 把 Loop 当无状态 while：不落盘、不记事件，断点恢复、审计、回放全都做不了，线上出问题只能靠猜。
- 只看总耗时与总 token：这两个是结果指标，定位不到"哪一步开始跑偏"，真正有用的是重复动作率与无进展步数。
