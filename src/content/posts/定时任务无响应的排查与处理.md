"定时任务无响应"通常有四种截然不同的形态，**第一步必须先区分**，因为每种的根因和解法完全不同。**核心思路：定时任务的核心是"触发"与"执行"两段，任何一段卡住都会表现为无响应。**

1) **先区分四种形态**
| 形态 | 典型表现 | 大概率根因 |
|---|---|---|
| **① 根本没触发** | 到点后任务一次都没跑，日志里无任何记录 | **Cron 表达式错、时区错、调度器没启动、任务被禁用** |
| **② 触发了但卡住不结束** | 日志停在某一行，不再更新 | **死锁、DB 锁等待、下游超时未设、线程被阻塞** |
| **③ 执行了但结果不对** | 有日志、任务"成功"了但业务没生效 | **事务未提交、异步未触发、分片只跑了部分、时区/边界问题** |
| **④ 堆积/重复执行** | 同一个任务同时跑多个，或任务追着上一个跑 | **上一轮没结束下一轮又触发**（无并发控制） |

2) **第一步：确认任务到底跑没跑** ⭐
**最有效的动作是去查"任务实际执行记录"，而不是看代码。**
- **Spring `Quartz`** → 查 `QRTZ_*` 表（`QRTZ_TRIGGERS`、`QRTZ_FIRED_TRIGGERS`）；**`QRTZ_FIRED_TRIGGERS` 里有残留行 = 有任务卡住没释放** ⭐
- **Spring `@Scheduled`** → 在方法首行打印时间戳与线程名；**注意它默认是单线程，同一任务的多次触发会被排队**（不会并发，但会**堆积**）
- **XXL-JOB / PowerJob / ElasticJob** → 看**调度中心**的执行日志、失败重试记录、**任务分片与路由**
- **Linux `crontab`** → `crontab -l` 确认配置；**`grep CRON /var/log/syslog`** 看是否触发；⚠️ **cron 的环境变量极其贫瘠**（只有 `PATH`/`HOME` 等极少数）

3) **第二步：确认"触发"这一段**（对应形态①）
- **Cron 表达式是否正确** ⭐ —— **六位 vs 五位**（Spring 是 6 位：秒 分 时 日 月 周；Linux 是 5 位）—— **这是最高频的坑**
- **时区** ⭐ —— **服务器时区与应用时区不一致**，任务会在"看起来不对的时间"触发或延后；Spring 需显式设 `zone = "Asia/Shanghai"` 或用 `@Scheduled` 的 `zone` 属性；容器内时区常是 **UTC**（Docker 默认 UTC，**容器里跑定时任务是踩坑重灾区**）
- **调度器是否启动** —— `@EnableScheduling` / `@EnableScheduling` + `@EnableAsync` 是否生效；Quartz 的 `SchedulerFactoryBean` 是否随容器启动
- **任务是否被排除** —— `@Scheduled` 的 bean 是不是 `final`、方法是不是 `private`、类是不是没被 Spring 扫描到（**`@Scheduled` 方法不能是 private**）
- **分布式下是否只有一个节点在跑** ⭐ —— 多实例部署时**每个实例都会触发一遍**，需引入**分布式锁**或使用 XXL-JOB 这类带调度中心的方案

4) **第三步：确认"执行"这一段**（对应形态②，最难定位）
**用 `jstack` 看线程状态** —— 定时任务的线程名很有辨识度（`scheduling-1`、`pool-3-thread-1`、`xxl-job-executor-0`）：
- 停在 **`SocketInputStream.socketRead0`** → **在等下游 HTTP 响应**（未设超时或超时太长）
- 停在 **`Unsafe.park` / `Object.wait`** → **在等锁**（**定时任务与其他线程争抢同一把锁**）
- 停在 **HikariCP `getConnection`** → **连接池耗尽**（定时任务与在线业务共用连接池，⚠️ **高并发场景下定时任务会抢光连接**）
- 停在 **MySQL `Innodb_lock_wait`** → **数据库行锁等待**（另一个事务持锁未提交）
- 停在 **`CountDownLatch.await`** → 等待异步子任务
- **线程状态是 `BLOCKED`** → **死锁**（`jstack` 会直接打印 deadlock 检测结果）

5) **第四步：查数据库与下游**
- **慢 SQL** → 开启慢查询日志；**定时任务里的大查询、全表 update/delete 是常见元凶**
- **长事务** → 定时任务的事务持锁过久，**阻塞在线业务**（这是最恶劣的影响）
- **大批量操作** → 定时任务一次性处理百万行，**没有分批** → 长时间持锁 + 大量日志 → 应**分批提交**（每批 N 条）
- **下游服务超时** → 是否设置了合理的 connect/read timeout；**没有超时 = 无限等待 = 线程永久泄漏**

6) **第五步：确认"结果"这一段**（对应形态③）
- **事务是否提交** —— **异常被吞掉（catch 后只打日志不抛）→ 事务不回滚但也不提交？** 更常见的是**catch 里没回滚**，或**方法没加 `@Transactional`**（Spring 自调用导致事务失效 ⚠️）
- **异步是否真的触发** —— `@Async` 方法是否在同一类内部自调用（**不走代理，失效**）；线程池是否满
- **分片任务是否只跑了部分** —— 分片参数（`shardIndex`/`shardTotal`）是否传递正确
- **边界条件** —— **月末/年末边界**、时区、`cron` 的日/周字段冲突
- **执行日志与业务结果是否一致** —— 调度中心显示"成功"不等于业务生效

7) **⭐ 核心防护：给任务加"三道闸"**
- **① 超时闸** —— **所有下游调用必须有超时**；给整个任务加**总超时**（框架层或用 `Future.get(timeout)` + `cancel`）
- **② 并发闸** —— 防止同一任务重复执行：**分布式锁**（Redis/ZK）保证集群内只有一个实例在跑；单机可用 `AtomicBoolean` 或调度框架的"阻塞策略"
- **③ 进度闸（断点续跑）** —— **记录执行进度**（如已处理的 ID/时间点），下次从断点继续，而不是从头再来。**这是长任务能安全重试的前提。**

8) **⭐ 任务不能重叠执行（堆积问题）**
- **Spring `@Scheduled`** —— 默认**单线程**，同一任务不会并发，但**前一轮没结束下一轮会排队**（日志里时间戳会"越积越多"）。解法：改用 `SchedulingConfigurer` 配置 `ThreadPoolTaskScheduler`（**注意 `poolSize` 默认是 1**），并保证任务**幂等**
- **Quartz** —— 可用 `@DisallowConcurrentExecution` 禁止同一 Job 并发
- **XXL-JOB** —— 调度中心有**阻塞策略**（单机串行/丢弃后续/覆盖之前）
- **通用解法**：**任务开始时检查"上一轮是否还在跑"**，在则跳过本轮并告警

9) **⭐ 任务必须幂等**
定时任务会**因为网络抖动、下游超时、调度中心重试而重复执行**。因此**每个定时任务都要设计成幂等的**：
- 用**业务唯一键 + 状态机**（如"已处理"标记）而非依赖"只执行一次"
- 用**乐观锁/版本号**防并发写
- 用**数据库唯一索引**兜底（`INSERT` 冲突即跳过）
> **"不重复执行"是做不到的，"重复执行也不出错"才是正确设计。**

10) **监控与告警**（预防性，比事后排查更重要）
- **执行心跳**：任务开始/结束都打点，**监控"上次开始时间"与"上次结束时间"的间隔** → **超时未结束自动告警**
- **执行时长监控**：P95/P99 耗时趋势，**突然变长要预警**
- **失败告警**：异常必须**主动通知**（钉钉/企微/邮件），**不能只写日志**
- **积压监控**：队列长度、待处理条数
- **分布式锁监控**：拿不到锁时告警（说明有节点异常）

11) **排查流程（可直接照做）**
```
① 确认形态：没触发 / 卡住 / 结果不对 / 堆积
② 查执行记录（QRTZ 表 / 调度中心日志 / 应用日志）
③ 没触发 → 查 cron 位数、时区、@EnableScheduling、方法可见性、多实例重复
④ 卡住 → jstack 看线程卡在哪（下游调用? 锁? 连接池? DB锁?）
   → 查慢SQL、长事务、连接池、下游超时
⑤ 结果不对 → 查事务提交、@Async 自调用失效、分片参数、边界条件
⑥ 补上防护：超时闸、并发闸、进度闸 + 幂等 + 心跳告警
```

12) **面试答法建议**。四点：① **先分四种形态**（没触发/卡住/结果不对/堆积），因为根因与解法完全不同；② **触发侧排查**（**cron 六位 vs 五位**、**容器时区 UTC**、`@EnableScheduling`、方法不能 private、**多实例重复触发**）；③ **执行侧排查靠 `jstack` 看线程卡在哪**（下游调用/锁等待/连接池/DB 锁）+ 慢 SQL 与长事务；④ **三条防护（超时闸/并发闸/进度闸）+ 幂等设计 + 心跳告警**。**第②③点最能体现实战经验 —— 时区与 cron 位数是最常见的两个坑。**

## 附：一些容易忽略的细节
- **Spring `@Scheduled` 的 `fixedRate` 与 `fixedDelay` 区别**：前者是**按上次开始时间间隔**（含执行耗时），后者是**上次结束后再等**。**`fixedRate` 在任务耗时大于间隔时会堆积** —— 排查时注意这个差异
- **`@Scheduled` 的默认线程池只有 1 个线程** —— 多个定时任务会**互相阻塞**！这是"某个任务不跑了"的隐形原因
- **Linux cron 不加载登录 shell 的环境变量** —— `java`/`PATH` 找不到是经典坑，要用**绝对路径**
- **容器内时区** —— Docker 默认 UTC，**容器化定时任务必须显式设 TZ**
- **夏令时** —— 跨时区调度时 DST 会导致任务"跳过一次或多跑一次"
