工具返回超大结果时，正确的做法不是在提示里把它截断，而是**不让完整结果进入上下文**：在工具边界就分页限量、服务端过滤投影、压缩成结构化摘要，把原文外置到存储里只回填摘要加引用，再用 token 配额和分批处理把总量管住。原因很直接，一次超大返回会瞬间吃满上下文窗口、抬高成本、稀释注意力，后续推理质量随之断崖式下降。

## 为什么一次超大返回就足以毁掉后续推理

工具返回超大结果是 Agent 系统最常见的工程问题之一，它的危害不是"占一点地方"，而是把上下文这个稀缺资源一次性花光，而且花得毫无收益。核心思路只有一句：**不要把完整结果放进上下文**。

三个后果值得分开说，因为它们对应三种不同的修法：

- **占窗口**：一次超大返回就能吃掉剩余预算，真正重要的系统指令、用户约束、已经确认过的结论被挤出去，模型随后开始"忘事"，重复问已经答过的问题。
- **抬成本**：结果一旦写进消息列表，后面每一轮请求都会重新带上它，等于同一份数据被反复计费，轮次越多越贵，长任务上这项开销会持续累积。
- **稀释注意力**：上下文越长，模型对其中部信息的利用越不稳定，真正有用的几行关键数据淹在海量噪声里，判断质量反而比不调用工具时更差。

所以问题的定位不是"输出太长了要不要截"，而是"结果该以什么形态进入上下文"。

## 超大结果分三类，策略不能一招切

不同来源的超大结果，能下手的层次不一样：结构化数据可以在查询侧就削减，半结构化内容适合切片检索，非结构化大对象只能先搬出去再引用。先分类，再选策略。

| 类型 | 典型例子 | 首选处理 |
| --- | --- | --- |
| 结构化数据 | 数据库查询返回几行、API 返回大 JSON | 分页限量、服务端过滤投影、字段裁剪 |
| 半结构化内容 | 长文档、网页、日志 | 分块索引、先检索片段、分级下钻 |
| 非结构化大对象 | 整份代码库、大文件、二进制 | 外置存储、只回填摘要与可寻址引用 |

分类的意义在于避免用错工具：对一份整库代码做"分页"没有意义，而给一条 SQL 查询套"分块索引"同样没有意义。

## 第一层：在工具边界就把结果裁掉

这一层改的是工具本身，收益最大，因为数据根本没机会进入上下文。

**分页与限量**是最基础的手段：工具接口本身就支持 `limit`、`offset`、`page_size`、字段裁剪，**默认就返回前 N 条并注明总数**。不要让模型自己去请求全量再自己截断——那时数据已经付过费和占过窗口了。

**服务端过滤与投影**是把过滤条件、排序、字段选择**下推到数据源**，只返回真正需要的数据。

:::tip[最优解]
这是最优解——减少的不只是上下文，还有网络传输与数据库压力。
:::

**工具层内容消毒**同样属于这一层：大结果里常混入 HTML 标签、脚本、大段重复内容、无关的二进制片段，应在进入上下文前**剥离标签、去重、过滤噪声**。这一步成本低、收益高，纯粹是字符串处理，却能省掉大量无意义的 token。

一次"限量 + 投影 + 摘要 + 引用"合起来的回填长这样（字段名各家实现略有差异，结构大同小异）：

```text
// 工具定义：默认限量、只取需要的字段
{
  "name": "query_orders",
  "parameters": {
    "type": "object",
    "properties": {
      "status": { "type": "string" },
      "limit": { "type": "integer", "default": 20 },
      "offset": { "type": "integer", "default": 0 },
      "fields": { "type": "array", "items": { "type": "string" } }
    }
  }
}

// 回填给模型的内容：统计 + 摘要 + 异常项 + 引用，而不是全量数据行
{
  "total": 8421,
  "returned": 20,
  "summary": "近 30 天待发货订单 8421 条，其中 3 条状态异常，集中在同一仓库",
  "anomalies": ["order_88213", "order_88240", "order_88301"],
  "next_offset": 20,
  "raw_ref": "runs/1024/orders.jsonl#L1-L20"
}
```

模型拿到的信息足够继续判断，需要细节时按 `raw_ref` 回读那一段，而不是把八千行都搬进对话。

## 第二层：上下文里只放摘要和引用

如果工具侧实在没法削减（比如一份第三方返回的整页 HTML、一个巨大的日志文件），就在回填前做形态转换。

**结果摘要与结构化提取**：由工具层或一个廉价的模型调用，把原始结果**压缩成结构化的关键字段**（结论、关键数值、异常项、计数），而不是保留自然语言长文本。判据很朴素：摘要要能支撑"下一步做什么"这个决策，而不是复述原文。

**结果外置与引用**：把完整结果存到外部存储（文件、对象存储、数据库），上下文里只放**一段摘要 + 可寻址的引用**（如文件路径、结果 id、行号范围）。Agent 需要细节时再按需回读。这与"记忆外置"是同一思想——上下文负责索引与判断，存储负责事实与证据。

**分块检索与分级读取**：对长文档做**分块与索引**，先检索出相关片段；需要更多细节时按 chunk 逐级下钻（先看摘要层，再看段落层，最后看原文）。

| 手法 | 进上下文的东西 | 需要细节时怎么回读 |
| --- | --- | --- |
| 结果摘要 | 结论、关键数值、异常项、计数 | 重新查一次，或读外置结果 |
| 结果外置 | 摘要加文件路径、结果 id、行号范围 | 按引用读取指定片段 |
| 分块分级读取 | 命中片段的摘要层 | 逐级下钻到段落层、原文 |

三种手法的共同点是把"是否需要"这个判断交给模型，把"具体内容"留在上下文外面。

## 第三层：用预算和节奏兜住总量

前两层是单次调用的处理，这一层管的是整个会话的总量。

**上下文预算硬约束**：在组装提示时设定**每类内容的 token 配额**（工具结果最多占 X%，检索内容最多占 Y%），超出的按优先级裁剪。优先级通常按"对当前决策的必要性"排：系统约束最高，其次是当前子任务的直接证据，再次才是背景资料。

:::tip[硬约束]
没有配额就一定会失控。
:::

**分页迭代与流式处理**：若任务本身需要遍历大量数据，不要把全部结果塞进一次上下文，而应**分批处理**——每批进上下文、处理完只保留结论，滚动前进。流式读入的意义在于边读边筛，只保留命中的行与统计量，中间数据用完即弃。

**子 Agent 隔离上下文**：把这类"读得多、结论少"的遍历工作放进子 Agent，主循环只接收它返回的结论。这样主循环的上下文不会被中间数据污染，也保住了后续推理的清晰度。

## 常见追问

**Q：直接在回填时把字符串截断到固定长度不行吗？**
A：不推荐。裸截断会把 JSON 切成半截、把关键结论切在半句上，模型读到残缺结构反而更差。正确做法是按字段投影、给计数与汇总、附引用，让被裁掉的部分仍然可寻址。

**Q：压缩成摘要会不会丢掉模型真正需要的那条细节？**
A：所以要摘要配引用。摘要负责让模型判断"要不要看细节"，引用负责让它按需取回原文；只有摘要没有引用，模型只能猜；只有原文没有摘要，窗口直接爆掉。

**Q：什么时候必须让大结果留在上下文里？**
A：只有当任务要求逐字符比对、精确改动这类必须看原文的场景。即便如此也应先缩小范围（定位到文件、行段）再放入，而不是整份塞进去。

**Q：同一个大结果被多轮重复带入，怎么彻底避免？**
A：两条路并行：一是结果外置后只保留引用，二是历史压缩时把已完成轮次的大结果替换成摘要或占位符。只靠模型自己"记得不用再发"是不可靠的。

## 易错点

1. **把整个文件、整张表、整个网页直接塞进提示**。指望模型自己"看重点"，实际结果是关键约束被噪声挤掉，答非所问。
2. **让模型先请求全量再自己截断**。截断发生在窗口已被占用、费用已经产生之后，限量和投影必须做在工具侧。
3. **把大结果反复重发**。每轮都带上，等于成本翻倍，还会持续稀释注意力，越到后面越容易出错。
4. **只截断不留引用**。截断后模型既看不到细节也没有回读路径，只能凭猜补全；摘要必须带可寻址的引用。

正确做法永远是**在工具边界就把结果裁剪好**，而不是等它进了上下文再想办法。

## 一句话记住

核心不是截断文本，而是在工具边界就把结果裁成摘要与引用。
:::
