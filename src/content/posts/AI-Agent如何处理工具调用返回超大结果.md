## 核心结论

工具返回超大结果是 Agent 系统最常见的工程问题之一，它会瞬间吃满**上下文窗口**、抬高成本、稀释注意力，导致后续推理质量断崖式下降。核心思路是**不要把完整结果放进上下文**。

## 问题分类

超大结果分三类：**结构化数据**（数据库查询返回几行、API 返回大 JSON）、**半结构化内容**（长文档、网页、日志）、**非结构化大对象**（整份代码库、大文件、二进制）。不同类型要配不同策略，不能一招切。

| 类型 | 典型例子 |
| --- | --- |
| 结构化数据 | 数据库查询返回几行、API 返回大 JSON |
| 半结构化内容 | 长文档、网页、日志 |
| 非结构化大对象 | 整份代码库、大文件、二进制 |

## 解决方案

### 分页与限量

最基础的手段：工具接口本身就支持 `limit`、`offset`、`page_size`、字段裁剪，**默认就返回前 N 条并注明总数**。不要让模型自己去请求全量再自己截断。

### 服务端过滤与投影

把过滤条件、排序、字段选择**下推到数据源**，只返回真正需要的数据。

:::tip[最优解]
这是最优解——减少的不只是上下文，还有网络传输与数据库压力。
:::

### 结果摘要与结构化提取

由工具层或一个廉价的模型调用，把原始结果**压缩成结构化的关键字段**（结论、关键数值、异常项、计数），而不是保留自然语言长文本。

### 结果外置与引用

把完整结果存到外部存储（文件、对象存储、数据库），上下文里只放**一段摘要 + 可寻址的引用**（如文件路径、结果 id、行号范围）。Agent 需要细节时再按需回读。这与“记忆外置”是同一思想。

### 分块检索与分级读取

对长文档做**分块与索引**，先检索出相关片段；需要更多细节时按 chunk 逐级下钻（先看摘要层，再看段落层，最后看原文）。

### 分页迭代与流式处理

若任务本身需要遍历大量数据，不要把全部结果塞进一次上下文，而应**分批处理**：每批进上下文、处理完只保留结论，滚动前进。必要时用子 Agent 隔离上下文，避免污染主循环。

### 上下文预算硬约束

在组装提示时设定**每类内容的 token 配额**（工具结果最多占 X%，检索内容最多占 Y%），超出的按优先级裁剪。

:::tip[硬约束]
没有配额就一定会失控。
:::

### 工具层内容消毒

大结果里常混入 HTML 标签、脚本、大段重复内容、无关的二进制片段，应在进入上下文前**剥离标签、去重、过滤噪声**。这一步成本低、收益高。

## 反模式

- 把整个文件、整个表、整个网页直接塞进提示。
- 指望模型自己“看重点”。
- 把大结果反复重发（每轮都带上，等于成本翻倍）。

:::caution[反模式]
正确做法永远是**在工具边界就把结果裁剪好**。
:::
