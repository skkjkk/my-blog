线程数没有万能公式，稳妥的做法是先按任务类型给一个起点公式，再用压测数据收敛：CPU 密集型任务取「核数 + 1」，IO 密集型任务按「核数 ×（1 + 等待时间 / 计算时间）」估算、常从核数的 2 倍起步。这两个值都只是起点，最终的最佳线程数要靠在同规格机器上压测找拐点，并且受队列容量、下游连接池、容器配额这些瓶颈条件的共同约束。

## 先分清任务类型，公式只是起点

设置线程数之前，先看任务的时间花在哪：是占着 CPU 在算，还是在等网络和磁盘返回。两者的起点公式不一样，但都只是起点。

- CPU 密集型：几乎全在计算，线程大部分时间占着 CPU，多开线程只会加剧上下文切换，收益很小。
- IO 密集型：大部分时间在等待，CPU 在此期间是闲置的，多开线程才能把 CPU 喂满。

确定起点之后，还要拿队列容量、下游连接池大小、内存和容器配额去校验一遍，再用压测收敛到具体数字。

## CPU 密集型任务：线程数 ≈ 核数 + 1

这类任务几乎全在计算，线程数与 CPU 核数对齐即可，多出的一个线程用于在某个线程因页缺失或被中断时补位，避免出现空闲的 CPU 核心。继续往上加线程，吞吐基本不再增长，代价却是上下文切换和线程栈内存的开销。

适合纯计算型业务，如加密、编解码、图像处理。判断方式很直接：如果火焰图上线程几乎都在跑业务代码，没有阻塞在 socket 读或数据库等待上，就属于这一类。

## IO 密集型任务：线程数应显著大于核数

任务大部分时间在等待网络或磁盘，CPU 在这段时间是闲置的，所以线程数应显著大于核数，常按核数的 2 倍起步，再依据「等待时间 / 计算时间」之比折算。经典估算公式是 核数 ×（1 + 等待时间 / 计算时间）：等待与计算大致一比一时，结果正好是核数的 2 倍，这也是 2 倍这个起步值的由来。

适合接口调用、数据库读写、文件上传下载。要注意这个比值是估出来的，下游一变慢，比值就变大，线程数也得跟着调，所以最终还得靠压测确认。

## 压测驱动才是定值的方式

用与生产同规格的机器跑基准流量，把线程数逐档往上调，关注两个指标：吞吐量是否还在随线程数上升，以及响应延迟的分位值。**当吞吐不再增长、延迟开始明显上升时，就是最佳拐点。** 辅看上下文切换次数与 CPU 利用率：切换次数陡增、CPU 已接近打满，说明再加线程已经不划算。

压测环境要接真实的下游依赖或等价的桩，否则「等待时间 / 计算时间」的比值是假的，测出来的拐点位置也会失真。

| 任务类型 | 起点公式 | 加线程的收益来自 | 典型场景 |
| --- | --- | --- | --- |
| CPU 密集型 | 核数 + 1 | 几乎没有，多出的一个只是补位 | 加密、编解码、图像处理 |
| IO 密集型 | 核数 ×（1 + 等待/计算），常从 2 倍起 | 让闲置的 CPU 去跑别的任务 | 接口调用、数据库读写、文件上传下载 |

## 线程数受下游瓶颈限制

若所有线程都访问同一个数据库连接池，而连接池只有 20 个连接，把线程数设到几百并不会提升吞吐，反而造成大量线程在池上排队，延迟和内存一起上涨。线程数应与下游瓶颈资源的使用者数量匹配：连接池大小、下游服务的并发上限、限流阈值，取其中最紧的那个当参考。

换个说法，瓶颈在哪一层，线程数就由那一层决定，单方面加线程只是把压力堆在瓶颈前面。

## 参数必须有界，拒绝策略要明确

这几个参数要成套设计，拆开看单个值没有意义：

1. 最大线程数与队列容量都要设上限：无界队列会让最大线程数这层保护失效，任务积压时直接 OOM。
2. 拒绝策略要明确：通常用「调用者执行 + 限流」，让提交方自己慢下来形成反压；或者自定义策略，把任务持久化后转入补偿流程，因为直接丢弃在多数业务里不可接受。
3. 丢弃类的策略只适用于任务本身可丢弃、且有降级兜底的设计。

有界队列配合调用者执行，适合有明确容量规划、且需要背压的接口服务。

## 线程工厂、容器总量与动态调参

这三件事决定了池子上线后好不好维护：

- 线程工厂要可观测：给线程设置可读名称（如 `biz-handler-3`）并配置 `UncaughtExceptionHandler`，排查问题时可精确定位到池与任务，异常也不会被默默吞掉。
- 容器环境注意总量：线程数是按整个进程统计的，同一 JVM 内多个业务线程池的总数应控制在受限运行环境的允许范围内；容器的 CPU 配额不一定等于 JVM 看到的核数，先确认实际可用处理器数再套公式。
- 优先选择支持动态调参的实现：原生 `ThreadPoolExecutor` 提供了 `setCorePoolSize`、`setMaximumPoolSize`，能在运行时改参数；需要配置热更新、运行指标监控与告警时，可用阿里 `dynamic-tp` 这类框架，避免改一个参数就要重启服务。

```java
int cores = Runtime.getRuntime().availableProcessors();
// CPU 密集型取 cores + 1；IO 密集型先按 cores * 2 起步，再用压测收敛
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    cores + 1, cores * 2, 60L, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(1000),              // 队列必须有界，积压才有上限
    new NamedThreadFactory("biz-handler-"),      // 自定义工厂：线程可命名、异常有出口
    new ThreadPoolExecutor.CallerRunsPolicy());  // 满了让提交线程自己跑，形成反压
```

## 常见追问

**Q：为什么 CPU 密集型是核数 + 1，而不是核数？**
A：加的那个线程是补位用的，某个线程因页缺失或被中断时能顶上，避免出现空闲的 CPU 核心。加更多就没意义了，只会增加切换开销。

**Q：IO 密集型到底该设成核数的几倍？**
A：看等待时间与计算时间的比值。大多数时间在等下游时，比值大，线程数就该远超核数；反之接近计算型。倍数只是起点，最终以压测的吞吐与延迟拐点为准。

**Q：线程数设大一点不是更保险吗？**
A：不是，它被下游瓶颈卡着。连接池只有 20 个连接时，几百个线程只是在池上排队，吞吐不变而延迟和内存都变差。

**Q：能不能不重启就改线程数？**
A：原生 `ThreadPoolExecutor` 的 `setCorePoolSize`、`setMaximumPoolSize` 支持运行时调整；要配置热更新和指标监控告警，可用 `dynamic-tp` 这类框架。

## 易错点

- **把公式当答案**：核数 + 1 和 2 倍都只是起点，不压测就上线，等于用别人的机器参数跑自己的业务。
- **用无界队列还配了最大线程数**：队列永远排不满，`maximumPoolSize` 形同摆设，任务积压时直接 OOM。
- **只调线程数不看下游**：连接池、下游限流不跟着扩，加线程只会把排队位置从线程池里挪到下游去。
- **线程池不留名字、不设异常处理**：出问题时线程栈里全是 `pool-3-thread-17`，定位成本极高。

## 一句话记住

:::tip
先按任务类型套公式给起点，再压测找「吞吐不涨、延迟抬头」的拐点，全程受下游瓶颈约束。
:::
