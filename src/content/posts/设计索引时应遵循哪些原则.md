索引设计的目标是：**用最少的索引，换取最大的查询收益，同时把写入成本控制住**。下面按"**先做 → 再定顺序 → 最后收尾**"的顺序给出原则。

1) **⭐ 第一原则：先梳理核心查询路径，再建索引**
**不要"给每个字段都加索引"**。正确做法是：
- 统计**慢查询日志 / `pt-query-digest`** → 找出高频慢 SQL
- 梳理出系统的**核心查询组合**（哪些 SQL + 哪些 WHERE / JOIN / ORDER BY 条件）
- **按实际查询组合建索引**，而不是按字段建索引
> **索引是为查询服务的，不是为字段服务的。**

2) **⭐ 第二原则：联合索引优先，用最左前缀匹配**
大多数查询都是"一个等值条件 + 一个范围/排序条件"，所以应该建成**联合索引**而不是多个单列索引。
- **优势**：一个联合索引可覆盖多种查询组合；单列索引多了会让**优化器选择空间变大、更容易选错**
- **⚠️ 冗余判断**：`(a,b,c)` 能覆盖 `a`、`a+b`、`a+b+c` → **不要再单独建 `(a)`**

3) **⭐ 第三原则：把等值条件放前面、范围条件放最后**
联合索引 `(a, b, c)` 中：
- `WHERE a=? AND b>? AND c=?` → **c 失效**（范围查询之后的列无法继续用于索引查找）
- 所以**等值列在前、范围/排序列在后** → `WHERE a=? AND c=? AND b>?` 的顺序才是最优
> **这条决定了联合索引的列顺序**，是最核心的原则之一。

4) **⭐ 第四原则：区分度高的列靠前**
区分度 = 该列不同值的数量 / 总行数。**接近 1 的列（唯一 ID）区分度最高**。
- 性别、状态、类型这类**低区分度列放前面，会让后续列的过滤能力被浪费**
- ⚠️ **但排序/范围条件的列要放最后**（第 3 条）→ **两者冲突时，优先保证"范围条件放最后"，因为那直接决定后续列能否生效**
> **联合索引列顺序 = 区分度 + 等值在前范围在后 + 高频查询优先，综合权衡。**

5) **⭐ 第五原则：尽量构造覆盖索引（避免回表）**
如果查询用到的所有列都能从同一个索引拿到 → **不需要回表** → 性能大幅提升。
- 手段：把常用的 `SELECT` 列**追加到联合索引末尾**
- ⚠️ **代价**：索引变大 → 写入变慢、占用更多空间 → **不要为了覆盖索引把大字段（TEXT/VARCHAR(1000)）塞进索引**

6) **第六原则：前缀索引控制长字段的索引大小**
长 `VARCHAR` / `TEXT` 列 → `KEY idx_name (name(20))`。
- ⚠️ **限制**：不能用于覆盖索引、不能用于排序、不能加唯一约束
- ⚠️ 前缀长度要够区分（`name(3)` 区分度极低 → 效果差）

7) **⭐ 第七原则：不要给"低区分度单列"建索引**
性别、是否删除这类只有两三个取值的列，单独建索引后优化器大概率仍会全表扫描（**走索引还要回表反而更慢**）。
- ✅ 可以作为**联合索引的一部分**（排在后面）
- ❌ 不要作为独立索引

8) **⚠️ 第八原则：写多的表要控制索引数量**
日志表、流水表这类**写多读少**的表，索引越多，**每次 INSERT/UPDATE/DELETE 的维护成本越高**。
- 必要时**定期归档**、按时间**分区**

9) **⭐ 第九原则：避免在索引列上做运算、函数、隐式转换**
索引里存的是**原始值**，一旦在查询时对列做运算，索引就不可用：
- ❌ `WHERE DATE(create_time) = '2024-01-01'` → ✅ `WHERE create_time >= '...' AND create_time < '...'`
- ❌ `WHERE phone = 13800138000`（varchar 字段传数字）→ ✅ **类型对齐**
- ❌ `WHERE col + 1 = 10` → ❌ `WHERE col LIKE '%x'`（前缀通配）

10) **⭐ 第十原则：定期清理无用索引**
索引不会自动失效，会**一直消耗写入成本与空间**。用 **`pt-index-usage`** 或慢日志分析，找出**从未被使用过的索引**并删除。
- ⚠️ **删前确认**：该索引不是某个联合索引的最左前缀
- ⚠️ 大表删索引用 **在线 DDL**（gh-ost / pt-osc）避免锁表

11) **⭐ 第十一原则：主键的选择**
- 用 **`BIGINT`**（不是 `INT`），**短**（**UUID 字符串做主键是灾难**：36 字符 + 无序 → 页分裂 + 所有二级索引膨胀）
- 尽量**单调递增**（顺序追加 → 少页分裂、缓存命中率高）
- 分库分表场景用**雪花算法**（有序 BIGINT）或**号段模式**

12) **设计流程（可直接照做）**
```
① 收集慢 SQL / 高频查询 → 列出核心查询组合
② 设计联合索引：等值在前、范围在后、区分度高在前
③ 检查能否构造覆盖索引（追加常用 SELECT 列）
④ 排除低区分度独立索引、排除冗余索引
⑤ 上线后监控索引使用率与写入耗时
⑥ 定期用 pt-index-usage 清理未使用索引
```

13) **面试答法建议**。三点：**① 先讲方法论（先梳理查询路径再按查询组合建索引，而非按字段建）；② 核心的列顺序原则（等值在前、范围在后、区分度高在前，并说明三者冲突时以"范围放最后"优先）；③ 覆盖索引与索引数量权衡 + 定期清理无用索引**。**第二点的"范围条件之后的列失效"是最能体现细节的考点。**
