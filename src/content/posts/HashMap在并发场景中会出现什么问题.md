HashMap 是**非线程安全**的容器，并发使用会出四类问题：**put 并发导致数据覆盖与丢失、并发扩容导致元素凭空消失、可见性缺失导致写入读不到，以及 JDK 7 特有的环形链表死循环**。根因是它**没有任何同步保护**：扩容、put、get 都由多个步骤组成、彼此不可分割，而 `table`、`size`、`threshold` 又都不是 `volatile`。JDK 8 用尾插法修掉了死循环，但其余问题一个都没修。

## 问题清单与共同根因

四类问题看起来分散，其实是同一个根因的不同表现。第一，**没有任何同步手段**：`HashMap` 的方法上没有 `synchronized`，内部也没有 CAS 或并发容器那套结构，多个线程完全可以同时进入 `putVal`、`resize`。第二，**每个操作都是多步的**：一次 `put` 要走"计算 hash 与下标 → 定位桶 → 遍历链表或红黑树 → 判断是否已存在 → 写入并增加 `size` → 判断是否扩容"，任何一步都可能被别的线程插进来。第三，**状态字段没有可见性保证**：`table`、`size`、`threshold` 都是普通字段，写入后不会强制刷回主内存，别的线程读到的可能是旧值。三条叠在一起，就得到了下面四类后果。

## 问题一：put 并发导致数据覆盖与丢失

多个线程同时 put **同一个桶**时，最容易出问题的是"空桶判断"。两个线程都读到该桶为 `null`，各自认为自己是第一个写入者，于是**后写的直接把先写的覆盖掉**，先写的那条数据从此不存在。**更隐蔽的是"检查存在性"与"写入"不是原子的**：线程 A 判断完"这个 key 还不存在"、正准备写入，线程 B 抢先写入并返回，线程 A 仍按"不存在"的判断继续写，**B 的数据就凭空消失了**。这类丢失不会抛异常、不会打日志，线上往往表现为"计数少了几个""缓存里莫名少了一条"。

```java
Map<String, Integer> map = new HashMap<>();

// "读 → 加一 → 写"是三步，两个线程同时执行，可能只生效一次
map.put("cnt", map.getOrDefault("cnt", 0) + 1);

// 并发计数要用原子复合操作，而不是 get 之后再 put
ConcurrentHashMap<String, Integer> safe = new ConcurrentHashMap<>();
safe.merge("cnt", 1, Integer::sum);
```

## 问题二：并发扩容导致元素凭空消失

扩容本身不是原子操作：`resize()` 里先 `new` 一个新数组，再把旧数组的元素逐个迁移过去，最后把 `table` 指向新数组。两个线程同时触发扩容时，**各自持有一份自己的新数组、各自迁移元素**。线程 A 迁移完把 `table` 指向自己的新数组，线程 B 随后也完成迁移并覆盖 `table` —— **A 迁移的结果被整体丢弃**，那些只存在于 A 那个数组里的元素就人间蒸发了。**这是 HashMap 在并发下最典型的数据丢失场景**，损失往往是一整段元素，而不是零星几条。

## 问题三：JDK 7 的环形链表死循环

JDK 7 扩容用**头插法**：遍历旧桶的链表，把每个节点依次插到新桶的头部，于是链表顺序会被反转。并发扩容时，线程 A 把节点 B 迁到新桶并让 B 指向 A 正在处理的那个旧节点，线程 B 同时在做方向相反的操作，两边交错执行的结果是**两个节点的 next 互相指向对方，形成环形链表**。之后任何线程 `get` 命中这个桶，遍历链表的循环就永远走不出来 —— **CPU 飙到 100%、线程无法终止**，排查时只看得到一坨卡在 `HashMap.get` 的栈。

**JDK 8 改用尾插法修复了这个问题**：扩容时按 `hash & oldCap` 把一条链拆成低位、高位两条链，两条链都保持原有相对顺序再挂到新桶上，逻辑上不会产生环。要注意这是"修掉了成环"，而不是"修好了线程安全"。

## 问题四：可见性、size() 与读一致性

`table`、`size`、`threshold` 这些字段**没有 `volatile` 修饰**，也不在任何同步块内，所以**一个线程写入的数据，另一个线程可能永远看不到**：JMM 允许指令重排序，也允许线程把值留在自己的工作内存里。表现就是"明明 put 了却 get 不到"，而且**不可复现**，换个机器、换个负载就消失了。

`size()` 同样不安全。它读的是 `size` 这个普通 `int` 字段（不是加锁遍历 `table` 现算），而 `put`、`remove` 对它的自增自减是"读-改-写"三步，多个线程会互相覆盖，所以并发修改时返回的可能是任意中间值，**甚至偏小**。

`get` 虽然只读，也**可能读到不一致的状态**：扩容期间 `table` 引用已经切到新数组、旧数组里的桶被陆续迁走，此时读旧数组就**读不到本该存在的 key**。**即使没有两个线程同时写，只要 put 与 get 并发，也可能出现"刚放进去就取不到"**。

## 正确做法：首选 ConcurrentHashMap

| 方案 | 实现方式 | 并发能力 | 主要代价 |
| --- | --- | --- | --- |
| `ConcurrentHashMap` | JDK 8 放弃 Segment 分段锁，改为 CAS + `synchronized` 锁单个桶的头节点 | 最高，读完全无锁、不同桶可并发写 | `size()` 只是估算值，迭代器弱一致 |
| `Collections.synchronizedMap` | 外面包一层，所有方法共用一把锁 | 低 | 读也要抢锁，并发度等于 1 |
| 外部自己加锁 | 所有访问点在同一个锁内 | 取决于锁粒度 | 只适合访问点集中、竞争不激烈的场景 |
| `Hashtable` | 遗留类，全方法 `synchronized` | 低 | 性能差且不允许 `null`，新代码不要用 |

`ConcurrentHashMap` 之所以成为默认答案，关键在三点：

- **读操作不加锁**：靠桶头节点的 volatile 读、以及节点的 `val` 与 `next` 的 volatile 语义保证可见性，所以读很快，读到的是某个时刻的快照，但复合操作仍需 `merge`、`compute` 这类原子方法。
- **写操作只锁当前桶的头节点**：锁粒度极细，落在不同桶上的写可以真正并行，并发度远高于一把大锁。
- **`size()` 是估算值**：JDK 8 用 `baseCount` 加 `CounterCell` 数组分散计数，避免所有线程抢同一个计数器，所以并发下拿到的只是近似值，**不要用它做精确判断**。
- **不保证迭代顺序**，遍历用的是弱一致性迭代器：不会抛 `ConcurrentModificationException`，但可能读到、也可能漏读并发修改期间的新值。**如果业务强依赖 Map 的有序性，或者需要精确的 size，`ConcurrentHashMap` 都不合适**，前者考虑 `ConcurrentSkipListMap` 或加锁的 `TreeMap`，后者应该从业务上绕开"靠 size 判断"。

## 常见追问

**Q：JDK 8 的 HashMap 到底还安不安全？**
A：不安全。尾插法只解决了 JDK 7 的环形链表死循环，put 覆盖、并发扩容丢元素、可见性问题依然存在，`table` 和 `size` 仍然没有同步。所以"JDK 8 的 HashMap 线程安全了"是**错误认知**。

**Q：那 `Collections.synchronizedMap` 是不是就够了？**
A：功能上正确，它对每个方法加同一把锁，不会再丢数据。但并发度等于 1，读操作也要排队，高并发下会成为瓶颈，只在并发很低、改造量要求最小时才考虑。

**Q：既然有 `ConcurrentHashMap`，还需要 `HashMap` 吗？**
A：需要。方法内的局部变量、单线程构建完再对外只读发布的场景，`HashMap` 更轻、没有额外开销。判断标准是"有没有第二个线程会同时碰到它"，而不是"是不是集合"。

**Q：为什么说丢数据比死循环更危险？**
A：死循环至少症状明显，CPU 打满、线程卡死，能被监控和线程栈抓到；丢数据是静默的，`size` 少一条、缓存少一条都不会报错，往往等到对账不平或用户投诉才被发现。

## 易错点

- **以为 JDK 8 之后 HashMap 就线程安全了**：只修了成环死循环，数据覆盖、扩容丢失、可见性一个都没修。
- **以为 get 是只读的所以并发没问题**：扩容期间读到旧数组，会读不到刚 put 进去的 key。
- **拿 HashMap 当本地计数器**：`get` 再 `put` 是复合操作，必须换 `ConcurrentHashMap` 的 `merge` 或 `compute`，或者自己加锁。
- **用 `size()` 做精确判断**：并发下它可能是过期值甚至偏小，用它做限流、分片、判空都会出错。
- **把 Hashtable 或 synchronizedMap 当成优化**：正确但并发度极低，且 `Hashtable` 不允许 `null` 值，老代码迁移时容易踩。

## 一句话记住

:::tip
并发下 HashMap 会静默丢数据，JDK 7 还会死循环卡死线程。
:::
