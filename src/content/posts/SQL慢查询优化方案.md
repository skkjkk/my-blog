慢查询优化是一个**闭环**，不是一次性动作：**发现慢查询 → 定位瓶颈 → 分析执行计划 → 针对性优化 → 验证效果 → 防回归**。核心原则是三条：**先定位、再优化；先索引、后改写；用数据说话。** 真正拉开差距的不是记住了多少条优化技巧，而是能不能先分清「慢」属于哪一类原因 —— 缺索引、SQL 写法、数据量与逻辑、还是锁等待与资源，这四类的解法完全不同，定位错了就是白做。

## 第一步：把慢查询捞出来

开启**慢查询日志**（`slow_query_log=ON`，`long_query_time` 建议设 0.1~1 秒，生产环境别设 0，否则日志量会失控），再用 **`pt-query-digest`** 做归类聚合，拿到 **总耗时最高、单次最慢、调用次数最多** 三个维度的 top SQL。

**⚠️ 最容易漏掉的是「总耗时」这个维度** —— 单次 10ms 但调用 10 万次的 SQL，往往比单次 5 秒的 SQL 更值得优化：前者吃掉的是数据库的整体吞吐和连接占用，后者只是一次偶发的尖刺。只看「单次最慢」会长期忽略高频小 SQL 的累积成本。

## 第二步：分清「慢」的四类原因

**慢日志只能告诉你「慢」，不能告诉你「为什么慢」。** 动手前先按下面的表归类，四类原因的解法完全不同：

| 症状（慢日志 / EXPLAIN 看到的） | 原因归类 | 首选解法 |
| --- | --- | --- |
| `type=ALL`、`rows` 远大于实际返回行数 | 缺索引 / 索引失效 | 补索引；消掉函数运算与隐式转换 |
| `Extra` 出现 `Using filesort`、`Using temporary`，写法别扭 | SQL 写法问题 | 改成能用上索引的写法（去子查询、去函数、拆查询） |
| 主查询很快，但总耗时很高、SQL 条数成千上万 | 数据量或业务逻辑问题 | 批量取数、join 代替循环、预聚合 |
| `Rows_examined` 不多，但耗时很长 | 资源问题（锁等待、连接池排队、下游慢、GC 停顿） | 查锁等待链、缩短事务、扩容连接池 |

**这四类的解法完全不同，定位错了会白做** —— 给 N+1 查询加索引、给缺索引的表加缓存，都是典型的「做了很多却没变快」。

## 第三步：用 EXPLAIN 分析执行计划

`EXPLAIN` 给出的是**优化器的预估**，重点看五个字段：

- `type`：访问类型，`ALL` 就是**全表扫描**，是最该先消灭的一档
- `key`：实际使用了哪个索引，为空说明根本没走索引
- `rows`：预估扫描行数
- `key_len`：索引使用程度，能看出联合索引用到了第几列
- `Extra`：`Using filesort`（额外排序）、`Using temporary`（临时表）、`Using join buffer`（被驱动表没走索引）

再看 **`EXPLAIN ANALYZE`** 拿到真实执行数据，重点关注**预估行数与实际行数的偏差** —— 偏差大说明统计信息过期，或者优化器选错了索引。

```sql
-- 先看执行计划：重点核对 type / key / rows / Extra
EXPLAIN SELECT id, title, created_at
FROM article
WHERE author_id = 42
ORDER BY created_at DESC
LIMIT 20;

-- 再看真实执行数据：对比预估行数与实际行数
EXPLAIN ANALYZE SELECT id, title, created_at
FROM article
WHERE author_id = 42
ORDER BY created_at DESC
LIMIT 20;
```

## 方案一：加对索引

**这是收益最高的首选**，成本最低、见效最快。

- 为高频查询条件建索引，**联合索引遵循最左前缀** —— 查询条件跳过了第一列，后面的列就用不上索引
- 避免对索引列做**函数运算与隐式转换**（如 `WHERE DATE(created_at) = '2026-01-01'`、字符串列传数字），会直接导致索引失效
- 用**覆盖索引**减少回表：查询要的列都在索引里，就不必再回主键索引取整行
- **区分度低的列不适合做独立索引**（性别、状态这类只有几个取值的列）
- **⚠️ 索引不是越多越好**：每个索引都会拖慢写入，并占用 buffer pool 的空间

## 方案二：改写 SQL

同一件事往往有好几种写法，常用的七个改写方向：

- **`UNION ALL` 替代 `UNION`**：去掉不必要的去重开销
- **深分页用延迟关联**：先在索引上定位 id，再 join 回表，替代大 offset
- **消除 N+1 查询**：用一次 `IN` 或 join 批量取
- **避免 `SELECT *`**：减少传输量与回表
- **拆分复杂查询**为多条简单查询
- **小表 join 大表时让小表作驱动表**
- **用条件更新替代「先查后改」**：`UPDATE ... WHERE count >= 1` 天然防超卖

深分页改写的对比如下，前提是 `ORDER BY` 的字段上有索引：

```sql
-- 慢：大 offset 要先扫描并丢弃前面 100 万行，再取 20 行
SELECT id, title, created_at FROM article
ORDER BY created_at DESC LIMIT 1000000, 20;

-- 快（延迟关联）：子查询只在索引上定位这 20 个 id，再回表取整行
SELECT a.id, a.title, a.created_at
FROM (SELECT id FROM article ORDER BY created_at DESC LIMIT 1000000, 20) AS t
JOIN article AS a ON a.id = t.id;
```

## 方案三：改表结构与数据组织

索引和 SQL 都改不动了，再动表结构，改动大所以要放在后面。

- **垂直分表**：宽表按访问场景拆分，不常用的宽字段（大 `text`、很少读的列）拆到副表
- **分区表**：按时间或维度**裁剪扫描范围**，查询里必须带分区键才生效（MySQL 5.7+ 支持分区裁剪）
- **合理的数据类型**：`varchar` 长度要够但别过长、金额用 `decimal` 而非 `double`、能不用 `text` 就不用
- **适当冗余**：把高频 join 的少量字段冗余进来，以消除代价高昂的 join

## 方案四：解决「数据量或逻辑」问题

**这是最容易被误判成「索引问题」的一类**，症状是单条 SQL 的 `Rows_examined` 并不大，但整条链路很慢。

- **N+1 查询**（ORM 懒加载导致 1 次主查询 + N 次子查询）→ 批量预加载或 join
- **循环内查库 / 写库** → 合并成批量操作
- **笛卡尔积**（漏了 join 条件、或关联条件没走索引导致结果集爆炸）→ 补齐关联条件，用 `EXPLAIN` 核对两张表的 `rows` 乘积
- **大表全量统计** → 预聚合汇总表或物化视图
- **深分页**（`LIMIT 1000000, 20` 要扫描并丢弃 100 万行）→ **延迟关联**或**游标分页**（记住上一页最后一条的排序值）

## 方案五：架构层优化

单机怎么优化都到了瓶颈，才往上走一层，每一项都有额外代价：

- **引入缓存**（Redis 扛热点读，⚠️ 注意**缓存穿透 / 击穿 / 雪崩**）
- **读写分离**（查询分流到从库，⚠️ 注意**主从延迟**）
- **分库分表**（单表超千万级时的最后手段，会带来跨片查询与分布式事务）
- **异步化**（不需要实时返回的走 MQ 削峰）
- **限流降级**（高峰期保护数据库）

## 方案六：参数与配置层面

- 调大 `innodb_buffer_pool_size`（buffer pool），让索引与热点数据常驻内存，减少磁盘读
- 调整 `innodb_flush_log_at_trx_commit`：在可接受持久性损失时用它提升写性能（设为 1 最安全，性能优先的取舍要先评估宕机丢数据的风险）
- **⚠️ `max_connections` 与连接池要匹配**：连接池上限加起来大于数据库连接上限，高峰期会直接排队等待

## 锁等待与长事务要单独看

慢日志里若大量 SQL 的 `Rows_examined` 不多但耗时很长，**可能是锁等待，而不是扫描慢**。看 `innodb_lock_wait_timeout`，用 `SHOW ENGINE INNODB STATUS` 或 `performance_schema.data_locks` 看**锁等待链**（谁持有锁、谁在等谁）。

**长事务是锁等待的常见根源** —— 必须缩短事务长度、**事务中不做远程调用**（RPC、HTTP），否则一个慢接口就能把行锁一直攥到超时，把整张表的并发打崩。

## 验证与防回归

⭐ 这一步最容易被跳过，但最关键。

- **验证**：用**相同负载压测**，对比优化前后的**耗时、扫描行数、逻辑读、P99**，而不是只看单次执行时间
- **防回归**：把优化后的 SQL **固化到 CI 的慢查询检测里**（例如用 `pt-query-digest` 做基线对比，或在预发环境跑 `EXPLAIN` 校验扫描行数），**防止「优化 A 引入 B 变慢」**

## 优化的优先级排序

实战中按这个顺序做，性价比最高：

| 顺序 | 手段 | 为什么排这个位置 |
| --- | --- | --- |
| 1 | **加索引 / 改写 SQL** | 成本最低、收益最大，改动只在索引和 SQL |
| 2 | **消除 N+1 与循环查库** | 常是「看起来像索引问题」的真因，改代码即可 |
| 3 | **改表结构（分表、分区、冗余）** | 有 DDL 与迁移成本，但不牵动整体架构 |
| 4 | **加缓存** | 扛读有效，但引入缓存一致性、穿透/击穿/雪崩问题 |
| 5 | **读写分离 / 分库分表** | 架构改动大，带来主从延迟与跨片查询 |
| 6 | **调参数** | 兜底手段，不解决根本问题 |

前两项成本最低、收益最大；后面几项架构改动大、引入复杂度高（缓存一致性、主从延迟、分片带来的跨片查询），所以**调参数永远放在最后**。

## 常见易错点

- **「慢就等于缺索引」** → 错。⭐ 大量慢查询的真实原因是**代码层面的 N+1、循环查库、不必要的全量查询**。**先看 `Rows_examined` 与返回行数的比值** —— 比值接近 1 说明索引已经高效，比值极大才是扫描了太多行。**在没分清原因前就加索引，可能只是让写入变慢而查询没变好。**
- **「建了索引就一定会走」** → 错。对索引列做函数运算、隐式类型转换、最左前缀断裂都会让索引失效，必须回头确认 `EXPLAIN` 的 `key` 列真的有值。
- **「只优化单次最慢的那条 SQL」** → 不全对。总耗时 = 单次耗时 × 调用次数，高频小 SQL 的累积成本经常更高。
- **「压测通过就算收工」** → 错。没有 CI 基线守护，下一次需求迭代很容易把扫描行数打回原形。

## 常见追问

**Q：加了索引查询还是慢，先查什么？**
A：先看 `EXPLAIN` 的 `key` 列。为空说明索引没被用上，多半是函数运算、隐式转换或最左前缀断裂；`key` 有值但 `rows` 依然很大，说明区分度低或本来就要扫这么多行，这时该做的是改写 SQL、减少返回字段或改表结构。

**Q：为什么优先看「总耗时最高」，而不是「单次最慢」？**
A：优化的目标是整体吞吐，不是个别尖刺。单次 10ms、一天调用几百万次的 SQL，占用数据库的时间和连接资源往往超过一天偶发几次的 5 秒慢查询，优化它的收益覆盖面更广。

**Q：深分页为什么慢，延迟关联为什么快？**
A：`LIMIT 1000000, 20` 要求先扫描并丢弃前 100 万行，成本与 offset 成正比。延迟关联让子查询只在二级索引上顺序扫描定位 20 个主键，再回表 join，实际回表只有 20 次。offset 再大就该换成**游标分页**（记住上一页最后一条的排序值）。

**Q：SQL 实在优化不动了，直接加缓存行不行？**
A：缓存解决的是**热点读**，不解决查询本身的复杂度：冷数据照样打库，还要额外承担穿透/击穿/雪崩与一致性成本。正确顺序是先把索引和 SQL 改到合理水平，再用缓存扛峰值。

## 面试怎么答

1. 闭环流程（慢日志 + `pt-query-digest` → `EXPLAIN` / `EXPLAIN ANALYZE` → 优化 → 压测验证 → CI 防回归）
2. 手段分层（索引 → 改写 SQL → 表结构 → 缓存 → 架构 → 参数），越往后代价越大
3. 强调「先分清原因」（缺索引 / SQL 写法 / N+1 与逻辑 / 锁等待与资源），其中 N+1 和深分页是最典型的「不是索引问题」
4. 强调验证用 `Rows_examined` 与返回行数的比值和 P99，且必须压测 + CI 防回归

第三、四点是区分度最高的部分，能把「加索引」和「这不是索引问题」讲清楚，基本就稳了。

## 一句话记住

:::tip
**先定位后优化，先索引后改写，用扫描行数比值和 P99 说话。**
:::
