死循环是 Agent 系统最常见的线上故障之一，表现为任务不结束、token 与费用持续上涨、或者在两个状态间反复横跳。它的本质是**终止条件与进展检测缺失**，而不是模型「笨」。因此解决思路是把它当工程问题而不是智力问题：先按类型识别循环，再分层检测，用四重预算兜底，触发后先注入引导换路径，仍不行就按 L1 到 L6 逐级降级，最后熔断转人工。

## 先分清五种「循环」

死循环不是一个笼统的概念，处置手段取决于它属于哪一类。分不清类型就盲目调参，通常只是把同一段循环换了个措辞继续跑下去。

| 循环类型 | 典型表现 | 主要检测手段 |
| --- | --- | --- |
| **完全重复** | 同样的动作、同样的输入，连着做 | 签名重复检测 |
| **语义重复** | 动作表述不同但实质一样，比如反复用不同措辞搜索同一份文档 | 语义相似检测 |
| **状态循环** | A 状态 → B 状态 → A 状态来回横跳 | 状态签名加无进展检测 |
| **假进展** | 每步都有新输出，但实际没有更靠近目标 | 无进展检测，看状态有没有变 |
| **等待循环** | 反复重试一个必然失败的调用 | 工具失败率、同一错误码统计 |

判断时先看**任务状态或环境状态有没有变化**，再看动作本身像不像重复。假进展是最容易漏掉的一类，因为它表面上一直在产出，日志里看起来很热闹。

## 检测手段要分层

从最便宜的手段往上加，不要一上来就上 embedding 相似度，那样既慢又贵。可用的手段有五条：

- **签名重复检测**：把最近 K 步的动作与观测归一化成签名（动作名、关键参数、观测摘要的 hash），检测滑窗内的重复模式。它最便宜也最有效，应该当第一道防线。
- **语义相似检测**：对动作与结果做 embedding，识别「签名不同但实质相同」的循环，用来兜住换个措辞接着转的情况。
- **无进展检测**：判定任务状态或环境状态是否根本没有变化，连续 N 步增量为零。这是最本质的判据，因为它直接对应「有没有变好」。
- **工具失败率**：连续调用同一工具失败、同一错误码反复出现，说明这条路径本身不通，再试只是等待循环。
- **停滞检测**：连续 N 步之后验收条件仍未满足且状态无变化，此时已经不是慢，而是卡住了。

```python
def loop_guard(step_history, budget):
    signature = hash(action_name + key_args + digest(observation))
    if step_history.window(K).count(signature) >= 2:
        return "inject_hint"      # 滑窗内签名重复：先注入引导，要求换路径
    if state_delta(step_history, N=3) == 0:
        return "replan"           # 连续 N 步状态零增量：升级为重新规划
    if budget.used_ratio() >= 0.8:
        return "downgrade"        # 预算用到 80%：提前降级，不要等撞墙
    return "continue"
```

几个判据落在同一个守卫函数里，返回的不是「终止」而是**下一步该做哪个动作**，这样检测才能和后面的恢复阶梯接上。

## 硬性预算与提前预警

预算是兜底而不是主要手段，它保证最坏情况下的损失有界：

- **最大步数**、**最大 token**、**最大金额**、**最大墙钟时间**四重上限相互独立，任一超限即熔断。
- 金额上限不能省，成本和死循环是强绑定的：转得越久，token 与费用涨得越快。
- 关键是**提前预警**：走到 80% 预算时就触发降级或收敛提示，而不是撞墙才停，因为撞墙时钱已经花完了。
- 只设预算不设进展检测会误杀正常的长任务，所以预算要和停滞检测配合使用。

## 处置：先打断引导，再分级恢复

检测到循环之后，默认动作不是「终止」，而是「打断并引导」。终止会把一次还能救的任务变成失败，而引导常常一步就能把它拉回正轨。引导有三种手段：

- **注入已尝试方案清单**：在上下文里写「你已尝试过 A、B、C」，要求换工具、换参数或换思路，避免模型从零重来。
- **强制多样性**：连续两步动作相同时，强制要求换一条路径，先打破动作层面的单调重复。
- **注入外部信息**：把原始目标与硬约束重申一遍，帮模型重新对齐，防止它在多轮之后跑偏。

引导无效时再按阶梯恢复，**每一级都要有明确触发阈值**，否则降级逻辑本身会变成新的不确定性来源：

| 级别 | 动作 | 什么时候进入这一级 |
| --- | --- | --- |
| L1 | 换路径：注入引导，要求换工具或换参数 | 滑窗内出现重复签名 |
| L2 | 重规划：从微调参数升级为重新分解任务 | 引导后连续若干步仍无进展 |
| L3 | 换更强的模型，或换一套提示策略 | 重规划后依然卡在同一处 |
| L4 | 缩小任务范围，拆出一个可完成的子任务先交付 | 任务规模超出当前能力，硬啃不下来 |
| L5 | 子 Agent 隔离：把卡住的任务交给上下文干净的子 Agent 重试 | 怀疑主上下文已被污染，越试越乱 |
| L6 | 熔断并转人工 | 前面各级都无效，或预算即将耗尽 |

L5 的价值在于隔离污染：主上下文里已经塞满失败尝试，模型会围着错误前提打转，换一个干净的上下文重试，往往比继续在原上下文里重试更有效。

## 根因排查：先修工具与目标，再谈恢复

死循环的根因大多不在模型，而在工具契约和目标定义。事后恢复只能止损，改根因才能让同类循环不再出现。

| 根因 | 模型的处境 | 改法 |
| --- | --- | --- |
| **工具报错但错误信息不可诊断** | 不知道该改什么，只能原样重试 | 返回可诊断的错误：哪个参数错、期望什么格式 |
| **工具返回空结果** | 分不清是「没有」还是「调用错了」 | 工具明确区分「查无结果」和「执行失败」 |
| **目标本身不清晰** | 不知道什么算完成，于是一直做下去 | 补齐验收契约，给出可判定的完成条件 |
| **能力不足** | 任务超出模型或工具的能力范围，怎么试都不成 | 提前拆小，换成能力范围内的一串子任务 |

前两类最容易被忽略：它们看起来像模型在乱试，实际是工具把信息吞掉了，模型只能盲猜。

## 结构性预防

恢复是止损，预防才是降低发生率的手段，而且下面这些手段落地成本都很低：

- **每类动作设调用次数上限**，而不是只给整个任务一个总预算，防止某一类动作独吞额度。
- **工具失败自动降级**：同一工具失败 N 次就换路径，而不是继续重试。
- **给子任务设独立预算**，防止一个子任务吃掉全部额度，让后面的子任务还没开始就被熔断。
- **默认不设「无限重试」**，任何重试都要有次数上限和退避。
- 把终止条件和降级阈值写进配置，和代码一起评审，别散落在提示词里靠自觉。

## 可观测性：死循环的根因大多看得见

死循环几乎不会毫无征兆地发生，它一定会在指标上留下痕迹。至少要记录四个指标：

- **重复动作率**：有多少步是同一签名的重复，反映循环的严重程度。
- **无进展步数占比**：有多少步没有推动状态变化，这是最直接的健康度指标。
- **同工具连续失败次数**：定位是哪一个工具在制造等待循环。
- **每任务步数分布**：长尾里有多少任务步数异常偏高，用来发现还没被投诉的慢循环。

**死循环的根因 90% 能在这些指标里看出来**；没有这些指标，就只能靠用户投诉发现，而投诉到来时，钱往往已经花过一轮了。

## 常见追问

**Q：只把「模型说完成了」当终止条件，行不行？**

不行。模型经常在没做完时就宣称完成，完成判定要尽量用程序化验收，模型自述只能当辅助信号。

**Q：检测到重复就直接终止不好吗？**

直接终止会把还能救的任务变成失败。更划算的顺序是先注入「已尝试过 A、B、C」逼它换路径，不行再重规划，终止是 L6 才用的手段。

**Q：换成更强的模型是不是就没有死循环了？**

不是。换模型只是 L3 的一级降级手段，能提高单步成功率，但不改变「没有终止条件、没有进展检测」的结构性缺陷，预算和检测该有还得有。

**Q：怎么区分「任务本来就长」和「已经卡住」？**

看状态有没有增量，而不是看步数。步数多但每步都在推进，是长任务；连续 N 步状态零变化，就是停滞。

## 易错点

- **错的直觉：卡住了就重试。** 同一个必然失败的调用重试一百次，只是把等待循环拖长。正确做法是先看错误码，同一工具连续失败就换路径。
- **错的直觉：设了最大步数就万事大吉。** 只看步数会误杀正常长任务，也会等到撞墙才发现预算已耗尽。正确做法是预算加无进展检测双保险，并在 80% 处提前预警。
- **错的直觉：Agent 转不出来是模型笨。** 更常见的是工具错误信息不可诊断、空结果不区分、目标没有验收契约，模型缺的是信息不是智力。
- **错的直觉：循环是提示词问题，改改措辞就好。** 提示词改善能降低概率，但确定性兜底必须落在代码里：签名检测、预算上限、分级恢复都要有。

## 一句话记住

:::tip[一句话记住]
死循环不靠模型变聪明，靠检测、打断、分级恢复、硬预算这套确定性机制。
:::
