主流 LLM Agent 框架可以按**抽象层次**分为三类：面向最终用户的通用 Agent 产品、面向开发者的 Agent 框架、以及面向单个环节的工具库。选型时先确定自己在哪一层。

## 通用 Agent 产品

（面向终端用户，不直接写代码）。**Manus** 是代表性产品，强在**通用任务执行**：沙箱环境、浏览器与文件操作、多步骤规划、异步交付结果。**Claude Code** 强在**代码与终端场景**，人机协作紧密（权限确认、diff 审阅）。**OpenAI 的 Operator / Codex** 强在**与自家模型深度协同**。这类产品的共同特点是**把底层复杂性（沙箱、权限、上下文）都藏起来了**。

## 通用 Agent 开发框架

（写代码构建自己的 Agent）。**LangGraph**（LangChain 团队）——**图式编排**，把 Agent 建模为状态图，节点与边显式定义，**支持循环、人在环、持久化与断点恢复**，是当前企业落地最主流的选择。**AutoGen**（微软）——**多 Agent 对话驱动**，以"群聊"为抽象，擅长多角色协作与代码执行，v0.4 后架构重写。**CrewAI**——**角色分工式**，用"角色-目标-任务"的直觉抽象写多 Agent 分工，上手快。**Semantic Kernel**（微软）——**面向 .NET 与 Java 企业的 SDK 路线**，强调与既有企业系统集成与可测试性。**OpenAI Agents SDK**——**轻量、原生**，提供 handoff、guardrail、tracing，贴近 OpenAI 生态。**Google ADK**——**多语言（Python/Java/Go/TS）**，与 Gemini、A2A 深度整合，**支持 A2A 协议**，是企业级与协议化的代表。

## 工具库 / 编排中间件

（只做某一层，可嵌进自己的系统）。**LlamaIndex**——**数据与检索层最强**，文档解析、索引、检索、查询引擎，适合以 RAG 为核心的应用。**Haystack**——**生产化的检索与流水线**，强调可测试性与可组合性。**DSPy**——**不做编排，做优化**，用声明式模块与自动优化（prompt/权重）来提升模块效果，是"优化层"的代表。**Spring AI**（Spring 官方）——**企业 Java 生态整合**，把模型调用、向量库、工具、MCP 抽象成 Spring 风格的统一 API，**对 Java 团队是最低迁移成本的选择**。

## 协议层

（不是框架，是标准）。**MCP** 解决"如何接工具与数据"，**A2A** 解决"如何与别的 Agent 协作"。协议层的价值在于**跨框架互通** —— 用 MCP 写工具，用 A2A 做协作，上面跑哪个框架都行。

## 横切的生产化工具

。**LangSmith**（追踪与评估）、**Langfuse / Helicone**（开源可观测）、**Arize Phoenix**（开源评估与追踪）、**Traceloop**（OpenTelemetry 风格）、**dynamic-tp**（Java 动态线程池）、**Langfuse** 等。**这一层往往是决定"能不能上生产"的关键。**

## 选型的关键判据

。**① 语言与生态**（Java 团队 → Spring AI / ADK / Semantic Kernel；Python 团队 → LangGraph / CrewAI / AutoGen）。**② 编排复杂度**（流程固定 → 简单 SDK；复杂状态机与循环 → LangGraph；多角色协作 → AutoGen / CrewAI）。**③ 是否需要跨框架互操作**（需要 → 用 MCP / A2A 做协议层）。**④ 生产化要求**（可观测、评估、持久化、权限 —— 这四项是筛子的关键）。**⑤ 成本**（框架自身开销、是否强制绑定某家模型）。

## 一个务实的判断

。**不要为了用框架而用框架**。很多生产系统真正需要的只是"**模型调用 + 工具执行 + 状态持久化 + 预算守卫**"这四件事，自己写反而更可控。框架的价值在**编排复杂度和协作模式**真正变复杂之后才显现。**先用简单方案跑通，遇到瓶颈再引入框架。**

## 框架的通用通病

。**抽象泄漏**（框架的抽象与你的真实需求不匹配时，要绕框架写代码）；**版本迭代快、API 不稳定**（生产项目要锁版本）；**隐式成本**（框架默认的重试、多次调用、遥测上报会推高 token 消耗）；**调试困难**（抽象层数多，链路难追踪）。**这三点是选型时要问的。**
