主流 LLM Agent 框架可以按**抽象层次**分为三层：面向最终用户的**通用 Agent 产品**、面向开发者写代码构建 Agent 的**开发框架**、只做单个环节的**工具库**；此外还有两个不算框架但要单独提及的层——**协议层**（MCP / A2A）与**生产化工具层**（追踪、评估、可观测）。回答这道题的顺序应该是**先分层再点名字**，因为不同层的东西根本不能横向比较，选型错的第一步往往就是把产品拿去和框架比。

## 为什么必须先分层，而不是直接背框架名

同一个问题里其实混着两类东西：**你直接拿来用的产品**，和**你用来造产品的东西**。前者付费即用，你买到的是别人做好的沙箱、权限、上下文管理；后者是库和 SDK，你买到的是一套抽象，剩下的工程都要自己写。

分层之后每个名字才有确定的位置：

- **产品层**决定「我一个人能干多大的活」，评价标准是任务完成率、交付物质量、可干预程度。
- **框架层**决定「我的系统长成什么样」，评价标准是编排能力、状态管理、是否支持循环与人在环。
- **工具库层**决定「某个环节能不能做扎实」，评价标准是检索质量、可测试性、可组合性。
- **协议层与生产化层**决定「跨系统能不能互通、能不能上生产」，评价标准是互通性与可观测性。

所以「Manus 和 LangGraph 哪个好」是个伪问题：一个是成品，一个是建材。

## 第一层：面向最终用户的通用 Agent 产品

这一层不需要写代码，用户给目标和验收标准，产品自己拆解、执行、交付。

- **Manus**：强在**通用任务执行**——沙箱环境、浏览器与文件操作、多步骤规划、异步交付结果，最终给的是可用的成品而不是一段文字。
- **Claude Code**：强在**代码与终端场景**，人机协作非常紧密，权限确认与 diff 审阅是它的核心交互，每一处改动都在人的确认之下落地。
- **OpenAI 的 Operator / Codex**：强在**与自家模型深度协同**，模型能力更新能第一时间反映到产品行为上。

这类产品的共同特点是把底层复杂性全藏起来了：**沙箱、权限、上下文管理都不需要你操心**，代价是你能改的地方很少，深度定制只能通过提示词和有限的配置。

## 第二层：通用 Agent 开发框架（写代码构建自己的 Agent）

这一层是面试最容易被追问的地方，每个框架的抽象心智模型都不一样：

| 框架 | 背后团队 | 编排抽象 | 主要强在哪 |
| --- | --- | --- | --- |
| LangGraph | LangChain 团队 | 状态图，节点与边显式定义 | 支持循环、人在环、持久化与断点恢复，企业落地最主流 |
| AutoGen | 微软 | 多 Agent 对话驱动，群聊式 | 多角色协作与代码执行，v0.4 后架构重写 |
| CrewAI | CrewAI 团队 | 角色分工式 | 用「角色-目标-任务」的直觉抽象写多 Agent 分工，上手快 |
| Semantic Kernel | 微软 | SDK 路线，偏 .NET 与 Java | 与既有企业系统集成、强调可测试性 |
| OpenAI Agents SDK | OpenAI | 轻量、原生 | 提供 handoff、guardrail、tracing，贴近 OpenAI 生态 |
| Google ADK | Google | 多语言 SDK | 支持 Python/Java/Go/TS，与 Gemini、A2A 深度整合，是协议化的代表 |

这一层的核心差别在**把 Agent 抽象成什么**：图、群聊，还是岗位。**LangGraph 把 Agent 当状态机**，节点做什么、边怎么走都写明，循环和中断点就是图的一部分，所以复杂业务流程好控；**AutoGen 把 Agent 当群聊成员**，靠角色之间的消息往来推进，多角色协作自然，但整体路径不像图那样可预测；**CrewAI 把 Agent 当岗位**，先定义角色和目标，再派任务，思路最贴近人的组织方式。这三者的取舍本质是「可控性」和「表达成本」之间的取舍。

## 第三层：只做单个环节的工具库与中间件

这一层不负责整体编排，特点是能嵌进你自己的系统里，把某一环做到最好。

- **LlamaIndex**：**数据与检索层最强**，覆盖文档解析、索引、检索、查询引擎，适合以 RAG 为核心的应用。
- **Haystack**：**生产化的检索与流水线**，强调可测试性与可组合性，流水线里的每个组件都能单独换、单独测。
- **DSPy**：**不做编排，做优化**，用声明式模块配合自动优化（提示词乃至权重）来提升模块效果，是「优化层」的代表。
- **Spring AI**：Spring 官方出品，把模型调用、向量库、工具、MCP 抽象成 Spring 风格的统一 API，**对 Java 团队是迁移成本最低的选择**。

判断一段需求该不该用这一层，看的是「问题是不是集中在一个环节上」：如果难的是把文档切好、把检索召回率提上去，这就是 LlamaIndex / Haystack 的活；如果难的是多个步骤怎么串、断了怎么续，那是上一层的活。

## 协议层：MCP 与 A2A，不是框架而是标准

协议层最容易答错，因为它的名字经常和框架混在一起。**MCP 解决「如何接工具与数据」，A2A 解决「如何与别的 Agent 协作」**，两者都是标准而不是实现。

协议层的价值在于**跨框架互通**：工具按 MCP 写好，协作按 A2A 对接，上面跑 LangGraph 还是 ADK 都不影响。这也意味着它不替代框架——框架管编排，协议管接口。企业里真正的收益是避免被某一家框架锁死：换编排层的成本从「所有工具重写」降到「换一层壳」。

## 横切的生产化工具：决定能不能上生产

这一层不参与业务逻辑，但没有它系统就出不了测试环境。

- **LangSmith**：追踪与评估，链路的每一步都能回看。
- **Langfuse / Helicone**：开源可观测方案，管调用记录、成本与延迟。
- **Arize Phoenix**：开源评估与追踪，偏效果评测。
- **Traceloop**：OpenTelemetry 风格的链路埋点，方便接进既有监控体系。
- **dynamic-tp**：Java 动态线程池，用于 Agent 侧并发与资源治理。

**这一层往往是决定「能不能上生产」的关键**：能跑通 demo 和能上生产之间差的不是模型，是出错时你看不看得到、花了多少钱你算不算得清。

## 选型五条判据

| 判据 | 怎么问自己 | 结论倾向 |
| --- | --- | --- |
| 语言与生态 | 团队主力语言是什么 | Java 团队看 Spring AI / ADK / Semantic Kernel；Python 团队看 LangGraph / CrewAI / AutoGen |
| 编排复杂度 | 流程是固定几步，还是带循环和分支的状态机 | 流程固定用简单 SDK；复杂状态机用 LangGraph；多角色协作看 AutoGen / CrewAI |
| 跨框架互操作 | 会不会换编排层、要不要和别人的 Agent 对接 | 需要就用 MCP / A2A 做协议层 |
| 生产化要求 | 可观测、评估、持久化、权限这四项是否齐 | 这四项是筛子的关键，缺一项就可能上不了线 |
| 成本 | 框架自身开销多大、是否强制绑定某家模型 | 绑模型的框架谈判空间小，换模型的迁移成本高 |

## 一个务实的判断：不要为了用框架而用框架

很多生产系统真正需要的只是四件事：**模型调用 + 工具执行 + 状态持久化 + 预算守卫**。这四件事自己写一份不大的代码反而更可控——没有多余的抽象层，出问题能直接定位。

**框架的价值在编排复杂度和协作模式真正变复杂之后才显现**：步骤多到需要断点恢复、角色多到需要隔离上下文、流程需要人随时介入，这些才是框架替你省下来的成本。所以合理的路径是**先用简单方案跑通，遇到瓶颈再引入框架**，而不是一开始就选一个最全的。

## 框架的通用通病

- **抽象泄漏**：框架的抽象与真实需求不匹配时，你得绕开框架写代码，最后变成「框架用了一半、自己的实现一半」，两边都难维护。
- **版本迭代快、API 不稳定**：这一层还在快速演进，生产项目必须锁版本，别指望小版本平滑升级。
- **隐式成本**：框架默认的重试、多次调用、遥测上报都会推高 token 消耗，账单上看见的是结果，看不见的是这些默认行为。
- **调试困难**：抽象层数一多，一次失败要在好几层日志里对时间线，链路追踪不做好基本没法排查。

这四点在技术选型时要逐条确认，确认不了就等于把风险敞口留到了上线之后。

## 常见追问

**问：Manus 这类产品和 LangGraph 这类框架，实际项目里怎么选？**
答：先看你要的是「用」还是「造」。要交付具体任务的成果，用产品；要做一个能嵌进业务系统、自己控制流程和数据的 Agent，用框架。两者也可以叠加，产品负责探索，框架负责落地。

**问：AutoGen 和 CrewAI 都是多 Agent，区别在哪？**
答：AutoGen 的抽象是**群聊对话**，Agent 之间靠消息往来推进，灵活但路径不如图清晰；CrewAI 的抽象是**角色-目标-任务**，先把岗位定好再派活，结构清楚、上手快，代价是流程设计的自由度低一些。

**问：MCP 已经是标准了，是不是就不需要 Agent 框架了？**
答：不是同一个维度。MCP 只规定「怎么接工具和数据」，不规定多步任务怎么规划、状态怎么持久化、人怎么介入，这些仍然是框架的职责。协议让框架之间能互通，但不替代编排。

**问：Java 团队做 Agent，你会怎么选？**
答：优先 Spring AI，因为它把模型调用、向量库、工具、MCP 统一成 Spring 风格 API，团队既有工程习惯和测试体系能直接复用，迁移成本最低；需要多语言和协议化协作再看 Google ADK；如果已有大量 .NET 或既有企业系统要集成，Semantic Kernel 更顺。

## 易错点

- 把产品和框架放在一起比：Manus 是成品，LangGraph 是建材，评价标准都不一样，比出来的结论没有意义。
- 以为功能列表越长越好：框架多出来的每项能力都是一层抽象，用不上就是纯负担，绕开它写代码的成本往往比自研更高。
- 把 MCP 当成一个框架：它是工具与数据的接口标准，本身不做编排，装上一个 MCP 服务不等于有了 Agent。
- 忽略隐式成本与版本风险：默认重试、多次调用、遥测上报都会推高 token，加上 API 不稳定，生产项目必须锁版本并单独核算调用成本。
- 把可观测当上线后再补：追踪与评估这一层决定能不能上生产，等出了问题再补，前面的调用记录已经没了。

## 一句话记住

先分层再选型：产品是用、框架是造、协议是通、工具是补。
:::
