上下文窗口是模型在单次推理中能“看到”的 token 总量上限，系统提示、工具定义、历史消息、检索到的资料、工具执行结果，以及给当前输出预留的额度，全都挤在这一个上限里。Agent 工程里几乎所有难题，最终都能追溯到**这个窗口是有限且昂贵的**这一事实：它既是容量约束，也是成本约束。

## 它到底是什么

上下文窗口衡量的不是“模型记住了多少”，而是“这一次请求一共能塞进多少 token”，输入和输出共用同一个额度。装进去的东西大致有六类：系统提示（身份、规则、格式要求）、工具定义（名称、描述、参数 schema）、多轮历史消息、检索到的资料片段、工具执行结果，以及为模型当前这一步输出预留的空间。因为按 token 计量，中文、英文、代码、JSON 的折算比例不同，一份看起来很短的原始 HTML 或日志，实际占用可能远超预期。所以更准确的理解是：**窗口是这个请求的输入加输出总额度，不是模型的长期内存**。

## 为什么它同时是容量约束和成本约束

两个方向同时收紧，而且互相放大。容量方向上，窗口一满就必须丢弃或压缩历史，而丢弃天然意味着丢信息——被丢掉的可能正是几十步之前定下的约束。成本方向上，每个 token 都要付费，且每一轮推理都要把全部历史**重新发一遍**，同一段历史会被反复计费，于是成本随步数呈超线性增长。两点合起来，**上下文管理是 Agent 系统最主要的成本项和性能瓶颈**，它不是后期优化项，而是从第一版就要参与设计的东西。

## 为什么“记忆”必须外置

Agent 往往需要记住几十步之前的事实、用户的偏好、已经做过的历史决策，这些内容放不进窗口，硬塞只会加速触顶并抬高每轮成本。解决办法是把状态外置到外部存储：文件系统、向量库、KV 存储、任务树，都可以承担这个角色。上下文里只保留**当前决策必需的最小信息加引用**——比如文件路径、记录 ID、任务节点编号，而不是内容本身。这样窗口占用与任务总历史就解耦了：任务跑得再长，窗口里也只是一串指针。

## 为什么长程任务会退化

步数增加之后，窗口里堆满冗长的 observation、失败的尝试和格式啰嗦的工具返回，噪声占比上升、关键目标被稀释，注意力被拉散。更麻烦的是窗口触顶后的处理：早期关键信息要么被直接截断，要么被粗暴摘要掉，于是出现**目标漂移**（越走越偏离原始需求）和**错误级联**（早期一次错误判断被后面所有步骤继承）。这说明“上下文变长后能力变差”是结构性问题，不是模型不够聪明；换更强的模型只能抬高天花板，改不了这个结构。

## 上下文压缩的四种策略

四种策略各有代价，没有哪一种能单独撑住生产环境：

| 策略 | 做法 | 代价 |
| --- | --- | --- |
| 截断 | 保留最近 N 轮，更早的直接丢 | 最简单，但会丢早期定下的约束 |
| 摘要 | 用模型把历史压成一段摘要 | 压缩率高，但细节与精确数值会失真 |
| 外置 | 结果存到外部，上下文只留引用 | 最稳，但增加了检索依赖 |
| 结构化保留 | 只保留实体、数值、决策点、未决事项等结构化片段 | 关键事实保得住，但需要额外的抽取与维护逻辑 |

生产中通常**分层组合**使用：硬约束用结构化保留并在每轮重申，过程性叙述交给摘要，长结果外置只留指针，最近的上下文靠截断兜底。

## 位置效应：信息放在窗口哪里也有代价

长上下文的中间部分更容易被忽略，也就是常说的 lost in the middle。因此**重要内容应放在提示的靠前或靠后位置**，而不是埋在中间：系统约束和硬规则放最前，当前这一轮的目标在结尾再重述一次，大段原始资料夹在中间。这条约束与窗口大小无关，窗口再大它依然成立，所以它属于提示结构的纪律，而不是换个更大窗口就能解决的事。

## 它倒逼工具返回结果的设计

工具返回一大段 HTML 原文会瞬间吃满窗口，还顺手把关键信息淹掉。因此工具层应当**主动裁剪与摘要**：只返回与当前问题相关的片段、只返回前 N 条并注明总条数、或者只返回结构化字段而不是原始响应体。这里有一条容易被低估的判断：**工具结果的裁剪策略往往比换模型更能提升 Agent 表现**，因为噪声是工程侧注入的，模型再强也只能在噪声里找信号。

## 它和上下文工程（Context Engineering）的关系

Prompt Engineering 关注单次提示该怎么写；Context Engineering 关注的是**每一轮该往窗口里放什么**——检索什么、压缩什么、隔离什么、丢弃什么。窗口有限，取舍就是必然的，于是“每轮放什么”从写作技巧升级成了系统能力。这正是“上下文窗口是最核心约束”的深层含义：约束发生在窗口，功夫花在取舍。

## 关键要点

- 窗口就是一次推理的输入加输出总额度，系统提示、工具定义、历史、检索资料、工具结果、输出预留共用它。
- 容量与成本同时约束：满了要丢历史，且每轮重发全部历史，成本随步数超线性增长。
- 状态必须外置（文件系统、向量库、KV、任务树），窗口里只留最小信息加引用。
- 长上下文退化来自噪声堆积与早期信息被截断，表现为目标漂移和错误级联。
- 压缩只有四类手段——截断、摘要、外置、结构化保留，生产里分层组合使用。
- 工具返回要主动裁剪摘要，这条常常比换模型更有效。

## 常见追问

**问：窗口越大是不是就越好？**

答：不是。更大的窗口只降低触顶概率，成本、延迟和中间信息被忽略的问题都还在，噪声也更容易堆进来。真正决定效果的是“每轮放什么”的管理能力。

**问：为什么不把全部历史直接塞进去，让模型自己挑？**

答：因为每轮都要重发全部历史，token 成本随步数超线性增长，延迟同步上涨；而长窗口中间的信息本身容易被忽略。全塞等于把成本交给账单、把准确性交给运气。

**问：压缩历史会不会把关键约束压掉？**

答：会，所以要分层。硬约束（业务规则、输出格式、验收条件）结构化保留并每轮重申，只有过程性历史才允许摘要或截断。低估这一点，压缩就会变成越压越跑偏。

**问：那上下文窗口和上下文工程是一回事吗？**

答：不是。窗口是模型的物理上限，是约束本身；上下文工程是在这个约束下的取舍方法，包括检索、压缩、外置、隔离、丢弃这几类动作。

## 易错点

- **以为窗口满了模型会自动忘记最旧的内容。** 窗口没有任何自动淘汰机制，不主动截断或摘要，就是超限报错或被动截断，关键约束可能在毫无提示的情况下消失。
- **以为上下文工程就是写好系统提示词。** 系统提示只是窗口里的一小块，真正的取舍发生在检索、压缩、外置、隔离这几处，只调提示词改不了窗口占用。
- **以为提升 Agent 表现优先换更大的模型。** 噪声是工程侧注入的，换模型不会消除噪声，而工具返回的裁剪策略往往比换模型更有效。
- **以为压缩等于总结成一段话。** 一段话摘要会丢掉精确数值和硬约束，结构化保留（实体、数值、决策点、未决事项）才是关键信息的正确存法。
