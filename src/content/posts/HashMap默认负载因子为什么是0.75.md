0.75 是**空间利用率与冲突代价之间的折中点**：它让哈希表在大部分时间里冲突很少，同时又不会为大量空桶浪费内存。在理想哈希下，负载因子为 α 时一个桶里的元素数近似服从泊松分布，0.75 恰好落在「桶大多只有 0 到 1 个元素、长链尾部刚开始变重」的位置，所以 JDK 把它取作 `HashMap` 的默认值。

## 负载因子到底是一个什么比例

`loadFactor = size / capacity`，表示**桶数组被填充的平均比例**。`size` 是键值对数量，`capacity` 是桶数组长度，两者相除就是「平均每个桶装了几个元素」。扩容的判定门槛是：

- 阈值 `threshold = capacity × loadFactor`
- `size` 超过这个阈值时，容量翻倍并重新散列，这一趟搬移是 O(n)
- 默认容量 16、负载因子 0.75，所以第一次 `put` 初始化之后阈值是 12

关键在于：**负载因子本身不是「冲突概率」，而是「什么时候扩容以控制冲突」的阈值**。它越低，扩容越早，冲突越少，代价是内存和搬移次数。

```java
// 无参构造：默认容量 16、默认负载因子 0.75，表在第一次 put 时才真正分配
Map<String, Integer> map = new HashMap<>();        // 首次 put 后容量 16、阈值 12
// 也可以自己给初始容量：容量会被向上取整到 2 的幂，阈值 = 容量 × 0.75
Map<String, Integer> big = new HashMap<>(2048);    // 阈值 1536，装 1000 个元素不会扩容
```

## 0.75 的直观含义：容量用到 3/4 就翻倍

0.75 意味着**平均每个桶只装 0.75 个元素**，而且刚扩容完的那一瞬间，`size` 只占新容量的 3/8（37.5%），**大多数桶还是空的**。

这正是它降低冲突的机制：扩容把元素摊薄到两倍的桶里，冲突概率随之明显下降。

以初始 16 为例走一遍：

| 阶段 | 容量 | 阈值 | 当前 size | 实际占用率 |
| --- | --- | --- | --- | --- |
| 首次 put 后 | 16 | 12 | 0 | 0% |
| 填到阈值 | 16 | 12 | 12 | 75% |
| 扩容后 | 32 | 24 | 12 | 37.5% |

所以每次扩容都是「从 75% 掉回 37.5%」，系统由此得到一个喘息期，不会马上又撞阈值。

## 为什么不用 0.5

冲突确实会更少，但两头的成本都翻倍：

- **空间浪费大**：一半的桶常年是空的，桶数组还要占双份内存
- **扩容更频繁**：阈值只有容量的一半，装同样多的元素要经历更多次扩容
- **每次扩容都是 O(n) 的搬移**，还要重新分配一整块数组

换句话说，用一倍的数组内存换来的冲突改善很有限，**得不偿失**。

## 为什么不用 1.0 或 0.9

1.0 看似把空间用满、最不浪费，实际是**灾难性的**：满载意味着**大量桶同时挂着多个元素**，链表长度暴涨，查找从 O(1) 退化成接近 O(n)，红黑树从「罕见兜底」变成「常见形态」。

这里有个容易搞反的方向：**负载因子越高，扩容反而越少**（阈值 = 容量 × 负载因子，能塞的元素更多），所以 1.0 的代价不是「扩容更频繁」，而是**全程贴着极限跑**——扩容前那一段，几乎所有操作都落在高冲突区，平均延迟和 P99 尾延迟一起被拉长。

0.9、0.99 是同一问题的缓和版：空间是省了，但冲突尾巴依然很重，且高占用下扩容那一次要迁移的元素接近整个容量，这一趟的停顿也更明显。0.75 让扩容时机落在「3/4 满」，**既压住了冲突，又不把迁移量顶到极限**。

## 泊松分布给出的理论依据

在**理想哈希**（哈希函数完全均匀、元素独立）下，把 `m` 个元素放进 `n` 个桶，每个桶的元素数服从二项分布，`m`、`n` 都较大时可用**泊松分布**近似，均值就是负载因子 α。于是：

- 某个桶为空概率 `e^(-α)`
- 某个桶至少有一个元素的概率 `1 - e^(-α)`

| 负载因子 α | 空桶概率 `e^(-α)` | 桶内元素期望 | 非空桶占比 |
| --- | --- | --- | --- |
| 0.50 | 60.7% | 0.50 | 39.3% |
| **0.75** | **47.2%** | **0.75** | **52.8%** |
| 1.00 | 36.8% | 1.00 | 63.2% |

**0.75 附近正是「冲突开始明显增多」的拐点**：负载再往上，桶内元素数的尾部迅速变重，一个桶挂 3 到 4 个元素的概率显著上升；而 0.75 时绝大多数桶只有 0 个或 1 个元素。JDK 8 的 `HashMap` 源码注释里就是用这套泊松论证来说明「长链有多罕见」的，这也正是 0.75 成为通用默认值的理论依据。

## 和树化阈值 8 是配套设计的

JDK 8 让链表长度达到 8 时转成红黑树，但这个转换还有一个前置条件：**桶数组长度 ≥ 64**（`MIN_TREEIFY_CAPACITY`），不够 64 就先扩容而不是树化。

8 之所以敢取 8，是因为在 0.75 的负载下「某个桶自然堆到 8 个节点」的概率小到可以忽略，树化只是极端情况的兜底，不是常态。反过来，**如果负载因子被调到接近 1，8 就不再罕见**，树化会频繁发生——而 `TreeNode` 比普通 `Node` 更占内存（大约两倍），维护逻辑也更复杂。负载因子和树化阈值是一起定的，不能只看其中一个。

## 扩容时元素只有两种落点

容量始终是 2 的幂，索引靠 `(n - 1) & hash` 算出来，所以扩容成两倍之后，原来在索引 `i` 的节点**只可能去两个位置**：`i` 或 `i + oldCap`。JDK 8 正是利用这一点，把一条链拆成 lo、hi 两条低开销的链：

```java
// JDK 8 HashMap.resize() 的核心逻辑（简化示意）
if ((e.hash & oldCap) == 0) {
    // 高位是 0：留在原索引 i
    loTail.next = e;
    loTail = e;
} else {
    // 高位是 1：挪到 i + oldCap
    hiTail.next = e;
    hiTail = e;
}
```

所以扩容**不需要重新计算哈希**，只判断一个 bit，单次搬移的常数很小。但扩容次数与负载因子成反比——负载因子调得越低，扩容越勤，这部分总成本就越大。

## 实践中要不要调

**默认 0.75 对绝大多数场景是合适的**，不要一上来就改。只在两类场景考虑调整：

- **读多写少、且极度在意内存**（超大规模缓存、内存敏感型服务）：可以调低，比如 0.66，同时把初始容量设得更大，避免调低因子导致扩容次数上升
- **写多、追求吞吐**：可以略微调高，比如 0.85，但要接受冲突增加带来的查找变慢

**调高负载因子前必须用压测验证**，因为它会直接影响 P99 延迟。另外 `new HashMap<>(initialCapacity, loadFactor)` 只校验负载因子必须大于 0 且不是 NaN，**并不会限制它不超过 1**——能设，但设了没有意义。

## 常见追问

**Q：负载因子能设成大于 1 吗？**
A：构造器允许，但超过 1 意味着元素数可以多于桶数，平均每个桶要挂一个以上节点，查找必然退化，实际不会这么用。

**Q：把负载因子调低到 0.5 是不是一定更快？**
A：单次查找更快，整体未必。内存多占一倍、扩容次数变多、GC 压力更大，是否值得取决于场景和压测结果。

**Q：为什么初始容量是 16？**
A：16 是 2 的幂，`(n - 1) & hash` 才能等价于取模，扩容时也只需看哈希的一个 bit 就能决定元素的新位置。

**Q：树化阈值 8 和负载因子有关系吗？**
A：有。8 是在 0.75 下几乎不会自然出现的链长，所以树化只是兜底；负载因子逼近 1 时它会变成常态。

## 易错点

- **把负载因子当成「冲突概率」本身。** 它是扩容阈值的比例（`size / capacity`），真正决定冲突的是哈希分布和实际占用率。
- **以为负载因子越高扩容越频繁。** 方向反了：阈值 = 容量 × 负载因子，因子越高，两次扩容之间能塞的元素越多，扩容次数反而更少；代价是冲突和查找退化。
- **以为扩容后表马上又满了。** 容量翻倍，占用率必然掉到原来的一半左右（0.75 × 0.5 = 0.375，即 37.5%），不存在「刚扩容完又立刻扩容」的循环。
- **以为链表长度到 8 就一定转红黑树。** 还有前置条件：桶数组长度 ≥ 64，否则优先扩容。

## 一句话记住

:::tip
**容量用到四分之三就扩容：冲突压得住，也只闲置四分之一的容量。**
:::
