动态 API 调用指 Agent 在运行时**根据任务需要发现、选择并调用 API**，而不是把要调用的接口在代码里写死，它是 Agent 从"演示"走向"能干活"的关键能力。工程上它靠四件事撑住：**工具怎么被 Agent 看见**（静态注册、动态发现或现场生成）、**调用怎么被校验授权**、**结果怎么规范化回填**、**错误怎么回传给模型让它自我纠正**。

## 获取 API 的三条路径：静态、动态发现、动态生成

三条路径不是互相排斥的选择题，而是按工具集稳定性分层组合的三种来源：

| 路径 | 工具描述从哪来 | 适合的场景 | 主要代价 |
| --- | --- | --- | --- |
| **静态注册** | 启动时把常用接口以工具形式注册进目录，描述与参数 schema 固定 | 工具集稳定、需要最可控的行为 | 工具变多后目录臃肿，模型选择变难 |
| **动态发现** | 运行时通过 OpenAPI/Swagger 规范、API 目录或 MCP 的 `tools/list` 拉取 | 工具集持续演进、外部接口面积大 | 拉取慢且耗 token，描述可能与实现漂移 |
| **动态生成** | 模型根据文档或示例**现场构造**调用 | 长尾接口、一次性调用 | **风险最高**，必须靠校验拦截 |

实践中更常见的是分层组合："静态注册打底 + 动态发现补充"，高频接口写死成固定工具，长尾接口按需拉取，动态生成只在一个被强校验包围的沙箱里开放。

## 工具目录本身就是瓶颈

工具一多，模型的**选择准确率会下降**：注意力被稀释，上下文被工具描述撑大，多个描述之间还会互相干扰，最后模型选了个"差不多但不该用"的工具。所以真正要设计的不是"怎么发 HTTP 请求"，而是**怎么把正确的少数工具摆在模型面前**：

- **工具检索**：先用 embedding 把候选集缩小到少数几个，再让模型在小候选里选。
- **按场景动态裁剪**：只暴露当前任务相关的工具，换场景就换目录。
- **描述去重与职责分离**：避免两个工具功能模糊，让模型分不清该用哪个。

这三条是同一件事的三个方向——**缩小候选、对齐场景、说清边界**。

## 从 tool_call 到回填的完整链路

一次动态调用的标准链路如下，任何一环缺失都会变成线上事故：

```text
模型读工具描述 → 输出 tool_call(name, arguments)
  → 参数校验：JSON Schema 结构 + 语义 + 跨参数一致性
  → 权限裁决：能力令牌决定这次调用允不允许
  → 执行：真实 HTTP 调用，带超时与重试
  → 结果规范化与裁剪
  → 回填给模型，进入下一轮
```

两个容易被忽略的点：**参数校验不只校验结构**，还要校验语义（日期是否合法、金额是否为正）和跨参数一致性（起止时间是否颠倒、分页参数是否自相矛盾）；**结果必须先裁剪再回填**，原始响应里的冗余字段既浪费 token，也会干扰模型的下一步判断。

## 五道必须有的防护

动态调用把"调什么"交给了模型，防护就必须落在执行层，而不是指望模型自觉：

| 威胁 | 对应措施 |
| --- | --- |
| 路径穿越、SSRF | **参数白名单 + 路径规范化** |
| 提示注入把请求引到内网 | **URL 域名白名单** |
| 模型冒用他人身份 | **参数级鉴权**：不能用模型传来的 user_id 作为身份 |
| 重试造成重复写入 | **幂等键** |
| 大结果撑爆上下文 | **响应大小上限** |

其中最容易出错的是第三条：身份只能来自会话与令牌，凡是"出现在参数里的身份"一律视为不可信输入。

## 错误处理：把可诊断信息回传给模型

API 返回 4xx/5xx 时，正确做法是把**可诊断的错误**回传给模型（例如"字段 x 缺失，需用 y"），让它自我纠正；而不是抛异常直接终止循环——一次参数写错就整轮失败，是 Agent 最常见的体验崩塌点。

同时要区分错误类型：对 429 限流、5xx 等**可重试错误**重试，并配合**指数退避与熔断**；对参数错误这类不可重试错误，重试多少次结果都一样，只会把限流放大。

## OpenAPI 规范是工具定义的唯一事实来源

让 API 描述成为**唯一事实来源**：工具 schema、SDK、契约校验与 Mock 都从规范生成，不再各处手写一遍。

关键在方向：**把"从代码生成文档"升级为"从规范生成代码"**，才能保证 Agent 看到的工具定义与真实实现不漂移——而工具定义与实现漂移，正是工具调用失败最常见的根因。

## 动态发现的代价：缓存与版本失效

每次调用都全量拉取工具列表不可行：**慢，而且耗 token**，工具一多直接把上下文吃掉。可行做法是**本地缓存 + 版本失效**，只拉变更部分。

另一个隐性成本是**变更的平滑过渡**：工具描述一改，运行中的 Agent 行为可能突然变化。所以描述变更要有灰度与版本化，让在途会话按旧版本跑完，新会话再切到新版本。

## MCP 把工具发现与描述标准化

MCP 提供的正是**标准化"工具怎么被发现和描述"**的机制：`tools/list` 做动态发现，加上统一的 schema 约定，把"每家接口一套接法"收敛成一套协议。**用 MCP 承接动态 API 调用，是当前生态的主流做法。**

## 本质区别：谁来决定调哪个接口

静态调用里，**"调什么"是开发者决定的**；动态调用里，**"调什么"是模型决定的**。这一句差别决定了整个安全模型的位置——**安全边界的落点必须从开发者转移到执行层**，这就是为什么所有动态调用都必须过工具网关，而不是让模型拿着凭据直连。

## 常见追问

**Q：动态生成（让模型现场构造请求）能上生产吗？**
能，但必须把"生成"和"执行"拆开：生成只是候选，执行前要过 schema 校验、域名白名单与权限裁决，任何一步不过就退回并告知模型原因。

**Q：工具很多时怎么保证选对？**
先检索再选择：用 embedding 把候选缩到少数几个，再让模型在小候选里挑；同时把职责重叠的工具拆开，别让两个工具都能完成同一件事。

**Q：接口报错该抛出还是回传？**
回传可诊断信息让模型改参数重试；只有不可重试的错误、或触碰权限边界时才终止整轮。

**Q：MCP 和 OpenAPI 是替代关系吗？**
不是，互补。OpenAPI 描述 HTTP 契约，MCP 解决"工具怎么被发现、怎么描述、怎么调"的通道问题，实践中常把 OpenAPI 转成 MCP 的工具描述。

## 易错点

- 把"动态"理解成"让模型自己拼 URL 发请求"。动态指的是**选择和参数由模型定**，执行必须经过网关，不能绕开校验与鉴权。
- 用模型传来的 `user_id`、`tenant_id` 当身份做鉴权。这些参数本身就是模型输出，等同于用户输入，永远不可信。
- 把 4xx 和 5xx 一起重试。参数错误重试多少次都一样，只会放大限流；可重试的只有限流和临时故障。
- 每次请求都全量拉 `tools/list`。慢且耗 token，工具一多直接撑爆上下文，必须本地缓存加版本失效。

## 一句话记住

:::tip[一句话记住]
动态调用把"调什么"交给模型，所以校验、鉴权和网关必须留在执行层。
:::
