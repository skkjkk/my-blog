动态 API 调用指 Agent 在运行时**根据任务需要发现、选择并调用 API**，而不是把要调用的接口在代码里写死。它是 Agent 从"演示"走向"能干活"的关键能力。

## 三条获取 API 的路径

。**静态注册**（把常用接口在启动时以工具形式注册进目录，描述与参数 schema 固定）—— 最常见、最可控；**动态发现**（通过 OpenAPI/Swagger 规范、API 目录、或 MCP 的 `tools/list` 在运行时拉取）—— 适合工具集持续演进的场景；**动态生成**（由模型根据文档或示例**现场构造**调用）—— 灵活但**风险最高**，必须靠校验拦截。

## 工具目录管理是核心

。工具一多，模型选择准确率会下降（注意力被稀释）、上下文被撑大、描述互相干扰。做法：**工具检索**（先用 embedding 把候选集缩小到少数几个，再让模型在小候选里选）、**按场景动态裁剪**（只暴露当前任务相关的工具）、**描述去重与职责分离**（避免两个工具功能模糊）。

## 动态调用的完整链路

。模型基于工具描述输出 `tool_call` → **参数校验**（JSON Schema + 语义 + 跨参数一致性）→ **权限裁决**（能力令牌）→ **执行**（真实 HTTP 调用，带超时与重试）→ **结果规范化与裁剪** → **回填**给模型。

## 必须有的防护

。**参数白名单与路径规范化**（防路径穿越、SSRF）；**URL 域名白名单**（防注入把请求引到内网）；**参数级鉴权**（不能用模型传来的 user_id 作为身份）；**幂等键**（防重试造成重复写入）；**响应大小上限**（防大结果撑爆上下文）。

## 错误处理决定可靠性

。API 返回 4xx/5xx 时，应当把**可诊断的错误**回传给模型（如"字段 x 缺失，需用 y"），让它自我纠正；而不是抛出异常终止循环。对 429 限流、5xx 等**可重试错误**要区分对待，配合**指数退避与熔断**。

## OpenAPI 规范的工程价值

。让 API 描述成为**唯一事实来源**：自动生成工具 schema、自动生成 SDK、契约可校验、Mock 可自动化。**把"从代码生成文档"升级为"从规范生成代码"**，才能保证 Agent 看到的工具定义与真实实现不漂移 —— 这是工具调用失败最常见的根因。

## 动态发现的代价

。每次都全量拉取工具列表不可行（慢且耗 token），必须做**本地缓存 + 版本失效**；工具描述变更后需**可平滑过渡**，否则运行中的 Agent 行为会突变。

## MCP 在这里的位置

。MCP 提供的正是**标准化"工具怎么被发现和描述"**的机制 —— `tools/list` 动态发现 + 统一的 schema 约定。**用 MCP 承接动态 API 调用，是当前生态的主流做法。**

## 与静态调用的本质区别

。静态调用里，**"调什么"是开发者决定的**；动态调用里，**"调什么"是模型决定的**。因此**安全边界的落点必须从开发者转移到执行层** —— 这就是为什么所有动态调用都必须过工具网关。
