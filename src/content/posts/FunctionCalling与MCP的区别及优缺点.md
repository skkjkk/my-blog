两者是**不同层次**的东西：Function Calling 是**模型接口层**的机制，MCP 是**应用与工具之间**的协议层。它们的区别不是"竞争关系"，而是"上下层关系" —— MCP 内部完全可以基于 Function Calling 实现。

## Function Calling 是什么

。模型接口提供的一种能力：你在请求里声明可用函数及其 JSON Schema，模型在需要时**返回结构化的调用请求**（函数名 + 参数），由**你的应用代码**去真正执行，再把结果回传给模型。模型侧只负责"决定调什么、传什么参"。

## MCP 是什么

。一套**标准协议**，规定了 AI 应用如何以统一方式**发现、描述、调用**外部工具与数据资源。工具由独立的 MCP Server 暴露，应用通过 MCP Client 连接，支持**动态能力发现**与**跨应用复用**。

## 关键差别在四点

。**① 层次不同** —— 一个是模型接口机制，一个是集成协议。**② 工具定义位置不同** —— Function Calling 的工具定义**硬编码在请求里**（由你的代码组装），MCP 的工具**由 Server 动态提供**，客户端通过 `tools/list` 拉取。**③ 复用范围不同** —— Function Calling 的工具**与这个应用绑定**；MCP Server **写一次可被多个 Host 复用**，这正是它解决"集成碎片化"的价值。**④ 能力边界不同** —— Function Calling 只管"模型怎么表达调用意图"，MCP 还管**传输、会话、能力协商、反向调用（Sampling/Roots）**。

## Function Calling 的优点

。实现**最轻**（无额外进程与协议栈）、延迟最低、没有额外故障点、与模型原生集成度高、调试直观（就是一次普通的接口调用）。

## Function Calling 的缺点

。工具定义**要手工维护并随请求重复发送**（占用上下文，工具一多就严重稀释注意力）；**无法复用**——每个应用、每个模型、每个 SDK 都要重写一套；**缺少协议级能力**（无动态发现、无反向通道、无标准错误语义）；**安全能力要自己实现**（参数校验、权限、超时、限流全在应用侧）。

## MCP 的优点

。**生态复用**（Server 写一次到处用）；**动态发现**（工具变更不影响客户端）；**协议标准化**（跨语言、跨厂商、跨框架互通）；**职责分离清晰**（Server 负责对接真实系统与数据清洗，Client 负责协议，Host 负责编排）；**天然的安全边界**（每个 Server 独立进程、独立会话，便于最小权限与故障隔离）；**支持反向能力**（Server 可复用宿主的 LLM 能力）。

## MCP 的缺点

。**引入了进程与网络开销**（stdio 尚可，远程 HTTP 有延迟）；**多一层抽象带来调试复杂度**（问题可能在 Client、Server、网络或模型任一层）；**Server 质量参差**（第三方 Server 可能数据不可信、有漏洞、行为不可预测）；**仍然不解决权限与注入问题** —— 它标准化了"怎么接工具"，安全还得宿主自己做；**对简单场景是过度设计** —— 只有一两个固定工具时，直接 Function Calling 更划算。

## 实践选型

。**单应用、工具少且固定、追求极简与最低延迟 → 用 Function Calling**；**多应用复用同一批工具、工具会持续演进、需要跨团队共享、需要标准化生态 → 用 MCP**。生产中常见**混合形态**：对外用 MCP 接入生态工具，内部对模型仍然表现为标准 Function Calling，由 MCP Client 承担转换。
