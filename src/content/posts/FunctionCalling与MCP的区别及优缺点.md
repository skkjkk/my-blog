两者是**不同层次**的东西，不是竞争关系，而是上下层关系：**Function Calling 是模型接口层的机制**，负责让模型输出结构化的调用意图；**MCP 是应用与工具之间的协议层**，负责工具怎么被发现、描述、调用和返回。MCP 内部完全可以基于 Function Calling 实现，所以真正要答的是"这两层各自解决了什么问题、代价是什么"。

## 层次差异：接口机制与集成协议

Function Calling 属于**模型接口能力**：你在请求里声明可用函数及其 JSON Schema，模型返回"要调哪个函数、传什么参数"，真正执行的是**你的应用代码**。MCP 属于**集成协议**：它规定 AI 应用如何以统一方式**发现、描述、调用**外部工具与数据资源，工具由独立的 MCP Server 暴露，应用通过 MCP Client 连接。

两者的分工可以这样记：前者回答"模型怎么表达调用意图"，后者回答"工具怎么被接进来、怎么在多个应用之间复用"。MCP 并没有绕开 Function Calling，它只是把"工具从哪来、怎么描述、怎么走网络"这一层标准化了，模型侧依然靠 Function Calling 决策。

## Function Calling 的一次完整调用链

链路是固定的四步：应用在请求里声明函数与 JSON Schema → 模型返回**结构化的调用请求**（函数名 + 参数）→ 应用**真正执行**这次调用 → 结果回传给模型，模型继续生成。模型侧只负责"决定调什么、传什么参"，它不执行任何动作，也不感知真实系统。

工具定义**硬编码在请求里**，由你的代码组装，所以它天然和这个应用、这个模型、这套 SDK 绑定。最小的一次工具声明长这样：

```json
{
  "name": "get_weather",
  "description": "查询指定城市的天气",
  "parameters": {
    "type": "object",
    "properties": { "city": { "type": "string" } },
    "required": ["city"]
  }
}
```

这段 JSON 每次请求都要跟着上下文一起发出去，工具越多，这部分固定开销越大。

## MCP 的一次完整调用链

MCP 采用 Client-Server 架构：Host（宿主应用）内嵌多个 Client，**每个 Client 与一个 Server 建立独立会话**。初始化时双方交换协议版本与能力声明，之后客户端通过 `tools/list` 拉取可用工具，再按描述调用，Server 把结果返回。**工具是动态发现的**，Server 增删工具不需要改客户端代码。

MCP 还管了 Function Calling 管不到的部分：**传输**（本地 stdio，远程走 SSE / Streamable HTTP 这类 HTTP 传输）、**会话**、**能力协商**，以及**反向调用**（Sampling / Roots）—— Server 可以反过来借用宿主的 LLM 能力与文件系统上下文，自己不必绑定模型。

## 关键差别在四点

| 维度 | Function Calling | MCP |
| --- | --- | --- |
| 所处层次 | 模型接口机制 | 应用与工具之间的集成协议 |
| 工具定义位置 | 硬编码在请求里，由应用代码组装 | 由 Server 动态提供，客户端 `tools/list` 拉取 |
| 复用范围 | 与这个应用绑定，换应用要重写一套 | Server 写一次，可被多个 Host 复用 |
| 能力边界 | 只管模型怎么表达调用意图 | 还管传输、会话、能力协商、反向调用 |

这四点里最容易被追问的是**复用范围**：Function Calling 解决的是"模型能不能调工具"，MCP 解决的是"工具能不能被所有应用共用"，后者才是它面对集成碎片化的价值。

## 两者的优缺点

- **Function Calling 优点**：实现最轻（无额外进程与协议栈）、延迟最低、没有额外故障点、与模型原生集成度高、调试直观（就是一次普通的接口调用）。
- **Function Calling 缺点**：工具定义要手工维护并随请求重复发送（占用上下文，工具一多就严重稀释注意力）；无法复用，每个应用、每个模型、每个 SDK 都要重写一套；缺少协议级能力（无动态发现、无反向通道、无标准错误语义）；安全能力要自己实现（参数校验、权限、超时、限流全在应用侧）。
- **MCP 优点**：生态复用（Server 写一次到处用）；动态发现（工具变更不影响客户端）；协议标准化（跨语言、跨厂商、跨框架互通）；职责分离清晰（Server 对接真实系统与数据清洗，Client 负责协议，Host 负责编排）；天然的安全边界（每个 Server 独立进程、独立会话，便于最小权限与故障隔离）；支持反向能力（Server 可复用宿主的 LLM 能力）。
- **MCP 缺点**：引入了进程与网络开销（stdio 尚可，远程 HTTP 有延迟）；多一层抽象带来调试复杂度（问题可能在 Client、Server、网络或模型任一层）；Server 质量参差（第三方 Server 可能数据不可信、有漏洞、行为不可预测）；仍然不解决权限与注入问题——它标准化了"怎么接工具"，安全还得宿主自己做；对简单场景是过度设计——只有一两个固定工具时，直接 Function Calling 更划算。

## 实践选型

判断标准只有一个：**这套工具要被几个应用用、会不会持续演进**。

- 单应用、工具少且固定、追求极简与最低延迟 → 用 Function Calling。
- 多应用复用同一批工具、工具会持续演进、需要跨团队共享、需要标准化生态 → 用 MCP。

生产中常见的是**混合形态**：对外用 MCP 接入生态工具，内部对模型仍然表现为标准 Function Calling，由 MCP Client 承担两层之间的转换。这也是"上下层关系"最直接的证据。

## 常见追问

**Q：MCP 会取代 Function Calling 吗？**
A：不会。MCP 是应用侧的集成协议，模型侧仍然要靠 Function Calling 表达调用意图；MCP Client 做的工作正是把 `tools/list` 拿到的工具描述转成函数声明塞进请求里，两者是配合关系。

**Q：工具多到几百个时怎么控制上下文？**
A：无论哪一层，工具描述最终都要以函数声明的形式进入上下文。常见做法是先按任务筛选或分组工具、把工具挂到子场景或子 Agent 上，用检索来决定这一轮暴露哪些工具。MCP 的动态发现解决的是"定义要不要手工维护"，并不解决"上下文被占满"。

**Q：用了 MCP 是不是就更安全了？**
A：只是边界更清楚。独立进程、独立会话、明确的工具描述让最小权限与故障隔离更容易落地，但工具越权、提示注入、结果可信度这些问题仍然要宿主自己处理：权限隔离、信任分级、脱敏与审计，一个都不能省。

## 易错点

- 把 MCP 说成"另一种 Function Calling"或"竞品"。两者不在同一层，MCP 内部就是用 Function Calling 驱动的，答成竞争关系等于答错了题。
- 以为上了 MCP 就不用做权限控制。协议只标准化"怎么接工具"，参数校验、权限、超时、限流依旧要宿主实现。
- 以为 MCP 的工具定义不进上下文。动态发现只是省了客户端改代码，工具描述最终仍要进模型上下文，工具越多注意力越稀释。
- 以为 MCP 一定要独立进程。stdio 是本地子进程，远程部署才涉及网络传输，别把"一定有网络开销"当成必然。

## 一句话记住

:::tip
Function Calling 让模型会调工具，MCP 让工具能被所有应用共用。
:::
