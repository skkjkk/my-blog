Agent 系统的核心组件可以按「感知、决策、执行、记忆」四个能力来划分，再加工具层、运行时控制层、评估与观测层三层配套。感知把外部世界的状态转成带来源标记的上下文，决策据此选出下一步动作，执行把动作落成真实的副作用，记忆跨步骤、跨会话保留状态；四者首尾相接构成闭环，而控制层负责让这个闭环安全、有限、可终止。

## 四个核心能力分别管什么

| 组件 | 负责什么 | 关键约束 |
| --- | --- | --- |
| **感知** Perception | 读取用户输入、工具执行结果、环境状态（文件、数据库、页面内容）、检索到的记忆 | 输出不是原始文本，而是结构化且带来源标记的上下文 |
| **决策** Decision | 任务分解、动作选择（选哪个工具、传什么参数）、结果不理想时重试／换路径／重新规划 | 质量直接决定 Agent 的上限，也是最依赖模型能力的一环 |
| **执行** Execution | 调用工具、写入外部系统、发起网络请求 | 唯一允许产生副作用的地方，权限与参数校验、限流、超时、幂等都在这一层 |
| **记忆** Memory | 短期存当前任务的上下文与中间结果，长期存跨会话偏好、历史经验、领域知识 | 解决「上下文窗口装不下」与「需要跨会话延续」两个问题 |

四句话可以单独背：

- 感知把世界转成**可追溯**的上下文，来源标记决定了后面信谁。
- 决策做三件事：拆任务、选动作、决定要不要重来。
- 执行是唯一能改外部世界的一层，所以所有校验都压在这里。
- 记忆分两档生命周期：跟随单任务的短期状态，和跨会话复用的长期经验。

## 感知、决策、执行、记忆各自的边界

**感知**负责把外部世界的状态转化为模型可理解的输入。范围包括用户输入、工具执行结果、环境状态（文件、数据库、页面内容），以及从记忆中检索到的信息。它的输出通常不是原始文本，而是结构化且带来源标记的上下文；来源标记很重要，因为后面要判断哪些内容可信、哪些可能夹带了注入指令。

**决策**是 Agent 的大脑，接收感知结果与目标，输出「下一步做什么」。它要做任务分解（把大目标拆成可执行的子任务）、动作选择（选哪个工具、传什么参数），以及在结果不理想时决定是重试、换路径还是重新规划。决策质量直接决定 Agent 的上限，也是最依赖模型能力的一环。

**执行**把决策落地为动作：调用具体工具、写入外部系统、发起网络请求。这一层是唯一允许产生副作用的地方，因此权限校验、参数校验、限流、超时控制、幂等处理都集中在这一层。执行层不应该「相信」模型的任何参数输出。

**记忆**负责跨步骤、跨会话保留状态。短期记忆保存当前任务的上下文与中间结果，长期记忆保存跨会话的用户偏好、历史经验与领域知识。它解决的是「上下文窗口装不下」和「需要跨会话延续」两个问题。

## 主线之外的三层配套

**工具层**管工具定义、参数 schema、工具检索与裁剪、结果封装。工具是 Agent 的手和眼，工具数量过多会稀释模型注意力，所以工具目录管理本身就是组件的一部分，而不是可选项。

**运行时控制层（Runtime / Orchestrator）**管状态机推进、上下文组装与预算管理、终止条件判定、重试与降级策略、错误分类与恢复。它是确定性的那一半，与模型这个「不确定的一半」配合工作。

**评估与观测层**记录完整轨迹、计算验收指标、支持事后归因。它是生产化 Agent 不可或缺的一环，缺了它线上问题就无法定位。

## 闭环是怎么转起来的

感知把世界转成上下文，决策基于上下文产出动作，执行把动作变成现实世界的变化，新的现实再被下一轮感知读到——这就构成了闭环。记忆横跨整个闭环提供历史，运行时控制层负责让这个闭环安全、有限、可终止。

一轮循环的骨架大致是这样，不确定的部分在 `decide`，确定的部分在控制层：

```js
while (!done) {
  const ctx = perceive();          // 感知：带来源标记的上下文
  const action = decide(ctx);      // 决策：选工具 + 定参数
  const result = execute(action);  // 执行：校验、限流、幂等后落副作用
  memory.write(result);            // 记忆：留下中间结果
  done = finishReason(ctx, result) // 控制层：预算 / 停滞 / 验收判定
    || budgetExceeded(ctx);
}
```

分层的意义不是画架构图，而是把「会出错」关进可校验的边界里：模型推理天然不确定，就让它只负责产出候选动作；校验、限流、终止这些必须确定的行为，交给控制和执行两层来兜底。这样出问题时你也能定位到是感知读错了、决策选错了，还是执行层没拦住。

## 常见追问

**Q：短期记忆和长期记忆的边界怎么划？**
A：按生命周期划。跟随单个任务、任务结束就可以丢弃的是短期记忆；需要跨会话复用、值得持久化的是长期记忆，判断标准是「下一次任务还需要它吗」。

**Q：为什么说决策层决定了 Agent 的上限？**
A：执行层和工具层是工程问题，靠校验、限流和兜底可以把可靠性做上去；但任务怎么拆、该走哪条路径只有模型能做，这一层不行，工程补不回来。

**Q：记忆为什么不直接塞进 prompt？**
A：上下文窗口装不下，全塞进去会挤掉当前任务真正需要的信息。检索、压缩、写入与淘汰需要独立策略，交给模型临时处理只是把问题挪了个位置。

**Q：工具是不是越多越好？**
A：不是。工具数量过多会稀释模型注意力、抬高选错概率，所以要靠工具检索与裁剪控制每次暴露给模型的工具集。

**Q：执行层为什么还要二次校验参数？**
A：因为模型输出的是概率生成的文本，参数可能是不存在的表名、越权的路径或非法取值，执行层是最后一道能把错误拦下来的关口。

## 易错点

- 把执行层当成「模型说调就调」的直通道，省掉权限与参数校验，模型幻觉出的参数直接落库。
- 把记忆等同于向量库。向量检索只是长期记忆的一种实现，短期状态管理与跨会话偏好不是加个库就自动解决的。
- 只用模型自述当终止条件。运行时控制层必须有自己的确定性判定（步数、预算、状态是否变化），否则模型一句「我完成了」就能让它提前收工，或者干脆永远不结束。
- 丢掉感知的来源标记，把网页、工具返回的内容直接当可信指令拼进上下文，等于主动打开提示注入的入口。

:::tip[一句话记住]
感知给上下文，决策定动作，执行出后果，记忆接历史，控制层负责收口。
:::
