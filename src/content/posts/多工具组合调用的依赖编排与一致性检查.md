**一、依赖编排要用确定性代码来驱动，而不是让模型自由决定顺序。** 具体做法是先把用户目标编译成一张工具依赖图，节点是工具调用，边是依赖关系。依赖有两类：控制依赖表示必须串行，数据依赖表示下游工具的入参来自上游工具的输出。调度器对这张图做拓扑排序，没有依赖关系的分支并行执行，下游节点由上游结果触发。这样既压缩了延迟，也避免了模型把步骤顺序搞错。编排层还必须支持动态重规划，当某个节点失败或者校验不通过时，只重规划受影响的子图而不是整体重来。每个工具在注册时就要声明自己的入参 schema、出参 schema、幂等性、是否有副作用以及错误码，这套契约是后续所有校验的基础。

**二、参数校验要做成多层漏斗，而不是单点校验。** 第一层是结构校验，用 JSON Schema 检查类型、必填项和枚举值；第二层是语义校验，检查范围、格式、单位、正则等业务含义，比如时间区间不能倒置、金额不能为负、分页大小不能超过上限；第三层是跨参数一致性校验，检查参数之间是否自洽，比如查询的开始时间必须早于结束时间、币种和金额单位要匹配、用户 ID 与订单 ID 是否属于同一租户；第四层是前置探测，在真正执行前先做一次轻量的可用性检查，确认目标资源是否存在、是否有权限、库存是否充足，相当于执行前的前置校验。校验失败之后的处理策略要分级：能自动修的就带着错误信息让模型重新生成参数，参数语义有歧义的就去向用户澄清，无法修复的则跳过并降级，同时把失败原因结构化地回灌给编排层。

**三、中间结果一致性检查要分层做，并且区分确定性判据和语义判据。** 第一层是结构一致性，校验上游实际输出是否真的满足下游入参的 schema，这一步应该由程序严格保证。第二层是实体对齐，确认同一次任务里不同工具返回的对象指向的是同一个实体，比如用户工具返回的用户 ID 与订单工具返回的所属用户 ID 能否对应上，这需要在中间结果之上维护一份实体标识映射表。第三层是量纲与口径一致性，检查时间时区、货币单位、金额精度、分页口径这类容易被不同工具实现差异坑到的地方。第四层是交叉验证，对关键事实用两条独立路径获取并比对，比如一个数据既来自业务库查询也来自聚合报表，不一致时按数据源权威级别判定，冲突无法自动解决就升级为澄清或人工介入。第四层之外还要有溯源记录，为每个中间结果标注来源工具、调用时间、版本和数据血缘，这样出现不一致时能快速定位到底是哪个环节出的问题。

**四、工程上的三条底线。** 编排、校验和一致性检查的判断逻辑要尽量下沉到确定性代码和规则引擎里，模型只负责填写参数和做语义理解，这样整体行为可预测、可测试。多步写操作要有幂等键和重放能力，涉及不可逆操作时采用补偿事务而不是真正的事务，因为外部系统往往不支持分布式事务。整个链路要有全链路追踪，记录每一步的输入、输出、耗时和校验结论，既便于回归测试，也便于在出问题时做失败归因。
