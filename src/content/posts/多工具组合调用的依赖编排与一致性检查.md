这类问题的共同解法是把判断交给确定性代码，模型只做语义理解和填参数。编排层先把用户目标编译成一张工具依赖图，用拓扑排序调度、无依赖就并行、失败只重规划受影响的子图；校验层用结构、语义、跨参数一致性、前置探测四层漏斗拦错；一致性层用结构对齐、实体对齐、量纲口径、交叉验证四道判据，再加溯源记录，把上游输出的问题在流入下游之前挡住。

## 依赖编排：先编译成工具依赖图，再拓扑调度

依赖编排要用确定性代码驱动，而不是让模型自由决定顺序。模型的强项是理解意图、抽取参数，弱项是稳定维护执行顺序；顺序一旦交给它，行为就不可预测，也没法做回归测试。做法是把目标编译成一张工具依赖图：节点是一次工具调用，边是依赖关系。

依赖分两类。控制依赖表示两个调用必须串行，数据依赖表示下游工具的入参来自上游工具的输出。调度器对这张图做拓扑排序，互不依赖的分支并行执行，下游节点由上游结果触发。这样既压缩了延迟，也避免了模型把步骤顺序搞错。

编排层还必须支持动态重规划：某个节点失败或校验不通过时，只重规划受影响的子图，而不是整体重来。已完成且校验通过的节点不该被重跑，否则既浪费预算，也会把已经确定的结果重新变成不确定的。

```text
graph  = 编译(用户目标)        # 节点 = 一次工具调用，边 = 控制依赖 / 数据依赖
ready  = 入度为 0 的节点

while ready 非空:
    batch   = ready 中互不依赖的节点        # 可并行
    results = 并行执行(batch)               # 每个节点执行前先过参数校验
    for node, out in results:
        校验出参(node, out)                 # 结构对齐 + 实体对齐 + 口径一致
        成功: 解锁依赖它的下游节点
        失败: 只重规划受影响的子图，已完成节点不重跑
```

## 工具注册时就要立契约

每个工具在注册时就要声明自己的契约：入参 schema、出参 schema、是否幂等、有没有副作用、以及错误码。这套契约是后续所有校验的基础——结构校验直接拿入参 schema 比对，一致性检查拿上游实际出参比对下游入参 schema，失败处理则按错误码决定是可重试、需要重规划还是直接中止。

契约缺失的代价是把判断全部推回给模型。没有 schema 就只能靠自然语言描述去猜参数长什么样，没有幂等声明就不知道重试安不安全，最后每一层检查都退化成「让模型看一眼」。

## 参数校验要做成四层漏斗

单点校验一定会漏，参数校验要按成本递增的顺序做成漏斗。第一层是结构校验，用 JSON Schema 检查类型、必填项和枚举值；第二层是语义校验，检查范围、格式、单位、正则这类业务含义；第三层是跨参数一致性校验，检查参数之间是否自洽；第四层是前置探测，在真正执行前先做一次轻量的可用性检查，确认目标资源存在、有权限、库存充足。

| 层次 | 查什么 | 典型例子 |
| --- | --- | --- |
| 结构校验 | 类型、必填、枚举，用 JSON Schema 表达 | 少传必填字段、把整数写成字符串 |
| 语义校验 | 范围、格式、单位、正则等业务含义 | 时间区间倒置、金额为负、分页大小超过上限 |
| 跨参数一致性 | 参数之间是否自洽 | 开始时间必须早于结束时间、币种与金额单位匹配、用户 ID 与订单 ID 属于同一租户 |
| 前置探测 | 执行前的轻量可用性检查 | 目标资源不存在、没有权限、库存不足 |

顺序不能反。越靠后的层次越贵：结构错在本地立刻能拒，前置探测往往要打一次真实接口或查一次真实库存。把贵的放在前面，等于用一次网络往返去拦一个类型错误。

## 中间结果一致性检查分四层

一致性检查要分层做，并且明确区分确定性判据和语义判据。第一层结构一致性，校验上游实际输出是否真的满足下游入参的 schema，这一层必须由程序严格保证，不能交给模型目测。第二层实体对齐，确认同一次任务里不同工具返回的对象指向同一个实体，比如用户工具返回的用户 ID 与订单工具返回的所属用户 ID 能否对应上，做法是在中间结果之上维护一份实体标识映射表。第三层量纲与口径一致性，检查时间时区、货币单位、金额精度、分页口径这些地方，不同工具的实现差异最容易在这里埋坑。第四层交叉验证，对关键事实用两条独立路径获取并比对，比如同一份数据既来自业务库查询也来自聚合报表，不一致时按数据源权威级别判定，冲突无法自动解决就升级为澄清或人工介入。

前两层是确定性的，可以写成断言；后两层依赖数据源与业务语义，属于需要规则和人工兜底的部分。把这两类混在一起做，结果是既写不出稳定断言，又不知道该在什么时候升级给人。

## 中间结果要带溯源记录

每个中间结果都要标注来源工具、调用时间、版本和数据血缘。这不是为了好看，而是为了不一致可归因：出问题时能顺着血缘回溯到具体哪一次调用、哪个数据源、哪个版本的实现。

没有溯源，一致性检查只能报「对不上」，却说不清是谁错了。工程上最后往往变成归咎于模型幻觉，而真正的原因可能是某个工具的时区处理改过一版。

## 失败处理策略要分级

校验失败之后不能一律重试，要按可修复程度分级。能自动修的错误，带着结构化错误信息让模型重新生成参数；参数语义有歧义、模型改不动的，向用户澄清；无法修复的，跳过该步并降级给出部分结果；所有失败原因都要结构化回灌给编排层，由编排层决定要不要重规划对应子图。

分级的价值在于避开两个极端：无脑重试会把同一个错误重复几遍还烧掉预算，一遇错就整体放弃则让一次小失误毁掉整条链路。

## 工程上的几条底线

- 判断逻辑下沉。编排、校验和一致性检查的判断尽量放进确定性代码和规则引擎，模型只负责填参数和做语义理解，这样整体行为可预测、可测试。
- 写操作要幂等可重放。多步写操作要有幂等键和重放能力，否则重试就是在制造重复副作用。
- 用补偿代替分布式事务。外部系统往往不支持分布式事务，涉及不可逆操作时用补偿事务收尾，而不是指望一个跨系统的强一致事务。
- 全链路追踪。记录每一步的输入、输出、耗时和校验结论，既便于回归测试，也便于出问题时做失败归因。

## 常见追问

- **问：为什么不让模型自己决定调用顺序？** 单步看起来合理，多步就会乱序和跳步，而且没有可测的执行轨迹。依赖图是显式的，能拓扑排序、能并行、能只重规划受影响的部分。
- **问：契约里的幂等声明有什么用？** 它决定重试是否安全。非幂等的写工具被重试会重复扣款或重复下单，所以只有声明幂等、或者带幂等键的调用才允许原样重试。
- **问：每个调用都要做满四层校验吗？** 不必。只读查询常常前三层加一次轻量探测就够，写操作和不可逆操作才值得付前置探测的成本。
- **问：交叉验证发现冲突怎么办？** 先按数据源权威级别自动裁决，并把裁决结论写进溯源；判断不了就升级为向用户澄清或人工介入，不要静默取其中一个。

## 易错点

- 把编排交给模型自由发挥。看着灵活，实际不可预测也不可测，步骤一多就开始乱序。
- 只做 JSON Schema 结构校验就以为校验完了。时间区间倒置、金额为负、租户不匹配这类错会全部漏过。
- 只比对 schema 不看实体。两个工具都返回了「用户」，schema 都对，但根本不是同一个人。
- 失败一律重试。非幂等写操作重试会重复执行，无差别重试还会把预算烧在没有修复可能的错误上。

## 一句话记住
