让 Agent 具备长期记忆，本质上是做一套**「写入决策 — 检索决策 — 遗忘决策 — 冲突治理」**的完整记忆系统，而不是简单地把对话存起来。判断一个方案够不够用，就看它能不能同时回答四个问题：什么信息该进库、按什么形态存、怎么把它召回来、以及旧事实和新事实打架时听谁的。四个环节缺一个，系统就会退化成一个只会膨胀、不会自洁的日志库。

## 记忆系统要解决的四个决策

没有记忆系统的 Agent 每次都从零开始：用户上次说过的偏好、上一轮已经确认的结论、之前踩过的坑，全部丢失，任务一长就开始原地打转。最常见的粗糙替代是把历史对话整段塞进上下文，代价是三重的——token 成本随步数上涨、无关内容稀释注意力、超出窗口后信息彻底丢失。

把记忆做成系统，就是把这四个决策显式化，让每一件都有明确的判定标准和代价：

- **写入决策**：什么值得存，存成什么粒度。
- **检索决策**：这次任务该把哪几条记忆捞出来，怎么排优先级。
- **遗忘决策**：哪些该退出活跃检索，退出的怎么处置。
- **冲突治理**：同一件事存了两条矛盾的记忆时，按什么规则裁决。

这四件事是耦合的，缺一个都算失败。只写不取，库再大也用不上；只取不淘汰，库无限膨胀、召回质量下降；不治理冲突，模型面对两条矛盾记忆时行为不确定。

## 写入：四个信号决定值不值得存

写入不是“把看到的都记下来”，而是一道筛子。用四个信号决定一条信息是否值得写入：

- **新颖性**：与已有记忆是否重复，重复的直接合并而不是再存一条。
- **重要性**：对未来任务的参考价值，一次性细节通常不值得占位。
- **置信度**：是用户显式陈述还是模型自己的推断，二者权重不同。
- **可复用性**：是可泛化的规律，还是一次性的事件细节。

写入时要做**原子化事件抽取**——把自然语言拆成独立、可判定真伪、带时间戳与实体的事实单元，而不是把整段对话塞进库。整段对话既不可检索也不可判定，拆成事实单元之后才能做去重、按槽位更新和冲突检测。

每条记忆还必须带元数据：**来源、置信度、时间戳、有效期、作用域、实体链接**。这些字段不是装饰，后面做结构化过滤、冲突裁决、可追溯审计全靠它们。

```json
{
  "content": "用户所在团队使用 Postgres 作为主库",
  "source": "user_explicit",
  "confidence": "high",
  "created_at": "2026-10-20T09:12:00+08:00",
  "valid_until": null,
  "scope": "project:blog-backend",
  "entities": ["用户", "Postgres", "blog-backend"]
}
```

## 存储：按内容形态分层

不同记忆的形态差别很大，用一套存储硬扛必然别扭。常见做法是按内容形态分层：

| 记忆形态 | 存什么 | 承载方式 | 检索方式 |
| --- | --- | --- | --- |
| 语义记忆（事实与知识） | 用户属性、领域事实、稳定结论 | 向量库 + 结构化数据库双写 | 向量做语义召回，字段做过滤与去重 |
| 情景记忆（任务轨迹） | 某次任务怎么做的、成没成 | 事件日志、时序库、对象存储 | 按时间与任务 id 检索 |
| 程序性记忆（经验与规则） | 可复用的做事流程与规则 | 知识库、知识图谱、规则文件 | 按场景匹配，可版本化、可审阅 |
| 工作记忆 | 当前任务的临时状态 | 上下文 + 外部 scratchpad（临时文件、KV 存储） | 直接读写，任务结束即释放 |

语义记忆之所以要**向量库与结构化数据库双写**，是因为两者能力互补：向量负责“意思相近就能召回”，字段负责“作用域、时间、去重键这些硬条件必须精确命中”，缺一边就会要么召回不准，要么过滤不了。程序性记忆强调可版本化、可审阅，因为它改一次影响所有后续任务，必须能回滚、能人工 review。

在此之上还可以加一层**知识图谱**承载实体关系，支撑多跳推理与实体对齐，把散落的事实单元连成网。

## 检索：多路召回 + 重排 + 上下文预算

单一向量检索在长记忆库上召回质量会明显下降——近义条目太多、专有名词和编号密集，纯语义匹配经常打偏。标准做法是并行做多路召回：

- **语义向量召回**：表达相近但字面不同的说法，比如“预算紧”和“成本敏感”。
- **关键词检索**：专有名词、编号、错误码这类必须精确匹配的内容。
- **结构化过滤**：作用域、实体、时间窗口的硬约束，先缩范围再召回。
- **图关系扩展**：沿知识图谱做一跳或两跳的关联，补上直接召回漏掉的实体。

多路结果合并后，用**交叉编码器或模型重排**统一排序，因为各路分数量纲不同，直接拼接不可比。

重排之后还要做**上下文预算管理**，否则检索再准也会把窗口撑爆：按 token 预算截断、对低优先级内容做摘要压缩、把高价值信息放在提示的首尾（规避长上下文中段的注意力衰减）、并按时间加权衰减，让旧记忆的优先级自然下降。

## 遗忘：是成本控制，不是物理删除

遗忘的动机是成本和质量，不是“清理垃圾”。三种机制常配合使用：

- **时间衰减**：给记忆设生存期或半衰期，过期后降低权重直至退出活跃检索。
- **容量淘汰**：按价值与访问频率组合打分，淘汰总分最低的那批。
- **冗余压缩**：把语义高度重叠的记忆聚类合并成一条，减少重复占位。

关键原则是**遗忘不等于抹除**：被淘汰的旧事实应当**归档**而不是物理删除，保留演进轨迹，这样后面出现冲突时才有据可查——“用户上个月说用 MySQL，这个月说用 Postgres”，只有归档能证明这是变更而不是错记。

同时要把**删除权交给用户**：能查看、能编辑、能清除。这是长期使用建立信任的前提，也是合规底线。

## 冲突治理：统一优先级 + 读写双侧检测

冲突有三类：同一事实槽位出现不同取值、不同来源的结论互相矛盾、新旧偏好并存导致行为不确定。

解决冲突按固定优先级裁决：

1. **时间优先**：更新的陈述覆盖更旧的。
2. **权威性优先**：用户显式陈述优先于模型推断。
3. **作用域优先**：更具体的作用域覆盖更宽泛的。
4. **置信度优先**：置信度高的胜出，同时保留冲突记录。

如果按上面几条仍分不出高下，就**保留双版本**并在适当时机向用户澄清，而不是悄悄挑一个。

检测必须在**读写两侧都做**：写入时查既有记忆是否与这条矛盾，检索时查这一批结果之间是否互相打架。只在一侧检测，冲突照样会漏到模型面前。

## 可追溯与可度量：工程配套

每条记忆要能回答三个问题：**谁说的**（来源与授权）、**什么时候说的**（时间戳）、**凭什么信**（置信度与证据）。这三点是记忆系统可审计、可纠错的前提，也是防止“记忆投毒”的基础。

记忆还要能被**度量**：写入量、命中率、检索延迟、被引用率、冲突发生率、失效淘汰率，以及最关键的一项——**记忆对任务成功率的实际贡献**，可以用消融实验衡量：关掉记忆看成功率掉多少。

**没有这些数据，记忆系统就无法迭代优化。** 只靠体感调参，很容易在“看起来记得更多”和“实际任务更差”之间反复摇摆。

## 常见追问

**问：开个向量库把历史对话都存进去，算不算长期记忆？**

答：只算“存了”，不算记忆系统。写入没有筛选、检索只有单路、没有遗忘也没有冲突治理，库里会堆满一次性细节，长记忆上纯向量召回质量还会明显下降。

**问：为什么一定要原子化成事实单元，整段存不行吗？**

答：整段对话噪声大且不可检索，也无法判定真伪。拆成独立、带时间戳与实体的事实单元后，才能做去重、按槽位更新和冲突检测。

**问：两条记忆冲突时到底听谁的？**

答：按时间、权威性、作用域、置信度的优先级依次裁决；仍然分不出就保留双版本并找时机向用户澄清，不要静默挑一个。

**问：遗忘会不会把有用的记忆丢掉？**

答：遗忘的目的是控成本、保召回质量，所以淘汰先归档再退出活跃检索，配合用户的查看、编辑、清除权限，出问题能回溯也能撤销。

## 易错点

- **把整段对话直接当记忆。** 噪声大、不可检索，召回时命中一堆无关片段，还占满预算。
- **只做写入不做遗忘。** 库无限膨胀，召回质量随之下降，最后检索延迟和准确率一起坏掉。
- **把记忆当成“万能知识库”，塞满无关内容。** 稀释注意力，比没有记忆更糟。
- **不做冲突检测。** 同一件事存在两条矛盾记忆，模型行为不确定，且没人知道它为什么这样答。

## 一句话记住

:::tip
长期记忆不是把对话存起来，而是写入、检索、遗忘、冲突治理四件事一起设计。
:::
