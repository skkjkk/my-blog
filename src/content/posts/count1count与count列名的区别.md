三者的**返回值完全相同**（都是行数），差别只在**执行方式与性能**。结论先给：**性能上 `COUNT(*)` ≥ `COUNT(1)` > `COUNT(列名)`**，这个差距在 InnoDB 上通常**几乎不存在**；`COUNT(*)` 与 `COUNT(1)` 是**同一份执行计划**，"`COUNT(1)` 更快"是 MyISAM 时代的老结论。`COUNT(列名)` 真正不同的是**语义**：它跳过 NULL，结果可能对不上，**无索引时还要回表**逐行判空，最慢。

## 根本原因：InnoDB 的行数无法像 MyISAM 那样直接读

- **MyISAM**：维护了精确的行数字段 → `COUNT(*)` 直接读，**O(1)**
- **InnoDB**：MVCC 下多版本并存，**没有精确行数** → `COUNT` 必须**扫一遍**、按事务可见性逐条判断才能得到准确值 → **O(n)**

:::tip
**所以"COUNT(*) 慢"的根因是 InnoDB 的 MVCC 特性，不是 SQL 写法问题。**
:::

## `COUNT(*)` —— 优化器会自动选最优索引

MySQL 会根据表结构选一个**最小的可用索引**去扫描（InnoDB 二级索引比聚簇索引小得多 → 扫描成本更低）。

:::tip
**因此 `COUNT(*)` 并不是"扫全表"，而通常只扫最小的二级索引。** 这也是为什么有二级索引时 `COUNT(*)` 会快很多。
:::

## `COUNT(1)` —— 会被解析器改写成 `COUNT(*)`

- **语义上等价**：常量 1 对任何一行都不为 NULL，数出来就是全部行数
- **MySQL 解析器识别到 `COUNT(1)` 后直接优化为 `COUNT(*)`**，可以用 `EXPLAIN` 对比两者计划，完全一致

:::tip
网上流传的"COUNT(1) 比 COUNT(*) 快"是**基于 MyISAM 的老结论**或**以讹传讹**，在 InnoDB 上**不成立**。
:::

## `COUNT(列名)` —— 只统计该列不为 NULL 的行

`COUNT(col)` 会**忽略该列为 NULL 的行**，因此结果可能与 `COUNT(*)` 不同。

- **有索引时**：优化器会**优先用该列的索引扫描**，但**只扫描索引中该列非 NULL 的部分**（InnoDB 二级索引中 NULL 值也会被索引）
- **⚠️ 无索引时**：这是**最慢**的形式 —— 必须**回表**读出每一行的列值再判断是否为 NULL → **比 COUNT(*) 慢得多**

## 实用对比表

| | COUNT(*) | COUNT(1) | COUNT(列名) |
|---|---|---|---|
| 结果 | 全部行数 | 全部行数 | **该列非 NULL 的行数** |
| InnoDB 代价 | 扫最小索引 | 同 COUNT(*)（改写） | 有索引→扫索引；无索引→**回表** |
| 能否用覆盖索引 | ✅ | ✅ | ✅（索引含该列时） |
| 推荐 | ⭐ **默认首选** | 无差别 | 只在业务确实要排除 NULL 时用 |

## 优化 COUNT 的三个实用手段

- **① 尽量给 COUNT 用的列建索引**（或在有二级索引的表上做 COUNT，让优化器走小索引）
- **② 估算值代替精确值**：`EXPLAIN` 里的 `rows` 字段是**估算行数**，大表上做精确 COUNT 纯属浪费
- **③ 维护计数**：对需要频繁精确统计的维度，**单独维护一张计数表**（或用 Redis 计数器 + 定期校准），用**最终一致**换性能

## 真实场景中最该关注的不是 COUNT(*) vs COUNT(1)，而是这三个

- **深分页的 `COUNT(*)`**：分页总数统计往往是慢查询的真正元凶 → 改成"是否有下一页"探测
- **`COUNT` + `WHERE` 的组合**：走索引扫描并**回表判断条件** → 尽量改写成覆盖索引
- **大表做精确 COUNT 本身就危险**：一条 `COUNT(*)` 可能扫千万行，**拖垮共享的 IO**

## 常见追问

**Q：`COUNT(*)` 真的会扫全表吗？**
A：不会。InnoDB 下优化器会挑**最小的可用索引**扫，通常只是二级索引，不回表；只有表上没有任何二级索引时才退化成扫聚簇索引。

**Q：既然要和 `COUNT(*)` 结果一样，写成 `COUNT(主键)` 不是更"精确"吗？**
A：结果确实一样（主键不可能为 NULL），但它会让优化器去扫**聚簇索引**，而聚簇索引里带着整行数据、页数远多于最小的二级索引，扫描代价更高。所以没有特殊理由，**默认写 `COUNT(*)`**。

**Q：分页页脚的总数太慢，怎么办？**
A：按代价从低到高：用 `EXPLAIN` 的 `rows` 给个**估算值**；改成"查 N+1 条判断有没有下一页"；对固定维度**单独维护计数表或 Redis 计数器**（接受最终一致）。

**Q：既然都慢，为什么不能给 COUNT 加缓存就完事？**
A：缓存能救读多写少的场景，但计数是**每写一次就要失效一次**的维度，更新冲突和一致性维护会变成新问题——所以要么接受估算，要么用计数表把"精确"这件事显式化。

## 易错点

- **错："`COUNT(1)` 比 `COUNT(*)` 快，因为它不用解析列名。"** 正确说法：在 InnoDB 上 `COUNT(1)` 会被改写成 `COUNT(*)`，两者计划一致，用 `EXPLAIN` 一比就清楚。
- **错："三种写法结果肯定一样，随便挑一个。"** 正确说法：只要该列允许 NULL，`COUNT(列名)` 就可能**比 `COUNT(*)` 少**。判断依据是业务要不要求排空，不是性能。
- **错："`COUNT(*)` 会把整行数据读出来，所以比 `COUNT(1)` 重。"** 正确说法：`COUNT` 只关心"这一行存在"，走索引即可，**不需要回表读整行**；真正会回表的是无索引的 `COUNT(列名)` 和带非覆盖条件列的 `WHERE`。
- **错："表才几百万行，COUNT 一下无所谓。"** 正确说法：单次 COUNT 是 O(n) 的顺序扫描，放在高频接口或分页总数里会反复放大，**慢查询往往出在这里而不是单条 SQL 的写法**。

## 面试怎么答

1. 返回值相同，差别在执行方式
2. 根因是 InnoDB MVCC 无法保存精确行数（MyISAM 是 O(1)，InnoDB 是 O(n)）
3. COUNT(1) 被优化器改写成 COUNT(*)，"COUNT(1) 更快"是过时结论；而 COUNT(列名) 只数非 NULL 且无索引时要回表，最慢。讲到第三点这一层，基本就能和只背过结论的人区分开

## 一句话记住

:::tip
**`COUNT(*)` 与 `COUNT(1)` 等价，`COUNT(列名)` 只数非 NULL，差别在执行方式。**
:::
