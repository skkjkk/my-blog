三者的**返回值完全相同**（都是行数），差别只在**执行方式与性能**。结论先给：**性能上 `COUNT(*)` ≥ `COUNT(1)` > `COUNT(列名)`**，但这个差距**在 InnoDB 上几乎不存在**。

1) **⭐ 根本原因：InnoDB 的行数无法像 MyISAM 那样直接读**
- **MyISAM**：维护了精确的行数字段 → `COUNT(*)` 直接读，**O(1)**
- **InnoDB**：MVCC 下多版本并存，**没有精确行数** → `COUNT` 必须**扫一遍**才能得到准确值 → **O(n)**

> **所以"COUNT(*) 慢"的根因是 InnoDB 的 MVCC 特性，不是 SQL 写法问题。**

2) **`COUNT(*)` —— 优化器会自动选最优索引**
MySQL 会根据表结构选一个**最小的可用索引**去扫描（InnoDB 二级索引比聚簇索引小得多 → 扫描成本更低）。
> **因此 `COUNT(*)` 并不是"扫全表"，而通常只扫最小的二级索引。** 这也是为什么有二级索引时 `COUNT(*)` 会快很多。

3) **`COUNT(1)` —— 语义上等价，MySQL 会直接改写成 `COUNT(*)`**
MySQL 解析器识别到 `COUNT(1)` 后**直接优化为 `COUNT(*)`**（可用 `EXPLAIN` 对比两者计划，完全一致）。
> 网上流传的"COUNT(1) 比 COUNT(*) 快"是**基于 MyISAM 的老结论**或**以讹传讹**，在 InnoDB 上**不成立**。

4) **`COUNT(列名)` —— 只统计该列不为 NULL 的行**
`COUNT(col)` 会**忽略该列为 NULL 的行**，因此结果可能与 `COUNT(*)` 不同。
- **有索引时**：优化器会**优先用该列的索引扫描**，但**只扫描索引中该列非 NULL 的部分**（InnoDB 二级索引中 NULL 值也会被索引）
- **⚠️ 无索引时**：这是**最慢**的形式 —— 必须**回表**读出每一行的列值再判断是否为 NULL → **比 COUNT(*) 慢得多**

5) **⭐ 实用对比表**
| | COUNT(*) | COUNT(1) | COUNT(列名) |
|---|---|---|---|
| 结果 | 全部行数 | 全部行数 | **该列非 NULL 的行数** |
| InnoDB 代价 | 扫最小索引 | 同 COUNT(*)（改写） | 有索引→扫索引；无索引→**回表** |
| 能否用覆盖索引 | ✅ | ✅ | ✅（索引含该列时） |
| 推荐 | ⭐ **默认首选** | 无差别 | 只在业务确实要排除 NULL 时用 |

6) **⭐ 优化 COUNT 的三个实用手段**
- **① 尽量给 COUNT 用的列建索引**（或在有二级索引的表上做 COUNT，让优化器走小索引）
- **② 估算值代替精确值**：`EXPLAIN` 里的 `rows` 字段是**估算行数**，大表上做精确 COUNT 纯属浪费
- **③ 维护计数**：对需要频繁精确统计的维度，**单独维护一张计数表**（或用 Redis 计数器 + 定期校准），用**最终一致**换性能

7) **⚠️ 真实场景中最该关注的不是 COUNT(*) vs COUNT(1)，而是这三个**
- **深分页的 `COUNT(*)`**：分页总数统计往往是慢查询的真正元凶 → 改成"是否有下一页"探测
- **`COUNT` + `WHERE` 的组合**：走索引扫描并**回表判断条件** → 尽量改写成覆盖索引
- **大表做精确 COUNT 本身就危险**：一条 `COUNT(*)` 可能扫千万行，**拖垮共享的 IO**

8) **面试答法建议**。三点：**① 返回值相同，差别在执行方式；② 根因是 InnoDB MVCC 无法保存精确行数（MyISAM 是 O(1)，InnoDB 是 O(n)）；③ COUNT(1) 被优化器改写成 COUNT(*)、"COUNT(1) 更快"是过时结论；而 COUNT(列名) 只数非 NULL 且无索引时要回表，最慢**。**第三点的"COUNT(1) 更快是谣言"能直接过滤掉大量背题的人。**
