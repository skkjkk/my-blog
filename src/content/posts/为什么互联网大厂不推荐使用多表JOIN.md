不是 JOIN 这个语法有问题，而是「多表 JOIN + 大表 + 分库分表」这套组合在互联网场景下代价失控。头号理由是分库分表之后，关联表经常落在不同实例上，数据库在物理层面就做不了关联；其次是嵌套循环带来的执行放大、锁范围扩大、深分页与从库复制压力。所以大厂的做法是把 JOIN 拆开，在应用层用冗余字段、宽表或批量组装来关联，同时用对账或最终一致把反范式的一致性代价兜住。

## 头号理由：分库分表之后，JOIN 在物理上就做不了

单库单表时，JOIN 只是执行计划里的一次关联运算，优化器想怎么排都行。一旦分库分表，同一个 JOIN 涉及的两张表会因为分片键不同而落在不同的库、甚至不同的实例上，而一条 SQL 的执行范围只能在单个实例内，跨实例没有把关联下推过去的手段，中间件也只能把两边数据拉到内存里做归并。真正做不到的是跨实例；同一实例的不同 schema 之间技术上还能写 `db1.t1 JOIN db2.t2`，但那样等于绕开了分片键路由，把多个库的数据汇到一处，规模一上来就不可控。

:::tip
这意味着：业务一旦重度依赖多表 JOIN，将来做分库分表时这部分代码要整体重写——这是架构演进上实实在在欠下的债。
:::

## 性能理由：嵌套循环的放大效应，索引决定生死

MySQL 的 JOIN 本质是嵌套循环（Nested Loop）的变体：取驱动表的每一行，到被驱动表里找匹配行。连接列有索引时，每一行是一次索引查找，外层 N 行就是 N 次查找；连接列没有索引时，退化成被驱动表全表扫描，复杂度变成 N × M，这才是线上 JOIN 变慢的真凶。较新的 MySQL 会对无索引的等值连接改走 Hash Join，先在小表上建哈希表再扫大表，数据量小时能救一把，数据量大时内存与临时空间照样扛不住。

看执行计划时要留意 `Using join buffer`，它说明连接列没走到索引，MySQL 只能把驱动表的数据塞进 join buffer 里做批量比对。所以 JOIN 的性能极度依赖「连接列有没有索引」，这也是绝大多数慢 JOIN 的根因。

## 并发理由：锁范围扩大，死锁与阻塞概率上升

多表 JOIN 的事务会同时持有多个表的行锁，而在不同的执行计划下，加锁顺序可能不一致：这次以 A 表为驱动表，统计信息更新后可能换成 B 表驱动，两个事务就可能以相反的顺序去锁同一批行。典型场景是两个事务分别按 A 表到 B 表、B 表到 A 表的顺序更新两张表，各自等着对方释放锁，直接死锁。

所以 JOIN 参与的事务更该短、更该固定访问顺序，事务里不要做远程调用，也不要把大结果集的 JOIN 包在事务里。

## 深分页与复制：两个常被忽略的代价

`JOIN ... ORDER BY ... LIMIT 100000, 10` 这类语句，优化器要先把 JOIN 的结果集拼出来，再排序，最后丢掉前 10 万行，代价随 offset 一路上涨，深分页加 JOIN 是慢查询的重灾区。能落地的改写是先在主表上分页拿 id，再按 id 批量取详情：

```sql
-- 第一步：只在主表上分页，走覆盖索引，不产生 JOIN
SELECT id FROM t_order WHERE user_id = 42 ORDER BY id DESC LIMIT 100000, 10;

-- 第二步：按 id 批量取详情，关联放到应用层，或在小结果集上做一次 JOIN
SELECT id, user_id, amount, status FROM t_order WHERE id IN (100001, 100002, 100003);
```

复制链路上还有一层代价：两张表分片键不一致时，同一个 JOIN 的两侧可能根本不在一个分片，只能跨节点拉数据，网络开销与延迟都往上走。另外要分清复制格式，ROW 格式下从库回放的是行变更事件，主库一条 JOIN 更新可能放大成大量行事件；STATEMENT 格式下从库要重放同一条 JOIN 语句，缺索引就会回放变慢，把主从延迟越拉越大。

## 应用层怎么拆：冗余字段、宽表、两次查询组装

三种做法各有适用面，选错场景会比原生 JOIN 更贵：

| 做法 | 怎么落地 | 适合的场景 | 主要代价 |
| --- | --- | --- | --- |
| 冗余字段（适度反范式） | 在主表直接存下高频关联字段，比如用户昵称、订单状态名 | 关联字段稳定、读多写少的维度 | 写入时要多维护一份数据，必须保证一致 |
| 宽表 | 面向查询场景预先构建宽表，数仓的星型模型、维度建模就是这个思路 | 列表页、报表、离线或准实时分析 | 构建与回刷成本高，字段冗余多 |
| 两次查询加应用层组装 | 先查主表拿到 id，再按 id 批量查关联表，最后在内存里拼装 | 主表结果集小、关联表可能已分片 | 多一次网络往返，要分批，防 N+1 |

第三种做法在社区里就叫 DataLoader：GraphQL 生态的 java-dataloader、Netflix DGS 都是这个模式，把同一轮请求里的 N 个 id 攒起来一次批量查回，再把结果分发回去。MyBatis-Plus 侧对应的是批量查询与批量操作能力，思路一致，但分批大小要自己控制，别一次 `IN` 几万个 id。

## 反范式的代价必须说清

冗余字段带来的是**一致性问题**：关联表改了，主表存的那份副本要跟着更新，漏一次就是脏数据。工程上的兜底有两条路，用定时任务对账（定期扫差异、补数据）或者走消息做最终一致（关联表变更后发事件，主表异步更新，接受短暂不一致）。

这也是为什么冗余只该加在真正读得极多的维度上，而不是把所有关联字段都搬过来——每多一个冗余字段，就多一条要对账的链路。

## 不是所有 JOIN 都要拆

一刀切地禁止 JOIN 是误读。小表关联小表、单表只有几千行的配置表或字典表，JOIN 完全没问题，拆开反而多出几次往返。拆 JOIN 本身也有成本，网络往返变多、应用层内存占用变大、组装与分页逻辑都要自己写，拆得不好比原生的 JOIN 更慢。

判断要不要拆，看四个维度：单表行数、连接列有没有索引、是否已经或将要分片、是否需要深分页。

## 常见追问

**Q：那 JOIN 到底还能不能用？**
A：能用，而且该用。要避开的是「大表 + 分片 + 高并发」下的跨节点关联，不是语法本身；单库小表的关联，写 JOIN 比手写两次查询更清晰也更快。

**Q：中间件不是能自动做跨库 JOIN 吗？**
A：中间件能做的是同分片键的关联（绑定表），多张表按同一套分片规则路由，JOIN 还能在每个分片内部各自完成；真要跨实例关联，只能把数据拉到内存归并或走联邦查询，网络与内存代价都在，规模一大就不受控。

**Q：直接上检索集群或者宽表不就行了？**
A：那是把关联成本前移到写入侧。检索集群要维护索引同步与一致性，宽表要维护构建与回刷，读确实变快了，但写链路复杂了；只有读远多于写、且查询模式稳定的场景才划算。

## 易错点

- **把「不推荐 JOIN」当成「JOIN 性能差」**。JOIN 在有索引、结果集小时非常高效，慢的从来不是语法，而是驱动表选错、连接列没索引、结果集被放大。
- **以为跨库 JOIN 一定报错**。同实例跨 schema 的 JOIN 是能跑的，硬墙在跨实例；但即便能跑，它绕过分片键路由、把多个库的数据汇到一处，规模上来就不可控。
- **以为拆 JOIN 是免费的**。拆完多出网络往返、内存组装、分批与分页逻辑，很容易拆出 N+1；先确认连接列有没有索引，再决定拆不拆。
- **以为反范式只是加个字段**。每加一个冗余字段就多一条一致性链路，没有对账或最终一致兜底，脏数据的代价远高于一次慢查询。

## 一句话记住

:::tip
JOIN 不是原罪，跨实例 JOIN 才是；拆到应用层的代价是一致性。
:::
