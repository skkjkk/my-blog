「无响应」是**症状**，根因可能落在**网络层、容器层、业务代码、存储层**任何一环，所以第一步不是猜，而是把请求链路切开、确认它卡在哪一层。最常见的两种形态是：服务端线程堆在**等客户端把请求体发完**，以及 **Tomcat 线程池或连接池被打满**，让新请求在队列里排队，看上去就像服务端没反应。

## 先确认「无响应」的四种形态

同样是"没反应"，四种形态指向完全不同的原因：

- **一直挂起直到超时**：最常见，链路里某一方在等对方。
- **立刻返回 5xx**：请求已经进到服务端，多半是业务异常或线程池拒绝。
- **返回 200 但响应体为空**：请求走完了，问题在业务逻辑或序列化。
- **连接被重置**：更可能是网关、负载均衡或防火墙主动断开。

最典型的"无响应"是**客户端与服务端都在等对方**：客户端等响应，服务端等剩余请求体，谁都不超时，连接就这么挂着。所以先问清楚是"一直转圈"还是"直接报错"，能把怀疑范围砍掉一半。

## 按链路逐段定位，先用 curl 绕开网关

上传请求的链路是固定的，排查就是一段一段缩小范围：

```
客户端 → 网关 / LB → Web 容器（Tomcat）→ 业务代码 → 存储（S3 / OSS / DB）
```

第一刀切在网关和服务端之间：**用 `curl -v` 直连后端服务（绕过网关）**。能正常响应，说明问题在网关或负载均衡；照样卡住，问题就在服务端，接着看线程栈。顺手盯住 `curl -v` 里的 `Content-Length` 和实际发出的字节数，两者对不上就是请求体没发完。

## 最有效的一步：用 jstack 看线程卡在哪一行

上传接口无响应时，线程栈会直接告诉你卡在哪：

```
jstack <pid>
jcmd <pid> Thread.print
```

- 停在 **`SocketInputStream.socketRead0` / `readBytes`**：正在等客户端数据，客户端没发完或网络中断。
- 停在 **`FileInputStream.read` / `FileChannel.read`**：正在读本地磁盘，撞上了磁盘 IO 瓶颈。
- 停在 **`Object.wait` / `park`**：在等锁或等队列。
- 停在 **`Http11Processor` / `ReadListener`**：在等请求体传输完成。
- 停在 **HTTP 客户端调用**（`HttpClient`、`OkHttp`、`RestTemplate`）：在等下游对象存储响应，这是**上传接口最常见的卡点**。

连续抓两三次栈，如果同一批线程都停在同一个方法上，卡点就确定了，不用再猜。面试里能直接说出"看线程栈卡在哪一行"的人，通常是真动手排过障的。

## 头号原因：请求体没传完

大文件上传时，如果中间的代理或网关有请求体大小限制，或者客户端在传输中断开，服务端会**一直等剩余的请求体**。表现出来就是：客户端上传到一半停住、服务端线程停在读 socket、连接不释放。

验证有三条：用 `curl -v` 对比 `Content-Length` 与实际发送量；检查网关的请求体限制（Nginx 的 `client_max_body_size`、LB 限制、WAF）；确认服务端是否收到了完整的 `Content-Length` 字节数。三项都正常还卡，才轮到怀疑业务代码。

## 接着查容器、业务线程池和连接池

这是"无响应"里最常见的配置原因，按三层往下看：

- **Tomcat `maxThreads`**：线程池打满后新请求只能排队，表现就是无响应。看 `catalina.out` 或 JMX 里的 `currentThreadsBusy`。
- **Tomcat `maxConnections` / `acceptCount`**：连接数打满，新连接卡在 accept 队列里等待。
- **Tomcat `connectionTimeout` / `maxKeepAliveRequests`**：超时与长连接配置不当，同样会造成挂起。
- **业务线程池**：请求在业务池队列里排队，必须看 `activeCount`、`queue.size` 和拒绝次数。
- **数据库连接池**：HikariCP 的 `pending` 持续不为 0，说明请求在等连接，这是上传后写 DB 时的经典卡点。

## 下游对象存储和数据库是隐形卡点

上传通常要写**对象存储（S3 / OSS / MinIO）**或**数据库 BLOB**，这两处最容易被漏掉：

- 对象存储客户端**超时没设或设得过大**、**连接池耗尽**、以及**在同步调用里直接上传**，都会让请求线程一直挂着。
- 数据库 BLOB 写入会让**事务变长、锁持有时间变长**，进而出现行锁等待，大对象还可能撑爆 `max_allowed_packet`。
- 下游被限流时（例如 S3 返回 `503 SlowDown`），客户端若没有重试上限，请求会一直耗在里面。

判断方法很直接：线程栈停在 HTTP 客户端调用上，就去量这一段下游调用的耗时，而不是继续在业务代码里翻。

## 从根因到处理方案

先分清**同步**与**异步**：同步上传让请求线程一直等到文件写完，长耗时、占资源、易超时；异步上传先把文件收到临时位置或直传对象存储，立刻返回 `taskId`，后续处理交给后台任务或消息队列，前端凭 `taskId` 轮询或订阅进度。大文件上传基本都该走异步，这一条同时解决了"无响应"和大文件长期占用连接、线程的问题。

| 根因 | 处理方案 |
|---|---|
| 请求体没传完 | 调大网关 `client_max_body_size`；检查客户端；改用分片上传 + 断点续传 |
| 线程池 / 连接池打满 | 调大线程数与队列；接口级限流；上传与普通业务分离线程池 |
| 同步上传耗时过长 | 改异步：先落临时目录或直传对象存储，返回 `taskId` |
| 对象存储同步调用阻塞 | 前端拿签名直传 OSS / S3，绕过业务服务器；设置合理超时 |
| 大 BLOB 存数据库 | 改存对象存储，DB 只存 URL 和元数据 |
| 磁盘 IO 瓶颈 | 临时目录用独立磁盘或挂载点；流式写盘；限制并发上传数 |
| 单文件过大 | 分片上传 + 断点续传 + 秒传（hash 去重） |
| 内存被占满 | 调大堆；用 `maxFileSize` / `maxRequestSize` 限制；流式处理避免全量读入内存 |

### 预防性设计比事后救火重要

- **限制大小**：`spring.servlet.multipart.max-file-size` / `max-request-size`，在入口就拒绝超大文件，而不是让它进来耗尽资源。
- **流式处理**：用 `MultipartFile.getInputStream()` 流式转发到对象存储，不要 `getBytes()` 全量读进内存。
- **上传与普通接口隔离**：独立线程池 + 独立连接池，避免大文件上传拖垮整个应用。
- **超时与熔断**：对下游设置明确超时，失败快速返回而不是挂起。
- **优雅降级**：队列满时明确返回"繁忙，请稍后"，而不是让请求无限等待。
- **监控告警**：上传接口的 P99 延迟、失败率、队列长度、磁盘使用率都要上看板。

### 照做即可的排查顺序

1. 用 `curl -v` 直连后端、绕开网关，先分清是网关问题还是服务端问题。
2. 用 `jstack` 看线程卡在哪一行：读 socket、读文件、等锁，还是等下游调用。
3. 看容器线程数、业务线程池的 active / queue、连接池的 pending。
4. 确认请求体是否传完，对比 `Content-Length` 与实际收到的字节数。
5. 看下游对象存储和 DB 的耗时与错误。
6. 定位后按上表处理，再补上入口限流、异步化与隔离。

## 常见追问

**Q：线程栈停在 `socketRead0`，就一定是客户端的问题吗？**
A：不一定。可能是客户端没发完或网络中断，也可能是中间代理先截断了请求体但连接没关，服务端还在等剩余字节。先比 `Content-Length` 和实收字节数，再查网关的请求体限制。

**Q：为什么前端直传对象存储能绕开这个卡点？**
A：业务服务器只负责签发上传凭证，文件流不经过应用线程，既不占 Tomcat 线程，也不吃应用带宽和内存。代价是要处理凭证有效期、上传回调校验和失败补偿。

**Q：分片上传到底解决了什么？**
A：单片体积小，一次请求不再是"要么全部成功、要么一直挂住"的长事务；中断只影响一片，可以续传，也给限流和并发控制留了抓手。

**Q：文件其实传上去了，接口还是超时，为什么？**
A：请求体已经收完，卡点挪到了下游，同步写对象存储或数据库 BLOB 时没设超时。把落库动作从请求线程里挪走（先返回 `taskId`）最稳。

## 易错点

- **只调大线程池**：上传是长耗时请求，线程池调得再大也会被大文件占满，正确做法是限大小、限并发、异步化，把长任务从请求线程里挪出去。
- **把 `socketRead0` 当成服务端卡死**：那只是线程在等数据，服务端没死；直接重启服务反而清掉了现场，先留一份线程栈。
- **用 `getBytes()` 读整个文件再上传**：小文件测不出问题，大文件直接 OOM，必须流式转发。
- **大 BLOB 直接存数据库**：事务变长、行锁等待、容易撞上 `max_allowed_packet`，应改为对象存储加 DB 存 URL。

## 一句话记住

:::tip
无响应先分清形态，再 jstack 看线程卡在哪一行，最后异步化加隔离。
:::
