"无响应"是**症状**，根因可能在**网络层、容器层、业务代码、存储层**任何一环。排查的关键是**先确定请求卡在哪一层**，而不是猜。

1) **第一步：确认"无响应"的真实形态**。是**一直挂起直到超时**（最常见）？还是**立刻返回 5xx**？还是**返回 200 但响应体为空**？还是**连接被重置**？**这四种指向完全不同的原因。** 最典型的"无响应"是 **客户端与服务端都在等对方**。

2) **第二步：分层定位卡点**
```
客户端 → 网关/LB → Web容器(Tomcat) → 业务代码 → 存储(S3/OSS/DB)
```
逐段验证：**用 `curl -v` 直连后端服务（绕过网关）** → 能否响应？→ 若能，问题在网关/LB；若不能，看服务端此时线程在干什么。

3) **第三步：看服务端的线程栈（最有效的一步）** ⭐
`jstack <pid>` 或 `jcmd <pid> Thread.print`。**上传接口无响应时，线程栈会直接告诉你卡在哪**：
- 线程停在 **`SocketInputStream.socketRead0`** / **`readBytes`** → **正在等客户端数据**（客户端没发完，或网络中断）
- 线程停在 **`FileInputStream.read`** / **`FileChannel.read`** → **正在读本地磁盘**（磁盘 IO 瓶颈）
- 线程停在 **`Object.wait` / `park`** → **在等锁或等队列**
- 线程停在 **`Http11Processor` / `ReadListener`** → **在等请求体传输完成**
- 线程停在 **HTTP 客户端调用**（`HttpClient`、`OkHttp`、`RestTemplate`）→ **在等下游（对象存储）响应** ← ⭐ **上传接口最常见的卡点**

4) **第四步：看请求是否"传完了"** ⭐⭐ **上传无响应的头号原因：请求体没传完**
大文件上传时，如果**中间有代理/网关有请求体大小限制**、或**客户端在传输中断开**，服务端会**一直等待剩余的请求体**。表现就是：**客户端上传到 50% 卡住、服务端线程停在读 socket、连接不释放**。
**验证**：`curl -v` 观察 `Content-Length` 与实际发送量；检查网关（Nginx `client_max_body_size`、LB 限制、WAF）；看服务端是否收到了**完整的 `Content-Length`**。

5) **第五步：看容器与连接池配置**（这是"无响应"最常见的配置原因）
- **Tomcat `maxThreads`** —— 线程池被打满 → **新请求在队列里排队，表现就是无响应**。检查 `catalina.out` 或 JMX 的 `currentThreadsBusy`。
- **Tomcat `maxConnections` / `acceptCount`** —— 连接数打满，新连接进 accept 队列等待。
- **Tomcat `connectionTimeout` / `maxKeepAliveRequests`** —— 超时配置不当。
- **业务线程池打满** → **请求在业务线程池队列里排队**。**必须检查线程池的 `activeCount`、`queue.size`、拒绝次数**。
- **数据库连接池打满**（HikariCP `pending`）→ 请求在等连接。**这是上传后写 DB 时的经典卡点。**

6) **第六步：看下游依赖**
上传通常要写**对象存储（S3/OSS/MinIO）**或**数据库（BLOB）**。检查：
- **对象存储客户端的超时是否合理**、**连接池是否耗尽**、**上传是否在同步调用里做**
- **数据库 BLOB 写入**：大 BLOB 会让**事务变长、锁持有时间变长、行锁等待**，甚至撑爆 `max_allowed_packet`
- **下游是否被限流**（S3 的 503 SlowDown、限流配额）

7) **第七步：区分"同步上传"与"异步上传"** ⭐
**同步**：请求线程一直等到文件写完 → **长耗时、高资源占用、易超时**。
**异步**（推荐）：**先接收文件到临时位置，立即返回**，由后台任务或消息队列完成后续处理。
> **大文件上传应一律走异步** —— 前端拿到 `taskId` 轮询或用 WebSocket 接收进度。**这既解决"无响应"，也解决大文件占用连接与线程的问题。**

8) **处理方案：从根因到优化**

| 根因 | 处理方案 |
|---|---|
| **请求体没传完** | 调大网关 `client_max_body_size`；检查客户端；**改用分片上传 + 断点续传** |
| **线程池/连接池打满** | 调大线程数与队列；**接口级限流**（避免大文件上传挤占普通请求）；**上传与普通业务分离线程池** |
| **同步上传耗时过长** | ⭐ **改异步**：先落临时目录/直传对象存储，返回 `taskId` |
| **对象存储同步调用阻塞** | 直传（前端拿签名直传 OSS/S3，**绕过业务服务器**）；设置合理超时 |
| **大 BLOB 存数据库** | **改为存对象存储，DB 只存 URL/元数据** |
| **磁盘 IO 瓶颈** | 写临时目录用**独立磁盘/挂载点**；**流式写盘**（不要全读进内存）；限制并发上传数 |
| **单文件过大** | **分片上传** + 断点续传 + 秒传（hash 去重） |
| **内存被占满** | 调大堆；用 `maxFileSize`/`maxRequestSize` 限制；**流式处理避免全量读入内存** |

9) **⭐ 预防性设计（比事后救火更重要）**
- **限制大小**：`spring.servlet.multipart.max-file-size` / `max-request-size`，**在入口就拒绝超大文件**，而不是让它进来耗尽资源
- **流式处理**：用 `MultipartFile.getInputStream()` **流式转发**到对象存储，**不要 `getBytes()` 全量读进内存**（大文件直接 OOM）
- **上传与普通接口隔离**：**独立线程池 + 独立连接池**，避免大文件上传**拖垮整个应用**
- **超时与熔断**：对下游设置明确超时；失败快速返回而非挂起
- **优雅降级**：上传队列满时**明确返回"繁忙，请稍后"**，而不是让请求无限等待
- **监控告警**：上传接口的 **P99 延迟、失败率、队列长度、磁盘使用率**都要看板

10) **排查流程（可直接照做）**
```
① curl -v 直连后端（绕网关）→ 区分是网关问题还是服务端问题
② jstack 看线程卡在哪一行（socketRead? 文件读? 下游调用? 锁等待?）
③ 看容器线程数、业务线程池 active/queue、连接池 pending
④ 确认请求体是否传完（Content-Length vs 实际发送）
⑤ 看下游对象存储/DB 的耗时与错误
⑥ 定位后按上表处理，并补上入口限流 + 异步化 + 隔离
```

11) **面试答法建议**。四点：**① 先分清"无响应"的形态与分层定位（curl 直连绕网关 + jstack 看线程卡点）；② 头号原因是"请求体没传完 + 线程池/连接池打满"，用 jstack 的 `socketRead0`/业务池队列/连接池 pending 佐证；③ 处理方案以"异步化 + 直传对象存储 + 入口限流 + 流式处理 + 线程池隔离"为主线；④ 预防设计（入口限制大小、流式避免 OOM、上传与普通接口隔离、超时熔断）。** 第二点能说出"看线程栈卡在哪一行"是最能体现排障经验的。
