短期记忆就是**当前任务内**模型需要记住的信息，它的载体是上下文窗口，所以所有设计最后都归结成一个问题：**有限的窗口如何装下该装的东西**。工程上不会只靠一招，而是几层叠加：窗口内用截断、摘要、结构化抽取、按重要性保留来控制增量；窗口外用外部存储加可寻址引用做无损回退；长内容在工具边界就裁剪掉；最后再用 token 配额、位置摆放和子 Agent 隔离兜住风险。

## 短期记忆的载体就是上下文窗口

短期记忆和长期记忆的分界线是「任务内」还是「跨任务」：会话结束就该忘的，放窗口里；要跨越会话留存的，才轮到向量库、档案库这类长期记忆。所以短期记忆没有独立的存储介质，它就是这一次请求里拼给模型的那串 token。

最朴素的形态就是消息列表：系统提示、历史消息、当前输入按顺序拼成一个请求。它的问题在于**只增不减**——每一轮的工具返回、检索片段、历史轨迹都会沉淀在里面，几轮之后就把窗口撑爆。因此短期记忆的核心矛盾不是「模型记不住」，而是「窗口装不下」，所有机制都是在窗口这条硬边界上做取舍。

## 窗口内的四类腾挪手段

窗口内能做的只有两件事：丢掉一部分，或者把留下来的压小。四种常见做法各有明确的代价边界。

### 滑动窗口截断

只保留最近 N 轮。优点是实现最简单、零成本、延迟最低；缺点是**硬性丢失早期信息**，而早期往往装着原始目标与硬约束，这正是目标漂移的直接来源——模型不是忘了怎么做，而是忘了为什么要做、不能做什么。改进办法是把「锚点」设为**永不参与截断**：系统提示、最初的目标陈述、最近一次的目标重申。

### 摘要压缩

用一个模型调用把旧消息压成摘要。优点是能保留语义要点、压缩比高；缺点是**有损且不可验证**：精确数值、ID、否定约束最容易在摘要里蒸发，多次压缩还会出现「摘要的摘要」，误差逐级累积，而且摘要本身要花额外的钱和延迟。改进办法是用**结构化摘要**，固定字段为已确认事实、已排除方案、关键参数、未决事项、硬约束，并保留原文指针以便回溯。

### 结构化抽取

只保留特定类型的信息：实体与属性、工具调用及其结果摘要、决策点、约束清单、错误记录，其余全部丢弃。优点是精准命中决策所需的信息，噪声小；缺点是抽取规则要按场景设计，通用性差，换个业务就得重写。

### 按重要性差异化保留

给消息打重要性分数，判断依据是三条信号：是否含约束、是否被后续引用、是否与失败相关。低分的压缩、高分的原样保留。它比统一截断或统一摘要都更优，因为压掉的恰好是低价值部分；代价是打分本身有成本，也存在误判风险，一旦把关键约束判成低分，后果和硬截断一样。

| 手段 | 省窗口 | 信息损失 | 额外成本 | 主要风险 |
| --- | --- | --- | --- | --- |
| 滑动窗口截断 | 大 | 硬性丢失且不可恢复 | 几乎为零 | 早期目标与硬约束被截掉，目标漂移 |
| 摘要压缩 | 大 | 有损且不可验证 | 每次摘要一次模型调用 | 精确值、ID、否定约束蒸发，误差累积 |
| 结构化抽取 | 中 | 只保留预设类型 | 抽取调用或规则开发 | 通用性差，换场景要重写 |
| 重要性打分 | 中 | 低分内容被压掉 | 打分本身有开销 | 误判会把关键约束一起压掉 |
| 外部化加引用 | 最大 | 无损 | 存储与检索链路 | 依赖回读决策，链路故障即失忆 |

## 外部化引用与工具边界裁剪：把膨胀挡在窗口之外

**外部化加引用**是把完整内容（长文档、大工具返回、历史轨迹）存到外部存储，上下文里只放**摘要加可寻址引用**——文件路径、记录 id、行号范围，需要时再回读。优点是无损、不占窗口、支持随机访问。缺点是引入了对检索的依赖，而且「什么时候该回读」本身就是一个决策问题，判断错了等于信息丢失。尽管有这层依赖，它仍是**生产环境最稳的形态**，因为它把「记不住」从不可逆的丢失变成了可再取的回退。

### 工具结果在工具边界就裁剪

这是短期记忆里**收益最高、成本最低**的一层。长日志、大段 HTML、原始数据、整份文档，在**进入上下文之前**就剥离标签、去重、只返回相关片段与计数。**不要等它进了上下文再压缩**——那时它已经吃掉预算、挤走了别的内容，还白付了一遍 token 和时间。

## 预算配额、位置效应与并行隔离

### 组装时给每类内容设 token 配额

设定每类内容的配额：工具结果最多占多少、检索内容最多占多少、历史轨迹最多占多少，超出按优先级裁剪。**没有配额就一定会失控**，因为每个环节单独看都倾向于「多塞一点更保险」，叠加起来就爆窗。配额的意义是把取舍从「最后谁先撞墙」变成「提前按重要性分配」。

```js
// 组装一次请求：先裁剪，再按配额填，锚点永远保留
function buildContext({ anchors, toolResults, retrieved, history, budget }) {
	return [
		...anchors,                                     // 系统提示、最初目标、最近一次目标重申
		...trimToolResults(toolResults, budget.tool),    // 已在工具边界裁剪，这里只兜底
		...trimByPriority(retrieved, budget.retrieved),  // 检索片段按相关度截断
		...summarizeIfNeeded(history, budget.history),   // 超配额时压成结构化摘要
	].flat();
}
```

### 高价值内容放在两头

长上下文中**中间部分的信息容易被忽略**，也就是常说的 lost in the middle，所以高价值内容应当放在提示的**靠前或靠后**位置：系统提示与最初目标在前，当前约束与本次要办的事在后，中间留给体量大、密度低的历史轨迹。

### 并行任务不要堆进主上下文

并行子任务各自的结果**不应全部堆进主上下文**，应当用**子 Agent 隔离**（各自上下文、只回结论），或者写入**共享黑板**（主上下文只留索引与摘要）。这是短期记忆设计里最容易被忽视、收益却极大的一条：它省的不只是 token，还有主上下文被无关细节污染之后的决策质量。

## 面试常见追问

**Q：为什么不直接换一个更大窗口的模型来解决？**
A：窗口变大只是把撞墙的时间往后推。成本和延迟会同步上升，长上下文里中间信息被忽略的问题也照旧存在；配额、裁剪、外部化这些手段在任何窗口尺寸下都得做，只是紧急程度不同。

**Q：滑动窗口截断和摘要压缩，实际项目里怎么选？**
A：看早期信息值不值钱。任务短、目标稳定，直接截断最省；任务长且早期含目标与硬约束，就必须加锚点，或者改用结构化摘要、外部化，否则一定目标漂移。

**Q：外部化以后只留引用，模型怎么知道该回读哪一段？**
A：引用的摘要要写得足够具体，比如文件路径、记录 id、行号范围，再补一句这段里有什么，让模型一眼判断值不值得读。回读最好做成一个可调用的工具，由模型显式决定何时取，而不是让主流程固定去读。

**Q：这些手段是选一个还是叠加用？**
A：叠加。常规组合是：工具边界先裁掉体积大头，再给各类内容定配额，历史超配额时用结构化摘要压，关键原文外部化挂指针，锚点永远豁免于任何裁剪。

## 易错点：把有损操作当成无损

- **把截断当成无损操作。** 截掉的那段不会自己回来，早期目标与硬约束一丢就是目标漂移，所以锚点必须永不参与截断。
- **等长内容进了上下文再压缩。** 那时已经付过 token 和延迟，正确做法是在工具边界就剥离标签、去重、只返回相关片段与计数。
- **以为摘要能替代原文。** 摘要是有损且不可验证的，精确数值、ID、否定约束最容易丢，必须保留原文指针以便回溯。
- **只调窗口大小，不设配额。** 窗口再大也会被填满，没有配额时每个环节都会多塞一点，最后仍是被动撞墙。

## 一句话记住

:::tip
本质是有损压缩＋外部化回退，关键不在压得多狠，而在该留的绝不丢且可回溯。
:::
