自增主键的上限不来自 `AUTO_INCREMENT` 这个机制，而来自**主键列的数据类型**：`INT UNSIGNED` 只有约 42.9 亿，`BIGINT UNSIGNED` 才是 **18446744073709551615**（约 1844 亿亿），到顶之后再 `INSERT` 会直接报主键冲突（`Duplicate entry ... for key 'PRIMARY'`），不会静默续写。但真实业务几乎撞不到 BIGINT 的上限，**更常见、更需要提前设计的是分库分表之后的主键冲突**，以及「建表时把主键类型选窄了」这个真正的高频事故。

## 上限由列类型决定，先算清四个上限

`AUTO_INCREMENT` 只是一个计数器，它能长到多大，取决于主键列的**数据类型**。建表时把主键写窄，就是给未来埋一个上限：

| 主键类型 | 最大值 | 量级 |
| --- | --- | --- |
| `INT` | 2147483647 | 约 21.5 亿 |
| `INT UNSIGNED` | 4294967295 | 约 42.9 亿 |
| `BIGINT` | 9223372036854775807 | 约 922 亿亿 |
| `BIGINT UNSIGNED` | 18446744073709551615 | 约 1844 亿亿 |

- **有符号 `BIGINT` 的上限只有无符号的一半**，存量大表里很多早已用掉大半，新表**优先用 `BIGINT UNSIGNED`**
- **更早的瓶颈是 `INT UNSIGNED`**：每天写入一千万行的话，42.9 亿个 ID 约 **429 天**用完，一年多就撞墙
- 所以面试里更要紧的判断不是「够不够」，而是**「当初为什么选了 `INT`」** —— 类型选窄才是真实事故的起点

## 自增主键的性能价值：顺序追加几乎不页分裂

自增主键**顺序递增 → 新行永远追加到 B+ 树最右侧 → 页分裂少、几乎无碎片**，空间利用率与缓存命中率都最好。**这是自增主键最大的价值，也是它至今仍是默认选择的原因** —— 它不只是「方便」，而是对聚簇索引最友好的写入模式。

:::tip
雪花算法虽然唯一，但低位是机器号 + 序列号，严格来说不是纯顺序：**趋势递增，页分裂略多于自增，但远好于纯随机 UUID**。要极致顺序，还可以在应用层生成有序 UUID。
:::

## 真正的现实风险：分库分表后的主键冲突

这比「用完」更常见。分库分表时若每张表都从 1 开始自增，必然冲突，常见解法有四种：

- **雪花算法（Snowflake）**：时间戳 + 机器号 + 序列号拼成 64 位 ID，**趋势递增、全局唯一**，是主流方案
- **号段模式**：发号器一次批量分配一段 ID（美团 Leaf 的做法），**性能最好**，数据库压力小
- **Redis `INCR`**：实现简单，但有单点与持久化风险
- **UUID**：**不推荐做聚簇索引主键** —— 无序导致**页分裂**、**索引膨胀**、空间浪费

## UUID 的坑：无序主键会撕裂 B+ 树

随机 UUID 作主键时，新行落在 B+ 树中间而不是尾部 → **页分裂严重、碎片化**，缓冲池命中率下降。表越大、写入越随机，这个代价越明显，而且它是**持续成本**，不是一次性的建表成本。

:::tip
正确做法是**让主键有序**：应用层生成有序 UUID（如 UUIDv7），或用 `UUID_TO_BIN(uuid, 1)` 把时间低位交换到前面；更常见的是直接用有序的 `BIGINT`（雪花算法）。
:::

## 主键快用完时怎么迁移

- **扩容主键类型**：`INT` → `BIGINT UNSIGNED`，大表用 **gh-ost / pt-online-schema-change** 做在线 DDL，避免长时间锁表
- **换成分布式 ID**：改用雪花算法或号段模式，**彻底摆脱单点计数器**
- **别指望 `ALGORITHM=INSTANT`**：MySQL 8.0 的 INSTANT 只覆盖加列这类元数据级操作，**改主键类型仍要重建表**

```sql
ALTER TABLE t_order MODIFY id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT;
```

## 另一个更隐蔽的「用完」：自增 ID 不连续

自增主键保证**唯一且单调递增**，但**不保证连续**（回滚、删除、插入冲突都会留下空洞）。

- **对外暴露自增 ID 会泄露业务量** —— 竞品拿两个订单号相减就能推断单量 → **对外用 UUID / 雪花，对内用自增**
- **拿自增 ID 当业务序号会出空洞** —— 工单号、流水号要求连续，就得用**专门的号段表**

## MySQL 8.0 的自增计数器持久化

MySQL 8.0 之前，自增计数器只存在内存中，**重启后按当前表的 `MAX(id) + 1` 重新初始化**：删过尾部数据再重启，自增值就会**回退、旧 ID 被重复使用**。MySQL 8.0 起，计数器变更随事务提交**持久化到 redo log**，重启后接着原来的值往下走，这个 ID 复用的老问题才算彻底解决。

:::tip
面试里主动说出「5.7 重启后自增值回退导致 ID 复用」，比背出 1844 亿亿这个数字更能证明你真的看过故障案例。
:::

## 面试怎么答

1. 上限认知：`AUTO_INCREMENT` 没有独立上限，上限是**列类型**的上限，`BIGINT UNSIGNED` 约 1844 亿亿，真实风险在分库分表的主键冲突
2. 解法：雪花算法 / 号段模式是主流，UUID 无序会页分裂，不适合做聚簇索引主键
3. 两个加分点：自增主键「顺序追加」的性能价值、MySQL 8.0 计数器持久化修掉了 5.7 重启自增值回退的老问题。第 3 点最能体现「踩过坑」的实战感

## 常见追问

**Q：既然会耗尽，为什么不用 UUID 做主键？**
A：UUID 唯一但随机，做主键等于把顺序写变成随机写，页分裂、碎片、索引膨胀都随之而来。要全局唯一又要顺序，就用雪花或 UUIDv7。

**Q：雪花算法有什么缺点？**
A：强依赖机器时钟，**时钟回拨**可能产生重复 ID（需要回拨检测或等待时钟追上）；机器号必须统一分配，否则同一毫秒同一个机器号会撞号。

**Q：自增 ID 会重复吗？**
A：正常不会重复，但**不保证连续**；8.0 之前重启还可能复用已删除的 ID，所以自增 ID 不能当业务凭证，也不要对外暴露。

**Q：分库分表之后还要不要自增？**
A：分片内可以继续自增，但全局唯一必须靠外部发号（雪花 / 号段 / Redis）。`auto_increment_increment` + `auto_increment_offset` 的步长法能撑双主或少量分片，分片一多就不好维护。

## 易错点

- **「自增主键就是 BIGINT UNSIGNED」**：错。`AUTO_INCREMENT` 与类型无关，`INT` 加自增仍是 21.5 亿上限，上限由列类型决定。
- **「5.7 主键用完重启会重置回 1」**：错。重启按 `MAX(id) + 1` 重新初始化，表现是**自增值回退、ID 复用**，不是回到 1。
- **「UUID 唯一所以适合做主键」**：唯一性和顺序性是两个要求，聚簇索引主键还要看写入是否顺序。
- **「加 `ALGORITHM=INSTANT` 就能在线改主键类型」**：INSTANT 覆盖不到改列类型，这类 DDL 仍要重建表，大表必须交给 gh-ost / pt-osc。

## 一句话记住

:::tip
自增的上限是列类型给的；真正要先设计的是分库分表后的全局唯一。
:::
