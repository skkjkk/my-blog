MySQL 的 `AUTO_INCREMENT` 计数器是**无符号 BIGINT（8 字节）**，最大值 **18446744073709551615**，用完之后 `INSERT` 会报 `Duplicate entry '0' for key 'PRIMARY'`。但**真实环境几乎碰不到这个上限**，真正需要提前规划的是"**主键用尽前的迁移方案**"和"**分库分表后主键冲突**"。

1) **⭐ 先看两个更容易踩的"伪上限"**
- **有符号 BIGINT 上限是 9223372036854775807**，只有**约 922 亿亿**，很多公司早已用掉大半 → **优先用 `BIGINT UNSIGNED`**
- **⚠️ 更早的瓶颈：`INT UNSIGNED` 只有约 42 亿**，单表自增主键在千万级/s 的写入下**一年多就可能耗尽**

2) **⭐ 真正的现实风险：分库分表的主键冲突**
这比"用完"更常见。分库分表时若每张表都从 1 开始自增，必然冲突。常见解法：
- **雪花算法（Snowflake）** —— 时间戳 + 机器号 + 序列号，**趋势递增、全局唯一**，是主流方案
- **号段模式** —— 发号器批量分配 ID 段（美团 Leaf），**性能最好**，数据库压力小
- **Redis `INCR`** —— 实现简单，但有单点与持久化风险
- **UUID** —— **不推荐做聚簇索引主键**：无序导致**页分裂**、**索引膨胀**、空间浪费

3) **⚠️ UUID 的坑（高频追问）**
随机 UUID 作主键 → 新行总是插到 B+ 树中间 → **页分裂严重、碎片化**、缓冲池命中率下降。
> **正确做法：用有序的 UUID（如 UUIDv7 / 时间有序 Snowflake）**，或用 **有序的 `BIGINT`（雪花算法）**。

4) **⭐ 主键用尽时的迁移方案**
- **扩容为主键类型**：改 `INT` → `BIGINT`（`ALTER TABLE ... MODIFY id BIGINT`），大表用 **gh-ost / pt-online-schema-change** 在线 DDL，避免锁表
- **换分布式 ID**：改用雪花算法 / 号段，**彻底摆脱单点计数器**
- **⚠️ MySQL 8.0 的 `ALTER TABLE ... ALGORITHM=INSTANT`** 只支持部分操作（如加列），**改主键类型仍需重建表**

5) **⭐ 另一个更隐蔽的"用完"：自增主键的"业务不连续"**
自增主键保证**唯一且单调递增**，但**不保证连续**（回滚、删除、插入冲突都会留下空洞）。
- ⚠️ **对外暴露自增 ID 会泄露业务量**（竞品可通过 ID 差推断订单量）→ **对外用 UUID/雪花，对内用自增**
- ⚠️ **依赖自增 ID 做业务序号（如工单号）会出空洞** → 需要连续编号要用**专门的号段表**

6) **⭐ 自增主键的性能代价（与 B+ 树的关系）**
自增主键**顺序递增 → 新行永远追加到 B+ 树最右侧 → 页分裂少、无碎片** → 空间利用率与缓存命中率都最好。**这是自增主键最大的价值。**
> **对比**：UUID / 雪花虽然唯一，但雪花有**低位随机**（机器号+序列号），严格来说不是纯顺序，页分裂略多于自增但远好于纯 UUID；需要极致顺序可用 **MySQL 8.0 的有序 UUID 替换方案**。

7) **MySQL 8.0 的自增主键持久化改进**
MySQL 8.0 起，自增计数器改为**每次事务提交时持久化到 redo log**，不再是"每条语句都写"。这解决了经典问题：**MySQL 5.7 中主键用尽后重启实例，计数器会被重置回 1 → 产生主键冲突**（因为计数器存在内存中且不持久）。
> **面试提到这个点会显得你关注过真实故障案例。**

8) **面试答法建议**。三点：**① 上限认知（BIGINT UNSIGNED 约 1844 亿亿，真实风险在分库分表的主键冲突）；② 解法（雪花算法 / 号段模式是主流，UUID 无序会页分裂不能用）；③ 两个加分点（自增主键"顺序追加"的性能价值、MySQL 8.0 计数器持久化修复了 5.7 重启计数器回退的老 bug）**。**第三点最能体现"踩过坑"的实战感。**
