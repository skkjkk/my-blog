深度分页指的是 `LIMIT offset, size` 中 **offset 极大**的场景（如第 50 万页）。它的核心问题是：**数据库必须先扫描并丢弃掉 offset 行，才能返回那 size 行** —— 扫了 50 万行只给你 10 行，白白浪费。

1) **为什么慢（本质原因）**
`LIMIT 1000000, 10` 的执行过程是：**从索引/数据页里读出前 1000010 行 → 逐行丢弃前 1000000 行 → 返回最后 10 行**。**成本与 offset 大小成正比，与返回行数无关。**

2) **⭐ 方案一：延迟关联（覆盖索引 + 二次回表）**
思路：**先在覆盖索引里扫出主键，再拿主键回表取数据** —— 因为丢弃主键比丢弃整行数据便宜得多。
```sql
SELECT t.* FROM order t
JOIN ( SELECT id FROM order ORDER BY id LIMIT 1000000, 10 ) x
ON t.id = x.id;
```
子查询走**覆盖索引**（只读索引不回表），只对最终 10 行做回表 → **扫描量从"100 万整行"降到"100 万个索引项 + 10 次回表"**。

3) **⭐ 方案二：游标方式（书签分页）—— 唯一真正 O(1) 的做法**
不记页码，**记上一页最后一条记录的排序值**，下一页从它往后取：
```sql
SELECT * FROM order WHERE id > 1000000 ORDER BY id LIMIT 10;
```
无论翻到第几页，**每次都只扫 10 行**，性能恒定。
> **代价：无法跳页**（用户点"第 500 页"时你无法直接定位）。**这是"无限滚动"列表页的正确姿势**；页码跳转场景仍需用方案一。

4) **方案三：业务侧改造**
- **搜索引擎**（Elasticsearch）做深度分页
- **二次查询法**：先查 id 列表（`LIMIT`），再用 `IN` 批量回表 —— 与延迟关联同源
- **数据量小的场景**：一次性把数据加载到应用内存/缓存（如 Redis ZSET），前端本地翻页

5) **⚠️ 前提：排序字段必须有索引且是稳定的**
- `ORDER BY` 字段**没索引** → 排序本身就是 filesort，延迟关联也救不了
- **排序字段不唯一**（如按 `create_time` 排序）→ **翻页时数据变动会导致重复/遗漏**，必须加唯一字段做 tie-breaker：`ORDER BY create_time, id`
- **必须走唯一索引或确定性的排序** → 否则优化器可能选错索引

6) **⚠️ 其他容易踩的坑**
- **`LIMIT` 不带 `ORDER BY`** → 结果集顺序不确定，**分页必然错乱**
- **深分页 + `count(*)`** → `SELECT COUNT(*) FROM ...` 每次都要扫全表，**比翻页本身还慢**；应改用"是否有下一页"的探测（`LIMIT 1 OFFSET n` 判断存在性）或维护计数表
- **`COUNT(*)` 在 InnoDB 上无法用索引统计**（MVCC 下行数不精确），这是 InnoDB 的固有代价

7) **优化效果对比（经验值）**
| 方案 | 扫描量 | 页码跳转 | 复杂度 |
|---|---|---|---|
| `LIMIT 1000000, 10` | 100 万行 + 10 次回表 | ✅ | 无 |
| **延迟关联** | 100 万索引项 + 10 次回表 | ✅ | 中 |
| **游标方式** | 10 行 | ❌ | 低 |

8) **面试答法建议**。三点：**① 本质是"扫了 offset 行只返回 size 行"，成本与 offset 成正比；② 两个核心方案（延迟关联用于可跳页、游标方式用于无限滚动且真正 O(1)）；③ 前提条件（排序字段有唯一索引、避免带 COUNT(*)、ORDER BY 必须确定性）**。**第二点的"游标 = 唯一 O(1)"最能体现对代价模型的判断。**
