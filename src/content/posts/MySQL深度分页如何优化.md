深度分页指的是 `LIMIT offset, size` 中 **offset 极大**的场景（如第 50 万页）。它的核心问题是：**数据库必须先扫描并丢弃掉 offset 行，才能返回那 size 行** —— 扫了 50 万行只给你 10 行，白白浪费。

## 为什么慢（本质原因）

`LIMIT 1000000, 10` 的执行过程是：**从索引/数据页里读出前 1000010 行 → 逐行丢弃前 1000000 行 → 返回最后 10 行**。**成本与 offset 大小成正比，与返回行数无关。**

## 方案一：延迟关联（覆盖索引 + 二次回表）

思路：**先在覆盖索引里扫出主键，再拿主键回表取数据** —— 因为丢弃主键比丢弃整行数据便宜得多。

```sql
SELECT t.* FROM order t
JOIN ( SELECT id FROM order ORDER BY id LIMIT 1000000, 10 ) x
ON t.id = x.id;
```

子查询走**覆盖索引**（只读索引不回表），只对最终 10 行做回表 → **扫描量从"100 万整行"降到"100 万个索引项 + 10 次回表"**。

## 方案二：游标方式（书签分页）—— 唯一真正 O(1) 的做法

不记页码，**记上一页最后一条记录的排序值**，下一页从它往后取：

```sql
SELECT * FROM order WHERE id > 1000000 ORDER BY id LIMIT 10;
```

无论翻到第几页，**每次都只扫 10 行**，性能恒定。

:::tip
**代价：无法跳页**（用户点"第 500 页"时你无法直接定位）。**这是"无限滚动"列表页的正确姿势**；页码跳转场景仍需用方案一。
:::

## 方案三：业务侧改造

- **搜索引擎**（Elasticsearch）做深度分页
- **二次查询法**：先查 id 列表（`LIMIT`），再用 `IN` 批量回表 —— 与延迟关联同源
- **数据量小的场景**：一次性把数据加载到应用内存/缓存（如 Redis ZSET），前端本地翻页

## 前提：排序字段必须有索引且是稳定的

- `ORDER BY` 字段**没索引** → 排序本身就是 filesort，延迟关联也救不了
- **排序字段不唯一**（如按 `create_time` 排序）→ **翻页时数据变动会导致重复/遗漏**，必须加唯一字段做 tie-breaker：`ORDER BY create_time, id`
- **必须走唯一索引或确定性的排序** → 否则优化器可能选错索引

## 易错点（直觉 vs 正确）

- **容易错的直觉**：`LIMIT` 不写 `ORDER BY` 也能分页，数据库总会给个固定顺序。**正确说法**：没有 `ORDER BY` 时结果集顺序不确定，同一句 SQL 两次执行都可能不同，分页必然重复或漏行，排序必须显式且确定性。
- **容易错的直觉**：深分页慢只是翻页慢，先把 `COUNT(*)` 总数查出来再分页没关系。**正确说法**：深分页下 `SELECT COUNT(*)` 每次都要扫全表或扫掉一大段索引，常常比翻页本身还慢；应改成"是否有下一页"的探测（`LIMIT 1 OFFSET n` 判断存在性），或单独维护计数表。
- **容易错的直觉**：`COUNT(*)` 在 InnoDB 上应该像 MyISAM 那样能 O(1) 直接报出行数。**正确说法**：MVCC 下每个事务可见的行集合不同，行数本来就不精确，InnoDB 没法维护一个直接可用的计数，只能扫一个较小的索引去数，这是 InnoDB 的固有代价。

## 优化效果对比（经验值）

| 方案 | 扫描量 | 页码跳转 | 复杂度 |
|---|---|---|---|
| `LIMIT 1000000, 10` | 100 万行 + 10 次回表 | ✅ | 无 |
| **延迟关联** | 100 万索引项 + 10 次回表 | ✅ | 中 |
| **游标方式** | 10 行 | ❌ | 低 |

表里比的是**量级和代价构成**，不是实测数字：延迟关联省掉的是"搬运整行数据"，游标方式省掉的是"扫描 offset 行"本身，所以它才是分页结构的改变而不只是句法的改写。

## 常见追问

**问：面试被问到这道题，按什么顺序答？**
**答：** 先说本质是"扫了 offset 行只返回 size 行"，成本与 offset 成正比；再讲两个核心方案（延迟关联用于可跳页、游标方式用于无限滚动且真正 O(1)）；最后补前提条件（排序字段有唯一索引、避免带 `COUNT(*)`、`ORDER BY` 必须确定性）。其中"游标 = 唯一 O(1)"最能体现对代价模型的判断。

**问：延迟关联照样要扫 100 万个索引项，凭什么算优化？**
**答：** 因为它扫的是覆盖索引里的主键，只读索引不回表：丢弃一个索引项比丢弃一整行数据便宜得多，而且只有最终 10 行才回表，代价的量级结构变了。

**问：为什么说游标方式是唯一真正 O(1) 的，它的代价是什么？**
**答：** 它把"第几页"换成"上一页最后一条记录的排序值"，每页都从这个值往后取 10 行，与页码无关；代价是无法跳页，用户点"第 500 页"时定位不到，所以它只适合无限滚动列表。

**问：排序字段不唯一会怎样，比如只按 `create_time` 排？**
**答：** 翻页期间数据有增删时，同一时间戳的多行在边界处先后顺序不稳定，会导致重复或遗漏，必须加唯一字段做 tie-breaker，写成 `ORDER BY create_time, id`。

## 一句话记住

:::tip
深分页的关键是少扫：能跳页用延迟关联，无限滚动用游标。
:::
