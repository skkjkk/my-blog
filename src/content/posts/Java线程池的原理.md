Java 线程池的原理可以拆成三条主线：用一个 `ctl` 变量同时记录运行状态和工作线程数；用一条四段式的降级规则决定任务是新建线程、进队列、扩线程还是被拒绝；用一组 `Worker` 反复从队列取任务、按 `keepAliveTime` 回收多余线程。所以它不是一个黑盒调度器，而是“状态机 + 有界队列 + 一群会自己找活干的线程”的组合，几乎所有参数配置的坑，都能在这三条主线上找到出处。

## 核心机制：一个 ctl 变量同时记录状态和线程数

线程池的状态判断和线程数增减，全部围绕一个 `AtomicInteger` 字段 `ctl` 展开：高位存运行状态，低位存工作线程数。这样打包的好处是状态与线程数永远被同时读到，不会出现“状态已经是 STOP、线程数还是旧值”的撕裂；所有修改都通过 CAS 完成，既保证并发安全，又省掉了争用激烈的锁。

对外它暴露 `runStateOf()` 与 `workerCountOf()` 两个取值方法，内部用 `compareAndSet` 一次性完成“校验 + 更新”，这正是它敢把两个维度压进一个变量的底气。

状态一共五个，只能单向推进：RUNNING 接新任务也处理队列；SHUTDOWN 不接新任务但继续处理队列；STOP 既不接新任务也不处理队列，并中断正在执行的任务；TIDYING 表示所有线程都已终止、准备执行 `terminated()` 回调；TERMINATED 表示回调执行完毕。进入 TIDYING 前必须先确认线程数为 0，这个“清空线程再收尾”的顺序，保证了终止回调看到的一定是一个干净的池。

## 任务提交是四段式降级

`execute()` 收到任务后按固定顺序判断，前一步不成立才走下一步：

1. 线程数小于 `corePoolSize`：直接新建一个核心线程，把这个任务当作它的第一个任务（`firstTask`）执行。
2. 核心线程已满：尝试 `workQueue.offer()` 入队，入队成功就交给空闲线程去取。
3. 入队失败（队列已满）：线程数小于 `maximumPoolSize` 时新建非核心线程来跑。
4. 仍放不下（已达最大线程数）：交给拒绝策略，默认的 `AbortPolicy` 直接抛 `RejectedExecutionException`。

| 顺序 | 判断条件 | 动作 | 相关参数 |
|---|---|---|---|
| 1 | 线程数 < corePoolSize | 新建核心线程，任务作为它的 firstTask | corePoolSize |
| 2 | 否则尝试入队 | offer 成功，等空闲线程来取 | workQueue 容量 |
| 3 | 入队失败（队列满） | 线程数 < maximumPoolSize 时新建非核心线程 | maximumPoolSize |
| 4 | 已达最大线程数 | 交给拒绝策略处理 | RejectedExecutionHandler |

记住这个顺序，就能解释大量“参数配了却不生效”的现象：任务走哪条路，取决于队列满没满，而不是线程数到没到顶。

## 为什么队列必须是有界的

上面第 3 步依赖“入队失败”，而队列一旦无界，`offer` 永远不会失败，于是“扩到最大线程数”这层保护完全失效，任务只会在队列里无限堆积，直到内存扛不住。**这也是线程池最容易被忽视的一条硬约束：无界队列等于关掉了 `maximumPoolSize`。**

有界队列的代价是拒绝会真的发生，所以队列容量和拒绝策略要一起配：容量决定积压能容忍多久，拒绝策略决定积压之后的兜底动作。想把队列当缓冲又不肯承担拒绝，本质上是在赌流量不会打满。

## 工作线程是一个 Worker 对象

每个 `Worker` 自身实现 `Runnable`，并且持有自己的第一个任务（`firstTask`）。线程启动后进入取任务循环：优先轮询工作队列，减少多个线程抢同一把锁的时间；队列为空时则阻塞等待新任务入队，而不是空转。

`Worker` 内部还借了一层 AQS（`AbstractQueuedSynchronizer`），用一个不可重入的锁标记“当前线程是否正在执行任务”。这层标记的用途在关闭时体现出来：`shutdown()` 只会中断空闲等待的线程，正在干活的线程要等任务跑完，避免任务被硬生生打断。

## 一份可以直接抄的构造代码

把构造参数从上往下读一遍，就能对上前面那条降级链：

```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    4,                                        // corePoolSize：常驻线程数
    8,                                        // maximumPoolSize：队列满后才用得上
    60L, TimeUnit.SECONDS,                    // keepAliveTime：非核心线程空闲多久退出
    new ArrayBlockingQueue<>(200),            // 有界队列：让“扩到最大线程数”这层真正生效
    r -> new Thread(r, "order-handler-" + r.hashCode()),
    new ThreadPoolExecutor.CallerRunsPolicy() // 拒绝时让提交线程自己跑，形成反压
);

pool.execute(() -> handleOrder());   // 异常会被抛出，可被 UncaughtExceptionHandler 捕获
pool.shutdown();                     // 不再接新任务，队列里的任务跑完再终止
```

要注意的是：`maximumPoolSize` 只有在队列满之后才有意义。所以“核心 4、最大 8、队列 200”这种配置的真实效果是，前 4 个任务直接起线程，接下来 200 个进队列排队，直到第 205 个任务才把线程扩到 8。

## 线程回收靠 keepAliveTime

线程在 `keepAliveTime` 内取不到任务就退出，工作线程数随之减一。退出时还会重新检查一遍：如果池仍在运行、且线程数低于应维持的底线，就补建一个线程把位置占回来，所以核心线程数可以自动维持，不需要调用方干预。

如果打开 `allowCoreThreadTimeOut(true)`，核心线程也会按同样的超时规则回收，适合波峰波谷差异明显的服务；代价是低谷过后要重新预热，第一波请求会多吃一点创建线程的延迟。

## 任务抛异常不会拖垮线程池

任务里抛出的异常会被 `runWorker` 捕获并继续向外抛，当前 `Worker` 以“突然完成”的方式退出，这个线程才真正结束；退出流程会补建一个新的 Worker 顶替它，池里其他线程照常服务，队列中剩余的任务也不会因此停摆。

所以结论是：异常不会拖垮整个池，但会丢掉这一条线程上的现场。这也是线程池里必须自己 try-catch、并给线程工厂配 `UncaughtExceptionHandler` 的原因；另外 `submit()` 提交的任务，异常被包在 `Future` 里，不调用 `get()` 就完全静默，是另一处常见盲区。

## 关闭有 shutdown 和 shutdownNow 两种语义

`shutdown()` 把状态改为 SHUTDOWN：不再接受新任务，但会把队列中已提交的任务跑完再终止，配合 JVM 关闭钩子就是标准的优雅停机。

`shutdownNow()` 直接把状态推到 STOP：尝试中断正在执行的任务，并把未执行的任务从队列里取出、返回给调用方，由调用方决定重投还是落库补偿。

两者的差别值得记牢：`shutdownNow()` 不保证任务不丢，也不保证线程立刻停下——不响应中断的任务照样跑完，返回给你的那批任务如果没人接，就等于被丢弃。

## 复用的线程会串号：ThreadLocal 必须 remove

线程池的线程会被复用，同一个线程可能先后处理属于不同请求的任务。若在任务里设置了 `ThreadLocal` 却没清理，下一个任务就会读到上一个请求的残留数据，造成数据串号，严重时甚至越权拿到别人的上下文。

**凡使用 `ThreadLocal`，必须在任务的 `finally` 中显式 `remove()`**，不要指望线程结束时自动清理——线程池里的线程根本不会结束。传递上下文更稳的做法是显式传参，或使用支持自动清理的上下文传递组件，而不是把 `ThreadLocal` 当全局变量用。

## 四个最容易踩的坑

- **以为线程数到 `maximumPoolSize` 才进队列**：顺序恰好相反，先占满核心线程，再进队列，队列满了才扩线程。
- **以为无界队列更“安全”**：它只会把拒绝推迟成 OOM，同时让 `maximumPoolSize` 彻底失效。
- **以为 `shutdownNow()` 一定停得下来**：它只是发中断信号，且会把队列任务取走返回，没人处理就是丢失。
- **以为 `submit()` 的异常会被打印**：异常封在 `Future` 里，不 `get()` 就静默；要暴露就得用 `execute()` 或统一在 `Future.get()` 处处理。

## 常见追问

**Q：核心线程满了为什么不直接扩到最大线程数，而是先进队列？**
A：入队几乎零成本，扩线程却要付栈空间和调度的代价，所以先攒进队列复用现有线程。但队列因此成了优先级更高的缓冲，队列容量和最大线程数必须一起调，否则扩容永远轮不到。

**Q：`maximumPoolSize` 设成 100，为什么线上线程一直只有 8 个？**
A：因为队列没满就不会触发扩容。用的要是无界队列，第 3 步永远不会发生，`maximumPoolSize` 形同虚设。

**Q：任务跑完了，线程池里的线程为什么不减少？**
A：核心线程默认不超时，用阻塞等待任务的方式常驻。要回收核心线程，得开 `allowCoreThreadTimeOut(true)`；非核心线程则按 `keepAliveTime` 自动回收。

**Q：为什么说线程池不能随便用 `Executors` 工厂方法？**
A：固定大小池配的是无界队列、缓存池允许线程数几乎无上限，两者都绕开了降级链里的保护，任务一堆积就是内存风险。生产上更稳妥的是手工构造 `ThreadPoolExecutor`，把队列和拒绝策略显式写出来。

## 一句话记住

:::tip
任务先占核心线程，再进队列，然后扩到最大线程数，最后才拒绝。
:::
