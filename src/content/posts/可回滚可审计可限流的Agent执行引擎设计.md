核心思路是把引擎做成**事件溯源加状态机**，而不是一条不断追加消息的对话循环。真相只存放在一个只追加、不修改的事件日志里，任务状态、上下文和产物都是事件日志物化出来的视图。这条约束一旦成立，可回滚、可审计、可限流三个目标就都能自然导出：回滚是从某个检查点重放事件重建状态再执行补偿，审计就是事件日志本身，限流是对事件推进速度施加的配额约束。

## 为什么是事件溯源而不是消息列表

最朴素的做法是把 Agent 跑成一个不断追加的 messages 数组：每一步把模型的输出压进数组，状态就隐含在数组的长度和内容里。这条路在演示阶段很省事，但一旦要上线就会同时暴露三个问题：

- **状态不可重建**。想知道「第三步时上下文里到底有什么」，只能反推当时的数组，而数组已经被后续步骤改写过。
- **副作用不可解释**。工具调用直接写进外部系统，中间崩了没有记录能说明哪一步已经生效、哪一步只是发出去还不知结果。
- **成本不可控**。没有独立的推进节奏，就没有加配额、限速、熔断的抓手。

事件溯源把「发生了什么」和「现在是什么状态」拆开：事件是不可变的事实，状态是可随时重算的缓存。工程上也顺带得到几个好处：事件日志可以直接当重放输入，物化视图坏了可以重建，检查点可以只存引用而不存全量快照。

## 核心模块与职责划分

模块划分的原则是**唯一写者、单一副作用出口、真相与视图分离**。下表是各模块的职责与其必须守住的边界：

| 模块 | 职责 | 必须守住的边界 |
| --- | --- | --- |
| 编排器 | 维护任务依赖图、决定下一步动作、触发重规划 | 状态转移的唯一写者，只通过发布事件推进状态 |
| 状态存储 | 持久化事件日志、物化视图、步骤版本号、检查点 | 只接收事件，不承载业务判断 |
| 上下文管理器 | 把状态渲染成模型可用的提示视图，管理 token 预算、摘要压缩、缓存命中 | 只产出视图，不持有真相 |
| 工具网关 | 参数校验、能力令牌校验、幂等键、重试、结果缓存、熔断 | 唯一允许产生外部副作用的模块 |
| 策略引擎 | 授权判定、审批流转、风险分级、数据脱敏 | 先判定再放行，判定结果自身也要落事件 |
| 预算守卫 | 按步骤数、token 数、金额和时间实时扣账 | 超限时触发降级或熔断，不静默放行 |
| 调度器 | 并发度、优先级、租户配额的公平调度 | 不参与任务语义，只决定谁先跑 |
| 沙箱执行器 | 承载不可信代码 | 越权访问一律拒绝，不做兜底放行 |
| 评估器 | 用程序化断言和独立评判做验收 | 结论要作为事件落盘，可复核 |
| 审计追踪 | 脱敏后的输入输出、路由决策、工具调用、校验结论、预算消耗、模型与提示版本一并落盘 | 只追加，不允许就地修改 |
| 补偿注册表 | 把每个不可逆的写操作与其补偿动作成对登记 | 登记发生在执行之前，不是失败之后补 |

几个容易混淆的分工要点：

- **编排器不做 IO，工具网关不做决策**。编排器只根据当前视图选下一步并发布意图事件，工具网关收到意图后负责校验、幂等与重试，把结果写成结果事件。这样「谁决定了什么」和「实际发生了什么」在日志里天然分开。
- **上下文管理器不保存状态**。它每次从状态存储读视图、按 token 预算做摘要压缩与缓存命中，产出一次性的提示；这样重放时上下文可以按同一规则重算，不会出现「当时的提示已经找不回来」。
- **评估器与编排器分开**。验收如果和决策是同一段代码，就等于自己给自己判卷，程序化断言加独立评判才构成一道外部关卡。

## 三层状态机制

状态按粒度分三层，各自只解决自己那一层的问题：

| 层级 | 状态取值 | 关注点 |
| --- | --- | --- |
| 任务层 | 待运行、运行中、已挂起、降级中、已完成、已失败、已取消、已超时 | 对外可见的生命周期，回滚本身也是一个状态 |
| 步骤层 | 待执行、执行中、成功、失败、跳过、已补偿 | 单步的推进与补偿是否完成 |
| 事件层 | 所有状态变化的原始记录 | 唯一真相，其余都是它的投影 |

回滚不是一个动作而是一个状态，流转为**回滚中到已回滚**，这样回滚过程本身也可被观察、被中断、被审计。

三层状态之外还有四条硬规则，破坏其中任何一条，整套设计都会出现对不上的状态：

1. 状态转移只能由编排器发起，工具网关只负责写事件，不做状态决策。
2. 每个步骤携带预期版本号做乐观并发控制，版本不匹配直接拒绝，防止重放导致重复副作用。
3. 每个有副作用的步骤必须先进入预备态再进入提交态，避免中途崩溃留下不一致。
4. 系统要周期性生成检查点，保存状态、上下文引用和产物指针，使恢复不必从头重放。

## 可回滚：补偿语义而不是撤销语义

外部系统往往不支持真正的分布式事务，所以回滚的真实含义是**执行一组反向的补偿动作，把系统推回一个语义上等价的状态**，而不是抹除历史。历史不该被抹除，事件日志里那次「已经发生的事」永远在，补偿只是在其后追加新的对立事件。

由此推出几个要求：

- 每个写操作必须在执行前就登记好它的补偿动作，登记动作属于预备态的一部分，执行失败也要登记，因为外部调用可能已经生效。
- 补偿动作本身必须幂等，因为补偿也可能失败重试，甚至可能在恢复时被执行两次。
- 回滚粒度可以是单个步骤、某个子图或者整个任务，粒度越小越好用，但补偿顺序必须按依赖的反向拓扑走。
- 数据面要配合做软删除和版本标记，让逻辑上的撤销有据可查，而不是物理删掉一条记录。

下面这段伪代码展示了预备、提交与补偿如何围绕幂等键和版本号组织：

```ts
async function runStep(step: Step, ctx: ExecCtx) {
  // 1. 乐观并发：版本不匹配直接拒绝，防重放
  if (step.expectedVersion !== ctx.currentVersion) {
    throw new VersionConflict(step.id);
  }

  // 2. 预备态：先登记补偿动作，再产生副作用
  const key = idempotencyKey(step.id, step.attempt);
  await ctx.compensation.register(step.id, step.compensate);

  const prepared = await ctx.gateway.call(step.tool, step.args, { key, phase: "prepare" });
  await ctx.events.append({ type: "step.prepared", stepId: step.id, prepared });

  // 3. 提交态：只有提交成功才认为这一步生效
  const committed = await ctx.gateway.call(step.tool, step.args, { key, phase: "commit" });
  await ctx.events.append({ type: "step.committed", stepId: step.id, committed });
  return committed;
}

// 回滚时按反向拓扑执行补偿，补偿自身幂等，重复执行无副作用
async function rollback(taskId: string) {
  for (const step of await ctx.compensation.reverseOrder(taskId)) {
    await step.compensate();
    await ctx.events.append({ type: "step.compensated", stepId: step.id });
  }
}
```

## 可审计：让审计成为一等公民

审计不是日志的副产物，而是和业务状态同等重要的数据。要做到「任何一次历史运行都能查清」，至少要满足三件事：

- 事件日志只追加，并用**前序哈希把事件串成链**，任何篡改都会在链上暴露。
- 落盘内容要包含**决策依据而不只是结果**：为什么选了某个工具、为什么走了降级、为什么判定任务完成。只记录结果，事后只能看到「它这么做了」，解释不了「它为什么这么做」。
- 审计存储与业务数据分离，并按敏感级别分视图，不同角色只能看到各自有权查看的字段，脱敏在写入审计的那一刻发生，而不是查询时临时处理。

再加上可重放这一条，审计链路才闭环：给定事件序列和当时的模型与提示版本，就能把这次运行完整重演一遍，用于复盘、回归和事故定责。

## 可限流：多维配额而不是只限 QPS

只做请求级限流挡不住 Agent 的成本失控，因为一次任务可能跑几十步、每步都带大上下文。限流要分四层同时施加：

| 层次 | 限什么 | 目的 |
| --- | --- | --- |
| 入口层 | 按租户和用户的并发数与每秒请求数 | 防止单个租户挤占资源 |
| 执行层 | 单任务的最大步骤数、最大 token、最大金额、墙钟时间 | 构成任务的硬性上限 |
| 工具层 | 单个工具的并发与速率，连续失败率触发熔断与半开探测 | 保护下游，故障时快速失败 |
| 调度层 | 有界队列做背压，队列满时按优先级拒绝或排队 | 防止内存和下游被拖垮 |

配额采用**预扣加结算**的方式：任务开始时预授权额度，每一步实时扣减，结束时结算。这样既能防止并发下的额度超发，也能在中途就发现预算即将耗尽并触发降级，而不是等到最后一步才发现钱不够。

## 对外接口与编排模板

引擎对外要暴露清晰的生命周期接口，把控制面收敛成少数几个动词：创建任务、查询状态与视图、请求暂停与恢复、请求取消与回滚、按检查点恢复、订阅事件流。事件流订阅很重要，它让前端和上游系统不必轮询，也天然支持把执行过程实时展示给用户。

这些接口之上再叠一层面向业务的编排模板，把典型的多步任务沉淀成可复用的模式，业务方只填槽位，不重新发明状态机和补偿逻辑。

## 常见追问

**Q：为什么不直接把整段对话历史存数据库就好了？**
A：对话历史只是「模型看到了什么」，回答不了「系统做了什么、外部世界变成了什么样」。事件日志记录的是带类型的动作与结果，既能重放出对话视图，也能重放出工具副作用和预算消耗，而对话数组两样都做不到。

**Q：回滚到底能不能保证一致？**
A：不能保证强一致的原子性。外部系统不支持分布式事务，补偿动作也可能失败或部分生效，所以目标是**最终语义等价**：补偿可重试、补偿本身幂等、回滚失败要升级为人工介入并如实记录在事件流里，而不是假装成功。

**Q：有了乐观并发控制，为什么还要幂等键？**
A：两者防的是不同问题。版本号防的是「基于过期视图重复推进」，幂等键防的是「同一次调用被重复投递」，比如网络超时后网关重试。真实系统里超时重试无法避免，所以幂等键必须在工具网关这一层强制。

**Q：审计日志写全量输入输出，隐私和成本怎么办？**
A：审计写的是脱敏后的内容，敏感字段在写入时替换或掩码，原始值只存在受控的加密存储中并按权限分级访问；成本上用分层存储与采样策略控制，但决策依据、路由与校验结论这类元数据必须完整保留。

## 易错点

- **把回滚当成撤销**。错。历史不会被删除，回滚是在日志后面追加补偿事件，把外部状态推回语义等价点；指望「撤掉那条记录」在跨系统场景里必然失败。
- **让工具网关顺手改任务状态**。错。状态转移的唯一写者是编排器，网关只写结果事件。两边都能改状态，很快就会出现「事件说成功、状态说失败」的对不上账。
- **只在入口做限流**。错。入口 QPS 看起来正常、单任务却跑了很多步并烧掉大量 token 的情况完全可能，执行层的步骤数与 token 上限、金额上限、墙钟时间才是真正兜底的那道闸。
- **把有副作用的步骤一步写完**。错。缺少预备态与提交态，进程在中间崩溃时就无法判断这次调用到底生效没有，补偿也就无从下手。

:::tip
事件日志是唯一真相，状态是它的投影，回滚写补偿、审计靠哈希链、限流卡住事件推进速度。
:::
