两者的差别可以归纳为四个层面：连接方式、传输格式、并发模型，以及其他功能特性。其中最本质的是并发模型——HTTP 1.0 每发一个请求就新建一条 TCP 连接，HTTP 1.1 用持久连接把连接复用起来，但同一条连接上的响应仍然必须按顺序返回；HTTP 2.0 把多路复用直接做进协议层，一条连接上并发承载多个流，从而从根本上消掉了应用层队头阻塞。

## 连接方式：短连接、持久连接与协议层多路复用

HTTP 1.0 默认是短连接：每发送一个请求就要新建一次 TCP 连接，响应结束后再关闭。连接本身是带开销的——三次握手、慢启动这些成本每次都要重付一遍，走 HTTPS 的话还要在每个连接上再做一次 TLS 握手；更麻烦的是同一个主机上的多个请求无法复用连接，只能各自建连，或者在服务器端把请求排起队来。

HTTP 1.1 把这笔开销压了下来：Keep-Alive 持久连接先以扩展形式出现在 1.0 后期，到 1.1 变成默认开启，一条 TCP 连接上可以先后承载多个请求，握手次数随之减少。但要注意它解决的是「连接能不能复用」，还没解决「能不能并发」——这正是下一节要讲的事。

HTTP 2.0 则把多路复用做在了协议层：一条连接上可以同时承载多个请求-响应，连接的复用不再需要应用层去凑。

## 传输格式：从文本报文到二进制分帧

HTTP 1.0 和 1.1 的报文都是文本格式：请求行、头部（一串纯文本键值对）、空行、正文依次排下来，人眼可读，抓包也容易看懂。代价是每次请求都要携带完整的头部信息，而 Cookie、User-Agent 这类头部往往又长又重复，同一个客户端连续发几十个请求，这些字节就要原样重传几十遍，开销非常明显。

HTTP 2.0 改成了二进制分帧层：一条消息被拆成若干个帧，每个帧带有定长的帧头，帧头里记录帧的类型（比如 HEADERS、DATA）以及它属于哪个流。正因为有了这套统一的二进制帧结构，头部才可以交给 HPACK 算法压缩——常见头部字段放进静态表，连接上下文里出现过的头部放进动态表，后续只传一个索引号，而动态表在同一条连接内持续复用，重复头部的传输量因此显著下降。

## 并发模型：应用层队头阻塞是怎么被消掉的

这是两者最本质的差异。

HTTP 1.1 虽然有了持久连接，但同一条连接上的响应必须按顺序返回：前一个响应没收完，后面的请求即使发出去了也只能等着。浏览器为了减少不确定性默认并不开启流水线，实际表现就是一条连接上一次只跑一个请求，这就是应用层的队头阻塞（head-of-line blocking）。

要规避它只能多开连接，典型手段是域名分片——把静态资源拆到多个域名下，绕开浏览器对同源连接数的限制。但连接数本身既受浏览器限制也受服务器限制，而且每多一条连接就要多做一次 TCP 握手和 TLS 握手，服务器端每条连接还要单独占一份资源，代价并不便宜。

HTTP 2.0 引入了流（stream）的概念：一条连接上可以承载多条流，每条流对应一个请求-响应，不同流之间的帧可以并发交错发送、乱序到达，接收端按帧头里的流标识重新组装成完整消息。请求之间不再互相等待，应用层队头阻塞因此被从根本上消除。

## 其他功能特性：流控、优先级、推送与 TLS

- **流量控制**：HTTP 2.0 同时提供连接级和流级流控，接收方通过窗口更新告诉发送方自己还能收多少，避免某条流或整条连接被灌满。
- **优先级**：流可以声明依赖关系与权重，让关键资源排在前面传输；不过各家浏览器实现策略并不统一，实际收益有限。
- **头部压缩**：就是上一节的 HPACK，属于 2.0 的标配能力，1.0 和 1.1 都没有。
- **服务端推送**：服务器可以主动推送客户端还没请求、但大概率需要的资源；这项能力实践中收益有限，主流浏览器后来陆续移除了支持。
- **加密**：HTTP 2.0 的规范里 TLS 并不是强制的，明文版本（h2c）也合法存在；但主流浏览器只实现基于 TLS 的 h2，所以真实部署中基本等同于要求加密。

## 各版本对比

| 维度 | HTTP 1.0 | HTTP 1.1 | HTTP 2.0 | HTTP 3 |
| --- | --- | --- | --- | --- |
| 连接方式 | 短连接，每请求一条 | 持久连接默认开启 | 一条连接复用到底 | 一条连接复用到底 |
| 传输格式 | 文本报文 | 文本报文 | 二进制分帧 | 二进制分帧 |
| 并发手段 | 多开连接 | 多开连接、域名分片 | 单连接多路复用 | 单连接多路复用 |
| 头部压缩 | 无 | 无 | HPACK | QPACK |
| 队头阻塞 | 有 | 应用层有 | 应用层已解决，TCP 层仍在 | 两层基本消除 |
| 底层传输 | TCP | TCP | TCP | 基于 UDP 的 QUIC |

## 常见追问

**Q：HTTP 2.0 的多路复用，是不是让浏览器能同时发更多请求了？**
A：方向反了。并发数量级本来就是靠多开连接堆上去的，多路复用的核心价值是让并发请求**不必再依赖多条物理连接**——一条连接就能高效承载大量并发流，连接数和握手次数都降下来，再叠上头部压缩，整体开销更低。

**Q：既然 2.0 已经解决了队头阻塞，为什么还要有 HTTP 3？**
A：它解决的只是应用层队头阻塞。HTTP 2.0 仍然跑在 TCP 上，一旦底层丢包，TCP 为保证有序交付会把整条连接上的数据一起卡住等重传，所有流都被牵连，这就是 TCP 层的队头阻塞。HTTP 3 改用基于 UDP 的 QUIC，在用户态自己实现可靠传输与多路复用，才能把这个层面的阻塞也去掉。

**Q：为什么很多人说 HTTP 2.0 必须用 HTTPS？**
A：规范上并没有强制，明文版本是合法的；但主流浏览器只实现基于 TLS 的版本，线上部署就等于必须加密。这是实现层面的选择，不是协议文本的规定。

**Q：HTTP 1.1 已经有持久连接了，为什么还要域名分片？**
A：持久连接解决的是「连接能不能复用」，域名分片解决的是「一条连接上一次只能串行处理」。1.1 无法在单连接上并发，想提高并行度只能多开连接，而浏览器对同源连接数有限制，于是把资源拆到多个域名下绕过这个限制。

## 易错点

- **把多路复用说成「并发数变多了」**。错。它改变的是并发请求的承载方式，从多条物理连接换成一条连接多条流，并不是凭空提高了浏览器允许的并发上限。
- **说 HTTP 2.0 彻底没有队头阻塞**。错。应用层的没有了，TCP 层的还在，丢包时整条连接都要等重传，这正是 HTTP 3 要解决的问题。
- **说 HTTP 2.0 强制使用 TLS**。不准确。规范里 TLS 是可选的，是浏览器只支持加密版 h2 才让它成了事实上的标准。
- **以为二进制分帧只是为了「换成二进制更省字节」**。不止如此。它的关键是给每个帧打上类型和流标识，让流可独立寻址、交错传输，并由连接级上下文支撑头部压缩，多路复用和 HPACK 都建立在它之上。

## 一句话记住

:::tip
连接复用、二进制分帧、单连接多路复用消掉应用层阻塞，TCP 层阻塞仍在。
:::
