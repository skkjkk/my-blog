## 索引失效的判定主线

索引失效是指**明明建了索引，优化器却选择不用它**，导致全表扫描、查询变慢。判断和排查的主线只有一条：**用 `EXPLAIN` 看实际走了哪个索引（`key` 列）**，而不是靠猜。

:::tip[面试加分点]
能主动说出"用 `EXPLAIN` 的 `key` 列判断，而不是靠猜"，比背出所有失效场景更能体现实战能力。
:::

## 写法问题导致的索引失效

这类失效的根源是 SQL 写法让 B+ 树无法直接比较列值，解法是**改写 SQL 让索引天然可用**。

### 在索引列上使用函数或表达式

比如 `WHERE DATE(create_time) = '2024-01-01'`、`WHERE age + 1 = 20`。

**原因**：B+ 树索引存的是原始列值，加了函数后无法直接比较。

**解法**：把函数移到常量侧（`create_time >= '2024-01-01' AND create_time < '2024-01-02'`），或建**函数索引**。

### 类型隐式转换

字段是 `varchar` 而查询传了数字（或反之），如 `WHERE phone = 13800138000`（phone 是 varchar）。

**原因**：字符列与数字比较时 MySQL 会把列转成数字，索引失效。

**解法**：**参数类型与字段类型保持一致**。

:::caution
这是最隐蔽的一类，因为 SQL 看起来完全正常，但实际发生了隐式转换。
:::

### 违反最左前缀原则

联合索引 `(a, b, c)` 无法在只查 `b`、或 `a` 后面跳过的场景使用（如 `WHERE b = 1`、`WHERE a = 1 AND c = 3`）。

**解法**：调整索引顺序或补建索引。

### 以 `%` 开头的模糊匹配

`WHERE name LIKE '%abc'` 无法使用索引；`LIKE 'abc%'`（前缀匹配）**可以**。

**解法**：改用全文索引，或加前缀列索引，或用搜索引擎。

### `OR` 连接的条件里有列没索引

`WHERE indexed_col = 1 OR unindexed_col = 2` 通常会导致全表扫描。

**解法**：给 OR 两侧的列都建索引，或改写为 `UNION`（注意去重开销）。

### 联合索引中出现范围查询后，后续列无法再用于等值匹配

`WHERE a = 1 AND b > 10 AND c = 3` 中，`c` 无法参与索引定位（只能作为索引条件下推的过滤条件）。这是 B+ 树的查找特性决定的。

### `ORDER BY` / `GROUP BY` 的列与索引顺序不一致

或排序方向与索引方向不匹配（`ASC` vs `DESC` 混用），会出现 `Using filesort`。

**解法**：让排序字段成为索引的**前导列**，或建立与排序方向一致的索引。

### `JOIN` 时关联字段没有索引

或关联字段两侧类型不一致（`int` join `varchar`）导致隐式转换。

### 隐式字符集或排序规则不一致

JOIN 两张表时字段的字符集不同（如 utf8mb4 与 utf8），会发生转换导致索引失效。

## 优化器决策导致的索引失效

这类失效是优化器基于成本估算做出的"合理选择"，不是 SQL 写法错误。

### 否定条件：`!=`、`<>`、`NOT IN`、`IS NOT NULL`

这类**否定条件通常优化器认为全表扫描更快**（命中结果占比高时）。

**解法**：数据分布倾斜时（如 `status != '0'` 命中 99% 行）确实不该用索引；命中少量时才值得配合其他条件强制走索引。

### `IS NULL` / `IS NOT NULL`

在某些数据分布下不走索引（大量 NULL 时）。相比 `= NULL`（永远不成立，写法错误）更常见的问题是**误用**。

### 数据量太小或区分度太低

表只有几百行，优化器认为全表扫描成本更低；列的区分度极低（如性别、状态）时，即使建了索引也不走。

:::note
这是"优化器的合理选择"，不是 bug。
:::

### 统计信息过期

数据大幅变动后索引统计未更新，优化器基于错误的基数估算选错索引。

**解法**：`ANALYZE TABLE` 重新收集统计信息。

### 优化器估算成本出错

`rows` 预估与实际扫描行数差距大时，优化器可能选错。

**解法**：`ANALYZE TABLE`、改写 SQL 让路径更明确、必要时用 `FORCE INDEX` / `IGNORE INDEX` 干预。

:::caution
`FORCE INDEX` / `IGNORE INDEX` 是最后手段，因为会随数据分布变化而失效。
:::

## 排查顺序与根本性解法

### 排查顺序

① `EXPLAIN` 看 `type`（是否 `ALL`）、`key`（实际索引）、`rows`（扫描行数）、`Extra`（`Using filesort` / `Using temporary`）；② 用 `EXPLAIN ANALYZE` 对比**预估行数与实际行数**；③ 若是统计信息问题就 `ANALYZE TABLE`；④ 若是写法问题就改 SQL；⑤ 最后才考虑 `FORCE INDEX`。

### 根本性的解法

**大部分"索引失效"其实是 SQL 写法问题，不是索引本身的问题**。与其纠结"为什么不用索引"，不如**改写 SQL 让索引天然可用**（把函数移走、类型对齐、调整联合索引顺序）。

:::tip[核心记忆点]
**索引是给优化器用的，改写 SQL 永远比加索引更优。**
:::

## 索引失效场景速查表

| 失效场景 | 典型示例 | 核心解法 |
|---------|---------|---------|
| 函数/表达式 | `WHERE DATE(create_time) = '2024-01-01'` | 函数移到常量侧，或建函数索引 |
| 类型隐式转换 | `WHERE phone = 13800138000`（phone 是 varchar） | 参数类型与字段类型保持一致 |
| 违反最左前缀 | `WHERE b = 1`（联合索引 `(a,b,c)`） | 调整索引顺序或补建索引 |
| `%` 开头模糊匹配 | `WHERE name LIKE '%abc'` | 全文索引、前缀列索引、搜索引擎 |
| OR 含无索引列 | `WHERE indexed_col = 1 OR unindexed_col = 2` | 两侧都建索引，或改写为 `UNION` |
| 否定条件 | `WHERE status != '0'` | 命中少量时配合其他条件强制走索引 |
| 范围查询后列 | `WHERE a = 1 AND b > 10 AND c = 3` | 调整索引列顺序 |
| 排序方向不匹配 | `ORDER BY` 与索引 `ASC`/`DESC` 混用 | 排序字段做前导列，或建同向索引 |
| JOIN 字段无索引/类型不一致 | `int` join `varchar` | 补索引、对齐类型 |
| 字符集不一致 | utf8mb4 join utf8 | 统一字符集 |
| 统计信息过期 | 数据大幅变动后未更新 | `ANALYZE TABLE` |
| 成本估算出错 | `rows` 预估与实际差距大 | `ANALYZE TABLE`、改写 SQL、必要时 `FORCE INDEX` |
| 数据量太小/区分度低 | 几百行表、性别列 | 优化器合理选择，无需处理 |
