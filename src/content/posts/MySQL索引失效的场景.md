索引失效就是明明建了索引，优化器却没用它，查询退化成全表扫描。判断只有一条主线：用 `EXPLAIN` 看实际走了哪个索引（`key` 列），`key` 为空、`type` 是 `ALL` 就说明没走索引，不靠猜。根因分两类：一类是 SQL 写法让 B+ 树没法直接比较列值，改写法就能恢复；另一类是优化器估算成本后觉得全表扫描更便宜，属于合理选择而不是 bug。

## 先分清两类根因，再谈具体场景

这两种失效的性质完全不同，混在一起背就会得出「索引失效一律改写 SQL」或者「一律 FORCE INDEX」的错误结论。**写法类**：索引本身没问题，是 SQL 让索引没法用——列上套函数、类型隐式转换、违反最左前缀、`%` 前缀匹配，这类**改写 SQL 就能恢复**。**优化器类**：索引可用，但优化器算完成本后判定全表更划算——命中比例高、表太小、区分度太低、统计信息过期，这类**是成本决策，不是缺陷**。

判断归属只要两步，看 `EXPLAIN` 的两个列：

- `possible_keys` 有值、`key` 为空：索引可用但被优化器放弃，属于优化器类。
- `possible_keys` 本身是空的：写法上索引压根不可能被用上，属于写法类。
- `key` 有值但 `rows` 很大：索引走偏了，多半是统计信息过期或成本估算失真。
- 任何情况下先看 `type`：`ALL` 是全表扫描，`index` 是全索引扫描，`range`、`ref`、`const` 依次更精确。

## 写法类失效：SQL 让 B+ 树没法直接比较列值

这类根因可以统一成一句话：B+ 树里存的是列的**原始值**，并按索引定义的顺序排好，一旦比较的对象不是列本身，或者比较顺序接不上索引的排序，就无法定位到具体的索引项。下面按出现频率排列。

### 索引列上套函数或表达式

`WHERE DATE(create_time) = '2024-01-01'`、`WHERE age + 1 = 20` 都属这一类。**原因**：索引里存的是原始的 `create_time` 和 `age`，套上函数后每一行都要先算一遍才能比较，只能全扫。**解法**：把函数移到常量侧，写成 `create_time >= '2024-01-01' AND create_time < '2024-01-02'`；或者直接建**函数索引**，把表达式本身作为索引键。

### 类型隐式转换

字段是 `varchar` 而查询传了数字，比如 `WHERE phone = 13800138000`（`phone` 是 `varchar`）。**原因**：字符列与数字比较时，MySQL 会按数字语义比较，等于对列做了一次隐式类型转换，索引里的字符串顺序用不上了。**解法**：参数类型与字段类型保持一致，写成 `phone = '13800138000'`。

:::caution
这是最隐蔽的一类，因为 SQL 看起来完全正常，肉眼看不出问题，只有 `EXPLAIN` 才能发现它退化成全表扫描。
:::

### 违反最左前缀原则

联合索引 `(a, b, c)` 在 `WHERE b = 1`、`WHERE a = 1 AND c = 3` 这类跳过了前导列的查询里用不上。**原因**：索引先按 `a` 排序，`a` 相同才按 `b` 排，再按 `c` 排；`a` 没确定时，`b` 和 `c` 在整个索引里是无序的。**解法**：调整索引列顺序，或为高频查询单独补建索引。

### 以 % 开头的模糊匹配

`WHERE name LIKE '%abc'` 无法使用索引；`LIKE 'abc%'` 这种前缀匹配**可以**。**原因**：后缀匹配的起点在索引里不连续，找不到扫描的起始位置。**解法**：改用全文索引，或加前缀列索引（把常查的前缀抽成独立列，再查这一列），或交给搜索引擎。

### OR 连接的条件里有一侧没有索引

`WHERE indexed_col = 1 OR unindexed_col = 2` 通常会导致全表扫描。**原因**：OR 要求两侧都能用索引，只要一侧用不上，整体就只能合并成一次全表扫描。**解法**：给 OR 两侧的列都建索引，或改写成 `UNION`（注意去重开销，不需要去重时用 `UNION ALL`）。

### 范围查询之后，后续列不再参与定位

`WHERE a = 1 AND b > 10 AND c = 3` 中，`c` 无法参与索引定位，只能作为索引条件下推的过滤条件。**原因**：`b` 是范围，范围内的 `c` 不再有序，这是 B+ 树的查找特性决定的。**解法**：按「等值列在前、范围列在后」重排索引列顺序。

### 排序、分组的列或方向与索引不一致

`ORDER BY` / `GROUP BY` 的列不是索引前导列，或者排序方向与索引不一致（`ASC` 与 `DESC` 混用），执行计划里就会出现 `Using filesort`。**解法**：让排序字段成为索引的**前导列**，或建立与排序方向一致的索引。

### JOIN 时关联字段没有索引

关联字段没索引，被驱动表只能全表扫描；关联字段两侧类型不一致（`int` join `varchar`）还会触发隐式转换，等同于对被驱动表的列套了一层函数。**解法**：给关联字段补索引，并把两侧类型对齐。

### 隐式字符集或排序规则不一致

JOIN 两张表时字段字符集不同（如 utf8mb4 与 utf8），比较前必须先做字符集转换，转换后的值在索引里无序，索引随之失效。**解法**：统一两张表的字符集与排序规则。

## 优化器类失效：不是写错，是算下来不划算

这类场景索引建了、写法也没毛病，但优化器基于成本估算主动放弃。共同点是「用索引反而更贵」：命中的行占比太高，回表的随机 IO 超过一次顺序全扫；或者数据量太小，多一次索引查找并不划算；或者估算依据本身就是错的。判断的关键是比例和分布，不是条件里出现了什么符号。

### 否定条件：!=、<>、NOT IN、IS NOT NULL

这类否定条件在命中结果占比高时，优化器认为全表扫描更快。**解法**：数据分布倾斜时（例如 `status != '0'` 命中 99% 的行）确实不该用索引，硬加索引只会更慢；只有命中少量行时，才值得配合其他条件让它走索引。

### IS NULL 与 IS NOT NULL

这两者同样在某些数据分布下不走索引，比如大量 NULL 的行、或 `IS NOT NULL` 几乎命中全部行。这里要区分两个不同的问题：`= NULL` 永远不成立，属于**写法错误**，必须改成 `IS NULL`；而 `IS NULL` / `IS NOT NULL` 写法正确却不走索引，那是成本选择。

### 数据量太小或区分度太低

表只有几百行时，优化器认为全表扫描的成本更低；列的区分度极低（如性别、状态）时，即使建了索引也走不上。

:::note
这是优化器的合理选择，不是 bug，不要急着加 `FORCE INDEX`。
:::

### 统计信息过期

数据大幅变动后索引统计没有更新，优化器基于错误的基数估算选错了索引。**解法**：`ANALYZE TABLE` 重新收集统计信息，再回头看执行计划。

### 优化器估算成本出错

`EXPLAIN` 的 `rows` 预估与实际扫描行数差距大时，优化器可能选错索引或选错 JOIN 顺序。**解法**：先 `ANALYZE TABLE`，再改写 SQL 让可选路径更明确（比如把 OR 拆成 UNION、先缩小结果集），必要时才用 `FORCE INDEX` / `IGNORE INDEX` 干预。

:::caution
`FORCE INDEX` / `IGNORE INDEX` 是最后手段，因为数据分布一变，原本帮上忙的强制索引就可能变成拖后腿的原因。
:::

## 排查顺序：从 EXPLAIN 到改 SQL

按顺序走，前一步没排除就不要跳到下一步：

1. `EXPLAIN` 看四个字段：`type`（是否 `ALL`）、`key`（实际用的索引）、`rows`（预估扫描行数）、`Extra`（`Using filesort` / `Using temporary` / `Using index condition`）。
2. 用 `EXPLAIN ANALYZE` 对比**预估行数与实际行数**，偏差大说明统计信息过期或成本估算失真。
3. 若是统计信息问题，`ANALYZE TABLE` 后重新看执行计划。
4. 若是写法问题，改写 SQL：把函数移走、类型对齐、调整联合索引顺序。
5. 以上都不解决，最后才考虑 `FORCE INDEX` 干预。

最小改写示例：

```sql
-- 失效：列上套了函数，索引用不上
SELECT * FROM orders WHERE DATE(create_time) = '2024-01-01';

-- 恢复：改成范围条件，索引可用
SELECT * FROM orders
WHERE create_time >= '2024-01-01' AND create_time < '2024-01-02';
```

**根本性的解法**：大部分所谓「索引失效」其实是 SQL 写法问题，不是索引本身的问题。与其纠结「为什么不用索引」，不如先改写 SQL 让索引天然可用——把函数移到常量侧、把参数类型对齐、把等值列调到联合索引前面，都是不必新增索引就能见效的动作。

## 索引失效场景速查表

| 失效场景 | 典型示例 | 核心解法 |
|---------|---------|---------|
| 函数或表达式 | `WHERE DATE(create_time) = '2024-01-01'` | 函数移到常量侧，或建函数索引 |
| 类型隐式转换 | `WHERE phone = 13800138000`（`phone` 是 varchar） | 参数类型与字段类型保持一致 |
| 违反最左前缀 | `WHERE b = 1`（联合索引 `(a,b,c)`） | 调整索引顺序或补建索引 |
| `%` 开头模糊匹配 | `WHERE name LIKE '%abc'` | 全文索引、前缀列索引、搜索引擎 |
| OR 含无索引列 | `WHERE indexed_col = 1 OR unindexed_col = 2` | 两侧都建索引，或改写为 `UNION` |
| 范围查询之后的列 | `WHERE a = 1 AND b > 10 AND c = 3` | 调整索引列顺序（等值在前、范围在后） |
| 否定条件 | `WHERE status != '0'` | 命中少量时才配合其他条件强制走索引 |
| 排序方向不匹配 | `ORDER BY` 与索引 `ASC` / `DESC` 混用 | 排序字段做前导列，或建同向索引 |
| JOIN 字段无索引或类型不一致 | `int` join `varchar` | 补索引、对齐类型 |
| 字符集不一致 | utf8mb4 join utf8 | 统一字符集与排序规则 |
| 数据量太小或区分度低 | 几百行的表、性别列 | 优化器的合理选择，通常无需处理 |
| 统计信息过期 | 数据大幅变动后未更新 | `ANALYZE TABLE` |
| 成本估算出错 | `rows` 预估与实际差距大 | `ANALYZE TABLE`、改写 SQL、必要时 `FORCE INDEX` |

## 常见追问

**Q：`EXPLAIN` 的 `key` 是 NULL，怎么判断属于哪一类失效？**

A：先看 `possible_keys`。有候选却没选上，说明索引可用但被成本决策放弃，去查命中比例、表大小和统计信息是否过期；连候选都是空的，说明写法上就不可用，去查函数、隐式转换、是否跳过前导列、是否 `%` 前缀。再看 `rows` 与 `filtered`，估算明显失真就是统计信息的问题。

**Q：`LIKE '%abc'` 真的没救吗？**

A：索引本身是按前缀有序的，后缀匹配定位不到起点。可选做法是把字符串反转后单独存一列，再对这一列做前缀匹配（`LIKE 'cba%'`），也可以用全文索引；数据量大、检索要求灵活的通常直接交给搜索引擎。

**Q：联合索引 `(a, b, c)`，为什么 `WHERE a = 1 AND c = 3` 用不上 `c`？**

A：索引整体先按 `a` 排、相同时再按 `b`、再按 `c`。`b` 没给值，`c` 在 `a = 1` 命中的那一段里是无序的，只能先取出 `a = 1` 的索引项再逐行回表过滤，`c` 起不到缩小扫描范围的作用。

**Q：区分度低的列（比如性别）到底该不该建索引？**

A：单独用收益很低，命中一半的行时回表开销超过全表扫。但它可以作为联合索引的一部分，或者在覆盖索引场景下仍然有效——查询只取索引里已有的列、不需要回表时，走索引依然更省。

## 易错点

1. **以为 `WHERE phone = 13800138000` 这样写没问题**：`phone` 是 `varchar` 时，列会被隐式转成数字再比较，索引失效；给参数补上引号才对。这类错误肉眼看不出，只能靠 `EXPLAIN` 发现。
2. **以为 OR 里有一个条件有索引就能走索引**：另一侧没有索引时，整个 OR 通常退化为全表扫描；正确做法是两侧都建索引，或改写成 `UNION ALL`。
3. **以为范围查询后面的列完全没用**：它不参与索引定位，但还能参与索引条件下推做过滤，`Extra` 里会显示 `Using index condition`；只是扫描范围不会因为这一列而缩小。
4. **以为索引失效都能靠 `FORCE INDEX` 解决**：统计信息过期或命中比例过高时强行指定索引，回表次数会暴增，可能比全表扫描更慢。先 `ANALYZE TABLE`，再考虑干预。

## 一句话记住

:::tip
判定看 `EXPLAIN` 的 `key` 列；能改 SQL 解决的，就别急着加索引。
:::
