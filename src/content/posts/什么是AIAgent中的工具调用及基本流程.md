工具调用（Tool Calling / Function Calling）是指模型不直接输出答案，而是输出一个**结构化的"我想调用某个工具、参数是这些"**的请求，由宿主程序真正执行后把结果回传给模型，模型再基于结果继续输出。它是 Agent 获得"手脚"的关键机制，本质是把"说什么"和"做什么"拆成两件事：模型只产出意图，执行权始终在程序手里。

## 工具调用是"意图"与"执行"的两段式机制

先从最容易被说反的一句讲起：**模型本身不执行任何东西**。模型输出的只是一段结构化的意图描述——工具叫什么、参数是什么——它并不知道这个工具背后是本地函数还是外部 API，也不知道调用到底成没成功。真正的执行动作发生在宿主程序里：程序解析这段结构化的请求，决定要不要执行、执行哪个实现、怎么处理异常。

这一点非常关键，它决定了整条链路上谁负责什么：

- **模型负责"表达"**：选工具、填参数、判断结果够不够用、决定继续调还是给最终答案。
- **宿主负责"动作"**：校验参数、真正调用、捕获失败、把结果写回消息列表。
- **参数必须由程序校验**，绝不能因为模型说"要调用某工具"就直接放行——模型可能填错类型、漏必填字段，甚至凭想象编一个不存在的工具名。

所以工具调用的可靠性，一半取决于模型选得对不对，另一半取决于宿主这一侧校验和兜底做没做全。

## 基本流程是四步循环

完整链路是一个可以反复执行的循环，四步分别为：

1. **注册工具**：把工具的名称、功能描述、参数 schema 随请求一起发给模型。模型只能看见你发给它的这部分，没发过去的工具等于不存在。
2. **模型决策**：若需要用工具，模型返回 `tool_calls` 结构（工具名 + JSON 参数）而非文本；若不需要，直接输出最终答案，流程到此结束。
3. **宿主执行**：程序解析 `tool_calls`，真正调用本地函数或外部 API，捕获成功或失败。
4. **回填结果**：把执行结果按 `tool_call_id` 组织成 `tool` 消息追加进消息列表，模型再据此继续推理，可能再次请求工具。

**第四步之后模型可能输出最终答案，循环结束**；也可能带着新信息再发起一次调用，于是回到第二步。这也解释了 Agent 为什么天然是多轮的：每一轮都在"决策—执行—观测"之间来回。

职责划分可以这么记：

| 步骤 | 谁来做 | 关键动作 | 出错时的典型表现 |
|---|---|---|---|
| 注册工具 | 宿主 | 把名称、描述、参数 schema 随请求发送 | 工具没注册，模型只能用别的手段凑答案 |
| 模型决策 | 模型 | 输出工具名与 JSON 参数，或直接给答案 | 选错工具、参数缺字段或类型不符 |
| 宿主执行 | 宿主 | 解析请求、校验参数、真正调用、捕获异常 | 放行脏参数、异常打断整个流程 |
| 回填结果 | 宿主 | 按 `tool_call_id` 组装 `tool` 消息写回上下文 | 结果缺字段、错误信息不可诊断 |

一次最小调用在消息层面大致是这样（字段名各家实现略有差异，结构大同小异）：

```text
// 1. 随请求一起下发的工具定义
{
  "name": "get_order_status",
  "description": "按订单号查询物流状态，仅支持已支付订单",
  "parameters": {
    "type": "object",
    "properties": { "order_id": { "type": "string" } },
    "required": ["order_id"]
  }
}

// 2. 模型返回的调用请求（不是给用户看的文本）
{
  "tool_calls": [
    { "id": "call_1", "name": "get_order_status", "arguments": { "order_id": "A10086" } }
  ]
}

// 3. 宿主执行后回填的 tool 消息，用 id 与上面的请求对齐
{
  "role": "tool",
  "tool_call_id": "call_1",
  "content": "{\"status\":\"运输中\",\"eta\":\"预计两天内送达\"}"
}
```

## 工具描述就是提示词，参数 schema 是契约

模型判断该用哪个工具，完全依赖你写的工具描述与参数 schema，它看不到你的代码注释、内部文档和口头约定。**描述含糊、命名不当、职责重叠，都会直接导致选错工具**——比如两个工具都叫"查询信息"，模型只能靠猜。反过来，**工具描述的质量往往比换一个更强的模型更能提升准确率**：把"什么时候该用、什么时候不该用、返回什么"写清楚，选错工具的概率会明显下降。

参数 schema 则是模型和程序之间的契约。用 JSON Schema 声明必填字段、类型、枚举、取值范围，模型会据此生成参数，程序则用它做校验与类型转换——同一份 schema 被两边消费，才有对齐的可能。**schema 与实际实现不一致，是线上调用失败最常见的原因**：模型老老实实按 schema 传了 `order_id`，函数内部却按 `orderId` 取值，看起来"模型调错了"，实际是契约写错了。设计工具时值得守住的几条：

- 一个工具只做一件事，名字动词开头、语义唯一，避免职责重叠。
- 描述里写清适用场景和不适用场景，比罗列参数更重要。
- 能枚举就别用自由文本，能标必填就别留给模型猜。
- schema 改动要当成接口变更来管，实现和声明一起改。

## 返回结果要结构化并带错误信息

工具失败时，正确的做法是把**可诊断的错误信息**回传给模型（如"参数 id 不存在"），而不是抛异常中断整个流程——模型往往能根据错误自行纠正，换个 id、补个字段、换条路径再试一次。**错误回填正是 Agent 具备自我修复能力的来源**：它把"失败"从终止信号变成了新的观测。

要做到这一点，回填内容得守两条：

- **结构化**：字段稳定、可解析，别只塞一句自然语言。成功时给出关键字段，失败时给出错误类型和可操作的提示。
- **可诊断**：写清"哪里错了、期望什么"，而不是"调用失败"。模型没有你的日志，它只能读你回填的文字。

结果体积也要控制：返回内容过大时不要原样塞回上下文，先裁剪字段或做摘要，否则一次调用就可能把上下文窗口挤爆，后面的推理反而变差。

## 并行调用与两种实现模式

**并行工具调用**：模型可以在一次响应中返回多个 `tool_calls`，宿主并发执行后一次性回填，这能显著降低多工具场景的延迟。代价是要自己兜住并发问题——写操作互相覆盖、下游被打满配额、失败一半时状态不一致，这些都得靠限流、幂等和顺序约束来防。

**两种实现模式**的区别也常被问到：

- 有的实现是**模型主动决定何时调用工具**（真正的 tool calling），工具的选择和执行时机由模型在结构化输出里给出，宿主只负责执行。这种方式在多轮对话中更稳，因为工具调用是模型原生的输出形式。
- 有的是**模型只输出一个"调用意图"，再由代码解析执行**（ReAct 风格：思考、行动、观察三步循环，靠文本解析出要调什么）。这种方式更透明可控，每一步都能被人读懂和干预，但解析脆弱、多轮容易跑偏。

一句话取舍：追求稳定和规模化选前者，追求可解释和可干预选后者。

## 与普通 Function Calling 的边界

模型接口层面的 function calling，只是"结构化输出 + 工具定义"这一套机制，它解决的是**"模型能不能准确表达自己想调用什么"**。而完整的 Agent 工具调用还要包含执行侧的工程能力：**权限、限流、幂等、结果缓存**——这些决定了"线上敢不敢让它真的执行"。

这两层要分清：只有 schema 和 tool_calls，你能得到一个演示；把执行侧的权限边界、速率上限、重复调用去重、结果复用补齐，才能得到一个能上生产的 Agent。面试里这一点常被用来区分"用过 API"和"做过系统"。

## 常见追问

**Q：模型返回的 tool_calls 可以直接执行吗？**
A：不能。工具名可能不在注册表里，参数可能缺字段或类型不符，宿主必须先校验，不合规就拒绝执行并把原因回填给模型。

**Q：工具调用失败了，为什么不让整个流程报错退出？**
A：因为模型能读错误信息自我纠正。抛异常等于放弃这次纠错机会，错误回填则把失败变成一次新的观测，这也是 Agent 自我修复能力的来源。

**Q：什么时候不能用并行工具调用？**
A：工具之间有顺序依赖，或存在写副作用、共享配额时。这类场景要串行执行，或者用幂等键保证重复执行不产生额外影响。

**Q：工具描述写得再细，模型还是选错，怎么办？**
A：先查职责是否重叠、命名是否容易混淆、schema 是否和实现不一致，这三项是最常见的选错原因；再考虑拆分工具粒度，最后才考虑换模型。

## 易错点

1. **以为模型"调用了工具"就等于工具真的执行了**。模型只输出意图描述，执行发生在宿主程序里，模型对执行结果一无所知，除非你把结果回填给它。
2. **把工具描述当文档，写在代码注释或内部 wiki 里**。模型只看得见随请求发送的那份描述和 schema，没发过去的部分对它不存在。
3. **把参数 schema 当成只给模型看的说明书**。程序同样要拿它做校验和类型转换；schema 与实现不一致，是线上调用失败最常见的原因。
4. **把接口层的 function calling 当成完整的 Agent 工具调用**。缺了权限、限流、幂等、结果缓存，这套机制只能在演示里跑。

## 一句话记住

:::tip
模型只输出调用意图，执行权、校验权和回填格式都在宿主程序手里。
:::
