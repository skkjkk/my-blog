工具调用（Tool Calling / Function Calling）是指模型不直接输出答案，而是输出一个**结构化的"我想调用某个工具、参数是这些"**的请求，由宿主程序真正执行后把结果回传给模型，模型再基于结果继续输出。工具调用是 Agent 获得"手脚"的关键机制。

1) **基本流程是四步循环**。第一步**注册工具**，把工具的名称、功能描述、参数 schema 随请求一起发给模型；第二步**模型决策**，若需要用工具，模型返回 tool_calls 结构（工具名 + JSON 参数）而非文本；第三步**宿主执行**，程序解析 tool_calls、真正调用本地函数或外部 API、捕获成功或失败；第四步**回填结果**，把执行结果按 tool_call_id 组织成 tool 消息追加进消息列表，模型再据此继续推理，可能再次请求工具。**第四步后模型可能输出最终答案，循环结束**。

2) **模型本身不执行任何东西**。这一点非常关键：模型只产出"意图描述"，真正的执行权在宿主程序手里。**参数必须由程序校验**，绝不能因为模型说"要调用某工具"就直接放行。

3) **工具描述就是提示词**。模型判断该用哪个工具，完全依赖你写的工具描述与参数 schema。描述含糊、命名不当、职责重叠，都会直接导致选错工具。**工具描述的质量往往比换更强的模型更能提升准确率。**

4) **参数 schema 是契约**。用 JSON Schema 声明必填字段、类型、枚举、取值范围，模型会据此生成参数，程序则用它做校验与类型转换。schema 与实际实现不一致是线上调用失败最常见的原因。

5) **返回结果要结构化且带错误信息**。工具失败时应把**可诊断的错误信息**回传给模型（如"参数 id 不存在"），而不是抛异常中断整个流程 —— 模型往往能根据错误自行纠正。错误回填能让 Agent 具备**自我修复能力**。

6) **并行工具调用**。模型可以在一次响应中返回多个 tool_calls，宿主并发执行后一次性回填，这能显著降低延迟，但要注意并发副作用与限流。

7) **模式差异**。有的实现是模型主动决定何时调用工具（真正的 tool calling），有的是模型只输出一个"调用意图"再由代码解析执行（ReAct 风格）。前者在多轮中更稳，后者更透明可控。

8) **与普通 Function Calling 的边界**。模型接口层面的 function calling 只是"结构化输出 + 工具定义"这套机制；而完整的 Agent 工具调用还包含**执行侧的权限、限流、幂等、结果缓存**。这两层要分清，面试中常被追问。
