A2A（Agent2Agent）是由 Google 发起、逐渐成为社区标准的 **Agent 间通信协议**，用来让独立的、可能由不同团队开发、部署在不同厂商基础设施上的 Agent 相互发现、协商并协作完成任务。它和 MCP 不在同一层面：MCP 把「Agent 如何接入工具与数据」标准化，A2A 把「Agent 如何与另一个 Agent 协作」标准化——前者是纵向接入，后者是横向协作。

## 两者解决的不是同一层问题

一句话概括分工：**MCP 是纵向的**（应用 ↔ 工具／数据），把能力接入统一化；**A2A 是横向的**（Agent ↔ Agent），把协作标准化。这两个方向并不冲突，因此一个 Agent 可以同时扮演两个角色——它既能作为 MCP Client 去使用别人提供的工具与数据，也能作为 A2A Server 被别的 Agent 调用。

理解这一点，很多「A2A 会不会替代 MCP」的疑问就不成立了：工具接入与 Agent 协作是两件事，边界不同、解决对象不同，只是在同一个系统里同时出现。

## Agent Card：机器可读的自我描述

每个 Agent 用一张**机器可读的 JSON 卡片**公开自己的能力，卡片里包含名称、描述、能力列表、支持的技能与输入输出模式、认证方式、服务端点 URL。它的作用相当于「名片 + 能力契约 + 自我介绍」三合一，让别的 Agent 能**在运行时动态发现**它，而不必事先硬编码协作方。

下面是一张卡片的结构示意（省略了部分字段，取值只是示例）：

```json
{
  "name": "invoice-audit-agent",
  "description": "对发票做合规校验并标注风险等级",
  "url": "https://example.com/a2a",
  "capabilities": { "streaming": true, "pushNotifications": false },
  "defaultInputModes": ["application/json"],
  "defaultOutputModes": ["application/json"],
  "skills": [
    {
      "id": "audit-invoice",
      "name": "发票合规校验",
      "description": "按规则检查发票要素，输出风险项清单",
      "tags": ["finance", "compliance"]
    }
  ]
}
```

因此 Agent Card 有三重身份：它既是**发现机制**（别人怎么找到你），也是**契约**（你的输入输出长什么样、调用要什么凭证），更是**信任凭据**（能力描述越具体，调用方越容易判断你是否适合）。

## Task：协作以一个任务为单位

A2A 的协作单位是一个**有状态、有生命周期的任务**。Task 贯穿从创建到完成的整个过程，过程中有状态更新、有**流式的中间产物**（Artifact）推送、有多轮消息往来。这套模型与「一次 HTTP 请求-响应」完全不同：调用方拿到的不只是一个返回值，而是一个可跟踪、可中断、可继续推进的协作过程。

在协作模式上，除了最基础的「请求-响应」，A2A 还支持：

- **流式更新**：执行方持续推送进展与中间产物，调用方不必盲等。
- **多轮交互**：对方可以反问澄清、协商范围，而不是一次问清全部条件。
- **任务委托与转交**：把不适合自己做的事交给更合适的 Agent。
- **异步长任务**：任务可以在后台推进，调用方稍后再取结果。

## 互补关系：一个 Agent 同时戴两顶帽子

实践中一个典型 Agent 会**同时是 MCP Client 和 A2A Server**：它通过 MCP 拿到本地工具与数据，通过 A2A 把需要专业能力的部分委托给远端专家 Agent。用一句形象的话说：**MCP 管「手」，A2A 管「同行」。**

两者的差别可以并排看清：

| 维度 | MCP | A2A |
| --- | --- | --- |
| 解决的问题 | Agent 接入工具与数据 | Agent 与另一个 Agent 协作 |
| 方向 | 纵向：应用 ↔ 工具／数据 | 横向：Agent ↔ Agent |
| 交互模型 | 请求-响应，调用工具 | 有状态任务 + 流式更新 + 多轮消息 |
| 状态 | 无任务生命周期 | Task 从创建到完成有状态迁移 |
| 结果形态 | 直接回填调用结果 | 以 Artifact 交付中间与最终产物 |
| 对手方 | 自己接入的工具服务 | 另一个独立 Agent |

## A2A 特有但 MCP 没有的难题

因为对手方是 Agent 而不是工具，A2A 必须解决一批 MCP 不必操心的问题：

- **信任与身份**：对方 Agent 是否可信、如何认证它的身份与归属。
- **能力发现与匹配**：从大量 Agent Card 中选出真正合适的那一个。
- **跨组织的数据与责任边界**：数据能交出去多少、出了问题谁负责。
- **跨厂商的语义互操作**：能力描述、术语与结果语义要对得上。

MCP 之所以不突出这些问题，是因为调用方通常是**自己写的程序**，工具也是自己挑选、自己接入的，信任关系天然成立。

## 成熟度与适用边界

A2A 规范由 Google 发起并捐赠给开源基金会，与 MCP、AGNTCY 等一起构成了 Agent 互联生态。它的价值更多体现在**跨组织、跨厂商**的长程协作场景——这类场景里你无法规定对方的实现，只能靠协议对齐。反过来，在**单组织内部**做多 Agent 编排，直接用代码框架（LangGraph、AutoGen、Semantic Kernel 等）往往更简单可控，也更省掉协议层的信任与治理成本。

## 常见追问

**Q：A2A 会取代 MCP 吗？**
A：不会。MCP 是纵向的（应用 ↔ 工具／数据），A2A 是横向的（Agent ↔ Agent），一个 Agent 可以同时是 MCP Client 和 A2A Server，两者是互补关系。

**Q：A2A 和普通的 HTTP 接口调用差在哪？**
A：差在模型。普通调用是一次请求-响应；A2A 的协作单位是带状态的 Task，支持流式推送中间产物、多轮反问澄清、任务转交与异步长任务。

**Q：为什么 MCP 不太强调信任与责任边界？**
A：MCP 的调用方通常是自己写的程序，工具由自己挑选接入，信任前提已经成立；A2A 的对手方是另一个独立 Agent，身份认证、能力发现与数据边界就变成必须解决的问题。

**Q：单组织内部的多 Agent 协作也要上 A2A 吗？**
A：不一定。组织内用 LangGraph、AutoGen、Semantic Kernel 这类框架直接编排更简单可控；A2A 的价值主要在跨组织、跨厂商的长程协作。

## 易错点

- **把 A2A 当成「另一个 MCP」或替代品**：它们解决的是不同层的问题，方向一个是纵向、一个是横向，不存在替代关系。
- **把 A2A 想成一次远程调用**：Task 是有状态、有生命周期的，配套流式更新、多轮消息和中间产物，这是「一次 HTTP 请求-响应」覆盖不了的。
- **把 Agent Card 只当宣传文案**：它同时是契约与信任凭据，能力描述写不清，调用方就选不准、也不敢调。
- **以为协议对得上就能跨组织协作**：身份信任、数据与责任边界、语义互操作都是协议之外还要谈清楚的事。

## 一句话记住

:::tip
MCP 让 Agent 拥有「工具」，A2A 让 Agent 拥有「同事」。
:::
