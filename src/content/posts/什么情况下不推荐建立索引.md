不推荐建索引的典型情况可以归成六类：第一类是区分度极低的列，第二类是更新极频繁的列或整张写多读少的表，第三类是几乎不被 `WHERE`、`JOIN`、`ORDER BY` 用到的列，第四类是与已有联合索引最左前缀重复的索引，第五类是只有几百行的小表，第六类是 `TEXT`、`BLOB` 这类超长字段。另有两条要慎建：查询本身就要返回大量整行，回表随机 IO 可能比全表顺序扫描更慢；已经有 Redis 缓存或冗余字段能解决。根因是索引并不免费——它在提升查询速度的同时增加写入成本、占用额外存储，索引过多还会影响优化器选择。

## 判断标准：收益必须压过成本

辅助索引是额外的一棵 B+ 树，叶子节点存主键，命中后通常还要回表取整行。所以每建一条索引，等于同时买下「可能查得更快」和「写得更贵、占得更多」两笔账。判断只看两件事：一是这条索引能不能被核心查询真正用上——缩小扫描范围、避免排序、或者直接覆盖查询列；二是维护它的代价是否可接受——列的更新频率、表的数据量、存储与缓冲池占用。收益覆盖不了成本，就不该建。

落地时守住三条：

- 索引数量够用即可，上线前梳理核心查询路径，按实际查询组合建索引，不要凭感觉给每个字段都来一条。
- 定期用 `pt-index-usage` 或慢日志，清理从未被使用过的冗余索引。
- 删索引前确认它不是某个联合索引的最左前缀；大表删索引要走在线 DDL，避免锁表。

## 区分度极低的列：走索引可能更慢

性别、是否删除、状态这类只有两三个取值的列，区分度接近零。在这种列上建独立索引，优化器大概率仍然选择全表扫描——因为走索引还得回表，随机 IO 叠加起来反而更慢。判断口径可以粗略用「不同取值个数除以总行数」来衡量，数值越接近零越没有索引价值。原则是单列区分度低的字段不适合做独立索引，但可以作为联合索引的一部分：和高区分度列组合起来一起过滤，或者让联合索引顺带把它覆盖掉。

## 很少被用作查询条件的列

索引本质是给查询用的。如果某列几乎不出现在 `WHERE`、`JOIN`、`ORDER BY` 中，它就很少被优化器选中，建索引只是白白增加写入开销和存储占用。判断方法很直接：翻慢日志里实际执行的语句，看这一列到底出现过几次；上线后长期没被用到的索引，就是该清理的对象。

## 高频更新的列与写多读少的表

每次 `INSERT`、`UPDATE`、`DELETE` 都要同步维护索引树，涉及页分裂、日志写入和随机写盘，所以列更新越频繁，维护成本就越高。索引适合建在读多写少的列上，不适合作为更新频繁列的索引。整张表同理：日志表、操作流水这类写入远多于查询的表，索引数量应尽量控制，必要时定期归档或分区，把热数据和历史数据分开。

## 冗余索引与联合索引的顺序

联合索引 `(a, b, c)` 能覆盖以 `a`、`a+b`、`a+b+c` 为前缀的查询，所以再建一个 `(a)` 就是完全冗余的——最左前缀已经覆盖了它，只会增加写入成本。同时要注意联合索引与单列索引的顺序问题：`(a, b)` 和 `(b, a)` 也不是重复的索引，它们能服务的查询完全不同。

```sql
-- 已有联合索引 idx_abc (a, b, c)
ALTER TABLE t ADD INDEX idx_a (a);      -- 冗余：最左前缀 a 已被 idx_abc 覆盖
ALTER TABLE t ADD INDEX idx_bc (b, c);  -- 不冗余：不含最左列 a，idx_abc 用不上
```

## 小表、超长文本与高回表代价

- 数据量很小的表：几百行的表全表扫描成本可以忽略，建立索引带来的额外 IO 和维护成本反而是负担。
- 超长文本字段：对 `TEXT`、`BLOB` 这类大字段建普通索引意义不大，索引本身也占空间，更常见的做法是只索引前缀（指定索引长度），或者改用全文索引。
- 大量返回整行的查询：非覆盖索引需要回表，如果查询本身就要返回大量完整行，走索引的随机 IO 反而可能比顺序全表扫描更慢。

```sql
ALTER TABLE article ADD INDEX idx_title_prefix (title(20));   -- 只索引前缀，省空间
ALTER TABLE article ADD FULLTEXT INDEX ft_content (content);  -- 或改用全文索引
```

## 已有更优替代手段

用 Redis 缓存挡在数据库前面就能解决的高频查询，不必在数据库侧再建索引；用冗余字段避免 join 关联的表，也不必为 join 列都建索引。同理，能靠改写查询解决的事情先改查询——少返回整行、缩小结果集，往往比多加一条索引更划算。

## 常见追问

**Q：区分度低到什么程度就不值得建索引？**

A：看命中比例就能判断。如果某个取值能命中表里很大比例的行，优化器估算后仍要扫大量数据页，回表的随机 IO 就不划算，这时最多把它放进联合索引当辅助列。

**Q：已经有 `(a, b)`，还需要单独的 `(a)` 吗？**

A：通常不需要，最左前缀 `a` 已经被 `(a, b)` 覆盖。例外是要在 `a` 上做唯一约束，或者 `a` 的查询极多、希望索引更短更省空间时，才值得单独保留。

**Q：只按 `b` 或 `c` 过滤，能用上 `(a, b, c)` 吗？**

A：按最左前缀规则不能直接定位；只有当查询需要的列全在索引里、可以走覆盖扫描时才可能被用上，最终仍取决于优化器的成本估算。

**Q：加了索引反而变慢，可能是什么原因？**

A：回表随机 IO 太多、优化器选错索引、写入被索引维护拖慢，或者索引把缓冲池里的数据页挤了出去。

## 易错点

- 「区分度低的列绝对不能建索引」——错，是不能做独立索引，但它作为联合索引的一部分仍然有价值。
- 「`(a, b)` 和 `(b, a)` 是同一个索引」——错，顺序决定它能服务哪些查询，只有 `(a)` 相对 `(a, b)` 才算完全冗余。
- 「`WHERE` 里出现过的列就该建索引」——错，选择性差或者查询要返回大量整行时，回表代价可能超过全表顺序扫描。
- 「删索引没有风险」——错，先确认它不是别的联合索引的最左前缀，大表还要走在线 DDL 避免锁表。

## 一句话记住

:::tip
索引只服务核心查询：区分度低、写多读少、冗余重复、表小字段大，都不建。
:::
