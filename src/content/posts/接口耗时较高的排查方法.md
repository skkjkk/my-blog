排查耗时接口的通用思路是**先分层定位、再逐层下钻**，不要一上来就猜。耗时可能出现在网络传输、应用内部计算、数据库、缓存、下游 RPC 或 GC 中的任何一层。

1) **先看整体指标定位范围**。用监控/APM（SkyWalking、Arthas、Pinpoint、Elastic APM）看该接口的**全链路耗时分布**，确认是 P50 还是 P99 慢、平均值正常但长尾严重（长尾往往指向 GC、连接池争用或下游抖动）。同时看**调用量与耗时是否相关**：耗时随流量线性上升说明是容量瓶颈，流量不变而耗时突然上升说明是依赖故障。

2) **拆分耗时构成**。用 Trace 把一次请求拆成各段：网关接收、鉴权、业务逻辑、各次数据库查询、各次 RPC 调用、序列化、响应写出。先确定慢在**哪一段**，再深入那一段。

3) **排查数据库**。看慢查询日志与执行计划，是否缺索引、是否全表扫描、是否返回行数过多、是否锁等待；看连接池（`HikariCP`）的**活跃连接数、等待时间、超时次数**，连接池打满会让请求在获取连接时排队；看是否存在长事务、大锁或主从延迟。

4) **排查缓存**。看**缓存命中率**与**穿透/击穿/雪崩**。击穿（热点 key 过期瞬间大量请求打到库）要用互斥重建或逻辑过期；雪崩（大量 key 同时过期或缓存集群宕机）要用过期时间打散、多级缓存和熔断降级；穿透（查不存在的 key）要用布隆过滤器或缓存空值。

5) **排查下游 RPC**。看调用的**超时时间设置**是否合理、是否有**重试放大**（重试会把下游压力翻倍）、连接池是否耗尽、下游服务自身的耗时与错误率。特别注意**级联超时**：上游超时 3s、下游超时 3s 并发重试 3 次，一个慢接口会被放大成雪崩。

6) **排查 JVM 与 GC**。看 GC 日志与监控，**频繁 Young GC 说明分配速率过高**，Full GC 说明老年代压力或内存泄漏；用 Arthas 的 `trace`、`profiler`、`dashboard` 直接观察方法耗时与火焰图，定位到底是哪段代码在消耗 CPU。

7) **排查锁与并发**。看是否有线程池打满（任务排队）、`synchronized` 热点锁竞争、分布式锁等待；用 Arthas 的 `thread` 命令查看线程状态分布，`BLOCKED` 线程多说明存在锁竞争。

8) **排查序列化与数据量**。看响应体是否过大、是否把大对象整个查出来又做内存转换、JSON 序列化是否成为瓶颈；`ObjectMapper` 重复创建、Jackson 的日期格式化、BigDecimal 精度处理都可能拖慢序列化。

9) **排查资源与系统层面**。看 CPU、内存、磁盘 IO、网络带宽是否打满；容器环境下还要看**是否被 CPU limit 限流**（throttling）、内存是否触及上限触发频繁 GC。

10) **排查方法论上的要点**。**必须先复现并拿到证据，再动手改**。优先用**压测**对比不同方案，用**火焰图**定位热点，用 **Arthas** 在生产直接观测而无需改代码发版。同时要考虑**长尾问题** —— 平均值正常不代表没问题，要看 P99 和超时率。定位到原因后，**优化手段要分层考虑**：能改 SQL 就改 SQL，能加缓存就加缓存，能异步化就异步化，能降级就降级，最后才是加机器。
