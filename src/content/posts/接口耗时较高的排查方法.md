接口耗时高，先别猜优化手段，排查的核心是**先分层定位、再逐层下钻**。耗时可能落在网络传输、应用内部计算、数据库查询、缓存、下游 RPC、序列化或 GC 的任何一层，先在链路监控上确认慢在哪一段，再对那一段取证、复现、优化，最后才谈加缓存、异步化和加机器。

## 先看整体指标，缩小范围

用监控与 APM 工具（SkyWalking、Arthas、Pinpoint、Elastic APM）看这个接口的**全链路耗时分布**。第一步分清楚是 P50 慢还是 P99 慢：**平均值正常但长尾严重**，通常指向 GC 停顿、连接池争用或下游抖动；连 P50 也慢，说明这条路径上存在稳定的固定开销。

第二步看**调用量与耗时是否相关**：

- 耗时随流量线性上升，是**容量瓶颈**（线程池、连接池、CPU 或下游配额被打满）。
- 流量不变而耗时突然抬升，是**依赖故障或变更**（下游变慢、配置改动、缓存失效）。

这一步只负责把范围缩到一两层，不下最终结论。

| 症状 | 优先怀疑 | 先看什么 |
| --- | --- | --- |
| 平均值正常但 P99 很高 | GC 停顿、连接池争用、下游抖动 | GC 日志、连接池等待时间、下游 P99 |
| 所有接口一起变慢 | 整机资源或容器限流 | CPU、内存、磁盘 IO、CPU throttling |
| 只有走数据库的接口慢 | 慢 SQL、锁等待、主从延迟 | 慢查询日志、执行计划、锁等待 |
| 流量上涨才变慢 | 容量瓶颈 | 线程池队列、连接池活跃数、CPU 饱和度 |
| 流量没变却突然变慢 | 依赖故障或发布变更 | 下游耗时与错误率、变更记录 |

## 用 Trace 把一次请求拆成耗时片段

拿一条具体慢请求的 Trace，把它拆成若干段：**网关接收与排队、鉴权、业务逻辑、每一次数据库查询、每一次 RPC 调用、序列化、响应写出**。先确定慢在**哪一段**，再深入那一段，避免在十个方向同时改。

看 Trace 有两个细节要注意：

- 看**自身耗时**（span 的独占时间，扣掉子调用），否则父 span 会把下游的慢算到自己头上，越看越糊涂。
- 长尾接口要看**分位数和超时率**，不要只看平均值：平均值正常、P99 恶化，往往是排队、锁等待或 GC 造成的。

## 数据层：数据库与缓存

数据库这一层看四件事：

- **慢查询日志与执行计划**：是否缺索引、是否全表扫描、是否返回行数过多、是否锁等待。
- **连接池（`HikariCP`）**：活跃连接数、等待时间、超时次数。连接池打满时，请求的时间花在排队获取连接上，SQL 本身其实不慢。
- **长事务与大锁**：长事务长期持锁，会把别的请求拖成锁等待。
- **主从延迟**：读写分离后读到从库，延迟高会让「读一次就好」的接口变慢。

缓存这一层先看**命中率**，再看三种典型故障：**击穿**（热点 key 过期瞬间大量请求打到库，用互斥重建或逻辑过期）、**雪崩**（大量 key 同时过期或缓存集群宕机，用过期时间打散、多级缓存和熔断降级）、**穿透**（查不存在的 key，用布隆过滤器或缓存空值）。

## 调用层：下游 RPC 与超时重试

看下游调用时，除了「下游自己慢不慢」，还要看四个放大器：

- **超时时间设置是否合理**：设太长会把慢传导到上游，设太短会人为制造失败。
- **是否有重试放大**：重试会把下游压力翻倍，下游越慢越重试，越重试越慢。
- **连接池是否耗尽**：连接数不够时，请求卡在建连和排队上。
- **下游服务自身的耗时与错误率**：本层慢可能只是上游症状的投影。

特别注意**级联超时**：上游超时 3 秒、下游超时 3 秒、并发重试 3 次，一个慢接口就会被放大成雪崩。排查时要顺着调用链把每层的超时预算对齐，而不是单点调大某个值。

## 运行时：JVM、GC、线程池与锁

JVM 层面先看 GC 日志与监控：**频繁 Young GC 说明分配速率过高**（大量临时对象，常见于循环里拼装大对象、日志与序列化），**Full GC 说明老年代压力或内存泄漏**。

再用 Arthas 直接在生产观测，不用改代码发版：

- `trace` 看某个方法的调用耗时分布，定位是哪段代码慢。
- `profiler` 采火焰图，看 CPU 到底花在哪个热点方法上。
- `dashboard` 看线程与堆的整体水位。
- `thread` 看线程状态分布，`BLOCKED` 线程多说明存在锁竞争。

并发层面看三处：**线程池是否打满**（任务在队列里排队，接口耗时随排队长度上涨）、**`synchronized` 热点锁竞争**、**分布式锁等待**。这三类问题的共同特征是 CPU 不高、耗时却很高。

## 序列化、数据量与系统资源

最后一层常被忽略：

- **响应体过大**：把全量数据一次查出来再塞进 JSON，序列化和网络传输都会成为瓶颈。
- **大对象反复转换**：把大对象整个查出来又做内存转换（实体转 DTO、Map 转实体），CPU 和 GC 一起被拖垮。
- **序列化本身的开销**：`ObjectMapper` 重复创建、Jackson 的日期格式化、`BigDecimal` 精度处理，都可能拖慢序列化。
- **系统资源**：CPU、内存、磁盘 IO、网络带宽是否打满；容器环境下还要看**是否被 CPU limit 限流**（throttling）、内存是否触及上限导致频繁 GC。

## 排查方法论：先取证，再分层优化

**必须先复现并拿到证据，再动手改。** 没有证据的优化只是把猜测换了个位置。取证手段有三个：**压测**对比不同方案、**火焰图**定位热点、**Arthas** 在生产直接观测而无需改代码发版。

同时守住两条判断标准：

- **长尾问题**：平均值正常不代表没问题，要看 P99 和超时率。
- **分层优化顺序**：能改 SQL 就改 SQL，能加缓存就加缓存，能异步化就异步化，能降级就降级，最后才是加机器。

## 常见追问

**Q：线上接口 P99 突然升高，CPU 和数据库看起来都正常，先查哪里？**
A：先看 GC 日志和线程栈。CPU 不高而耗时高，典型的三个原因是 GC 停顿、锁等待、下游抖动，用 `thread` 看 `BLOCKED` 线程数、用 Trace 看下游 span 耗时，几步就能分开。

**Q：代码里只调了一次下游，为什么接口耗时是下游耗时的好几倍？**
A：多半是被重试、连接池等待、序列化和排队放大了。先看调用次数（是否隐含重试）、再看连接池等待时间、最后看响应体大小。

**Q：加机器能解决这个问题吗？**
A：只有容量瓶颈能靠加机器解决。如果是慢 SQL、锁竞争、缓存击穿或下游故障，加机器只是把同样的慢复制到更多实例上。

## 易错点

- **只看平均值**：平均值正常、P99 已经炸了，是最常见的误判来源，长尾必须单独看。
- **不做复现就直接改代码**：没有证据的优化经常改错方向，还把真正的瓶颈掩盖掉。
- **把「调大超时时间」当优化**：它只是把失败推迟，同时放大级联超时和重试风暴。
- **一上来就加缓存或加索引**：缓存会引入一致性问题，索引会让写入变慢；先定位到具体的那一层再动手。

## 一句话记住

:::tip
先分层定位，再逐层下钻；先拿到证据，再动手优化。
:::
