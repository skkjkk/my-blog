子 Agent 模式的本质是**用上下文隔离换结构复杂度**：父 Agent 把某个子任务整体委托给一个独立的 Agent 执行，子 Agent 有自己的上下文、提示和工具集，只把**结论**返回给父 Agent。它带来三项确定收益——主上下文不被中间过程撑爆、权限与故障的爆炸半径可控、子单元可独立评测；代价几乎都发生在交接处——任务描述不完整、结论丢失关键前提、失败无法归因。所以工程重点不是"要不要用"，而是把交接契约、委派判据、预算与深度约束定清楚。

## 它到底隔离了什么

隔离的不是任务，而是**上下文与执行责任**。子 Agent 内部有一整段独立的执行循环：它自己发提示、自己调工具、自己看工具返回的大段原始数据、自己试错重来，这些全部留在它自己的上下文窗口里。父 Agent 的交界面只有两个：进来的**任务描述**和出去的**结论**。正因为中间过程被挡在外面，父 Agent 的主上下文不会被几十次工具返回撑爆，可以继续做全局判断；也正因为中间过程被挡在外面，父 Agent 看不见子 Agent 踩过的坑，这就构成了后面所有挑战的根源。

## 五个优势：隔离、专业、并行、权限、可替换

- **上下文隔离（最主要收益）**：中间过程、试错记录、原始数据、大段工具返回都留在子 Agent 侧，父 Agent 只拿精炼结论，直接缓解主上下文膨胀。
- **专业化**：子 Agent 可以有专属的提示、专属工具集，甚至专属模型。代码审查 Agent 只带静态分析工具，数据清洗 Agent 只带 SQL 工具，工具集越小选错工具的概率越低。
- **并行**：互不依赖的子任务可以同时跑，压缩总墙钟延迟。
- **权限与故障隔离**：子 Agent 天然是权限边界，只给它完成任务所需的最小工具集；某个子 Agent 出错或被攻击，不会污染主上下文，爆炸半径可控。
- **可复用与可替换**：子 Agent 是独立可测的单元，可以单独评测、单独优化模型与提示、单独灰度。

## 五个挑战：从交接损失到循环委派

- **上下文交接处的信息损失（最核心）**：父传给子的任务描述可能不完整，因为父并不知道子需要哪段上下文；子返回的结论可能丢失关键前提，因为父看不到子踩过的坑。
- **委派决策本身的可靠性**：父要判断"该不该委派、交给谁"。该自己做却外包，或该外包却自己做，都会显著降低效率与质量。
- **错误传播与归因困难**：子失败时父只看到一句"失败"，分不清是任务描述不清、子能力不足，还是工具出错。
- **成本与延迟叠加**：子 Agent 有自己的系统提示、工具定义、至少一次模型调用，固定开销不小；串行委派累积延迟，并行委派推高并发与成本。
- **循环委派（乒乓）**：父把任务给子，子又往下委派，形成无限递归或互相推诿。

对策与挑战一一对应：交接用**结构化契约**（明确输入、输出 schema、成功标准、不可做的事），并要求子返回**结论 + 依据 + 未决问题**三部分；委派给**明确判据**（如"需要独立上下文且输出可验证"才委派），并把**委派决策正确率**当成指标记录；失败要求子返回**结构化失败原因分类**并保留**可追溯的子轨迹**；成本上只在**隔离收益确实大于开销**时才用，小任务直接父 Agent 做；循环上**限制委派深度**（如最多 1~2 层）、**子 Agent 不允许再委派**、**总预算与总步数父子共享**。

## 边界清单：八条必须写进设计的约束

| 边界项 | 具体约束 |
|---|---|
| 深度与递归 | 明确最多几层委派，超层直接拒绝而不是降级 |
| 权限继承 | 子只拿任务必需的工具子集，不继承父的全部权限；父对子只能收窄，不能放大 |
| 预算共享 | 父子共用同一份 token 与时间预算，防止子无限消耗 |
| 结果契约 | 子返回什么内容、什么格式、什么算成功，必须事先定义 |
| 失败语义 | 子失败是返回错误让父重试，还是父接管，必须事先定死 |
| 可观测性 | 父子调用挂同一个 trace id，能拼出完整调用树 |
| 幂等与副作用 | 子产生的外部副作用如何回滚与补偿 |
| 共享状态 | 父子通过外部存储共享状态，而不是靠来回传消息 |

## 最小交接契约长什么样

契约要显式到"换个人（或换个模型）照着也能执行"的程度。下面这份结构不是某个框架的规定，只是一份可直接抄的骨架，字段按任务增删：

```json
{
  "objective": "一句话说清要交付什么",
  "inputs": ["父侧已确定的约束、数据位置、上游结论"],
  "output_schema": { "conclusion": "string", "evidence": ["依据"], "open_questions": ["未决"] },
  "success_criteria": ["可程序化校验的验收条件"],
  "forbidden": ["不许做的事，如不得写库、不得再委派"],
  "budget": { "max_steps": 20, "max_tokens": "共享自父预算" }
}
```

配套要求是 `evidence` 与 `open_questions` 两个字段**不能为空占位**：父 Agent 是拿它们做校验和接续判断的，只有 `conclusion` 的返回等于把归因责任又推回给了看不见过程的父。

## 常见追问

**Q：子 Agent 和普通的工具调用（function calling）有什么区别？**
A：工具调用是父 Agent 在自己上下文里执行一步动作，结果回到父上下文；子 Agent 是一整段独立上下文里的执行循环，交回的只有压缩后的结论。选哪个看"中间过程值不值得占父上下文"。

**Q：并行开子 Agent 是不是更省钱？**
A：不是。并行压缩的是墙钟延迟，成本反而更高——每个子 Agent 都要带自己的系统提示、工具定义，并至少跑一次模型调用。省成本靠的是别委派小任务，不是靠并行。

**Q：子 Agent 的权限该怎么给？**
A：按任务给最小工具集，父对子只收窄不放大；带写操作的工具还要配幂等键与回滚方案，否则子侧半途失败会留下脏数据。

**Q：子 Agent 返回的结论能直接采信吗？**
A：不能，要按不可信输入做校验。子 Agent 同样可能被提示注入，也可能自信地答错，所以关键结论必须带依据，必要时父侧抽样复核原始证据。

## 易错点

- **把子 Agent 当并行加速器**：子任务本身很小的时候，系统提示、工具定义和至少一次调用的固定开销会吃掉全部收益。小任务直接父 Agent 做。
- **只传任务标题，不传上下文**：父以为子会自己去找，子其实缺关键约束，最后"答得漂亮但答错题"。输入、验收标准、禁止项都要写进契约。
- **让子 Agent 继承父的全部权限**：图省事的后果是爆炸半径被放大。正确做法是给最小子集，父对子只做权限收窄。
- **拿"子 Agent 说完成了"当成功**：要用程序化验收兜底，并要求返回结论、依据、未决问题三部分，父侧校验后再采信。
