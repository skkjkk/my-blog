MCP 的安全模型可以分成**六个层面**：传输与认证、授权与权限、工具执行、内容与上下文、数据与隐私、供应链与审计。但必须先说清一个前提：**MCP 本身只提供"连接与能力描述的标准化"，它不提供安全保证**。安全仍然要由 Host 侧与 Server 侧各自承担，下面每一层说的都是"该由谁在什么位置补上这一道防线"。

## 传输与认证层：链路本身怎么保护

本地 Server 走 **stdio**，安全边界是**进程隔离** —— Server 只能访问宿主愿意给它的一切，它拿到什么权限取决于宿主怎么启动它。远程 Server 走 **SSE / Streamable HTTP**，必须做 **TLS 加密**与**身份认证**，其中 **OAuth 2.1 是规范推荐**的做法，支持授权服务器与令牌委托。**要点**：令牌应**短期有效、可撤销、按最小范围签发**，并且要区分"用户身份"与"应用身份" —— 是"某个用户授权了这次访问"，还是"某个应用在代表自己调用"，两者的授权范围与追责对象完全不同。

## 授权与权限层：谁能做什么、由谁说了算

MCP 规范定义了**授权框架**，但具体的权限粒度由实现决定。核心原则是**用户可见、可撤回**：用户在 UI 上能看到"这个 Server 能访问什么"，并能随时撤销授权，而不是在配置文件里默默写死一堆 scope。另一条常被忽略的要求是 **Server 侧仍必须做资源级鉴权** —— 令牌只说"这个用户有权访问这个服务"，至于"能访问哪些具体资源"，要由 Server 拿到参数后自己再判一次。只做认证不做资源级鉴权，等于把越权判断全部押在 Client 的自觉上。

## 工具执行层：最关键的一层

这一层是攻击者收益最高的地方，也是设计时最容易漏的。要点如下：

- **参数校验必须在执行前完成**：schema 校验只是及格线，还要做语义校验（路径是否越界、域名是否合法）与跨参数一致性校验（声明的资源 id 与路径是否匹配）。
- **权限裁决在模型之外**：模型只负责提议调用，是否执行由 Server 侧的确定性代码裁决，模型的输出不能成为授权依据。
- **工具按风险分级**：只读 / 可逆写 / 不可逆三档，不可逆操作需要额外确认。
- **幂等键**：防止超时重试造成重复副作用，写类工具尤其需要。
- **超时与限流**：避免单次调用拖死会话或被当作放大攻击的入口。
- **结果裁剪**：防止超大结果与敏感字段直接进入模型上下文，撑爆窗口的同时也把数据带出了边界。

还有一条：**Server 端同样不能信任 Client 传来的 user_id** —— 身份应当从**验证过的令牌**里取，而不是从请求体里读。

## 内容与上下文安全层：进入模型之前先分级

Server 返回的数据在进入模型上下文前要**信任分级**（可信的 / 半可信的 / 完全不可信），**不可信内容必须显式标记**并与指令隔离，这是防**间接提示注入**的主要手段 —— 一份网页、一条 issue 正文都可能夹带指令。同一层里还要做三件事：Server 返回的**敏感字段应脱敏或按权限裁剪**；写入类操作要防止**路径穿越与 SSRF**；要防**工具描述投毒** —— Server 在工具描述里塞入恶意指令，模型读到描述就可能被操控，这是 **MCP 特有的攻击面**，因为描述是模型必然要读的"说明书"。

## 数据与隐私层：进来多少、留下多少

原则是**最小化返回**，只给模型当前任务真正需要的字段，而不是把整条记录丢进去。**传输与存储脱敏**要一并做：日志、审计记录同样要脱敏，不是只有响应体需要脱敏，很多事故是日志里躺着明文凭证。对外要有**用户数据不进入训练**的承诺，对内要有**跨 Server 的数据流向可追溯** —— 能回答"哪个 Server 的数据进了哪一次模型请求"，否则出了问题连影响面都圈不出来。

## 供应链与审计层：第三方代码与事后追责

MCP Server 常常是**第三方代码**，接入它就等于把对方的代码拉进了自己的信任边界，本质上扩大了攻击面。做法是：**来源审核与版本锁定**、**最小权限暴露**（按需启用工具，而不是把 Server 的能力全量打开）、**能力声明审计**（Server 声称的能力与实际行为是否一致）、**依赖漏洞扫描**、以及对 Server 做**隔离与沙箱**。与之配套的是审计：记录**谁在何时、代表哪个身份、调用了哪个 Server 的哪个工具、传了什么参数、返回了什么结果、是否被拒绝**，这是事后追责与发现异常行为的唯一依据。

## 边界与最小安全基线

**MCP 解决的是"怎么接工具"，不解决"该不该让工具做这件事"**。它**没有**提供：工具越权防护、提示注入防护、结果可信度保证 —— **这些必须在 Host 侧用能力令牌、信任分级、审计告警来实现**。最常见的误区就是"用了 MCP 就安全了"。把上面的层面压成一份能落地的基线，大致是这样：

| 基线项 | 挡的是什么风险 | 最小做法 |
|------|------|------|
| 远程链路 | 窃听、冒充 | 一律 TLS + OAuth 2.1，令牌短期有效、可撤销、最小范围 |
| 工具描述 | 描述投毒 | 视为不可信输入，进入上下文前与指令隔离 |
| Server 返回内容 | 间接提示注入 | 一律标记信任级别，不可信内容不直接当指令用 |
| 不可逆操作 | 误删误改、重复执行 | 走人工确认，并用幂等键防重试副作用 |
| 凭证 | 凭证泄漏 | 凭证不落 Server，身份从验证过的令牌中取 |
| 审计 | 事后无法追责 | 全量记录调用方、身份、工具、参数、结果与拒绝原因 |

## 常见追问

**Q：用了 OAuth 2.1，MCP 就算安全了吗？**
不算。OAuth 只解决"调用方是谁、被授权了什么范围"，资源级鉴权、参数校验、结果脱敏、提示注入防护都要在 Server 与 Host 侧单独做。

**Q：为什么权限裁决一定要放在模型之外？**
因为模型的输出只是概率性提议，可能被提示注入劫持，也可能幻觉出不存在的参数。裁决点必须是确定性的代码，模型最多只能发起请求。

**Q：工具描述投毒和普通提示注入有什么区别？**
普通注入发生在内容里，还有机会在内容进入上下文时拦一道；工具描述投毒发生在 Server（供应链）侧，而描述是模型一开始就读的"工具说明书"，信任链更长，只能靠来源审核、描述隔离与能力声明审计来防。

**Q：本地 stdio 的 Server 就可以不管安全了吗？**
不行。进程隔离只划定了边界，Server 拿到的仍是宿主赋予的权限，最小权限暴露、沙箱与审计同样必要。

## 易错点

- **把 MCP 当安全机制**：它标准化的是连接与能力描述，安全保证要由 Host 侧与 Server 侧各自实现。
- **相信 Client 传来的 user_id**：身份只能从验证过的令牌中取，请求体里的身份字段一律视为不可信。
- **令牌只做认证不做范围控制**：必须短期有效、可撤销、按最小范围签发，并区分用户身份与应用身份。
- **只脱敏响应、不脱敏日志与审计**：存储、日志、审计记录同属数据面，漏掉任何一处都等于没脱敏。

## 一句话记住

:::tip
MCP 只标准化连接，不承诺安全；裁决放在模型之外，审计必须保留全量。
:::
