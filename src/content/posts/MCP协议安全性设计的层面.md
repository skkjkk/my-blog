MCP 的安全模型可以分成**五个层面**，但必须先说清一个前提：**MCP 本身只提供"连接与能力描述的标准化"，它不提供安全保证**。安全仍然要由 Host 侧与 Server 侧各自承担。

1) **传输与认证层**。本地用 **stdio**，安全边界是**进程隔离** —— Server 只能访问宿主愿意给它的一切。远程用 **SSE / Streamable HTTP**，必须做 **TLS 加密**与**身份认证**（OAuth 2.1 是规范推荐，支持授权服务器与令牌委托）。**要点**：令牌应**短期有效、可撤销、按最小范围签发**，并区分"用户身份"与"应用身份"。

2) **授权与权限层**。MCP 规范定义了**授权框架**，但具体粒度由实现决定。核心原则是**用户可见、可撤回**：用户在 UI 上能看到"这个 Server 能访问什么"，并能随时撤销授权。**Server 侧仍必须做资源级鉴权** —— 令牌说"这个用户有权访问"，但"能访问哪些资源"要由 Server 按参数再判一次。

3) **工具执行层（最关键）**。**参数校验**必须在执行前完成（schema + 语义 + 跨参数一致性）；**权限裁决在模型之外**（模型只提议，Server 裁决）；**工具按风险分级**（只读 / 可逆写 / 不可逆，不可逆需额外确认）；**幂等键**（防重试造成重复副作用）；**超时与限流**；**结果裁剪**（防止大结果与敏感字段进入上下文）。**Server 端同样不能信任 Client 传来的 user_id** —— 身份应从**验证过的令牌**中取。

4) **内容与上下文安全层**。Server 返回的数据在进入模型上下文前要**信任分级**（可信的 / 半可信的 / 完全不可信），**不可信内容必须显式标记**并与指令隔离，防止**间接提示注入**。Server 返回的**敏感字段应脱敏或按权限裁剪**；写入类操作要防止**路径穿越与 SSRF**。同时要防**工具描述投毒** —— Server 在工具描述里塞入恶意指令，模型读到后可能被操控（这是 MCP 特有的攻击面）。

5) **数据与隐私层**。**最小化返回**（只给模型需要的字段）；**传输与存储脱敏**（日志、审计记录同样要脱敏，不是只有响应要脱敏）；**用户数据不进入训练**的承诺；**跨 Server 的数据流向可追溯**（哪个 Server 的数据进了哪次模型请求）。

6) **Server 供应链层**。MCP Server 常常是**第三方代码**，本质上扩大了攻击面。做法：**来源审核与版本锁定**、**最小权限暴露**（按需启用工具）、**能力声明审计**（Server 声称的能力与实际行为是否一致）、**依赖漏洞扫描**、**对 Server 做隔离与沙箱**。

7) **审计与可观测层**。记录**谁在何时、代表哪个身份、调用了哪个 Server 的哪个工具、传了什么参数、返回了什么结果、是否被拒绝**。这是事后追责与发现异常行为的唯一依据。

8) **一个必须记住的边界**。**MCP 解决的是"怎么接工具"，不解决"该不该让工具做这件事"**。它**没有**提供：工具越权防护、提示注入防护、结果可信度保证。**这些必须在 Host 侧用能力令牌、信任分级、审计告警来实现。** 常见误区是"用了 MCP 就安全了"。

9) **最实用的安全基线**。**① 远程 Server 一律 TLS + OAuth**；**② 工具描述视为不可信输入**；**③ Server 返回内容一律标记信任级别**；**④ 不可逆操作走人工确认**；**⑤ 凭证不落 Server**；**⑥ 全量审计**。
