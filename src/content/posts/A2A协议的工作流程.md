A2A 的工作流程可以分成六个阶段，核心是"**发现 → 匹配 → 委托 → 跟进 → 交付**"：编排方先拉取候选 Agent 的 Agent Card 拿到结构化能力清单，据此选出执行方，再按 Card 声明的 schema、携带**自己的**身份凭证发起委派，然后在流式通道上跟进状态、必要时多轮补充消息，最后从 Artifact 取回成果，整合进自己的流程。

## 六个阶段一览

六个阶段的分工可以先用一张表固定下来，后面各节展开细节。

| 阶段 | 编排方的主要动作 | 关键对象 | 拿到什么 |
| --- | --- | --- | --- |
| 发现 Discovery | 逐个拉取候选 Agent 的 Agent Card | Agent Card | 结构化的能力清单 |
| 匹配 Selection | 按描述与结构化能力筛选执行方 | Agent Card | 定下协作方 |
| 委派 Delegation | 按 schema 构造请求，携带自身凭证调用 | Task | task id 与初始状态 |
| 跟进 Streaming | 订阅流式通道，接收状态更新与中间产物 | 状态流 | 过程可见、可中断 |
| 多轮 Multi-turn | 收到 input-required 时补充消息 | Message | 澄清与补充材料 |
| 交付 Delivery | 取回 Artifact 并整合，失败时决定重试或降级 | Artifact | 最终成果 |

## 发现与匹配：把"谁有什么能力"变成可检索的数据

A2A 复用标准 Web 基础设施，Agent Card 放在约定路径 `/.well-known/agent-card.json`，编排方拿到候选列表后逐个拉取。Card 是一份机器可读的 JSON，包含名称、描述、技能列表、输入输出模式、交互模式支持情况、端点地址与认证方式。**这一阶段的目的就是把"谁有什么能力"变成结构化的、可供检索的数据**，而不是靠人记着谁能干什么。

匹配依据两类信息：Card 里的自然语言描述，以及结构化的能力声明。筛选可以由**规则**做（技能标签精确匹配），也可以由**模型**做（语义匹配，并权衡成本、延迟、负载）。**这是 A2A 最有价值的部分**——协作方不是部署时写死的，而是运行时决定的，所以 Card 描述写得准不准，直接决定选路准不准。

## 委派与流式跟进：状态托管在服务端

委派这一步最容易搞错的细节是身份：Client 按 Card 声明的 schema 构造任务请求，**携带自己的身份凭证**（而非对方的），向 Server 端点发起调用。Server 创建 Task、分配 id，状态先进入 `submitted`，随后转 `working`。**客户端可以立即拿到 task id 并异步跟进**，不必挂着等一个可能跑很久的结果。

跟进走 Server-Sent Events 或等价的流式通道，持续接收状态更新与中间产物。状态流转为 `submitted → working → (input-required) → completed / failed / canceled`。若进入 **`input-required`**，说明对方需要补充信息，这是可继续的中间态，客户端应回复消息并继续，而不是把它当成失败。

## 多轮消息与交付收尾

双方通过 Message 交换结构化内容（文本、文件、数据部件），完成澄清、补充材料、协商调整。**这一步是 A2A 区别于"一次调用"的关键**——长程协作往往需要多轮，一次请求一次响应远远不够。

任务完成后，成果以 **Artifact** 形式交付。客户端获取 Artifact（可能是文件引用或结构化数据），**整合进自己的流程**。若状态为 `failed`，则获取失败原因并决定**重试、换执行方还是降级**；整个任务可被**取消**。消息是过程沟通，Artifact 才是交付物，两者不要混为一谈。

## 完整时序

把六个阶段串起来看，一条完整链路是这样的：先按约定路径取 Card，再在本地完成选择，然后用自身凭证把任务投递出去，接着订阅流、必要时补消息，最后取回产物并整合。注意中间没有任何一步要求调用方一直阻塞等待——这正是它能支撑长任务的原因。

```
编排方  →  发现: GET /.well-known/agent-card.json
编排方  →  匹配: 依据 Card 选择执行方
编排方  →  委派: POST /tasks  (携带自身凭证, 符合 schema)
Server  →  返回: task id, status=submitted → working
Server  →  推送: 流式状态更新 + 中间产物 (SSE)
编排方  →  补充: 收到 input-required 时回复 Message
Server  →  推送: status=completed + Artifact
编排方  →  收尾: 取回 Artifact 并整合
```

## 工程要点：五条不能省的约束

1. **认证在发起时完成**，不是靠 Card 里的明文密钥——Card 只声明**认证方式**，不携带凭据。
2. **长任务必须异步化**，客户端要有断线重连与状态补查能力，否则一次网络抖动就丢掉进度。
3. **产物要能外置引用**，大文件不直接塞进消息，只回摘要加可寻址引用。
4. **失败要可归因**，区分对方能力不足、参数错误、超时、鉴权失败，归因错了重试就是白重试。
5. **全链路要有统一 trace id**，否则跨 Agent 排障极其困难。

## 与单 Agent 内部循环的差别

单 Agent 内部循环是"**同一进程内的同步调用**"：调工具、拿结果、接着下一步，失败重试都在一个进程里，边界清楚。A2A 是"**跨进程的异步委托**"——对方是独立主体，可能很慢、可能拒绝、可能挂掉，也可能做到一半反过来问你要更多信息。

因此分布式的那套问题一个都躲不掉：必须处理**超时、重试、幂等、对方不可用、对方拒绝**这些情况。把 A2A 当成远程函数调用来设计，几乎必然会在长任务上出问题。

## 常见追问

Q：为什么说匹配阶段是 A2A 最有价值的部分？
A：因为它让协作方在运行时决定。部署时写死的编排只能跟固定对象配合，而按 Card 匹配可以随时接新 Agent，代价是必须保证 Card 描述准确。

Q：`input-required` 和 `failed` 有什么区别？
A：`input-required` 是可继续的中间态，等调用方补信息、补材料或做协商；`failed` 是终态，只能取失败原因后决定重试、换执行方还是降级。

Q：Card 里写了认证方式，是不是就等于有密钥了？
A：不是。Card 只声明对方要求哪种认证方式，凭据由发起方在请求时携带自己的。把凭据写进 Card 属于把公开文档当保险箱。

Q：对方跑到一半失联了怎么办？
A：靠 task id 异步补查状态，客户端要有断线重连与状态补查能力；仍然拿不到就按超时处理，并保留可归因的失败原因。

## 易错点

- 把 Card 当凭据用：Card 只声明认证方式，真正发起时携带的是自己的凭证。
- 把 `input-required` 当失败处理：它是等着你补充消息的中间态，误判会白扔掉一个本可完成的任务。
- 同步阻塞等结果：长任务必须异步化，靠 task id 跟进，否则调用链一长就被超时打断。
- 把中间消息当交付物：Message 是过程沟通，最终成果走 Artifact，混用会让下游拿不到确定性产物。
