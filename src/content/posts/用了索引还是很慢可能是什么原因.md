**"加了索引但没走索引"和"走了索引但依然慢"是两类完全不同的问题** —— 第一类是**优化器选错了执行计划**，第二类是**执行计划没问题，但代价依然很高**。排查必须先分清是哪一类。

## 第一类：索引根本没被用上（优化器选错）

- **⚠️ 索引列上用了函数/表达式**：`WHERE DATE(create_time)=...` → 改写 SQL 或建函数索引
- **⚠️ 类型隐式转换**：`varchar` 列传数字 → **参数类型与字段类型对齐**
- **违反最左前缀**：`WHERE b=?` 用不上 `(a,b,c)`
- **`LIKE '%x'`** 前缀通配 → 索引失效
- **`OR` 连接了无索引的列** → 整条语句放弃索引
- **否定条件**（`!=`、`NOT IN`、`IS NOT NULL`）→ 优化器认为全表扫描更划算
- **统计信息过期** → `ANALYZE TABLE` 重新收集
- **优化器估算成本出错**（`rows` 预估与实际差距大）→ 必要时 `FORCE INDEX`（**最后手段**）

## 第二类：走了索引，但依然慢（更常见、更难）

- **⭐ 大量回表** —— 二级索引 + 非覆盖索引 → **N 次随机 IO** → **可能比全表扫描更慢**
- **⭐ 扫描行数太大** —— 索引把"全表扫"换成了"扫了 90% 的行"，本质没省事
- **⭐ 排序/分组无法利用索引** → `Using filesort` / `Using temporary` → **排序本身是 O(n log n) 的内存+磁盘操作**
- **⭐ 回表随机 IO 的放大** —— 查 10 万行 → 10 万次随机 IO

:::tip
**判断依据：对比 `rows`（预估扫描）与实际返回行数。** 接近 1 = 索引高效；比值极大 = **白建索引了**。
:::

## 最核心的判断方法

看 `EXPLAIN` 的 `rows` 与 `filtered`
- `rows` = 预估扫描行数；`filtered` = 过滤后剩余百分比
- **`rows × filtered` 才是真正参与比较的数据量**
- **这个值远大于实际需要的行数 → 索引没起到筛选作用**，只是"换了个更贵的全表扫"

## 六大"索引失效但不报错"的隐蔽原因

- **回表太多**（如 `SELECT *`）
- **`ORDER BY` 与索引顺序不一致** → filesort
- **`GROUP BY` 无法利用索引有序性** → temporary
- **联合索引在范围查询后的列失效**
- **`DISTINCT` / `UNION` 需要额外去重排序**
- **`COUNT(*)` 在 InnoDB 上无法用索引统计**（MVCC 特性）

## 排查流程（可直接照做）

一条可复现的路径：拿着 `EXPLAIN` 的字段逐项读，不要凭"加了索引应该快"的直觉猜。先定类型，再定量级，最后才动手改。前两步回答"索引有没有被选上"，后四步回答"选上了还值不值"。若在前两步就发现索引根本没被选上，直接回到第一类的失效清单；若是后几步才暴露问题，优化方向就落在覆盖索引和排序上。

```
① EXPLAIN 看 type：ALL=全表扫描（索引没用上）；range/ref=用上了
② 看 key：实际用的索引；possible_keys 与 key 不一致 = 优化器放弃了候选
③ 看 rows × filtered：扫描量级是否合理
④ 看 Extra：Using filesort / Using temporary / Using index condition
⑤ EXPLAIN ANALYZE：对比「预估行数」vs「实际行数」→ 偏差大 = 统计信息过期
⑥ 若用上了索引仍慢 → 看是否回表过多、是否排序落盘
```

## 优化手段（按优先级）

- **① 改写 SQL 让索引真正可用**（函数移走、类型对齐、调整联合索引顺序）
- **② 构造覆盖索引** —— 消除回表（**收益最大的单项优化**）
- **③ 减少排序/临时表** —— 让 `ORDER BY` / `GROUP BY` 顺着索引顺序
- **④ 强制指定索引** —— `FORCE INDEX` / `IGNORE INDEX`（**最后手段**，随数据分布变化会失效）
- **⑤ 更新统计信息** —— `ANALYZE TABLE`
- **⑥ 架构层** —— 缓存、分区表、读写分离、分库分表

## "重建索引"不是万灵药

很多人在 `EXPLAIN` 显示 `ALL` 时第一反应是"重建索引"。但**索引本来就在** —— 问题在于**优化器基于错误的成本估算放弃了它**。重建索引不会改变估算，除非**统计信息过期**，而那用 `ANALYZE TABLE` 就能解决（**快得多**）。

:::tip
**盲目重建大表索引是耗时且危险的操作（会产生大量 IO 与主从延迟）。**
:::

## 索引不是越多越好

索引多了 → 优化器选择空间变大、**可能选错**；写入变慢；存储膨胀。**"加了索引反而更慢"的另一个常见原因是索引过多导致选错计划或写入成本上升。**

每个二级索引都是一份独立维护的有序结构，还要带上主键列；写入时每多一个索引就多一次维护。所以索引应该按真实的查询模式建，而不是"怕慢就先加上"。

## 常见追问

**问：怎么一眼分清是"索引没被用上"还是"用了索引仍然慢"？**
**答：** 先看 `EXPLAIN` 的 `type`：`ALL` 说明索引根本没被选上，属于第一类；`range`/`ref` 这类说明用上了，属于第二类，要去查回表、排序和扫描量。

**问：判断索引到底有没有帮上忙，看哪个指标？**
**答：** 看 `rows × filtered`，它才是真正参与比较的数据量；再配合 `Extra` 里的 `Using filesort`、`Using temporary`、`Using index condition` 判断代价花在哪。

**问：优化按什么顺序做？**
**答：** 先改写 SQL 让索引真正可用，再造覆盖索引消除回表，然后减少排序和临时表，接着 `ANALYZE TABLE` 更新统计信息，`FORCE INDEX` 只留作最后手段。

**问：`type` 显示 `ALL`，重建索引能解决吗？**
**答：** 一般不能。索引本来就在，是优化器基于错误的成本估算放弃了它；只有统计信息过期时才有必要，而那用 `ANALYZE TABLE` 就够了，比重建大表索引安全得多。

## 易错点

- **直觉：加了索引，查询就一定走索引。** 正确说法：优化器是按成本选计划的，列上有函数、隐式类型转换、违反最左前缀、统计信息过期，都会让它放弃索引。
- **直觉：走索引一定比全表扫快。** 正确说法：非覆盖索引要回表，大量随机 IO 可能比一次全表扫更慢；扫了 90% 的行的索引扫描，本质没省事。
- **直觉：`type=ALL` 就该重建索引。** 正确说法：索引一直在，问题出在成本估算上，重建不改变估算，`ANALYZE TABLE` 更快也更安全。
- **直觉：索引越多，查得越快。** 正确说法：索引一多，优化器选择空间变大反而更容易选错，写入维护成本和存储也跟着涨。

## 一句话记住

:::tip
**先分清是没走索引还是走了仍慢，再用 `rows × filtered` 量化。**
:::
