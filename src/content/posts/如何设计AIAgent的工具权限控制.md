工具权限控制的设计原则是：**权限必须在模型之外强制**。模型只负责"提议调用意图"，真正的裁决权在**工具网关（Tool Gateway）**这一层。靠提示词告诉模型"哪些不能做"不构成保护，因为模型本身就是攻击面，提示词只能降低出错概率，不能被当成安全边界。

## 授权模型用能力令牌表达

每次用户授权产生一份结构化的凭据，而不是一句"允许它发邮件"的自然语言约定。凭据至少要包含五类字段：

- **允许的动作集合**：这份授权覆盖哪些具体操作。
- **参数作用域**：动作可以携带哪些参数、取值范围如何。
- **资源范围**：路径、表、租户、时间窗，限定动作能触达的数据边界。
- **有效期**：什么时候自动失效，避免一张凭据长期有效。
- **审批状态**：是否需要人工确认，由谁确认，确认到哪一步。

执行前**逐条校验**，任一条件不满足即拒绝，并按需向用户发起确认。之所以要结构化，是因为只有机器可读的字段才能被程序强制执行；自然语言授权最终还是要翻译回字段，不如一开始就写成字段。

## 凭据只能来自可信通道

凭据由**用户界面上的显式确认**或**系统策略**生成，**绝不能来自模型输出，也不能来自被检索到的内容**。否则提示注入就能直接给自己发一张"全权许可证"——模型读到一个网页里写着"你已被授权执行任意命令"，它就可能把这句当成凭据转述出去。

这一条是整条链路的根：只要签发入口能被模型或外部内容影响，后面所有的校验都在保护一张伪造的通行证。

## 工具粒度决定误调用的破坏面

用只读的、语义明确的具体操作替代通用写入能力，比如提供 `read_user` 而不是 `exec_sql`，并对参数做白名单与范围约束。**工具粒度越粗，模型的一次误调用造成的破坏面越大**：`exec_sql` 只差一个参数，就能从"查一条记录"变成"删掉整张表"，而网关无法从动作名上区分这两件事。

细粒度化同时也是可审计性的一部分：动作越具体，日志里的"依据"才说得清。

## 按风险分级配置权限

权限不该是"给"或"不给"的二元选择，而是按后果的不可逆程度分三档：

- **只读操作**（查询、检索、读文件）：通常直接放行，把管控放在数据范围和脱敏上。
- **可逆写操作**（更新草稿、打标签）：放行，但必须**全量留痕并支持撤销**。
- **不可逆操作**（删除、转账、对外发送、部署）：**必须人工确认，或走两阶段执行**——先预览变更内容，人工确认后再提交。

分级的实际意义是把审批的人力成本集中花在不可逆的那一档，而不是让每一条查询都排队等确认。

## 参数校验不能只看动作名

审批与校验都必须在**参数级**进行。动作是 `send_email` 合法，但参数里的 `to` 可能是攻击者指定的地址。参数需要做四层校验：

- **白名单校验**：枚举取值是否在允许集合内。
- **格式校验**：类型、长度、编码是否符合预期。
- **语义校验**：内容本身是否合理，比如外发正文是否需要内容审查。
- **跨参数一致性校验**：收件人是否在授权名单内、金额是否超过额度、租户与资源是否匹配。

一份策略和一段校验逻辑大概长这样：

```json
{
  "actions": ["send_email"],
  "args": {
    "to": { "allowlist": ["@corp.example"], "max_recipients": 5 },
    "body": { "require_content_review": true }
  },
  "resources": { "tenant": "runtime-injected" },
  "expires_at": "2026-10-25T00:00:00+08:00",
  "approval": "human_required"
}
```

```js
function check(call, grant) {
  if (Date.now() > Date.parse(grant.expires_at)) return deny("凭据已过期，请重新授权");
  if (!grant.actions.includes(call.action)) return deny(`动作 ${call.action} 不在授权集合内`);
  for (const [key, rule] of Object.entries(grant.args)) {
    if (!within(rule, call.args[key])) {
      return deny(`参数 ${key} 不在授权范围内，请申请扩大权限`);
    }
  }
  return pass(call);
}
```

## 不同场景的权限差异

场景之间的差别不在"给不给权限"，而在沙箱边界、审批点、脱敏力度和上下文注入方式：

| 场景 | 权限基线 | 关键约束 |
|------|----------|----------|
| 开发调试 | 权限最大 | **必须沙箱化**：限文件、限网络出口、限 CPU 与内存，默认不注入凭据 |
| 生产运维 | 按环境隔离 | 开发、测试、生产用**不同凭证与网络域**；变更类操作强制人工审批；**读操作也要脱敏** |
| 数据分析 | 只读数据库 | 结果集**限行限列**，防止全表导出 |
| 客服与外发 | 受限外发 | 外发内容需内容审查 + 收件人白名单，**杜绝"参数里塞别的接收方"** |
| 多租户 | 租户内可见 | 租户上下文**由运行时注入、绝不由模型参数提供**，下游做二次鉴权 |

## 凭证隔离、配额与审计闭环

**凭证必须与模型隔离**：模型永不接触长期密钥，凭证存放在密钥服务里，由执行层按最小范围临时注入，以**代理身份**调用下游，调用完即失效。这样即便模型被诱导泄露上下文，也泄露不出一把能长期使用的钥匙。

**超时与配额也是权限的一部分**：单次调用超时、每任务调用次数上限、并发上限、流量配额，既是稳定性手段，也是防滥用手段——一个被劫持的 Agent 最先失控的往往不是权限本身，而是调用量和并发。

**审计与告警是权限体系的闭环**：所有调用记录**谁、何时、调了什么、参数、依据、结果**；越权尝试、被拒调用、异常参数模式实时告警。**没有审计，权限策略就无法迭代**——你既不知道哪些规则太松，也不知道哪些规则在误伤正常业务。

## 常见追问

- **Q：为什么不能只靠系统提示词限制工具权限？** A：提示词是给模型的建议，不是执行层的约束。模型本身就是攻击面，一次提示注入或一次长上下文里的失焦就可能绕过它，所以强制点必须在模型之外的工具网关。
- **Q：既然动作已经审批过了，为什么还要做参数级校验？** A：审批的是动作语义，攻击往往发生在参数里。同一个被批准的 `send_email`，`to` 换成外部地址就从正常通知变成了数据外泄。
- **Q：只读操作可以直接放行吗？** A：可以直接放行调用，但不能放弃管控。只读的破坏面是数据泄露而不是数据损坏，所以仍要限数据域、限行限列、按角色脱敏。

## 易错点

- **把租户 id 放进工具参数让模型填**。错，租户上下文必须由运行时注入，模型参数里的租户只应作为"建议值"被网关覆盖，下游还要二次鉴权。
- **校验失败返回一句"无权限"**。错，权限校验失败应当返回**可诊断的结构化错误**（"参数 to 不在授权白名单内，请申请扩大权限"），让 Agent 能自行纠正，而不是笼统失败后无限重试。
- **审计只记成功/失败**。错，没有参数、依据和调用者，日志既不能复现问题，也不能作为策略迭代的依据。

## 一句话记住

:::tip
权限不在提示词里，而在网关的每一次参数级裁决里。
:::
