工具调用（Tool Calling / Function Calling）是指模型不直接输出答案，而是输出一份**结构化的「调用哪个工具、参数是什么」的请求**，由宿主程序真正执行后把结果回传，模型再基于结果继续输出。**模型只表达意图，执行权始终在程序手里。** Spring AI 把这件事做成了声明式的：方法加 `@Tool` 注解就是工具，方法签名自动生成参数 JSON Schema，解析、执行、回填的循环由框架驱动。

## 工具调用到底是什么

模型本身是一个文本生成器，它没有办法自己去查数据库、调接口、读文件。工具调用补的正是这一层：让模型用一段结构化的 JSON 说出「我想调哪个工具、带什么参数」，再由程序去落地执行。

所以它的本质是一次**权责切分**——模型负责决定「要做什么」，程序负责「能不能做、怎么做、做完怎么样」。模型只把话组织好，事实得由工具拿回来；这也解释了为什么工具返回的内容会被当成事实使用，而模型自己「回忆」出来的数字往往不可靠。

## 一次调用要经过哪四步

| 步骤 | 谁来做 | 产出 |
|------|--------|------|
| 注册工具 | 开发者 | 工具名 + 描述 + 参数 JSON Schema |
| 模型决策 | 模型 | tool_calls：工具名 + JSON 参数 |
| 宿主执行 | 程序 | 解析、校验、真正调用，并区分成功与失败 |
| 结果回填 | 程序 | 按 tool_call_id 组织成 tool 消息追加，模型继续推理 |

四步里模型只参与第二步，**它不执行任何动作**。第三步的校验和第四步的回填是最容易漏的：校验漏了会把脏参数直接打到下游，回填漏了模型就拿不到结果，只能自己编一个补上。

## 工具描述本身就是提示词

模型选哪个工具，完全依赖你给的描述与参数 schema。描述含糊、多个工具职责重叠、命名看不出用途，都会直接导致选错工具或者该调的时候不调。**提升工具选择准确率，改描述往往比换更强的模型更有效**，因为这是在补模型唯一的判断依据。描述里写「什么时候用它」，比只写「它是什么」有用得多。

## Spring AI 用注解声明工具

用 `@Tool` 注解声明方法，用 `@ToolParam` 描述参数，**方法签名会自动生成 JSON Schema**：

```java
class WeatherTools {

    @Tool(description = "查询某个城市当前的天气，用户问到出行、穿衣时使用")
    String currentWeather(@ToolParam(description = "城市名，例如杭州") String city) {
        if (city == null || city.isBlank()) {
            throw new IllegalArgumentException("city 不能为空");
        }
        return weatherApi.query(city);
    }
}

String answer = ChatClient.create(chatModel)
        .prompt("杭州今天适合跑步吗？")
        .tools(new WeatherTools())
        .call()
        .content();
```

把这样的对象放进 `ChatClient`（或 `ChatModel`）并绑定到请求，模型返回的 tool call 会被 Spring AI **解析成方法调用、通过反射真正执行**，结果再回传给模型继续对话。工具也可以在 `@Configuration` 里声明成 `ToolCallback`，交给容器统一管理。

## Spring AI 帮你省掉的四件事

- **声明式**：业务方法加注解即可成为工具，不需要手写 schema。
- **框架托管调用循环**：`ToolCallingManager` 负责解析与执行、结果回填、多轮衔接，**开发者不用自己写 while 循环**。
- **与 Spring 生态集成**：依赖注入、AOP、事务、配置管理都能直接作用在工具方法上。
- **抽象隔离**：底层可换 OpenAI、Anthropic、Ollama、Vertex AI 等多家模型，工具代码不跟着改。

## 多轮调用与 MCP 的关系

把 `ChatClient` 与工具绑好，请求时指定 `toolCallbacks`，Spring AI 会自动完成「模型 → 工具 → 回填 → 模型」的循环，直至模型不再请求工具。**需要精确控制时，可以用 `ToolCallingManager` 手动介入**，自行决定是否继续循环、何时终止。

Spring AI 同时支持 **MCP Client**，把 MCP Server 的工具接进 Spring 应用。在模型这一侧，两者最终都表现为同一套 tool call 机制，所以可以**混用**：一部分工具用 `@Tool` 本地声明（简单、无需部署），一部分通过 MCP 接入（复用生态），再由 Spring AI 统一编排。

## 生产环境要注意什么

- **参数校验仍然要自己做**：注解生成的是结构约束，语义与业务约束（金额上限、账号归属）要靠 `@Tool` 方法内部或 AOP 校验。
- **工具数量要控制**：工具过多会稀释模型的注意力，选择准确率反而下降。
- **执行要有超时与异常处理**：把异常捕获下来、转成**可诊断的错误消息**回传模型，别让一次报错打断整个循环。
- **敏感信息不要外露**：不要写进工具描述，也不要在参数回显里带出来。
- **治理逻辑独立成层**：权限与限流走独立的一层，不要在业务方法里散落判断；副作用类工具加**幂等键**防重复；工具返回值**裁剪**后再回填；不可逆操作要有**人在环确认**。Spring AI 提供了 `ToolCallAdvisor` 这类拦截机制，可以挂载治理逻辑。

## 常见追问

- **Q：工具调用和让模型直接回答有什么区别？** A：模型只输出调用意图，事实由真实工具返回，所以数据是可追溯的；权限、超时、重试这些工程手段也才有地方落。
- **Q：模型老是选错工具怎么办？** A：先改描述和 schema，把职责拆细、名字写清用途，通常这一步就见效；再看工具数量是不是太多；最后才考虑换模型。
- **Q：多轮工具调用要自己写循环吗？** A：不用，绑定工具后框架会一路跑到模型不再请求工具；只有要自定义终止条件（比如最多两轮、失败即停）时才用 `ToolCallingManager` 接管。
- **Q：本地 `@Tool` 和 MCP 工具怎么选？** A：只在本应用用、逻辑简单的走 `@Tool`；希望被多个客户端复用、独立部署维护的走 MCP，两者可以混用。

## 易错点

- **把工具描述写得太笼统**。模型没有判断依据只能猜，这是选错工具的**头号原因**，不是模型能力问题。
- **忘记回填工具结果**。模型拿不到结果就会自己编一个补上，比直接报错更危险，因为它编得像模像样。
- **工具内部抛异常导致循环中断**。应该捕获后转成可诊断的消息返回，让模型有机会修正参数再试一次。
- **在工具里做重逻辑**。工具应先做参数校验快速失败，重活丢给下游异步任务，别把工具当成业务编排层。

## 一句话记住
