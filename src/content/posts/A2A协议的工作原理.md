A2A 的工作原理可以用一句话概括：**每个 Agent 通过一张 Agent Card 公开自己的能力，通过 Task 把协作状态托管在服务端，通过流式更新暴露过程，通过 Artifact 交付成果。**

1) **基于标准 Web 基础设施**。A2A 复用 **HTTP + JSON**，Server 暴露 HTTP 端点承载任务 API。这带来两个直接好处：**企业网络与网关策略天然适用**（无需为 Agent 单独开协议栈）；**可用现成工具观测与调试**。

2) **发现阶段**。编排方在需要协作时，**拉取候选 Agent 的 Agent Card**（约定路径下的 JSON），解析出能力、技能、输入输出模式、交互模式与认证要求。**发现是运行时的、动态的** —— 编排方不必预先硬编码协作方。

3) **匹配与路由**。编排方（人或模型）依据 Card 中的**自然语言描述与结构化能力**，筛选出合适的执行方并决定委派方式。**Card 描述的准确度直接决定选路准确率** —— 这与工具描述的作用完全一致。

4) **任务发起**。Client 按 Card 声明的**输入输出 schema** 构造请求，**用自己 Agent 的身份凭证**发起任务调用，Server 创建一个 **Task**，分配任务 id，进入 `submitted` 状态。

5) **流式执行与状态更新**。Server 异步推进任务，状态从 `submitted` → `working` → 终态（`completed` / `failed` / `canceled`），过程中通过**流式通道推送状态变更与中间产物**。**注意 `input-required` 状态** —— 这允许 Server **中途反问调用方**补充信息，是支持多轮协作的关键。

6) **多轮消息往来**。双方通过 **Message** 交换结构化内容（文本、文件、数据部件），支持澄清、协商与逐步收敛。**消息是过程沟通，不等于交付物。**

7) **产物交付**。最终成果以 **Artifact** 形式交付，可以是文件、报告或结构化数据。**产物通常较大**，实践中同样需要"**摘要 + 引用**"策略（大产物外置、只回摘要与可寻址引用）。

8) **任务管理**。规范定义了查询状态、订阅更新、取消任务等操作，使长任务可异步推进、可中断。

9) **凭据与信任**。**每个 Agent 用自己的身份与对方通信**，凭证在请求中传递但**不写入消息内容**。Server 依据验证后的身份做**资源级鉴权**，并可**声明拒绝**某些委派。

10) **与 MCP 的分工在原理层面就体现出来了**。MCP 的原理是"**客户端拉取工具列表 → 调用工具 → 回填结果**"，主语始终是本地应用；A2A 的原理是"**对方是一个独立主体，它有自己的一摊事要做**" —— 所以需要任务生命周期、流式状态、多轮消息、产物交付与拒绝语义。**前者是函数调用，后者是任务委托。**

11) **一个直观的对比**。调用 MCP 工具像"**调用自己程序里的一个函数**"；使用 A2A 像"**把一件事托付给另一个部门的同事，然后跟进他做到哪一步**"。这个类比在面试中很有效。
