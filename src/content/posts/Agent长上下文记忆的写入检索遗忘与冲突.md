长上下文场景下，Agent 记忆要当成一个存储系统来设计：写入侧把「记录」升级为「筛选」，只留下有价值且可判定真伪的事实；检索侧用多路召回加重排，再按 token 预算装配上下文；遗忘侧把冷记忆归档而不是物理删除；冲突侧用时间、权威性、作用域、置信度四条优先级原则加读写双向检测来治理。

## 写入：把「记录」升级为「筛选」

长上下文里最有价值的能力不是存得多，而是判断什么值得存。写入门槛通常是四个信号的组合：

- **新颖性**：这条信息与已有记忆是否重复。
- **重要性**：它对未来任务的参考价值有多高，一次性的闲聊和结论性的偏好不该同等对待。
- **置信度**：来源是用户明确陈述还是模型推断。
- **可复用性**：它是否是可泛化的规律，而不是一次性的事件细节。

写入时要做**原子化事件抽取**，把一段自然语言拆成独立、可判定真伪、带时间戳和实体的事实单元，而不是把整段对话原样塞进记忆库。整段塞进去的代价是检索时只能整块召回，噪声和有效信息绑死在一起，既浪费预算又干扰判断。每条记忆还要带元数据，这是后面解决冲突和检索的基础：

| 元数据 | 作用 |
| --- | --- |
| 来源 | 用户明确陈述、工具返回、模型推断，决定冲突时的权威性权重 |
| 置信度 | 同一槽位两条都可信时，用它挑主版本 |
| 时间戳 | 时间优先原则的依据，也用于衰减和过期判定 |
| 有效期 | 价格、配置这类会变的事实需要显式过期 |
| 作用域 | 区分会话级、项目级、用户级，检索时做硬过滤 |

同时要主动做**去重与合并**：语义相近的旧记忆应该被合并更新，而不是不断堆叠出大量重复条目。同一件事存了十份，检索时既烧 token 预算，又让模型看到互相矛盾的说法。

## 检索：多路召回加重排

单一向量检索在长记忆库上召回质量会明显下降：向量擅长「表达不同但意思相近」，对专有名词、编号、错误码这类精确匹配不敏感，也做不了硬约束。所以通常的做法是并行做几路召回：

- **语义向量召回**：负责表达相近的表述。
- **关键词检索**：负责专有名词、编号、错误码这类必须精确命中的内容。
- **结构化过滤**：按作用域、实体和时间窗口做硬约束，先把不该出现的记忆挡在外面。
- **实体关系扩展**：沿实体关系做一跳或两跳的关联扩散，补上「这件事的另一半」。

几路结果合并后，用交叉编码器或者模型做重排，决定最终的注入顺序。重排之后还要做**上下文预算管理**：按 token 预算截断，对低优先级记忆做摘要压缩；把高价值信息放在提示的靠前或靠后位置，规避长上下文中段的注意力衰减；并可以按时间做加权衰减，让久未被引用的记忆自然下沉。

## 遗忘：本质是成本控制，不是删除

遗忘策略的本质是**成本控制**，而不是简单删除，因为记忆库无限膨胀会同时抬高检索成本、注入成本和冲突概率。遗忘有三种来源：

- **时间衰减**：给记忆设置生存期或半衰期，越久没被引用越容易失效。
- **容量淘汰**：记忆库达到上限时，按价值与访问频率的组合分淘汰。
- **冗余压缩**：把语义高度重叠的记忆聚类合并成一条更完整的表述。

这里有一个重要原则：**遗忘不等于抹除**，被淘汰的旧事实应当归档而不是物理删除，这样既保留了系统演进的历史轨迹，也让冲突发生后有据可查。同时要把删除权交给用户，允许查看、编辑和手动清除记忆，这是长期使用场景下建立信任的前提——用户一旦发现「它记错了还改不掉」，信任就没了。

## 冲突治理：统一原则加双向检测

记忆冲突主要有三类：

- **同一事实槽位出现不同取值**，典型表现是用户先说用 MySQL，后说改用 PostgreSQL。
- **不同来源对同一事实给出矛盾结论**，比如工具返回的配置和用户口述的对不上。
- **新旧偏好并存导致行为不确定**，这次按旧偏好答、下次按新偏好答，模型表现飘忽。

解决原则按优先级依次判断：

1. **时间优先**：新的观测默认覆盖旧的，前提是两条的作用域相同。
2. **权威性优先**：用户显式陈述的权重高于模型推断的权重。
3. **作用域优先**：更具体的作用域覆盖更宽泛的作用域，项目级约定不该被用户级泛泛说法盖掉。
4. **置信度优先**：两条都可信时保留高分的那条，但同时保留冲突记录，不要当没发生过。

自动解决不了的时候不要静默选择，而是保留双版本，并在合适的时机向用户澄清。最后，**冲突检测必须读写两侧都做**：写入时检测新记忆与既有记忆是否矛盾，检索时检测同一次召回的结果之间是否互相打架。只查写入侧是不够的，历史数据里可能早就并存两条矛盾记忆，只有到检索那一刻才会被同时召回、同时注入上下文，模型的行为就变得不确定了。

## 一个最小实现骨架

把上面四件事落成代码，写入侧和召回侧各一个函数就够说明问题：

```python
def remember(fact, meta):
    # 1) 门槛：新颖性和可复用性不足，只存摘要，不进记忆库
    if not meta.novel or not meta.reusable:
        return store_summary(fact, meta)
    # 2) 原子化：拆成独立、可判定真伪、带时间戳和实体的事实单元
    for unit in atomize(fact, meta):
        # 3) 去重合并：语义相近就更新旧条目，不新增
        old = find_similar(unit, scope=meta.scope)
        if old:
            merge(old, unit)
            continue
        # 4) 写入侧冲突检测：同槽位不同取值 / 来源矛盾
        clash = detect_conflict(unit, meta.scope)
        if clash:
            store_both(unit, clash)   # 保留双版本，标记为待向用户澄清
        else:
            store(unit)


def recall(query, scope, budget_tokens):
    hits = [
        vector_search(query),                    # 语义相近的表述
        keyword_search(query),                   # 专有名词、编号、错误码
        filter_by(query, scope),                 # 作用域、实体、时间窗口硬约束
        expand_by_entity(query, hops=2),          # 实体关系一到两跳扩展
    ]
    ranked = rerank(query, dedupe(flatten(hits)))  # 交叉编码器或模型重排
    picked = pack(ranked, budget_tokens)           # 按预算截断 + 低优先级摘要压缩
    return place_for_attention(picked)             # 高价值内容放靠前或靠后
```

这两个函数体现了前面所有原则：写入侧有门槛、原子化、去重合并和冲突检测，冲突无法裁决时保留双版本；召回侧并行四路再统一重排，最后按预算装配并照顾注意力位置。真实系统里每一句都是独立模块，但缺掉任何一步，剩下的部分都会退化。

## 常见追问

**Q：为什么不把所有对话原样存进向量库，简单又不怕漏？**

答：存得多不等于查得准。整段存会让一条记忆里混着噪声和有效信息，召回时只能整块捞出来；条目越多，重复和矛盾的条目也越多，检索成本、注入成本和冲突概率一起上升。所以要做原子化和写入门槛。

**Q：向量检索已经很方便了，为什么还要关键词和结构化过滤？**

答：向量擅长语义相近，但对错误码、编号、专有名词这类精确匹配不敏感，也表达不了「只看项目级、只看最近一段时间」这种硬约束。多路召回各管一段，最后统一重排，召回率和准确率都比单路好。

**Q：用户前后说法矛盾，到底听谁的？**

答：先按时间优先和权威性优先判断，作用域不同就先按作用域隔离。两条都站得住又无法自动裁决时，不要静默挑一个，保留双版本并在合适的时机向用户澄清，同时把冲突记录下来。

**Q：遗忘会不会把重要记忆删掉？**

答：遗忘不等于抹除。被淘汰的记忆归档而不是物理删除，需要时可以回溯，冲突也有据可查；同时把查看、编辑、清除的权限交给用户，这也是长期使用建立信任的前提。

## 易错点

- **把遗忘当成物理删除**：删掉就丢了系统演进的历史，冲突发生时无从追溯。正确做法是归档并保留可回溯路径。
- **只做写入侧冲突检测**：历史库里早已并存的矛盾记忆，只有检索时才会被同时召回。读写两侧都要查，召回后要再做一次一致性校验。
- **只靠向量相似度做检索**：错误码、编号、专有名词经常召不回来。必须补关键词路和结构化过滤。
- **把记忆当成越多越好的日志**：没有写入门槛、不做原子化，最后 token 预算全被低价值记忆吃掉，模型还被噪声带偏。

## 一句话记住

:::tip
写入靠筛选、检索靠多路召回、遗忘要归档、冲突留双版本，这是记忆系统的四道闸门。
:::
