从零设计 Agent 框架，我不会一开始就做"多 Agent 编排"，而是按**依赖顺序**优先实现下面六个模块。理由是：编排是上层建筑，而**上下文、状态、终止、工具安全**这四件事是所有上层能力的地基，缺一个上层都会塌。

## 上下文组装器（Context Builder）—— 优先级最高

。负责把系统提示、目标、工具定义、检索内容、记忆、历史轨迹、预算约束组装成每一次请求的提示。**为什么优先**：它是唯一的性能与成本瓶颈，也是质量波动的最大来源。核心能力应包括 token 预算分配、按优先级裁剪、工具结果的结构化压缩、位置效应处理（重要信息放首尾）。**没有这一层，其他模块再好也没用。**

## 工具执行网关（Tool Gateway）

。统一处理工具调用的参数校验、权限裁决、限流、超时、幂等、结果裁剪与错误规范化。**为什么优先**：它是**唯一允许产生副作用的地方**，也是安全的唯一入口点。把副作用收口到一个模块，后面所有的安全策略都有落点。

## 执行引擎（Runtime / Loop Engine）

。实现 Agent Loop 的状态推进，基于**事件溯源**而非简单 while，支持 checkpoint、断点恢复、幂等重放。**为什么优先**：决定了框架能不能上生产 —— 一个不能恢复、不能回滚的循环在生产上是不敢用的。

## 状态与记忆层（State & Memory）

。区分**工作状态**（任务树、子任务状态机、预算账本）与**长期记忆**（语义/情景/程序性记忆），提供写入筛选、多路召回、遗忘淘汰、冲突治理。**为什么优先**：长程任务的成败取决于状态能否被外置和可靠管理。

## 终止与恢复机制（Termination & Recovery）

。多重终止条件（成功验收、预算上限、停滞检测、循环检测）、错误分类（可重试/需重规划/需补偿/不可恢复）、分级降级链。**为什么优先**：失控的 Agent 代价不可控，这是"敢不敢上线"的分界线。

## 可观测与评估层（Observability & Eval）

。全链路 trace、每步的 token/延迟/工具成败记录、可重放、离线评测集与回归门禁。**为什么优先**：没有它，前面所有设计都无法验证和迭代。

## 上述六个模块之上

才实现**编排层**（多 Agent 的 supervisor / pipeline / parallel）、**子 Agent 机制**、**规划器（Planner）**、**反思机制（Reflexion）**。**为什么放后面**：它们都是在基础能力之上的组合，且**多数场景用不上** —— 先把单体 Agent 做扎实，比做一个花哨的多 Agent 编排更有价值。

## 接口设计上我会坚持的两条原则

。一是**模型可替换**：所有模型能力通过统一接口抽象（对话、结构化输出、工具调用、嵌入、重排），不让框架绑死在某一家。 二是**一切可注入**：检索器、记忆存储、工具执行器、守卫器都做成可替换接口，方便测试与定制。

## 最后才加"智能"的部分

：Planner、Critic、Self-Refine。**理由**：这些依赖强模型且收益不稳定，应当建立在稳定的基础设施之上，且**可按需开启**（开关式设计），避免默认拉高成本与延迟。
