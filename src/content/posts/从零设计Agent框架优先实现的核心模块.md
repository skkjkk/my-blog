我会按**依赖顺序**先实现六个模块：上下文组装器、工具执行网关、执行引擎、状态与记忆层、终止与恢复机制、可观测与评估层，而把多 Agent 编排、子 Agent、规划器、反思机制放到最后。理由是：上下文、状态、终止、工具安全是所有上层能力的地基，缺一个上层都会塌；编排只是上层建筑。

## 六个模块的依赖顺序

| 顺序 | 模块 | 一句话职责 | 为什么排在这个位置 |
| --- | --- | --- | --- |
| 1 | 上下文组装器（Context Builder） | 把提示、目标、工具、检索、记忆、轨迹、预算拼成一次请求 | 唯一的性能与成本瓶颈，也是质量波动的最大来源 |
| 2 | 工具执行网关（Tool Gateway） | 校验、鉴权、限流、超时、幂等、裁剪、错误规范化 | 唯一允许产生副作用的地方，安全的唯一入口 |
| 3 | 执行引擎（Runtime / Loop Engine） | 推进 Agent Loop 状态，支持 checkpoint 与重放 | 决定框架能不能上生产 |
| 4 | 状态与记忆层（State & Memory） | 外置工作状态，管理长期记忆的写入与召回 | 长程任务的成败取决于状态能否可靠外置 |
| 5 | 终止与恢复机制（Termination & Recovery） | 多重终止条件、错误分类、分级降级 | 失控的 Agent 代价不可控，是上线的分界线 |
| 6 | 可观测与评估层（Observability & Eval） | 全链路 trace、可重放、离线评测与回归门禁 | 没有它前面所有设计都无法验证和迭代 |

排序的依据不是模块的热度，而是**谁被谁依赖**：上层模块的每一个决策，最终都要落到这六层里的某一层去执行、去记账、去验收，所以它们必须先存在。

## 上下文组装器：唯一的成本与质量瓶颈

它负责把系统提示、目标、工具定义、检索内容、记忆、历史轨迹、预算约束组装成每一次请求的提示。**之所以排第一，是因为它是唯一的性能与成本瓶颈，也是质量波动的最大来源**——瓶颈不在调用模型这个动作本身，而在每次喂给模型的内容。

核心能力应当包含四项：

- **token 预算分配**：给系统提示、检索、记忆、轨迹各划多少额度，要显式算，不能靠自然溢出。
- **按优先级裁剪**：超预算时先砍谁，需要一条稳定的优先级，而不是每次随机丢。
- **工具结果的结构化压缩**：把长 JSON、长网页压成模型能用的摘要，而不是截断成半句。
- **位置效应处理**：重要信息放首尾，中间段天然不被重视。

没有这一层，其他模块做得再好也没用——它们产出的信息进不了模型的有效上下文，等于没做。

## 工具执行网关：把副作用收口到一个模块

它统一处理工具调用的参数校验、权限裁决、限流、超时、幂等、结果裁剪与错误规范化。

**它是整个框架里唯一允许产生副作用的地方，也是安全的唯一入口点。**这条收口带来的好处是复利式的：只要副作用只从这一个门出去，权限模型、审计日志、成本计费、限流熔断、人工审批都只需要在网关里实现一次，后面新增任何工具都自动继承。

反过来，如果允许某个模块绕过网关直接调网络、写文件、发消息，那安全策略就没有落点了——你无法回答"这个动作是谁批的、花了多少钱、失败了会不会重复执行"。

## 执行引擎：用事件溯源替代 while 循环

执行引擎负责 Agent Loop 的状态推进，关键设计是**基于事件溯源，而不是一个简单的 `while` 循环**，并在此之上支持 checkpoint、断点恢复与幂等重放。

```text
loop:
  event   = next_event()        // 模型输出 / 工具结果 / 外部信号
  state   = replay(event_log)   // 状态由事件重放得出，不是内存里就地修改
  append(event_log, decision)   // 先落盘再执行，崩溃后可从这里恢复
  if should_stop(state): break  // 终止判定是显式的一步
```

这个差别在生产上是决定性的：普通 while 循环把状态放在内存和不断追加的消息数组里，进程一崩全部丢失，也无法解释某一步为什么那么决策。事件溯源把每一步的输入、决策、结果写成不可变事件，状态只是事件重放出来的视图，于是断点恢复、幂等重试、事后复盘都变成自然能力。**一个不能恢复、不能回滚的循环，在生产上是不敢用的。**

## 状态与记忆层：工作状态和长期记忆分开治

这两件事经常被混成一个"记忆模块"，但它们的性质完全不同：

| 类型 | 内容 | 关键要求 |
| --- | --- | --- |
| **工作状态** | 任务树、子任务状态机、预算账本 | 强一致、必须外置存储、可 checkpoint、进程挂了能接上 |
| **长期记忆** | 语义记忆、情景记忆、程序性记忆 | 带写入筛选、多路召回、遗忘淘汰、冲突治理 |

工作状态是短期的、结构化的、要求准确的；长期记忆是跨任务的、模糊的、要求可召回可淘汰的。把两者塞进同一个存储，往往两边都做不好：既要事务又要相似度检索，最后只能妥协。

**长程任务的成败取决于状态能否被外置和可靠管理**——上下文窗口装不下整个任务，能装下的只有"当前状态的一份投影"。

## 终止与恢复：敢不敢上线的分界线

这一层包含三样东西：

- **多重终止条件**：成功验收、预算上限、停滞检测、循环检测，四条互不替代。
- **错误分类**：可重试 / 需重规划 / 需补偿 / 不可恢复，不同类型走不同分支。
- **分级降级链**：从换路径、重规划、换更强模型，一直到转人工，逐级加火。

**为什么必须优先做**：失控的 Agent 代价不可控——它可能一直调用付费接口、一直重试同一个失败动作、一直改写同一个文件。这条线划不清，工程上根本不敢让它碰真实系统。

## 可观测与评估：让前面的设计可验证

需要的能力是：全链路 trace、每一步的 token / 延迟 / 工具成败记录、可重放、离线评测集与回归门禁。

没有这一层，前面五个模块全部是"看起来对"的设计。上下文裁剪砍多砍少、终止阈值定高定低、降级链什么时候触发，这些参数只能靠观测数据来调；而离线评测集的作用是回归门禁，防止改一处坏一处。

## 编排层为什么反而放到最后

在上述六层之上，才实现**编排层**（多 Agent 的 supervisor / pipeline / parallel）、**子 Agent 机制**、**规划器（Planner）**、**反思机制（Reflexion）**。

**为什么放后面**：它们都是在基础能力之上的组合，而且**多数场景用不上**。先把单体 Agent 做扎实，比做一个花哨的多 Agent 编排更有价值——一个上下文管不好、状态存不住的单体 Agent，拆成多份只会把同一个缺陷复制多份。

## 接口设计上坚持的两条原则

- **模型可替换**：所有模型能力通过统一接口抽象（对话、结构化输出、工具调用、嵌入、重排），不让框架绑死在某一家。这条决定了模型降价或升级时，框架是"改一行配置"还是"重写一遍"。
- **一切可注入**：检索器、记忆存储、工具执行器、守卫器都做成可替换接口，方便测试与定制。可注入性直接决定可测试性——单元测试里能塞一个假工具，才谈得上回归。

## 最后才加"智能"的部分

Planner、Critic、Self-Refine 这类"让 Agent 更聪明"的组件，同样放在最后才加。理由有两条：它们**依赖强模型、收益不稳定**，且应当建立在稳定的基础设施之上，**可按需开启**（开关式设计），避免默认拉高成本与延迟。把它们做成默认开启的必经环节，等于用不确定的收益换取确定的开销。

## 常见追问

**Q：为什么不先做多 Agent 编排，它不是最有卖点的部分吗？**

A：编排是组合层，价值来自被组合的单元。单 Agent 的上下文、状态、终止没做好，编排只会把缺陷放大并复制多份；而且编排的调试成本远高于单体，没有可观测层根本定位不了问题。

**Q：六个模块只能先做一个，你选哪个？**

A：选上下文组装器。它是唯一同时决定成本、延迟和回答质量的地方，投入产出比最高，而且它不依赖其他模块就能独立生效。

**Q：执行引擎为什么要事件溯源，普通 while 循环差在哪？**

A：差在可恢复、可解释、可重放。while 循环的状态活在内存里，崩溃即丢失，也无法回放某一步的决策依据；事件溯源把状态变成事件的投影，断点恢复和幂等重试才有依据。

**Q：工具网关和普通的工具注册表有什么区别？**

A：注册表只解决"有哪些工具、参数长什么样"，网关解决"这次调用该不该放行、超不超时、失败重不重试、结果要不要裁剪"。前者是目录，后者是唯一能产生副作用的那道门。

## 易错点

- **把编排层当成第一优先级**。常见直觉是"多 Agent 才是 Agent 框架的核心"，实际上多数业务用单体 Agent 就够，先搭编排会让地基永久欠账。
- **把上下文组装理解成字符串拼接**。真正的难点是预算分配、优先级裁剪和位置效应，拼接只是最后一行代码。
- **让工具调用绕过网关直连**。任何一处直连都会让权限、审计、计费、限流失去统一落点，安全策略从此无法收敛。
- **终止条件只靠"模型说完成了"**。这是单一信号，缺少程序化验收和预算硬上限，失控时没有任何兜底。

## 一句话记住

:::tip[顺序别记反]
上下文 → 工具 → 运行时 → 状态 → 终止 → 可观测，编排与规划放最后。
:::
