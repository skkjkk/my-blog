A2A 的五大设计原则是**能力导向而非方案导向**、**Agent 自治**、**互操作性与可发现性**、**安全与隐私默认内建**、**可观测性与长期兼容**。五条合起来回答同一个问题：如何让不同厂商、技术栈各异的 Agent，在不规定彼此内部实现的前提下相互发现、安全协作并长期共存。因此 A2A 的定位始终是「Agent 之间的对等协作协议」，而不是一套 Agent 开发框架。

## 五条原则速览

先把五条并排放好，再逐条展开。这张表就是面试时可以直接背的骨架：

| 原则 | 核心主张 | 保证什么 |
| --- | --- | --- |
| 能力导向而非方案导向 | 只规定交互方式，不规定内部实现 | 异构 Agent 能共存 |
| Agent 自治 | 各自对内部状态与执行方式负责 | 协作方无需、也不应介入对方内部 |
| 互操作性与可发现性 | Agent Card + 标准数据格式 + 标准协议方法 | Agent 能互相找到并说同一种话 |
| 安全与隐私默认内建 | 凭据不共享、数据最小化、不强制委派 | 协同时不牺牲信任边界 |
| 可观测性与长期兼容 | 任务状态可追踪 + 能力协商 | 这套体系能被运维、能长期演进 |

## 能力导向而非方案导向

A2A **不规定 Agent 内部该怎么实现**——怎么规划、怎么用工具、用什么模型、什么架构，全部由 Agent 自主决定。协议只定义**它们之间如何交互**。

这条原则让 A2A 能容纳形态各异的 Agent（从简单工作流到复杂自主系统），也是它能跨厂商存在的前提。

可以把边界记成一句话：凡是「对方内部怎么做」的问题，A2A 都刻意不表态；凡是「两边怎么对得上」的问题——消息格式、能力声明、任务状态——A2A 才给出标准。边界划清了，协议就不会被某一种 Agent 框架绑架。

## Agent 自治

每个 Agent 保有自己的**内部推理、规划与执行逻辑**，对**自己的内部状态与执行方式负责**。协作方不介入也不需要了解其内部过程，只能通过 `Agent Card` 声明的契约与之交互。

自治是双向的：一方面「我不必向你解释内部过程」，另一方面「我有权不接受不适合我的任务」——后者在安全原则里的「不强制委派」中落成协议层的硬约束。正因为有自治，跨厂商协作才不需要先统一实现，只需要统一契约。

## 互操作性与可发现性

通过**标准化的 `Agent Card`**、**标准数据格式**、**标准协议方法**，让不同厂商、不同语言、不同技术栈的 Agent 能够互相发现并协作。

协议的价值就在这里——**打破生态孤岛**。

这三件套各管一段：`Agent Card` 管「怎么被找到」，标准数据格式管「彼此听得懂」，标准协议方法管「真的调得动」。缺任何一件，互操作都会退化成一家厂商内部的私有约定。

## 安全与隐私默认内建

A2A 通过三条机制保证安全与隐私，让协议能在企业间使用而不牺牲信任边界：

| 安全机制 | 具体做法 | 作用 |
| --- | --- | --- |
| 凭据不共享 | 每个 Agent 用**自己的身份**跟对方通信，凭据只随请求传递、绝不写在消息里 | 避免凭据泄露与身份冒用 |
| 数据最小化 | 只交换完成任务所必需的数据 | 减少敏感数据暴露面 |
| 不强制委派 | 对方可以在协议层明确声明「此任务我不接受」，调用方必须尊重 | 保护 Agent 的自治边界 |

:::note
「不强制委派」容易被忽略：调用方不能因为对方声明了不接受就绕过协议强行委派，这是协议层的硬性约束，不是礼貌性建议。
:::

三条机制共同表达的是「默认安全」的姿态：安全不是接入方额外加的一层配菜，而是协议自带的起点。

## 可观测性与长期兼容

协议要能长期活下去，既要看得见，也要改得动：

| 兼容机制 | 具体做法 | 作用 |
| --- | --- | --- |
| 任务状态可追踪 | 任务的生命周期、状态流转、中间产物都有标准化的表达 | 便于端到端追踪与调试 |
| 版本演进友好 | 通过**能力协商**（协商出的能力集决定后续可用方法）保证协议向前兼容 | 老客户端与新 Server 可以共存，不破坏既有集成 |

:::tip
「能力协商」是 A2A 长期演进的关键：双方先协商出共同支持的能力集，后续交互只使用该能力集内的方法，因此协议升级不会破坏已有集成。
:::

## 五条原则如何咬合

五条不是并列的五块拼图，而是有依赖关系的：

| 原则组合 | 保证什么 |
| --- | --- |
| 原则 1 + 2 | 异构 Agent 能共存 |
| 原则 3 | 它们能互相找到并说同一种话 |
| 原则 4 | 协同时不牺牲安全与隐私 |
| 原则 5 | 这套体系能被运维、被观察、且长期演进 |

**缺任何一条，A2A 都无法在企业级场景落地。**

面试时的答题节奏可以这样安排：

1. 先给出定位：**A2A 是 Agent 之间的对等协作协议**。
2. 再逐条给出五大设计原则，每条用一句话概括核心，不必展开过多细节。
3. 最后落到一句总结：**「它不关心你内部怎么做，只关心我们之间怎么对话、怎么互信、怎么长期一起活下去。」**

这比罗列协议细节更能体现理解深度——面试官想看到的是你对协议设计意图的把握，而不是背诵条款。

## 常见追问

**Q：五条原则里哪条最容易被忽视？**
A：安全原则里的「不强制委派」。它常被当成客套话，实际上调用方必须尊重对方在协议层声明的拒绝，不能绕过协议强行委派。

**Q：为什么 A2A 不统一 Agent 的内部实现？**
A：因为一旦规定内部实现，协议就退化成某个框架的专属接口，跨厂商协作的前提也就没了。只定交互，才能容纳从简单工作流到复杂自主系统的各种 Agent。

**Q：A2A 靠什么做到长期兼容？**
A：靠能力协商。双方先协商出共同支持的能力集，后续交互只使用该能力集内的方法，于是老客户端与新 Server 可以共存，协议升级不必破坏既有集成。

**Q：可观测性在协议层面体现在哪？**
A：任务的生命周期、状态流转和中间产物都有标准化的表达，端到端追踪与调试因此有据可依，而不是靠各方自己打日志猜。

## 易错点

- **把 A2A 当成 Agent 开发框架**：它不规定规划、工具、模型与架构，只定义 Agent 之间如何交互，内部实现完全由各自决定。
- **把「不强制委派」当礼貌性建议**：这是协议层的硬性约束，对方声明不接受后，调用方不能绕过协议强行委派。
- **把 `Agent Card` 只当成一张名片**：它是协作方唯一被允许依赖的契约，能力声明得越清楚，别人越容易判断该不该找你、能不能调得动。
- **以为用了 A2A 就自动安全**：协议给的是默认姿态——凭据不共享、数据最小化、不强制委派，具体认证授权仍需各方按自己的身份体系落实。

## 一句话记住

:::tip
A2A 只规定我们之间怎么对话、怎么互信、怎么长期共存，不管各自内部怎么实现。
:::
