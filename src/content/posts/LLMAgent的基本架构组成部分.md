一个 LLM Agent 的基本架构可以拆成五个组成部分——大模型、提示与模板层、工具、记忆、状态管理——再加一层贯穿其间的运行时控制。五个组成部分各自提供一种能力，运行时控制则是把能力串成循环的那部分确定性代码：它是“确定的一半”，与模型这个“不确定的一半”配合，决定了系统能不能真正把长任务跑完。

## 五个组成部分分别提供什么能力

| 部件 | 核心职责 | 缺了会怎样 |
| --- | --- | --- |
| 大模型（LLM） | 决策核心与推理引擎：理解意图、分解任务、选择工具、生成参数、组织最终答案 | 没有推理就没有决策，剩下的只是固定流程脚本 |
| 提示与模板层 | 系统提示、角色设定、任务描述、工具使用规范、输出格式约束，以及每一轮放什么进窗口的上下文组装 | 指令模糊，行为不可预测，也无法复现 |
| 工具 | 工具定义与描述（名称、功能说明、参数 JSON Schema）、执行引擎、结果处理（裁剪、摘要、错误规范化） | 没有工具就只是问答，碰不到外部世界 |
| 记忆 | 短期保存当前任务上下文，长期跨会话保存用户偏好、历史经验、领域知识 | 没有记忆就只是单轮，每一轮都从零开始 |
| 状态管理 | 任务树、子任务状态机、已完成产物、预算账本、验收结果，必须外置到外部存储 | 无法长程、无法恢复、无法回滚、无法被外部观察 |
| 运行时控制 | 组装上下文、调用模型、解析动作、执行工具、更新状态、判定终止、处理重试与降级、记录轨迹 | 无法治理，循环、预算与失败都会失控 |

前五个部件是能力，最后一层是把能力装配起来的骨架。上表的分法不是为了分类好看，而是为了让工程上每一块的责任边界清楚：换模型不该动状态，改提示不该动工具执行引擎。

## 大模型与提示层：把不确定性收敛成稳定行为

大模型通常通过统一接口抽象接入：对话、结构化输出、工具调用、嵌入、重排。这样做的直接收益是，规划环节与执行环节可以选用不同规格的模型——强模型做规划与复杂推理，便宜快的模型做执行与格式转换，而上层链路代码不必跟着改。

提示与模板层包含系统提示、角色设定、任务描述、工具使用规范与输出格式约束。这一层的文本质量直接决定行为质量：模糊的指令导致不可预测的行为，明确的指令配上示例则显著提升稳定性。它还负责上下文组装，也就是每一轮决定放什么进窗口，这在工程上往往与提示模板合为一层，因为两者回答的是同一个问题——这一轮模型能看到什么。

- 模型侧的关键是分工，而不是一味堆强模型。
- 提示侧的关键是明确：指令越具体、带示例，行为越稳。
- 上下文组装与提示模板合层，是因为格式和素材缺一不可。

## 工具与记忆：外接能力与跨轮经验

工具是 Agent 的手，包含三块：工具定义与描述（名称、功能说明、参数 JSON Schema）、执行引擎（真正调用外部系统）、结果处理（裁剪、摘要、错误规范化）。工具描述本身就是给模型看的提示，所以命名与描述的准确度，往往比换一个更强的模型更能提升工具选择准确率。

记忆分短期与长期。短期记忆保存当前任务的上下文——目标、近期轨迹、中间结果，本质上是上下文窗口加上裁剪与摘要；长期记忆跨会话保存用户偏好、历史经验、领域知识，需要写入筛选、检索、遗忘与冲突治理。记忆要解决的是两个具体问题：装不下，以及接不上。

- 工具描述写不准，模型就会选错工具或传错参数，这比模型能力不足更常见。
- 结果处理同样重要：原文过长要裁剪或摘要，报错要规范化，否则模型会被噪音带偏。
- 短期记忆靠压缩，长期记忆靠治理，两者机制不同不能混着做。

## 状态管理与运行时控制：可恢复性与确定性的一半

任务的状态与进度，包括任务树、子任务状态机、已完成产物、预算账本、验收结果。这些状态必须外置到外部存储，否则长程任务无法恢复、无法回滚、也无法被外部观察——上下文窗口不是数据库，它会被截断，也会在下一轮被重写。

运行时控制是驱动循环的那部分确定性代码，职责是：组装上下文、调用模型、解析动作、执行工具、更新状态、判定终止、处理重试与降级、记录轨迹。把它写成普通代码而不是塞进提示词里，是为了让每一步都可复现、可测试、可中断。

```
while 未终止:
    context = 组装(系统提示, 当前状态, 记忆检索结果, 近期轨迹)
    action  = 模型(context)          // 要么给最终答案，要么给工具调用
    if action 是工具调用:
        result = 执行引擎(action)    // 结果裁剪、摘要、错误规范化
        状态.写入(action, result)    // 外置存储，可回滚
    if 命中终止条件:                  // 完成、预算耗尽、停滞、循环、人工取消
        break
```

## 五者的关系与两个横切关注点

运行时控制是骨架，模型是大脑，工具是手脚，记忆提供历史与经验，状态提供进度与可恢复性。任何一环缺失，系统都会退化：

- 没有工具，就只是问答。
- 没有记忆，就只是单轮。
- 没有状态，就无法长程。
- 没有运行时控制，就无法治理。

架构上还有两个常被单列的横切关注点：可观测与评估（轨迹记录、指标、回归），以及安全与权限（能力令牌、工具网关、审计）。它们不改变主结构，但决定系统能不能上生产。

## 常见追问

Q：五个部分里最容易被低估的是哪个？
A：运行时控制和状态管理。模型能力可以靠换模型提升，但终止、重试、降级这些逻辑只能自己写；状态不外置，任务一长必然断。

Q：记忆和状态管理有什么区别？
A：记忆偏经验与知识，短期是当前任务上下文、长期跨会话沉淀；状态是当前任务的进度账本，随任务诞生和结束，要能回滚、能验收。

Q：上下文组装为什么常和提示模板算作一层？
A：两者回答的是同一个问题，这一轮模型能看到什么。模板定角色与格式，组装定素材，拆开反而容易互相打架。

Q：这五个部分一定都要有吗？
A：看任务形态。单轮问答可以没有记忆和状态；但只要任务是多步、要碰外部系统、要跑很久，工具、状态与运行时控制就省不掉。

## 易错点

- 把循环控制交给模型：终止判定、重试与降级必须是确定性代码，靠模型自述完成会失控。
- 用上下文窗口当状态存储：窗口会满、会被截断、不可回滚，状态必须外置。
- 指望换更强模型解决工具选错：工具命名与描述的准确度往往更关键，描述本身也是提示。
- 把长期记忆当成一个向量库就够了：缺了写入筛选、遗忘与冲突治理，记忆只会越积越脏。

## 一句话记住

:::tip
五个部件给能力，一层运行时控制给确定性；能力再强，没有这层就治理不住。
:::
