两者**都是索引**，但定位完全不同：**主键索引 = 唯一 + 非空 + 聚簇（数据的物理组织方式）**；**唯一索引 = 只保证"不重复"，不改变数据存储方式**。落到存储上，主键索引的叶子节点存放整行数据，查主键不回表；唯一索引默认是二级索引，叶子节点只存索引列值 + 主键值，取其他列还要回表。所以真正的差别不在"约束松紧"，而在**是不是聚簇索引**，以及**业务唯一性该由谁兜底**。

## 最本质的区别：是不是聚簇索引

- **主键索引必然是聚簇索引**（InnoDB）—— 叶子节点存放**整行数据**，数据与索引在**同一棵 B+ 树**上
- **唯一索引默认是非聚簇**（二级索引）—— 叶子节点存放**索引列值 + 主键值**，查完可能还要**回表**

:::tip
**这是最容易答错的点**：很多人以为"唯一索引和主键索引只是约束不同"，其实**连存储结构都不同**。
:::

## 唯一索引的真正价值：把"业务唯一性"下推到数据库

主键每表只有一个，必须非空且唯一（自增是常见做法，但不是必须）；而"手机号唯一""身份证唯一""订单号唯一"这类**业务唯一约束**，每张表可能有多个，只能靠唯一索引实现。
- **没有唯一索引** → 并发下会插入重复数据，只能靠应用层加锁校验（**有并发窗口，不可靠**）
- **有唯一索引** → 数据库直接拒绝，**是并发场景下的最后一道防线**

:::tip
**典型场景：并发创建用户，同一个手机号 —— 靠应用层"先查再插"必然有并发问题，靠唯一索引才能真正兜住。**
:::

## 约束严格度对比

| | 主键索引 | 唯一索引 |
|---|---|---|
| 唯一性 | ✅ | ✅ |
| **非空** | ✅ **NOT NULL** | ⚠️ **可为 NULL**（MySQL 中 NULL 不参与唯一性判断，可有多行 NULL） |
| 数量 | 每表 **仅 1 个** | **多个** |
| 聚簇索引 | ✅ 必然是 | ❌ 默认不是 |

## NULL 的特殊语义（高频细节）

MySQL 的唯一索引**允许多行 NULL**（因为 `NULL <> NULL` 判定为"不相等"）。

:::caution
**所以如果业务要求"该字段唯一且不能为空"，必须同时写 `NOT NULL`**，否则会出现多条 NULL 记录。
:::

## 性能对比

- 主键查询 → **不回表**，一次 B+ 树查找直接拿到整行
- 唯一索引查询 → 若查询列不在索引中 → **需要回表**（多一次随机 IO）

:::tip
**所以等值查询用唯一索引定位后，仍需回表拿其他列；而主键查询不需要。** 但如果查询只需要索引列，**两者性能几乎一致**（都是一次索引查找）。
:::

## 二级唯一索引的锁特性：记录锁与间隙锁

在 RR 隔离级别下，**对唯一索引做等值查找（`WHERE uk = ?`）会加记录锁（不加间隙锁）**；而对**非唯一索引**或**范围查询**会加**间隙锁/临键锁** —— 这直接影响并发插入能否被阻塞。

:::tip
**典型区别**：唯一索引上的 `WHERE uk = 'x'` 能**并发插入不同值**；普通索引的范围查询会**锁住间隙，阻塞插入**。
:::

## 唯一索引不是越多越好

- 每个唯一索引都是一棵独立 B+ 树 → **写入时都要维护**
- 唯一索引**太严格会拖慢写入**（要加唯一性校验、并发冲突时还会阻塞等待）
- 常见优化：**业务上允许重复但希望"去重"**的场景，用**普通索引 + 应用层去重**比唯一索引更灵活

## 主键的选择建议

- **聚簇索引决定了数据的物理顺序** → 主键应**尽量短**（`BIGINT` 优于 `UUID CHAR(36)`），因为**所有二级索引的叶子节点都存主键值** → 主键越长，**所有索引都会膨胀**
- **⚠️ 强烈不推荐用 UUID 字符串做主键**（36 字符 + 无序 → 页分裂 + 全索引膨胀）→ 用 **雪花算法（有序 BIGINT）** 或 **有序 UUID**

## 常见追问

**问：为什么说这俩的差别不是"约束松紧"，而是存储结构？**
**答：** 因为 InnoDB 的主键索引必然是聚簇索引，叶子节点存整行数据，表数据就长在这棵 B+ 树上；唯一索引默认是二级索引，叶子节点只存索引列值 + 主键值，拿到主键还要回表取整行。约束只是表象，聚不聚簇才决定数据怎么放、查询要不要多一次回表。

**问：主键已经保证唯一了，为什么还要用唯一索引？**
**答：** 主键每表只有一个，而"手机号唯一""订单号唯一"这类业务约束往往分散在好几个字段上，只能用唯一索引表达。它的价值是把业务唯一性下推到数据库：应用层"先查再插"在并发下存在窗口，唯一索引是最后一道防线，冲突时直接拒绝插入，不会留下重复数据。

**问：为什么说唯一索引查询可能更慢，但并发插入不同值时反而更顺？**
**答：** 慢在回表——查询列不在索引里就要多一次随机 IO，而主键查询一次 B+ 树就拿到整行。顺在加锁——RR 下对唯一索引做等值查找只加记录锁、不锁间隙，所以别人还能插别的值；非唯一索引或范围查询会加间隙锁/临键锁，把间隙锁住、阻塞插入。

**问：业务要求"唯一且不能为空"，只加唯一索引行不行？**
**答：** 不行。MySQL 里 NULL 不参与唯一性判断（`NULL <> NULL`），唯一索引允许多行 NULL，业务上漏填一次就会多出一条空记录。必须把列声明成 `NOT NULL`，唯一索引 + `NOT NULL` 才是完整的"唯一且非空"约束。

:::tip
**面试答题顺序**：先讲结构差异（是否聚簇）→ 再讲把业务唯一性下推的价值 → 最后讲锁粒度差异，锁这一层最能体现对 InnoDB 锁机制的掌握。
:::

## 易错点

- **直觉：唯一索引也顺带保证了非空** → 错。MySQL 的唯一索引可以有多行 NULL，要"非空"必须显式写 `NOT NULL`。
- **直觉：两者只是约束不同，存储上一样** → 错。主键索引必然聚簇、叶子节点存整行；唯一索引默认是二级索引、要回表，连数据怎么组织都不同。
- **直觉：有了唯一索引就不需要主键** → 错。主键每表仅一个、必须非空且唯一，还决定数据在聚簇索引里的排列；唯一索引可以多个、可为 NULL，替代不了主键。
- **直觉：唯一索引越多，数据越干净** → 错。每个唯一索引都是一棵独立 B+ 树，写入要维护、冲突时还会阻塞等待；只是"希望去重"而不要求强一致的场景，普通索引 + 应用层去重更灵活。

## 一句话记住

:::tip
**主键索引是聚簇索引，唯一索引是二级索引，业务唯一性靠它兜底。**
:::
