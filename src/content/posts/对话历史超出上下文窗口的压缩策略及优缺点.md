上下文压缩是把超出窗口的历史变成「还能继续干活」的上下文，动作可以拆成**丢什么、怎么合、放哪里**三个维度，对应七种策略，各有明确的代价边界。工程上通常不只选一种：先在工具边界裁掉体积大头，再用外部化保住无损原文，最后才用摘要或滑动窗口兜底。它同时决定长程任务的质量与成本，是 Agent 的基础设施而不是可选项。

## 七种策略一览：丢什么、怎么合、放哪里

先把七种策略摊在一张表里，再逐个说边界。表中「优点」「缺点」都是相对关系：没有任何一种能在无损、零成本、低延迟三项上同时满足。

| 策略 | 怎么做 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- | --- |
| 滑动窗口截断 | 只保留最近 N 轮消息，丢掉更早的历史 | 实现最简单、零额外成本、延迟最低 | 硬性丢失早期信息，而早期往往含原始目标与硬约束 | 几十步内的短任务 |
| 摘要压缩 | 用模型把历史压成一段摘要 | 保留语义要点，压缩比通常能到 5~10 倍 | 有损且不可验证，多次压缩误差逐级累积 | 中等长度、以语义为主的历史 |
| 外部化 / 引用 | 全文存外部存储，上下文只留摘要加可寻址引用 | 无损、不占窗口、支持随机访问 | 依赖检索，回读要花一轮，何时回读本身是决策 | 长程任务，生产环境最稳 |
| 结构化抽取 | 只保留实体属性、工具结果摘要、决策点、约束清单、错误记录 | 精准命中决策所需信息，几乎不损失 | 抽取规则要按场景设计，通用性差 | 决策链条清晰的任务 |
| 分层 / 递归压缩 | 先按轮次或事件压成段摘要，再对段摘要二次压缩 | 避免长文本一次性压缩导致信息崩塌 | 层次越多损失越重，实现更复杂 | 极长历史 |
| 按重要性差异化保留 | 给消息打重要性分，只压低分消息，高分消息原样保留 | 该留的留、该压的压，优于统一截断或统一摘要 | 打分本身要花一次判断成本，且有误判风险 | 约束多、关键消息稀疏的会话 |
| 工具结果特殊处理 | 在工具边界就裁剪，只返回相关片段、字段投影、计数摘要 | 收益最高、成本最低 | 每个工具都要单独设计裁剪口径 | 所有 Agent，最该先做的一层 |

这三个维度不是互斥的选项，而是同一条管线上的三层：**「丢」管取舍，「合」管改写，「放」管迁移**。真实系统里往往三层都在用，只是比例不同。

## 先做「丢」：滑动窗口截断与按重要性差异化保留

**滑动窗口截断**是最省的一招：只保留最近 N 轮消息，更早的直接丢弃。优点是实现最简单、零额外成本、延迟最低，缺点是硬性丢失早期信息，而早期往往包含原始目标与硬约束——**这正是目标漂移的直接原因**：模型没忘怎么做，只是忘了为什么要这么做、不能做什么。改进办法是保留「锚点」片段，让首轮系统提示与最近一次目标重申不参与截断，成本几乎为零却能挡住大部分漂移。

**按重要性差异化保留**（Selective Retention）把「一律丢最早的消息」换成「按分数决定丢谁」：为消息打重要性分数，判断依据是三条信号——是否包含约束、是否被后续引用、是否与失败相关，然后只压缩低分消息，高分消息原样保留。它比统一截断或统一摘要都更优，因为压掉的恰好是低价值部分；代价是打分本身要花一次判断成本，而且存在误判风险，一旦把关键约束误判成低分，后果和硬截断一样。

## 再做「合」：摘要压缩、分层递归与结构化抽取

**摘要压缩**用模型把历史压成一段摘要，能保留语义要点，压缩比通常能到 5~10 倍。但它有三个硬伤：一是**有损且不可验证**，摘要可能丢掉精确数值、ID、否定约束（比如「不要做 X」）；二是每次摘要都是一次模型调用，有延迟与成本；三是反复触发会出现**摘要的摘要**，误差逐级累积。改进方式是结构化摘要——固定字段，并保留原文指针：

```json
{
  "已确认事实": ["导出格式由 CSV 改为 XLSX", "对外 API 路径保持不变"],
  "已排除方案": ["引入第三方导出库（许可证不合规）"],
  "未决事项": ["单个文件的最大行数上限"],
  "关键参数": { "batch_size": 5000, "timeout_s": 30 },
  "原文指针": ["history://run-3/turn-12", "log://run-3/export.log#L120-L260"]
}
```

固定字段的价值在于**否定约束和未决事项有固定位置**，不会在自由文本摘要里被顺手抹掉；原文指针让压缩结果可回溯。

**分层 / 递归压缩**是同一思路的分段版：先按轮次或事件做分段压缩，得到段摘要，再对段摘要做二次压缩。好处是避免长文本一次性压缩导致信息崩塌，适合极长历史；坏处是层次越多信息损失越重，实现也更复杂，所以层次应当少而明确，而不是层层套娃。

**结构化抽取**只从历史里抽取特定类型的信息保留：实体与属性、已调用的工具及结果摘要、决策点、约束清单、错误记录，其余全部丢弃。它精准命中决策所需信息、几乎不损失，但抽取规则必须针对场景设计，通用性差，而且效果依赖模型的抽取质量。

## 最后「放」：外部化引用与工具结果裁剪

**外部化 / 引用**把完整内容存到外部存储，上下文只留摘要加可寻址引用——文件路径、记录 id、行号范围，需要时再回读。它无损、不占窗口、支持随机访问，**是生产环境最稳的方案**。代价是引入对检索的依赖：回读本身要花一轮；更麻烦的是「什么时候该回读」本身是个决策问题，判断错了就等于信息丢失，所以引用要写得足够具体，让模型一眼看得出该去读哪一段。

**工具结果特殊处理**常被当成细节，实际是收益最高、成本最低的一层。工具返回往往是体积大头却价值密度极低——长日志、大段 HTML、原始数据。正确做法是**在工具边界就裁剪**：只返回相关片段、做字段投影、返回计数摘要，而不是等整块结果进了上下文再压缩。压缩发生在源头，既不占窗口，也不消耗一次额外的压缩调用。

## 选型顺序与三条共性原则

按任务长度选主策略：**短任务**（几十步内）用滑动窗口即可；**中等长度**用结构化摘要加锚点保留；**长程任务**用外部化加按需回读，必要时叠加按重要性差异化保留。无论选哪种，共性原则只有三条：

- 压缩的对象必须是**低价值密度、高体积**的信息，别去动密度高的部分。
- 涉及**精确数值、ID、否定约束、未决问题**的内容，一律原样保留或外部存储。
- 压缩后必须能**回溯到原文**，否则一旦压错就无从纠正。

## 常见追问

**Q：为什么说外部化是生产环境最稳的方案？**
A：因为它是唯一无损且可回溯的一类：窗口里只放摘要和指针，原文始终存在外部，压错了可以重新回读，而不是像摘要那样压错就永久丢失。

**Q：摘要压缩最容易丢什么？**
A：精确数值、ID 和否定约束，尤其是「不要做 X」这类否定句——摘要倾向于保留做了什么，而抹掉明确禁止的部分。

**Q：压缩比是不是越高越好？**
A：不是。压缩比越高，丢信息的概率越大，而摘要类压缩又不可验证。判断标准是「决策所需信息是否还在」，而不是压掉了多少 token。

**Q：为什么工具结果要单独算一层？**
A：因为它体积最大、价值密度最低，在工具边界裁剪比进上下文后再压缩更便宜，也避免了把长日志白白计费一次。

## 易错点

- **把「上下文压缩」等同于「写摘要」**：摘要只是七种策略之一，而且是唯一「有损且不可验证」的一类，只靠它必然在长任务里翻车。
- **先塞进上下文再去压缩工具结果**：长日志和大段 HTML 应该在工具边界就被裁剪掉，等它进了窗口再压，已经付过一遍 token 和时间。
- **以为截断只是「上下文短一点」**：丢掉早期目标与硬约束是目标漂移的直接原因，锚点必须豁免于截断。
- **反复对摘要再摘要**：每一轮都是新的有损变换，误差逐级累积，宁可改写成分层结构并挂原文指针。

:::tip[一句话记住]
压缩只针对低价值、高体积的信息，而且必须能回溯到原文。
:::
