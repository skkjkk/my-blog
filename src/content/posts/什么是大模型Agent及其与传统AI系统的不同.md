大模型 Agent 是**以大语言模型为核心决策引擎**、能在环境中自主感知、规划、调用工具并持续行动以达成目标的软件系统。它与传统 AI 系统的分水岭不在模型强弱，而在**控制流归谁**：传统系统把「感知、决策、执行」拆成由工程师显式编排的固定流水线，走哪条分支都写在代码里；Agent 把决策权交给模型，由它在运行时决定下一步做什么。控制权一移交，确定性、副作用、测试方式和失败模式就跟着一起变。

## 最根本的区别是控制流的位置

传统 AI 系统的控制流**在代码里**：每个 if/else、每条规则、每个流程节点都是人提前写好的，输入进来就沿着这条固定路径走到出口。Agent 的控制流**在模型里**：代码只提供目标、可用工具和边界条件，具体下一步做什么、调几次、什么时候停，由模型在运行时判断。

直接后果是**同一输入可能走出不同路径**，行为不再完全确定。同一个问题问两次，一次直接回答、一次先去检索再补一次计算，这在传统流水线里不会发生。工程上要接受这个代价：Agent 的可靠性不能靠「重放同一输入」来证明，只能靠轨迹记录、多次采样和边界约束来兜住。

## 传统 AI 是「一次性推理」，Agent 是「闭环迭代」

传统系统的输入固定、输出固定，一次前向计算就结束——分类、回归、排序、检测都是这个形态，模型不参与决定「接下来还要做什么」。

Agent 走的是「感知 → 思考 → 行动 → 观察」的循环：每一步的观测回填进上下文，作为下一步决策的依据，方向偏了还能在中途修正。因此它能处理**步骤数无法预先确定**的任务：排障、检索、改代码这类「事先写不出完整流程」的活，传统流水线只能覆盖已知分支，Agent 能在运行时现编路径。

一个最小循环骨架大致是这样（各家接口字段不同，结构类似）：

```text
while step < MAX_STEPS:
    thought = model(messages, tools)        # 思考：决定下一步做什么
    if thought.done: break                  # 终止：模型声明完成
    result = execute(thought.tool_call)     # 行动：真正作用于环境
    messages.append(result)                 # 观察：结果回填，进入下一轮
    step += 1
```

循环本身不难写，难的是给它配一条不依赖模型自己判断的退出路径：步数、时间、预算三道上限至少要有其一，否则模型一旦认为「还没做完」就会一直转下去。

## 组件差异：从「模型 + 特征工程」到「模型 + 工具 + 记忆 + 运行时」

传统 AI 的组件是**模型 + 特征工程**：特征工程负责把原始数据变成模型能吃的输入，模型的职责是给出预测。Agent 的组件是**模型 + 工具 + 记忆 + 运行时**，在模型之外多了三块东西：

- **工具**，也就是「手」：检索、数据库、文件、代码执行、外部 API，让模型能作用于环境，而不只是输出文本。
- **记忆**：跨步骤保留任务状态、中间结果和历史经验，不必每一步从零开始。
- **运行时**：管预算、终止、恢复、重试的调控机制，把一次可能失控的自主行为关进笼子。

这四块的分工是：模型负责判断，工具负责执行，记忆负责连续性，运行时负责兜底。缺了运行时，前三块越强越危险。

## 传统 AI 通常没有副作用，Agent 有

传统系统的输出是预测结果或建议：一条推荐、一个分数、一段分类标签，算完就结束，错了最多是答错。Agent 会真实调用数据库、修改文件、发请求、执行代码，动作一旦落地就有副作用。

因此 Agent 必须额外处理**权限、幂等、事务、审计、回滚**——这几件事传统 AI 系统基本不用考虑。写操作要有幂等键，危险动作要有权限校验和人工确认，失败要能回滚或补偿，全过程要留可复查的轨迹。这部分工作量往往比「接一个模型」大得多，也正是演示版与生产系统之间的实际差距。

## 工程重心从数据与特征转到上下文与状态

传统 AI 的工程重点是**数据与特征**：清洗、采样、特征设计、离线指标，绝大部分精力花在「喂什么给模型」上。

Agent 的工程重点是**上下文工程、状态管理、可靠性与可观测性**：每一步该把哪些信息塞进上下文、多轮之后怎么裁剪与摘要、状态存在哪里、失败怎么恢复、轨迹怎么留下来复盘。这正是「Prompt Engineering 让位于 Context Engineering」的原因——单轮提示词的技巧只影响一次生成，而上下文里放什么、放多少，决定了整个循环能不能走对。

测试方式也随之改变。传统系统的输出可以用**固定样本回归验证**；Agent 路径不确定，**必须建立任务集 + 多次采样 + 统计口径 + 确定性回放**才能回归。这就是 Agent 评测比传统模型评测复杂得多的原因：单次跑通说明不了任何事，要看任务集上的分布。

## 失败模式：从「答错」到「过程性失败」

传统 AI 的失败基本只有一种：**精度不够**，答错、排序错、分类错。这种失败容易发现，也容易用指标度量。

Agent 除了答错，还会**过程性失败**：选错工具（该查库却去搜网页）、陷入循环（两个动作来回打转）、目标漂移（做着做着跑偏到别的任务）、越权操作（动了没权限碰的数据）、烧掉预算（步数失控）。这类失败单看每一步都「合理」，只有拉通整条轨迹才发现不对，所以需要专门的检测与恢复机制：轨迹监控、异常动作拦截、预算熔断、关键步骤人工确认。

## 选型与边界：混合式，而且是渐进的分界

Agent 适合**步骤不定、需要与环境交互、领域知识难以显式规则化**的任务。反过来，步骤固定的任务用传统流水线**更快、更便宜、更可控、更易测试**——把已知流程塞进 Agent，是用确定性换灵活性，还要多背一堆新的失败模式。

| 维度 | 传统 AI 系统 | 大模型 Agent |
|---|---|---|
| 控制流 | 在代码里，路径预先写死 | 在模型里，运行时动态决定 |
| 交互形态 | 一次性推理，输入输出固定 | 感知 → 思考 → 行动 → 观察的循环 |
| 组件 | 模型 + 特征工程 | 模型 + 工具 + 记忆 + 运行时 |
| 副作用 | 通常没有，只产出预测或建议 | 真实作用于环境，需权限与回滚 |
| 工程重心 | 数据与特征 | 上下文工程、状态管理、可靠性、可观测性 |
| 可测试性 | 固定样本回归 | 任务集 + 多次采样 + 统计口径 + 确定性回放 |
| 失败模式 | 精度不够，答错 | 答错 + 过程性失败（选错工具、循环、漂移、越权、烧预算） |
| 适合场景 | 步骤固定、流程已知 | 步骤不定、需与环境交互 |

**工程判断的标准是「这一步是否真的需要自主推理」**：需要就交给模型，按规则就能定的就写进代码。成熟系统普遍是混合式的，把确定的部分用代码写死，只把需要灵活判断的部分交给模型。

分界也是渐进的。推荐系统、搜索排序、画像推荐这些传统 AI 系统，只要引入「模型自主决定下一步调用哪个召回源或哪个策略」，就已经开始具备 Agent 的特征。**Agent 不是一个全新物种，而是 AI 系统设计中「自主性」这一维度的提升。**

## 常见追问

**Q：Agent 和传统 AI 的分界线到底在哪？**
A：看控制流。步骤由代码写死、模型只负责预测或生成，就是传统系统；模型在运行时自己决定下一步做什么，才算 Agent。

**Q：为什么说 Agent 更难测试？**
A：传统系统用固定样本就能回归；Agent 路径不确定，要任务集 + 多次采样 + 统计口径 + 确定性回放才能下结论，单次成功不能证明稳定。

**Q：Agent 一定比传统流水线更好吗？**
A：不是。步骤固定的任务用传统流水线更快、更便宜、更可控、更易测试，上 Agent 反而是负优化，还多出一堆过程性失败。

**Q：既然更贵更不可控，什么情况下非 Agent 不可？**
A：任务步骤数无法预先确定、又必须与环境交互时，例如排障、深度检索、改代码。这类活传统流水线覆盖不了，只能给目标和工具让模型现场规划。

## 易错点

1. **把「用了大模型」当成「做了 Agent」**。如果每一步调什么工具、调几次都由代码决定，控制流仍在代码里，那只是模型参与的流水线。
2. **以为 Agent 强是因为模型更强**。真正的分水岭是控制权移交：只要每一步仍由代码编排，模型再强也只是流水线上负责生成的一环，行为依旧确定，也谈不上自主。
3. **只写循环不写边界**。没有步数、时间、预算上限，又不给工具加权限校验，循环会一直转、动作会越权，账单和风险一起涨。
4. **用固定样本回归测 Agent**。一次跑通不代表稳定，要看任务集上的多次采样结果和轨迹回放，否则上线后才暴露过程性失败。

## 一句话记住

:::tip
区别不在模型多强，而在控制流归谁：代码编排，还是模型运行时自决。
:::
