多模态 Agent 的推理与纯文本 Agent 的本质差别在于：**输入不再是单一文本，而是多种模态的组合**；模型要同时完成"**看懂**"与"**决定下一步看什么/做什么**"两件事。

1) **多模态输入的三种典型形态**。**图文混合输入**（用户上传图片 + 文字提问，如看懂截图报错、分析图表）；**屏幕/环境感知**（Computer Use 场景，模型接收截图并输出鼠标键盘动作）；**文件与音视频**（PDF、扫描件、表格、录音转写、视频抽帧）。

2) **感知层要先做"转译"**。图像、屏幕截图、PDF、扫描件在送入模型前，通常需要**预处理**：图像缩放与裁剪（控制 token 消耗）、**OCR / 文档结构解析**（把扫描件转成结构化文本与表格）、**关键区域裁剪**（只保留信息密集的区域）、**音视频转写与抽帧**。**这一步直接决定成本与准确率** —— 一张 2000×2000 的原图和多张裁剪后的关键区域，效果可能差很多。

3) **图像常被"转成文本"进入推理链**。把视觉信息转成结构化描述（OCR 文本、元素坐标、布局关系、图表转成表格）后，**后续的推理就可以沿用纯文本 Agent 的全部技术**（工具调用、状态管理、规划）。这是目前工程上最实用的路径 —— 避免为"看"单独设计一套 Agent 机制。

4) **坐标与动作空间是 Computer Use 的核心**。模型输出的是**动作**（点击坐标、输入文本、滚动、按键），需要配套的**动作执行器**（截图 → 定位 → 点击）。难点在于**坐标精度**与**状态确认**（点完是否成功，要重新截图验证）。因此这类 Agent 的循环通常是"**截图 → 推理 → 动作 → 重新截图验证**"。

5) **多模态让"证据"变成可视的**。截图、界面元素、图表这些**本身就是可溯源的证据**，可以像引用文档片段一样引用它们的位置，这比纯文本场景的溯源更直观。

6) **多模态引入新的失败模式**。**视觉误读**（把按钮看成图标、读错数值）；**空间推理错误**（不知道元素被遮挡、在视口外）；**分辨率与尺寸问题**（小字看不清、坐标偏移）；**状态假设错误**（以为页面已刷新）。因此**必须做"动作后确认"**，不能只凭模型的一次输出就执行后续动作。

7) **多模态显著抬高成本**。图像 token 消耗远高于文本，且**每轮都要重新发送**（Agent 循环中反复传截图，成本翻倍）。缓解手段：**截图裁剪与降采样**、**只在必要时截图**（状态未变化就不截）、**关键帧去重**、**用文本状态描述替代重复截图**。

8) **多模态 Agent 的分层实现**。**感知模块**（截图/文档 → 结构化描述）→ **与纯文本 Agent 相同的决策层**（规划、工具调用、状态管理）→ **动作模块**（GUI 操作 / 工具执行）。**把多模态限制在"输入端"和"动作端"，决策层保持统一**，是当前最稳妥的架构。

9) **Agent 智能体的多模态记忆**。视觉记忆需要额外设计 —— 截图要存**结构化描述 + 关键区域**，而不是原图堆砌（成本与检索质量都会崩）。**能用文字描述表达的记忆，不要存成图片。**

10) **选型判断**。多模态 Agent 的价值在于"**需要理解非结构化视觉/听觉信息并据此行动**"的场景（GUI 操作、截图排障、票据识别）。若任务的数据本来就是结构化的（数据库、API），**先把数据转成文本再交给 Agent**，比强行走多模态更省、更稳。
