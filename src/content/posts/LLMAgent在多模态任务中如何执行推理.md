多模态 Agent 的推理与纯文本 Agent 的本质差别在于：**输入不再是单一文本，而是多种模态的组合**，模型要在同一轮里同时完成"**看懂**"与"**决定下一步看什么、做什么**"两件事。工程上的主流做法是把多模态限制在两端：感知层先把图像、屏幕、文档转成结构化描述（文本、元素坐标、布局关系），决策层沿用纯文本 Agent 的规划与工具调用，动作端再把决策翻译成点击、输入等真实操作。这样既不用为"看"重造一套 Agent 机制，也把成本与失败面收敛到少数几个可单独测试的环节。

## 多模态输入的三种典型形态

- **图文混合输入**：用户上传图片 + 文字提问，典型任务是看懂截图报错、分析图表。
- **屏幕/环境感知**：Computer Use 场景，模型接收屏幕截图并输出鼠标键盘动作。
- **文件与音视频**：PDF、扫描件、表格、录音转写、视频抽帧。

这三类对 Agent 的要求并不一样。前一类多是"单轮看清楚"就够，后两类还要处理**时序与状态**：页面会变，视频有先后，因此感知层与动作确认的设计压力更大。

## 感知层先做"转译"：预处理决定成本与准确率

图像、屏幕截图、PDF、扫描件在送入模型前，通常需要预处理。常见手段和它解决的问题：

| 预处理手段 | 解决什么 | 不做的代价 |
| --- | --- | --- |
| 图像缩放与裁剪 | 控制 token 消耗 | 大图直接进模型，贵且容易挤爆上下文 |
| OCR / 文档结构解析 | 把扫描件转成结构化文本与表格 | 模型只能靠像素猜字，数值与表格结构最容易错 |
| 关键区域裁剪 | 只保留信息密集的区域 | 无关区域白占注意力和预算 |
| 音视频转写与抽帧 | 把连续信号切成可推理的片段 | 无法定位"第几秒说了什么、哪一帧出了问题" |

**这一步直接决定成本与准确率。** 一张 2000×2000 的原图，和多张裁剪后的关键区域，效果可能差很多。所以多模态 Agent 的第一版工作往往不是调模型，而是把预处理流水线做对。

## 视觉信息常被"转成文本"再进入推理链

把视觉信息转成结构化描述——OCR 文本、元素坐标、布局关系、图表转成表格——之后，**后续的推理就可以沿用纯文本 Agent 的全部技术**：工具调用、状态管理、规划。这是目前工程上最实用的路径，避免为"看"单独设计一套 Agent 机制。

顺带还有一个好处：截图、界面元素、图表这些**本身就是可溯源的证据**，可以像引用文档片段一样引用它们的位置，比纯文本场景的溯源更直观——答案能直接指到"哪个区域的哪个按钮"。

## Computer Use 的核心是坐标、动作空间与动作后确认

模型输出的是**动作**（点击坐标、输入文本、滚动、按键），需要配套的**动作执行器**（截图 → 定位 → 点击）。难点在于**坐标精度**与**状态确认**：点完是否成功，要重新截图验证。因此这类 Agent 的循环通常是"**截图 → 推理 → 动作 → 重新截图验证**"。

```text
while not done:
  shot = screenshot()                  # 取当前界面状态
  plan = llm(goal, shot, history)      # 定位元素 + 决定动作
  act(plan.action, plan.args)          # 点击 / 输入 / 滚动
  shot2 = screenshot()                 # 动作后确认
  if not expected(shot2, plan.expect):
    replan()                           # 没达到预期就重规划，而不是接着连点
```

多模态同时引入了几类新的失败模式：

- **视觉误读**：把按钮看成图标、读错数值。
- **空间推理错误**：不知道元素被遮挡、或在视口外。
- **分辨率与尺寸问题**：小字看不清、坐标偏移。
- **状态假设错误**：以为页面已经刷新。

这些错误全都发生在"看"这一环，所以**必须做"动作后确认"**，不能只凭模型的一次输出就执行后续动作。

## 图像 token 显著抬高成本

图像 token 消耗远高于文本，而且在 Agent 循环里**每轮都要重新发送**：同一个界面反复传截图，成本随步数成倍上涨。四条缓解手段：

- **截图裁剪与降采样**：只传必要区域，按需降分辨率。
- **只在必要时截图**：状态未变化就不截。
- **关键帧去重**：连续多帧几乎一致时只保留一帧。
- **用文本状态描述替代重复截图**：把"当前页面有哪些元素"固化成文本，后面几轮直接引用。

## 分层实现与多模态记忆

典型分层是**感知模块**（截图/文档 → 结构化描述）→ **与纯文本 Agent 相同的决策层**（规划、工具调用、状态管理）→ **动作模块**（GUI 操作 / 工具执行）。**把多模态限制在"输入端"和"动作端"，决策层保持统一**，是当前最稳妥的架构：脆弱点被集中到两个可以单独测试、单独降级的模块里。

记忆也要跟着改。视觉记忆需要额外设计——截图要存**结构化描述 + 关键区域**，而不是原图堆砌，否则成本与检索质量都会崩。**能用文字描述表达的记忆，不要存成图片。**

## 选型判断：什么时候真该上多模态

多模态 Agent 的价值在于"**需要理解非结构化视觉/听觉信息并据此行动**"的场景：GUI 操作、截图排障、票据识别。反过来，若任务的数据本来就是结构化的（数据库、API），**先把数据转成文本再交给 Agent**，比强行走多模态更省、更稳。

## 常见追问

**Q：多模态 Agent 和"先 OCR 再交给文本 Agent"有什么区别？**
A：同一条思路的两个深度。"先 OCR"只拿到文字，拿不到元素坐标、布局关系和图表结构；多模态 Agent 把这些也转成结构化描述，并且能把动作产生的新截图回灌到下一轮决策，闭环更完整。

**Q：为什么强调决策层不要为多模态另写一套？**
A：规划、工具调用、状态管理这些能力和模态无关。把接口统一在"结构化描述"上，纯文本与多模态就能共用同一套决策逻辑，新模态只是多一个感知适配器，测试和降级都简单得多。

**Q：动作后确认一定得重新截图吗？**
A：GUI 场景多数是，因为界面状态只能从新截图里读到。若动作有可靠返回值（比如接口调用返回成功码），用返回值确认更便宜，截图确认留给"返回不可信"的操作。

**Q：成本压不下来怎么办？**
A：先问信息是不是本来就在结构化数据里，是就直接转文本给 Agent。确实必须看像素时，再靠裁剪降采样、按需截图、关键帧去重和文本化状态描述来压低每轮开销。

## 易错点

- **把"接了视觉模型"当成多模态 Agent**：视觉只是感知那一环，缺了动作执行器和状态确认，Agent 依然只能看不能做。
- **一次输出就连续执行多步动作**：视觉误读和状态假设错误会沿着动作链累积，正确做法是每步动作后重新截图确认。
- **把原图当记忆存起来**：视觉记忆要存结构化描述 + 关键区域，堆原图会让成本与检索质量同时崩掉。
- **为"先进"强行走多模态**：数据本来结构化的场景（数据库、API），先把数据转成文本再交给 Agent 更省更稳。

## 一句话记住

:::tip
多模态 Agent = 感知转译 + 文本决策 + 动作确认，多模态只留在两端。
:::
