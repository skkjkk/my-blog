数据库死锁是指**两个或多个事务互相持有对方需要的锁，且都在等待对方释放，形成循环等待**，导致双方**永久阻塞**。InnoDB 有死锁检测能力，会**主动回滚其中一个事务**让另一个继续，所以"数据库死锁"通常表现为**报 `Deadlock found` 错误**，而不是像 Java 那样真的挂死。

## 死锁形成的四个必要条件

（与 Java 死锁一致）
互斥条件、持有并等待、不可剥夺、**循环等待**。前三条由排他锁的语义本身决定，业务代码很难破坏；真正能由应用彻底消除的只有**循环等待**，所以这一条也是投入产出比最高的突破口：**统一加锁顺序**。

## InnoDB 如何检测与解决死锁

- **`innodb_deadlock_detect`**（默认 ON）→ 检测循环等待
- 检测到后选择**"代价最小"的事务回滚**（回滚的行数/锁最少）→ 返回 `ERROR 1213 (40001): Deadlock found when trying to get lock`
- **`innodb_lock_wait_timeout`**（默认 50 秒）→ 检测不到循环时的兜底超时（`ERROR 1205: Lock wait timeout exceeded`）

:::tip
**应用必须处理这两个错误码并重试** —— 这是分布式系统中数据库死锁的常态。
:::

## 最典型的死锁场景：两条 UPDATE 反向加锁

```sql
-- 事务 A                        -- 事务 B
UPDATE t SET v=1 WHERE id=1;    UPDATE t SET v=2 WHERE id=2;
UPDATE t SET v=2 WHERE id=2;    UPDATE t SET v=1 WHERE id=1;
```

双方各持一把行锁又互相等对方 → **死锁**。关键在于两条语句加锁的**顺序相反**：A 先锁 `id=1` 再要 `id=2`，B 先锁 `id=2` 再要 `id=1`，于是都成为对方的前置依赖，谁也走不到 `COMMIT`。

## 最容易忽略的场景：`UPDATE` 按非索引条件更新会锁全表

```sql
UPDATE t SET v=1 WHERE non_index_col = 'x';  -- 无索引 → 锁全表所有行
```
两个这样的语句并发执行 → **必然死锁**。因为条件列没有索引时，优化器只能全表扫描并给扫到的每一行加锁，两条语句各自锁住的行集互相覆盖，加锁顺序又由扫描顺序决定，几乎必然形成循环等待。

:::tip
**这就是"加了索引能减少死锁"的真正原因** —— 锁的范围从全表缩小到了少量行。**索引不仅影响性能，还影响并发正确性。**
:::

## 五大解决方案（按优先级）

- **① 统一加锁顺序** ⭐⭐ —— 最有效、最易落地。所有事务**按 ID 从小到大**更新（应用层排序），彻底消除循环等待
- **② 缩短事务** ⭐⭐ —— 事务越短持锁越短，冲突概率越低；**事务中禁止远程调用、禁止 RPC、禁止等待用户输入**
- **③ 减小锁范围** ⭐⭐ —— **所有 WHERE / JOIN / ORDER BY 的列都建索引**（否则行锁退化为表锁）
- **④ 应用层重试** ⭐⭐ —— 捕获 `1213`/`1205` 后**指数退避重试**（数据库死锁是正常现象，不是 bug）
- **⑤ 降低隔离级别** —— RC 级别下间隙锁更少（**MySQL 8.0 可 `innodb_lock_wait_timeout` + `NOWAIT`/`SKIP LOCKED`**）→ 死锁概率下降

## `SKIP LOCKED` —— 一个很实用的现代特性

```sql
SELECT * FROM queue WHERE status=0 LIMIT 10 FOR UPDATE SKIP LOCKED;
```
**直接跳过已被锁定的行** → 多个消费者**不会互相等待** → **队列消费场景彻底避免死锁**（MySQL 8.0+）。类似 Redis 的 `LPOP` 语义。

:::tip
**这是"用 MySQL 做任务队列"的现代最佳实践**，能讲出来很加分。
:::

## 排查手段

- **`SHOW ENGINE INNODB STATUS`** → 查看最近一次死锁的详细过程（**含两个事务各自的 SQL、持有的锁、等待的锁**）⭐ **最直接的证据**
- **`performance_schema.data_locks` / `data_lock_waits`** → 实时查看锁与等待关系
- **`information_schema.innodb_trx`** → 看当前运行中的事务（找出长事务）
- **`innodb_print_all_deadlocks`**（MySQL 8.0.20+）→ 开启后**把所有死锁记录到错误日志**，便于告警与统计

## 长事务是死锁的隐性根源

长事务持有锁不放 → 其他事务排队等待 → 锁范围持续扩大 → 死锁与超时频发。

:::tip
**必须监控 `innodb_trx` 中运行超长的事务**（如 > 60 秒）并告警；应用侧要确保事务边界清晰、`finally` 中回滚。
:::

## 常见追问

**问：InnoDB 遇到死锁会自己挂死吗？应用要不要处理？**
**答：** 不会挂死。`innodb_deadlock_detect` 默认开启，检测到循环等待后主动回滚"代价最小"的一方，把 `1213` 报给该事务，另一方继续执行；应用必须捕获 `1213`/`1205` 并退避重试，否则这次本该成功的请求就白丢了。

**问：死锁的根因通常是哪几类场景？**
**答：** 反向更新顺序（两条 `UPDATE` 交叉加锁）、`WHERE` 条件没走索引导致行锁退化成锁全表、以及长事务持锁不放；前两类是循环等待，第三类是把等待窗口无限拉长。

**问：根治死锁最有效的手段是什么？**
**答：** 统一加锁顺序——应用层把要更新的 ID 排序，所有事务按同一方向加锁，从结构上消灭"循环等待"这个必要条件；再叠加缩小锁范围（补索引）、缩短事务、应用层重试，`SKIP LOCKED` 则专门解决队列消费的争抢。

**问：为什么加了索引，死锁就变少了？**
**答：** 因为锁是加在扫描到的行上的。没索引时一条 `UPDATE` 要扫全表，等于锁住所有行，两个并发语句必然互相等待；有索引后只锁命中的少数几行，冲突面从整张表缩小到几行，死锁概率随之大幅下降。

## 易错点

- **把死锁当成程序 bug、报错就让用户重试失败**：并发写入下死锁是常态，InnoDB 已经替你回滚了代价较小的一方，正确做法是捕获 `1213`/`1205` 后指数退避重试，而不是把异常直接抛给用户。
- **以为调小 `innodb_lock_wait_timeout` 就"解决"了死锁**：它只是检测不到循环等待时的兜底超时，调小只是让等待更早失败、报 `1205`，死锁本身还在，得靠加锁顺序、索引、短事务去消除。
- **只盯着主键，以为锁范围自然很小**：`WHERE` / `JOIN` / `ORDER BY` 用到的列没索引时，扫描放大的部分都会被加锁，行锁直接退化成接近表锁。
- **以为降到 RC 隔离级别就没有死锁了**：RC 少的是间隙锁，死锁概率下降但并不为零，加锁顺序和索引仍然是必须做的。

## 一句话记住

:::tip
死锁是并发常态：统一加锁顺序 + 索引缩锁范围 + 应用重试。
:::
