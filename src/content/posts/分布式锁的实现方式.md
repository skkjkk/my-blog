分布式锁解决的是"多个服务实例并发操作同一份共享资源时的互斥"，实现上只有三条主流路线：数据库的唯一约束或行锁、Redis 的 `SET NX EX`、ZooKeeper 的临时顺序节点。选哪条取决于对可靠性、吞吐和运维复杂度的取舍，并发高、能容忍极小概率锁丢失的业务用 Redis，强一致要求高、规模不大的核心场景用 ZooKeeper。

## 基于数据库：唯一约束或 SELECT ... FOR UPDATE

最朴素的做法是建一张锁表，把资源标识作为主键：插入成功就代表拿到锁，删除记录就代表释放锁，互斥完全由主键唯一约束保证。另一种做法是在事务里用 `select ... for update` 对目标行加排他行锁，锁一直持有到事务提交或回滚。

它的优点是实现最简单、不需要引入任何额外组件；缺点是并发能力弱，所有抢锁请求都压在数据库上，而且 `for update` 必须在显式事务中才生效，事务一长，锁的持有时间就被放大到整个业务逻辑的耗时。适合并发量不高、对可靠性要求一般的内部场景，比如对账任务、后台批处理。

## 基于 Redis：SET NX EX 加锁，Lua 校验后释放

用 `SET key value NX EX seconds` 这一条命令原子地完成"key 不存在才写入 + 设置过期时间"，返回成功即拿到锁。释放时不能直接 `DEL`，要先比对 value 是不是自己写入的随机标识，再用 Lua 脚本把"比对 + 删除"合成一次原子操作，否则会出现误删他人持有的锁。

Redis 是内存数据库，吞吐高、延迟低，是目前最主流的选择。生产上一般直接使用 Redisson，它提供了可重入锁、看门狗自动续期、带超时的锁等待（`tryLock`），以及读写锁、信号量等多种数据结构，默认租期 30 秒、后台每三分之一租期续期一次。

```java
// 加锁：一条命令完成"不存在才写入 + 过期时间"
String token = UUID.randomUUID().toString();
Boolean ok = redis.opsForValue().setIfAbsent("lock:order:1001", token, Duration.ofSeconds(30));

// 释放：先比对 value 再删除，整体用 Lua 保证原子
String lua = "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end";
redis.execute(new DefaultRedisScript<>(lua, Long.class), List.of("lock:order:1001"), token);
```

## 基于 ZooKeeper：临时顺序节点，序号最小者得锁

在 `/lock` 这类父节点下为每个竞争者创建一个**临时顺序节点**，序号最小的那一个持有锁，其余节点监听自己的前一个节点，前一个消失就轮到自己，天然实现了公平排队。

临时节点与会话绑定，客户端宕机或会话超时后节点会被自动删除，所以不会出现"持有者死了、锁还在"的死锁。它的一致性语义比 Redis 更强：抢锁的判定走的是一致性写，不存在两个客户端同时认为自己持锁的情况。代价是部署与运维更重，写性能也低于 Redis。同一思路的还有 etcd，靠租约（lease）加版本号实现互斥，强一致且天然贴合 Kubernetes 生态。

## 三种方案的对比与选型

| 维度 | 数据库 | Redis | ZooKeeper |
| --- | --- | --- | --- |
| 实现复杂度 | 最低，建张锁表即可 | 低，一条 SET 命令 | 中，要理解节点与监听 |
| 并发与性能 | 弱，受数据库容量限制 | 最高，内存加单命令 | 中，写要走共识协议 |
| 一致性模型 | 跟随数据库本身 | AP，极端切换可能丢锁 | CP，强一致 |
| 死锁风险 | 靠过期清理或人工删记录 | 靠过期时间兜底 | 临时节点自动删除 |
| 适用场景 | 并发低、内部系统 | 高并发、允许极小概率丢锁 | 强一致、规模不大的核心链路 |

取舍可以浓缩成一句话：数据库实现简单但并发能力弱；Redis 性能最好但属于 AP 模型，故障切换的极端时刻可能丢失锁，需要业务侧做兜底；ZooKeeper 属于 CP 模型，强一致但可用性与性能都有代价。

另外要注意，很多场景真正的瓶颈不是互斥而是并发度，这类需求应该配合**分布式信号量**（限制并发数）、**分布式限流**、**幂等控制**一起解决；如果操作本身是幂等的，引入分布式锁带来的复杂度与故障风险可能远大于收益。趋势上也在从"各家自研锁"走向成熟的中间件或云厂商托管锁服务，以降低自研带来的正确性风险。

## 三个必须处理的工程细节

- **锁超时与续期**：锁一定要带过期时间，防止持有者宕机后形成死锁；但业务执行时间可能超过超时时间，所以需要看门狗机制定期续期，Redisson 默认就会自动续期。
- **误删锁**：释放锁时必须校验锁的持有者标识（如随机 UUID），否则 A 的锁超时后被 B 拿到，A 恢复后执行删除就会误删 B 的锁，这需要用 Lua 脚本保证"比对 + 删除"的原子性。
- **可重入**：业务可能嵌套加锁，需要记录持有者线程标识和重入次数，保证同一线程可重入、不同线程互斥。
- **公平性与多模式**：生产级还应支持 FIFO 排队、读写锁、红锁（RedLock）等形态，Redisson 基本覆盖了这些能力。

:::caution
看门狗只能解决"业务还没跑完但进程健康"的续期问题。进程长时间 Full GC、网络分区时续期同样会失败，锁照样提前过期。所以被锁保护的操作最好本身幂等，或在下游校验一个单调递增的 fencing token，避免"两个客户端都以为自己持锁"时写坏数据。
:::

## 常见追问

**Q：Redis 主从切换为什么会丢锁？**
A：Redis 复制是异步的，主节点写进锁还没来得及同步就挂了，从节点升主时这把锁并不存在，另一个客户端可以重新加锁成功，于是两人同时持锁。RedLock 想缓解这个问题，但业界对其安全性仍有争议，根本办法是让被保护的操作幂等或带 fencing token。

**Q：为什么释放锁必须用 Lua，不能先 get 再 del？**
A：`get` 和 `del` 是两条独立命令，两者之间锁可能刚好过期并被别人抢走，你比对的是旧值、删的却是新持有者的锁。Lua 在 Redis 里原子执行，才能保证比对与删除中间不被插入。

**Q：有看门狗就万无一失了吗？**
A：不是。看门狗只在持有者进程还活着、且能连上 Redis 时才能续期；进程假死、长时间停顿或网络不通时续期失败，锁就会过期。它是降低概率的手段，不是正确性的保证。

**Q：什么时候本地锁就够，不必上分布式锁？**
A：单实例部署、且并发只来自本进程多线程时，`synchronized` 或 `ReentrantLock` 就够，还更快、没有网络开销。只要存在多实例或多进程同时访问同一份资源，本地锁就完全失效，必须换成分布式锁。

## 常见易错点

- **先 GET 判断再 SET**：两步不是原子的，判空之后可能被别人抢先写入，必须用 `SET key value NX EX` 一条命令完成。
- **加锁忘了设过期时间**：持有者崩溃后锁永不释放，只能人工删 key 恢复，这是最常见的线上事故。
- **释放锁直接 DEL**：锁超时易主后再删除，会删掉别人的锁，进而让互斥彻底失效，务必比对 value 并用 Lua 删除。
- **拿 Redis 锁当强一致用**：Redis 是 AP 模型，极端故障下存在两人同时持锁的窗口，涉及金额、库存的强一致链路不能只靠它。

## 一句话记住

:::tip
三条路线看约束、看性能、看一致性；真正的难点在锁超时、误删与重入。
:::
