Reflexion 是一种给 Agent 加入**「自我反思与试错学习」**机制的范式：一次尝试做完（或某个动作失败）之后，模型用一段自然语言写清刚才为什么没成，把这段归因存进外部记忆，下一次尝试时再把它作为额外上下文带回去，从而在**跨轮次、跨任务**上少犯同一个错。一句话区分：ReAct 管的是当前任务内的局部纠错，Reflexion 管的是把错误沉淀成可复用的经验。

## 与 ReAct 的核心区别：多出一种输出类型

ReAct 的轨迹只有 Thought、Action、Observation 三种元素，**只在当前任务内做局部修正**——看到错误结果就换个动作再试，但**经验不沉淀、不会跨任务复用**。Reflexion 在这三种之外增加了 Reflection 这一环，把失败原因**显式地写成文字经验并持久化**，后续尝试中作为额外上下文带入，让 Agent **避免重复同类错误**。差别不在提示词写法，而在「错误信息最终去了哪里」：ReAct 让它消散在轨迹里，Reflexion 让它变成一条可检索的记忆。

| 维度 | ReAct | Reflexion |
| --- | --- | --- |
| 轨迹元素 | Thought、Action、Observation | 再加 Reflection（反思文本） |
| 纠错范围 | 当前任务内的局部修正 | 跨轮次、跨任务的自我改进 |
| 错误处理 | 换个动作再试，经验随轨迹丢弃 | 写成文字归因并持久化进记忆 |
| 记忆依赖 | 不要求外部记忆 | 依赖外部记忆才能生效 |
| 主要开销 | 步数带来的上下文增长 | 额外一次反思调用与相应延迟 |

## ReAct 是「当前任务内纠错」，Reflexion 是「跨任务改进」

这是最精准的一句话区分，也是面试中应当先给出的答案。ReAct 的自我纠正在**同一条轨迹内**发生：观察不符合预期，就在下一次 Thought 里调整方向；任务结束、轨迹丢弃，下一个类似任务从零开始。Reflexion 把「这次为什么失败」从模型的隐性直觉变成**显性的文字**，存到轨迹之外，于是第二个类似任务开局就带着上一次的教训。所以它不是 ReAct 的替代品，而是**加在执行循环外面的一层学习闭环**。

## 三种触发时机

按反思发生的位置可以分成三种：**行动前反思**（Act-Reflect-Act 循环中，在每次动作前先评估当前方案是否合理）、**行动后反思**（得到结果后总结成功或失败的原因）、**任务后反思**（整体完成后的总结与经验沉淀）。工程上最常用的是后两种：行动前反思要多花一次调用却还看不到新信息，收益最低；行动后与任务后的反思有真实观测作依据，归因质量最高。

## 经典实现是 Actor-Critic 双角色结构

Reflexion 的经典实现是一个 Actor-Critic 双角色结构：**Actor 负责产生动作**，**Reflector 负责生成反思文本**，**记忆模块存储反思**，轨迹在反思后被**截断重写**——把反思文本插入轨迹，作为新一轮的引导。这里要特别说清：Critic 不是打分器，而是**生成改进建议的另一个角色**，它交出来的是一段能直接贴回上下文的自然语言，而不是一个分数。

```text
第 1 次尝试：Actor 执行 → 轨迹 T1 → 验收不通过
反思      ：Reflector 读 T1 → 生成反思 R1「查用户要用 id 字段，不是 name」→ 存入记忆 M
重写轨迹  ：T2 的起点 = 任务目标 + R1（T1 只留结论，其余截断）→ Actor 重试
```

## 提升自我纠错能力的五个通用手段

- **可诊断错误回填**：工具失败时把具体原因交给模型，不是堆栈，而是「参数 x 不存在，请用 id 字段」。
- **外部验收**：用程序化断言或独立评判器判定成败，而不是采信模型自述「我做完了」。
- **失败模式归类**：把错误归入「选错工具 / 参数错 / 理解错 / 环境异常」，不同类别给不同的引导提示。
- **经验注入**：把历史失败经验压缩成简短规则放在提示开头，成本低、见效快。
- **重规划触发**：连续失败 N 次时跳出局部循环、重新分解任务，而不是在同一条策略上加倍重试。

## 代价与风险：反思不是免费的

反思本身要**消耗一次额外的模型调用**，延迟与成本都上升；反思质量取决于模型能力，**弱模型可能生成错误归因，反思错了比不反思更糟**；反思文本还会占用上下文窗口，反复累积反而稀释注意力；过度反思会让 Agent 反复怀疑自己、迟迟不行动。实践上要给反思**次数上限**与**触发条件**，比如只在连续失败或验收不通过时触发，而不是每一步都反思一遍。

## 与 Plan-and-Execute 的关系

Reflexion 改进的是**单次尝试的质量**，Plan-and-Execute 改进的是**长程结构**。两者不冲突，生产上常组合：外层用规划-执行分离控制整体结构，内层用 Reflexion 处理局部失败。判断标准很直接——问题出在「这一步做得对不对」就用 Reflexion，问题出在「整个任务该分几步、按什么顺序」就用规划。

## 常见追问

Q：Reflexion 需要微调模型吗？
A：不需要。它是提示词层面的机制，反思文本以自然语言写进记忆、再拼回上下文，靠上下文完成改进，模型参数不变。

Q：它和普通的失败重试有什么区别？
A：重试是原样再跑一遍，失败原因没有被表达出来；Reflexion 把原因写成文字并带进下一次尝试，改的是下一次的输入，而不是再赌一次运气。

Q：反思一定有用吗，什么情况下反而有害？
A：有验收信号时有用；没有验收信号时模型只能凭自我感觉归因，弱模型容易归错因，等于给下一次注入错误先验。所以要用外部验收或明确的错误回填来锚定反思的输入。

Q：反思文本存多长、存多久合适？
A：存规则不存故事，压缩成一两句可执行的约束（如「查用户信息必须用 id 字段」），再按任务类型检索，避免全量塞进上下文。

## 易错点

- 把 Reflexion 说成 ReAct 的替代品：它是叠加在 ReAct 或任何执行循环之上的学习层，执行循环本身照旧。
- 把 Critic 当成打分器：这里的 Critic 产出的是**改进建议**，回答「下次怎么做」，而不是「这次值几分」。
- 以为反思越多越好：每一步反思都要多一次调用，还容易让 Agent 陷入自我怀疑，只在连续失败或验收不通过时触发。
- 反思不进外部验收就是自说自话：没有断言或独立评判器，反思的结论本身也可能是错的，反而污染下一次尝试。

## 一句话记住

:::tip
ReAct 在任务内试错，Reflexion 把错误写成记忆，跨任务少犯同一个错。
:::
