生产级 Agent 架构通常分成五层：**接入层、编排层、模型与能力层、状态与记忆层、基础设施层**，外加贯穿全系统的**可观测与治理**。判断一套架构够不够生产级，看三条：编排是否由确定性代码承担、模型是否只做局部决策、所有副作用是否都收口在工具网关。

## 五层架构总览

| 层 | 关键模块 | 它解决的问题 |
| --- | --- | --- |
| 接入层 | 鉴权、租户隔离、限流、请求校验、幂等键、异步提交与状态订阅 | Agent 任务耗时长，同步 HTTP 撑不住 |
| 编排层 | 任务状态机、依赖图调度、步骤执行与结果汇总、重规划触发、人在环节点、降级链 | 多步执行要可控、可恢复、可审计 |
| 模型与能力层 | 模型路由器、工具网关、检索服务、子 Agent 管理 | 成本与效果的取舍，以及副作用的统一收口 |
| 状态与记忆层 | 外部状态存储、长期记忆库、写入筛选、检索、遗忘、冲突治理 | 断点续跑，以及记忆的治理 |
| 基础设施层 | 事件日志与 checkpoint、预算与配额守卫、密钥管理、沙箱执行、全链路追踪 | 回滚、恢复、成本与安全边界 |
| 可观测与治理 | 在线指标、全量 trace 与采样、离线评测、成本归因、告警 | 出问题能定位，改动能验证 |

表里每一行在下面展开。层与层的边界要清楚：接入层不关心最终用哪个模型，编排层负责调度而不持有模型凭证，任何写操作只走工具网关。

## 接入层：长任务必须异步化

接入层只做入口该做的事，不承载业务逻辑。它负责**鉴权、租户隔离、限流、请求校验、幂等键**：鉴权决定谁能调，租户隔离保证不同客户的任务与数据不串线，限流保护下游的模型与工具，请求校验挡掉结构不对的输入，幂等键让客户端重试不会重复创建任务。

最关键的一条是长任务要支持**异步提交加状态订阅**。Agent 任务耗时长（多步推理、多次工具调用），用同步 HTTP 死等会把连接池和网关一起拖垮；正确做法是提交后立刻返回任务 id，客户端再通过 SSE 或 WebSocket 订阅状态变化和中间产物。

## 编排层：确定性代码加模型局部决策

编排层是五个层里最核心的一层，包含六个部件：**任务状态机、任务依赖图调度、步骤执行与结果汇总、重规划触发、人在环节点、降级链**。

状态机的作用是把状态显式化：待运行、运行中、挂起、降级、完成、失败、取消、超时。状态写得明白，才能回答三个实际问题：任务现在卡在哪、能不能断点恢复、预算该不该结算。

```ts
// 状态显式化，才谈得上断点恢复、降级判断和预算结算
type TaskState =
  | "pending"
  | "running"
  | "suspended"
  | "degraded"
  | "done"
  | "failed"
  | "cancelled"
  | "timeout";
```

这一层应当是**确定性的代码**：执行顺序、重试、超时、降级都由代码控制，模型只做局部决策，例如这一步调哪个工具、参数怎么填、要不要换一条路径。把整条链路交给模型自由发挥，代价是不可复现、不可审计、出了问题定位不到具体环节。

## 模型与能力层：路由、工具网关、检索、子 Agent

四个部件分工明确：

- **模型路由器**：按难度与成本在多个模型之间选择，支持**级联升级**，便宜模型先跑，验证不过再升级到更强的模型。
- **工具网关**：负责参数校验、权限裁决、限流、幂等、结果裁剪。工具返回是给模型看的，所以要裁剪，不能把接口原始响应整段塞进上下文。
- **检索服务**：向量库加关键词，再加结构化过滤与重排，四者组合使用，而不是只靠向量相似度。
- **子 Agent 管理**：把可独立完成的子任务交给子 Agent，用干净的上下文执行，避免污染主上下文。

### 工具网关是副作用的唯一出口

架构上有一条硬原则：**副作用只能发生在工具网关**。所有外部写操作、代码执行、对外发送都必须经过它做权限与参数校验。这样系统的安全边界清晰、行为可审计；将来替换模型或框架时，核心资产（工具与状态）不受影响。

## 状态与记忆层：真相在事件日志

这一层分两块。**工作状态**指任务树、子任务状态机、上下文、产物引用，存放在**外部状态存储**里（数据库加对象存储），既不进模型上下文，也不留在进程内存。**长期记忆**独立成库（向量库加结构化表加知识图谱），并且必须带四段机制：**写入筛选、检索、遗忘、冲突治理**。缺写入筛选，记忆会被低质内容污染；缺遗忘，错误的旧结论会一直被召回；缺冲突治理，新旧事实会同时被检出来互相打架。

一条实现原则是**真相在事件日志，视图可重建**：事件日志是唯一真相，状态快照、任务列表、看板都是它的物化视图，视图坏了可以从日志重放重建。

## 基础设施层与可观测治理

基础设施层解决"跑得住、停得下、追得清"三件事：

- **事件日志与 checkpoint**：支撑回滚与断点恢复，是恢复能力的底座。
- **预算与配额守卫**：步数、token、时间、金额四重上限，配合预扣与结算，避免并发任务把预算冲爆。
- **密钥管理**：模型永不接触长期凭证，凭证只在工具网关一侧使用。
- **沙箱执行**：不可信代码一律进沙箱跑。
- **全链路追踪**：统一 trace id 贯穿接入、编排、模型与工具。

### 可观测与治理具体看什么

**在线指标**看成功率、P95 与 P99 延迟、单任务成本、工具成功率、重复动作率、重规划次数、预算消耗。**全量 trace 加采样**：失败任务全量记录，成功任务采样留存。**离线评测**用固定任务集做回归门禁，防止一次提示词改动把老能力打回去。**成本归因**把成本与成功率的变化定位到具体环节，比如是路由选错了模型，还是某个工具变慢。**告警**盯四类信号：注入命中、越权尝试、预算异常、成功率突降。

## 生产化的四个取舍与两个易被低估的模块

四个取舍没有标准答案，但必须显式做出来：

- **成本与成功率的平衡**：用级联（便宜模型先跑、验证不过再升级），而不是一味上最强模型。
- **延迟与成功率**：独立子任务并行，结果渐进式披露。
- **自主与可控**：高危动作走人在环，预算耗尽即降级。
- **可复现与灵活**：固定配置清单加录制回放保证可复现，同时允许模型版本灰度。

最容易被低估的两个模块，一是**上下文管理**，常被当作"简单拼接"，实际上是质量与成本的主要来源；二是**降级链**，它决定系统在预算耗尽、依赖故障时的表现，也决定"失败"是**明确失败**还是**静默错误**。这两个模块做得好，系统才算生产级。

## 常见追问

**Q：为什么编排层要用状态机，而不是一个循环加一堆 if 判断？**
A：状态机把挂起、降级、取消、超时这些非正常路径显式化，任务才能断点恢复、能审计、能按状态结算预算；写成循环时这些情况会混成一个笼统的"失败"。

**Q：状态到底存在数据库还是事件日志？**
A：真相在事件日志，数据库里的状态是物化视图。写入先落日志，再由日志推进视图，视图损坏可以重建，回滚也有依据。

**Q：级联升级会不会让延迟变高？**
A：会，所以级联要用在能验证的任务上：便宜模型先跑，用程序化校验判断是否通过，不通过才升级；同时让独立子任务并行、结果渐进披露，把用户感知到的延迟压下来。

**Q：为什么强调把副作用收口在工具网关？**
A：因为这是唯一能同时做权限校验、参数校验、幂等和审计的位置。副作用散落在各处，安全边界就没了，将来换模型或换框架也无法保证行为一致。

## 易错点

- **把编排交给模型自由发挥**。错误直觉是"让模型自己规划更灵活"；正确说法是编排层写确定性代码，模型只做局部决策，否则不可复现、不可审计。
- **把上下文管理当简单拼接**。错误直觉是"历史全塞进去最保险"；它其实是质量与成本的主要来源，需要裁剪、摘要、产物改为引用。
- **只做失败重试，不做降级链**。预算耗尽或依赖故障时没有降级路径，失败就会变成静默错误，用户看到的是"完成"，结果却是错的。
- **把工具网关当成转发层**。它必须做权限裁决、参数校验、限流、幂等与结果裁剪；只做转发等于同时放开了安全边界和上下文长度。

## 一句话记住

:::tip
接入做隔离，编排写代码，副作用收在工具网关，其余交给事件日志与可观测。
:::
