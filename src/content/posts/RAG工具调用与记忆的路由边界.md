记忆回答已知的自我与历史，检索回答语料中的知识，工具回答此刻世界是什么样并可以让世界发生变化，这就是三者的语义分界。边界模糊时按新鲜度和权威性排序：用户在当前对话中显式给出的最新陈述最高，其次是工具返回的实时数据，再次是系统记忆中的既有事实，最后才是文档检索结果。路由出错分漏路由、误路由、错路由、冲突路由四类，靠溯源、时效、支持度、冲突四道校验加行为侧指标来发现，回退要做成并行探测、扩大范围、显式呈现冲突、拒答或转人工的分层降级，而不是一步到位。

## 三者的本质边界：记忆答已知、检索答知识、工具答此刻

记忆是系统已经掌握的、属于用户或者项目本身的既有事实与偏好，它跨越会话存在，用来回答"你是谁、你的项目是什么样"这类问题。

检索是把外部非结构化文档语料引入上下文，回答的是"知识库里有没有这个答案"，它提供的是证据而非动作。工具调用则是执行一个真实动作，可以返回实时权威数据、进行计算或者改变外部系统状态，它天然带有副作用和可观测的成败。

把三句话压成一句：记忆回答已知的自我与历史，检索回答语料中的知识，工具回答此刻世界是什么样并可以让世界发生变化。这条分界的实用价值在于，它直接决定了后面每个环节的失败模式和兜底手段——记忆错了是事实陈旧，检索错了是证据不相关，工具错了则可能已经把外部系统改坏。

## 实际判定用四条规则，按顺序问

路由判定不需要复杂的分类模型，四条问题按顺序问下去就能覆盖绝大多数请求：

1. 问题是否涉及当前或实时的信息？涉及就应当走工具，因为静态语料必然滞后。
2. 问题是否需要改变外部状态？需要就必须是工具，这决定了写操作绝不能走检索。
3. 问题的主体是不是用户或者项目自身？是的话先查记忆。
4. 最后才判断是否属于文档知识库的内容，走检索。

顺序本身就是优先级：越靠前的规则越不能被后面的规则覆盖。第四步放最后，是因为检索结果最容易"看起来能答"，一旦提前命中，模型就会倾向于拿一段不相关但语义相近的文档敷衍过去。

```text
if   需要改变外部状态        → 工具（写，必须收敛、谨慎重试）
elif 需要实时或权威数据      → 工具（读）
elif 主体是用户或项目自身    → 记忆
elif 属于文档知识库的内容    → 检索
else                        → 澄清或拒答
```

## 边界模糊时的优先级：按新鲜度和权威性排序

用户在当前对话中显式给出的最新陈述最高，其次是工具返回的实时权威数据，再次是系统记忆中的既有事实，最后是文档检索结果，因为检索语料往往是滞后且版本不明的。这个顺序本质上是在按新鲜度和权威性排序，而不是按命中数量或相似度排序。

有一个工程细节常被忽略：检索在实现上往往也是一种只读工具，很多框架干脆把检索做成工具暴露给模型。所以语义上区分检索和工具之后，工程上还要区分两种模式：

- 预检索：路由器先查，命中就直接注入上下文，延迟低但可能查错。
- 按需检索：模型自己决定何时检索，可以多轮迭代，灵活但成本更高，长任务中通常以后者为主。

两者不是二选一，常见做法是用预检索兜住确定性强的问题，把模糊和长链路的部分交给按需检索。

## 路由出错主要有四类

四类错误的区分很关键，因为它们的检测手段和兜底动作完全不同：

| 类型 | 典型表现 | 后果 |
| --- | --- | --- |
| 漏路由 | 该检索没检索、该调工具没调 | 产生幻觉，或使用过期信息作答 |
| 误路由 | 不需要外部信息却去检索 | 噪声注入、成本浪费，甚至引入文档里的提示注入内容 |
| 错路由 | 选错了具体的工具或数据源，比如检索到相关但不正确的文档版本，或调用了不该用的接口 | 结论建立在错误的证据或动作之上，且往往看起来很完整 |
| 冲突路由 | 记忆与检索结果互相矛盾 | 模型行为不确定，同一问题两次回答不一致 |

## 检测要靠证据链而不是主观判断

判断一次回答是不是路由错了，不要靠"读起来对不对"，而要回到它引用了什么：

- 溯源校验：答案里的每一条断言都要能追溯到具体的记忆条目、文档片段或者工具返回，无法追溯的断言就是幻觉信号，这是识别漏路由最有效的手段。
- 时效校验：断言涉及最新或者当前，但来源时间戳过期，同样判定为漏路由。
- 支持度校验：逐条判断断言是否真的被证据支持，但要注意必须由独立的判断过程来做，否则会出现同源偏差。
- 冲突检测：对记忆和检索的结果做交叉比对。
- 行为侧指标：统计路由准确率、漏路由率、误路由率、各类路由路径的端到端成功率，以及平均成本和延迟。

离线评测集要专门构造三类样本——需要检索的、不需要检索的、需要特定工具的——并保证有一部分可以由规则自动判定，这样才能把"感觉变好了"变成可回归的数字。

## 回退要做成分层降级，而不是一步到位

- 提高召回是第一层：不确定路由时并行探测，把记忆、检索和只读工具都跑一遍再合并证据，鲁棒性最好但成本最高，一般只用在关键请求上。
- 证据不足时扩大范围是第二层：改写查询、多轮检索、更换数据源或者收紧检索条件，也可以降级到工具去取权威的实时数据。
- 出现冲突时是第三层：不要静默选择，要显式呈现冲突，并按前面的优先级给出结论和依据，必要时向用户澄清。
- 仍然无法支撑答案时是第四层：明确拒答或者转人工，绝不允许编造。

## 贯穿所有层级的一条原则和两个额外要求

原则是宁可多给证据也不要无据断言，宁可拒答也不要编造。

要求一是全程可观测，要记录每次走了哪条路由路径、触发了哪一级降级、依据的证据是什么，这样线上出问题才能定位到底是路由层错了还是生成层错了。

要求二是安全隔离，检索到的文档和工具返回的内容都要当作不可信数据处理，避免其中的指令被模型当成系统指令执行——这正是"误路由"会顺带引出的风险。

## 常见追问

**问：检索本身也能做成工具，那还有必要区分检索和工具吗？**
答：有必要。区别不在接口形态而在语义：检索只提供证据、不改变外部状态，可以并行多路召回、改写查询反复重试；写工具会改变世界，必须收敛并且谨慎重试。混为一谈的直接后果就是把写操作当成一次"查询"随手重放。

**问：为什么长任务里以按需检索为主，预检索不好吗？**
答：预检索延迟低，但路由在一次判定后就定死，查错了整条链都带着噪声走；长任务中需要什么证据会随中间结果变化，模型按需多轮检索更灵活，代价是成本和延迟更高，所以要靠在离线评测上算清这笔账。

**问：记忆和检索结果冲突时到底听谁的？**
答：默认听用户在当前对话中的显式最新陈述，其次是工具实时数据，再其次是记忆，最后是检索结果。双方都足够可信时不要静默覆盖，保留冲突记录并显式呈现，让用户来裁决。

**问：路由准确率怎么做离线评测？**
答：构造三类样本（必须检索、不该检索、必须调用特定工具），标注期望的路由路径，让其中一部分由规则自动判定，剩下的用独立的判断过程打分——判定模型最好和生成模型分开，否则同源偏差会把漏路由判成合格。

## 易错点

- 把"检索"和"工具"当成同一类能力：检索是只读证据来源，写操作走检索是典型事故，接口长得像不代表语义相同。
- 以为模型自己会判断该不该检索：没有强制路由时模型倾向于直接作答，漏路由表现为自信的幻觉，必须在链路外侧用溯源校验兜住。
- 用同一个模型既生成答案又判定证据支持度：同源偏差会让不相关的证据被判成"支持"，支持度校验必须独立。
- 只统计端到端准确率：这样定位不到是路由错了还是生成错了，必须按路由路径分别统计成功率、成本和延迟。

## 一句话记住

:::
