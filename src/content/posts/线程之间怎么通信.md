线程通信的本质，是**一个线程的执行结果或状态变化能被另一个线程感知，并据此决定自己的下一步动作**。Java 里没有"直接给某个线程发一条消息"的原语，线程之间也没有消息通道，所以通信只能靠共享状态或协调工具间接完成：等待/通知、共享变量加可见性保证、同步器、阻塞队列、异步结果传递。其中最基础也最常用的，是**共享内存加同步原语**。

## 五类手段的分工

先建立一张地图，面试时先说清"有哪几类、各自传什么"，再展开细节，比直接背 `wait`/`notify` 要完整得多。

| 手段 | 传递的东西 | 典型工具 | 主要代价 |
| --- | --- | --- | --- |
| 共享变量 + 可见性保证 | 状态值本身 | `volatile`、原子类、并发容器 | 可见性和原子性要自己保证 |
| 等待/通知 | "条件满足"的信号 | `wait` / `notify` / `notifyAll` | 必须配锁，编程模型容易写错 |
| 同步器 | 线程间的进度协调 | `CountDownLatch`、`CyclicBarrier`、`Semaphore` | 语义单一，不负责传数据 |
| 阻塞队列 | 对象本身（数据） | `BlockingQueue` 家族 | 队列与拷贝的额外开销 |
| 异步结果 | 任务的计算结果 | `Future`、`CompletableFuture` | 只是结果传递，不是过程通信 |

## 等待/通知机制（wait / notify / notifyAll）

最经典的"生产者-消费者"式通信。共享对象在 `synchronized` 块内操作：条件不满足时调用 `wait()` **释放锁并挂起**，另一个线程改变条件后调用 `notify()` / `notifyAll()` 唤醒它，被唤醒的线程**重新竞争锁**后才能继续执行。

**要点**：`wait` 必须在 `synchronized` 中调用，否则抛 `IllegalMonitorStateException`；条件判断必须用 `while` 而不是 `if`（防虚假唤醒，也防"被唤醒后条件又被别人改回去"）；**优先用 `notifyAll`**，因为 `notify` 可能唤醒一个不满足条件的线程，真正的信号就此丢失。

```java
class Buffer {
    private final int[] items = new int[10];
    private int count = 0;

    public synchronized void put(int value) throws InterruptedException {
        while (count == items.length) { // 用 while：被唤醒后重新检查条件
            wait();                     // 释放监视器锁并挂起
        }
        items[count++] = value;
        notifyAll();                    // 条件变了，唤醒所有等待者
    }

    public synchronized int take() throws InterruptedException {
        while (count == 0) {
            wait();
        }
        int value = items[--count];
        notifyAll();
        return value;
    }
}
```

还有一个容易忽略的对称性：`wait` 会释放锁，**`notify` 不会**。调用 `notify` 的线程仍持有锁，被唤醒的线程要等它退出同步块、释放锁之后才真正恢复运行。

## 共享变量 + 可见性保证

最轻量的通信方式：线程 A 修改共享字段，线程 B 读取并据此行动。**前提是必须保证可见性**——普通字段不行，要用 `volatile`（保证可见性与有序性）、原子类（`AtomicInteger` 等）、并发容器（`ConcurrentHashMap`），或者用 `synchronized` 包裹访问。

没有可见性保证时，"通知了对方也读不到"，这是实际排查中最常见的误判之一：代码看起来写了标志位，但读取方永远停在旧值上，表现成"卡住不动"。共享变量通信还要求想清楚一件事：如果本次传递涉及"读-改-写"或多个字段必须同时一致，那它就不再是"可见性"问题，而是原子性问题，需要原子类或锁来兜底。

## 同步器工具类

专门为线程间协调设计，语义清晰、可读性好，写出来的代码比手写 `wait`/`notify` 更难出错。

| 工具 | 协调什么 | 关键特性 |
| --- | --- | --- |
| `CountDownLatch` | 一个或多个线程等其他线程完成若干操作 | 计数归零放行，**不可重用** |
| `CyclicBarrier` | 一组线程互相等待到达屏障后一起继续 | **可重用**，一轮结束自动进入下一轮 |
| `Semaphore` | 同时访问某资源的线程数 | 许可数控制，**限流与资源池**的常用手段 |
| `Phaser` | 多阶段的屏障 | 支持**动态注册**参与者，阶段可推进 |
| `Exchanger` | 两个线程在同步点交换数据 | 一对一配对交换，适合双缓冲式交接 |

## BlockingQueue（阻塞队列）

**生产环境最实用的线程通信方式**。`put` 在队列满时阻塞、`take` 在队列空时阻塞，生产者与消费者都不需要自己写等待循环。它内部用 `ReentrantLock` + `Condition` 实现，而且**"不满"和"不空"是两个独立的条件队列**，唤醒时只唤醒对应条件上的线程，比 `wait`/`notifyAll` 精准得多，天然避开虚假唤醒和信号丢失。

常用实现按用途选：

- `ArrayBlockingQueue`：数组实现，**有界**，容量必须在构造时给定
- `LinkedBlockingQueue`：链表实现，容量可选，不指定容量时取 `Integer.MAX_VALUE`，实际上接近无界
- `PriorityBlockingQueue`：按优先级出队，无界
- `DelayQueue`：元素到期之后才能被取出，适合延迟任务
- `SynchronousQueue`：零容量，`put` 直接把元素移交给正在等待的 `take`

## 锁的 Condition 条件变量

`ReentrantLock.newCondition()` 可以在同一把锁上创建**多个独立的条件队列**，把"等队列不满"和"等队列不空"这类不同原因分开排队，精确唤醒满足特定条件的线程，比 `wait`/`notifyAll` 少掉大量无意义的唤醒。

**这正是 `BlockingQueue` 内部的实现方式**，也是复杂业务场景的推荐做法：一个锁配多个条件，条件与等待原因一一对应，代码意图也更清楚。

## 异步与回调

`Future` / `CompletableFuture` 用于"提交任务并异步取结果"。`CompletableFuture` 还支持回调（`thenApply`、`thenCompose`）、多任务组合与异常处理，把"结果回来之后做什么"写成链式调用。

需要明确定位：**这本质是"结果传递"而不是"过程通信"**——它让调用方不必阻塞等待一个已经提交的任务，但并不提供"两个正在运行的线程互相对话"的能力。

## 跨进程/跨系统的通信

一旦超出单进程线程范畴，就换成另一套手段：**消息队列**（Kafka、RocketMQ）、**事件总线**、**RPC 框架**（Dubbo、gRPC），它们内部靠网络协议加序列化实现。面试里常把两者混在一起问，回答时点明边界即可：跨进程通信的可靠性、顺序、重复投递等问题，线程级的 `wait`/`notify` 一个都解决不了。

## 必须区分"通信"与"同步"

⭐ 这是高频考点。**同步（synchronization）**是为了**保护共享资源的互斥访问**，保证数据正确；**通信（communication）**是为了**在线程间传递信息**。二者常常同时出现——`wait`/`notify` 既传递了信号（通信），又依赖 `synchronized` 保证共享状态的正确性（同步）。但**它们的目标不同**：`synchronized` 保护的是"数据"，`wait`/`notify` 传递的是"状态变化信号"。说不清这条分界，很容易把"加锁"直接当成"通信"来答。

## 三条实践原则

1. **通信的前提是可见性**——先保证共享状态能被对方读到，再谈通信。
2. **优先用高级工具而非原始 `wait`/`notify`**——`BlockingQueue`、`CountDownLatch`、`Semaphore` 语义清晰，自带背压与超时能力。
3. **用"传递不可变对象"代替"传递可变状态"**——通过队列或容器传递**构造完成的对象**（不可变），可以彻底避免"对方读到一半被你改了"的问题，这是 Java 并发设计中最重要的经验之一。

## 常见追问

**Q：`wait` 和 `sleep` 有什么区别？**
A：`wait` 是 `Object` 的方法，必须在 `synchronized` 块内调用，调用时**释放监视器锁**；`sleep` 是 `Thread` 的静态方法，不要求持锁，**也不释放任何已持有的锁**。所以抱着锁调用 `sleep` 时，别的线程在整个睡眠期间都进不来；而 `wait` 期间锁是放开的，别人可以进来改条件。

**Q：为什么强调用 `notifyAll` 而不是 `notify`？**
A：同一个对象上可能挂着等待不同条件的线程。`notify` 只随机唤醒一个，可能唤醒的是条件仍不满足的线程，它判断后继续 `wait`，而真正该被唤醒的那个始终没收到信号，表现为"程序不动了"。只有确认所有等待者等的是同一个条件时，`notify` 才勉强安全。

**Q：`CountDownLatch` 和 `CyclicBarrier` 怎么选？**
A：`CountDownLatch` 是"一等多"，计数归零后永久放行、**不可重用**；`CyclicBarrier` 是"多等多"，一轮到齐后自动进入下一轮、**可重用**。前者适合"主线程等若干子任务初始化完"，后者适合分阶段并行计算。

**Q：`volatile` 能替代锁做通信吗？**
A：只在"单写多读、不涉及复合操作"的场景够用，比如状态标志位。一旦涉及"读-改-写"或"一组相关状态必须一起一致"，`volatile` 就不够了，要换原子类、锁，或者干脆通过队列投递不可变对象。

## 易错点

- **把 `wait` 当成"不释放锁的睡眠"**——正好相反，`wait` 会释放监视器锁，不释放锁的是 `sleep`。
- **用 `if` 判断等待条件**——线程被唤醒后条件可能已再次不成立（被其他线程抢先消费），必须用 `while` 重新检查。
- **以为"共享一个变量"就等于通信**——没有 `volatile`、锁或并发容器提供的可见性，写进去的值对方可能永远读不到，等于没通信。
- **在 `synchronized` 之外调用 `wait`/`notify`**——直接抛 `IllegalMonitorStateException`，而且 `wait`/`notify` 必须基于同一个对象监视器。
- **混淆"同步"与"通信"**——加锁保证的是互斥与数据正确，信号传递才是通信，答题时把两者混成一句会显得概念不清。

## 一句话记住

:::tip
**通信的本质是状态变化被看见：先保证可见性，再用队列替代手写 wait/notify。**
:::
