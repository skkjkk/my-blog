InnoDB 选择 B+ 树，是因为它同时满足了**高扇出、稳定查询路径、顺序访问**三个条件，而这三点正好对应关系型数据库的典型访问模式：瓶颈在磁盘 IO 而不是 CPU，一次 IO 只能读进一页，所以索引结构必须让树尽量矮、叶子尽量有序。

## 瓶颈在磁盘 IO，树的层数就是 IO 次数

数据库索引的瓶颈在 IO 而不是 CPU。InnoDB 的数据页默认是 16KB，一次磁盘 IO 就能读入一整页；树每往下一层，基本就多一次页读取。因此衡量索引结构好坏的标准很直接：**同样的数据量，从根走到叶子要读几个页**。

二叉树每个节点只有两个分支，一页里塞不满，层数被数据量顶得很高，查一条记录就要爬十几层。B+ 树干脆把"页"当成节点单位，一个节点里塞满排序好的键、分成上千条分支——用**分支数换层数**，这是它在磁盘上胜出的第一层原因。

## 多路平衡：一个节点装上千个键，树只有三四层

B+ 树是**多路平衡树**，不是二叉树。非叶节点里存的是排好序的键和指向子页的指针，按 bigint 主键 8 字节、加上子页编号的固定开销粗算，16KB 的一页能放下上千个键，也就是**扇出上千**。

扇出大，树就矮：千万级的数据三到四层就能装下，查一个点只需要少量几次页读取。同时"平衡"保证了任何一条查询的路径长度相同，不会出现某条路径特别深、某条特别浅的抖动——这对数据库很关键，因为最坏情况才是你要为它留资源的情况。

## 非叶节点只存键，数据全部下沉到叶子节点

这是和 B 树最本质的区别。B 树的每个节点都同时存键和它对应的数据（行记录或行指针），而 B+ 树的非叶节点只有键和子页指针，**数据只存在叶子节点**。

好处很直接：同样的页空间里能装下更多键，扇出更大、树更矮、IO 更少。代价是每次查询都必须走到叶子才能拿到数据，点查不能"中途命中就返回"；但层数下降省下来的那几次 IO，比这一点损失更值。

## 叶子节点用双向链表串起来，范围查询顺着读就行

InnoDB 的 B+ 树把叶子节点按索引键顺序、用双向链表连接起来，带来两个关键好处：

- **查询路径长度稳定**：所有数据都在同一层，任意一条记录的查找代价一致，不会出现运气好一次命中、运气差一路穿到底。
- **范围查询和顺序扫描天然支持**：`BETWEEN` 这类条件先定位下界，然后沿叶子链表往后读，不需要回到根节点重新查找；按索引列 `ORDER BY` 也能顺着链表直接出结果，省掉排序。

后面这条正是 B+ 树胜出 B 树和哈希表的关键：哈希表定位快但不保序，范围查询直接退化成全表扫描；B 树的数据散在各层，范围查询只能中序遍历整棵树，用不上"顺序读"这件事。

## 叶子存整行，正好扛起聚簇索引

InnoDB 的主键索引是**聚簇索引**：叶子节点直接存放整行数据，索引和数据在同一棵 B+ 树上。所以按主键定位到叶子，就等于拿到了整行，不需要再回表，这就是"按主键查很快"的真实含义。

二级索引的叶子存的是"索引列值 + 主键值"，要查其他列就得拿主键回聚簇索引再查一次，也就是**回表**。B 树做不到这种干净的划分——数据可能落在任意一层，命中后还可能要继续往下找。

## 和其他候选结构对比

| 结构 | 等值查询 | 范围 / 排序 | 主要问题 |
| --- | --- | --- | --- |
| 哈希表 | O(1)，单点最快 | 不支持 | 不保序，范围、排序、最左前缀都用不上，冲突严重时退化 |
| 平衡二叉树（AVL / 红黑树） | O(log n) | 支持但代价高 | 一个节点只有两个分支，扇出小、树高，磁盘 IO 次数多得多 |
| B 树 | O(log n) | 支持 | 数据分布在所有层，范围查询要中序遍历整棵树，用不到叶子链表 |
| B+ 树 | O(log n)，层数最少 | 顺叶子链表即可 | 必须走到叶子才算命中，实现比哈希复杂 |

## B+ 树的有序性还顺带撑起了这些能力

- **最左前缀**：联合索引把多列按顺序拼成键，键有序，`WHERE a = ? AND b = ?` 才能连续定位；只给 `b` 就断链。
- **覆盖索引**：二级索引叶子自带主键值，查询列全在索引里就不用回表。
- **取极值**：`MIN` / `MAX` 直接读索引最左或最右的叶子，不必扫全表。
- **松散索引扫描（loose index scan）**：`GROUP BY` / `DISTINCT` 时跳过重复键，一个分组只读一条。
- **跳跃扫描（skip scan）**：MySQL 8.0 起，复合索引没有前导列的等值条件时，可以按前导列的有限取值逐个做范围查找。

容易混的一点：`MIN` / `MAX` 走的是索引两端的极值优化，松散索引扫描解决的是分组去重时的跳跃读，跳跃扫描（skip scan）解决的是前导列缺条件——三件事名字像，机制完全不同。

```sql
-- 主键索引上的范围查询：定位下界后沿叶子链表顺序读
SELECT * FROM orders WHERE id BETWEEN 1000 AND 2000;

-- 联合索引 idx_status_time (status, created_at) 上的最左前缀
SELECT id FROM orders WHERE status = 1 AND created_at > '2025-01-01';

-- 只关心有哪几种 status：松散索引扫描的典型形态，不必扫全部行
SELECT COUNT(DISTINCT status) FROM orders;
```

## 常见追问

**Q：为什么不用哈希索引？**
A：哈希只解决等值查找，键一哈希顺序就没了，范围、排序、最左前缀全都用不上，范围查询只能退化成全表扫描。另外 InnoDB 的哈希索引是自适应的，由引擎按访问热度自己建，用户不能直接创建。

**Q：B+ 树必须走到叶子才算命中，为什么反而比 B 树快？**
A：因为非叶节点不存数据，一页能装下更多键，扇出更大、树更矮。B 树的确可以中途命中提前返回，但它每页装的键少、整体层数更高，最终付出的是更多次磁盘 IO——而磁盘 IO 才是瓶颈。

**Q：三层 B+ 树能放多少行？**
A：取决于扇出。按 bigint 主键粗算，一个非叶页能放上千个键，三层就是上千乘上千，量级在千万行，四层到亿级。真实数字跟主键类型、行长都有关，面试里说量级即可，别报死数。

**Q：叶子节点为什么要用双向链表，单向不够吗？**
A：范围查询只往后读，单向也能跑；双向是为了 `ORDER BY ... DESC` 这类反向遍历时不必重新定位，页分裂和页合并时维护邻居关系也更方便。

## 易错点

- **把"B+ 树更快"说成"等值查询更快"**：单点等值哈希是 O(1)，比 B+ 树还快。B+ 树的优势在整体访问模式——范围、排序、稳定的查询代价，别拿单点等值去比。
- **以为非叶节点也存数据**：B+ 树的非叶节点只有键和子页指针，数据只在叶子层；说成"数据分散在各层"就是把 B+ 树讲成 B 树了。
- **以为按主键查只读一次磁盘**：根节点和上层节点通常常驻缓冲池，实际 IO 次数看缓存命中情况；准确的说法是"定位到叶子就拿到整行，不需要回表"。
- **把松散索引扫描和极值优化混为一谈**：松散索引扫描是分组去重时的跳跃读，`MIN` / `MAX` 靠的是索引两端的极值，不是同一个优化。

## 一句话记住

:::tip
B+ 树赢在扇出大、树矮、叶子有序：少几次 IO，还能顺着链表做范围查询。
:::
