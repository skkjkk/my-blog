把已有应用变成 MCP Server，本质是**在现有能力外面加一层协议适配**，把"业务函数"翻译成"带描述与 schema 的工具"。核心工作量不在协议，而在**把接口语义讲清楚**。

## 第一步：盘点能力并分类

。把现有应用的功能按 MCP 三类原语归位 —— **Tools**（可执行动作，如查询、创建、触发任务）、**Resources**（可读取的数据，如配置、报表、日志文件）、**Prompts**（可复用的提示模板）。判断标准是"**这个能力是被模型主动调用，还是被读取，还是给用户选**"。

## 第二步：选择暴露粒度

。**工具要细粒度** —— 用 `get_user_orders(date_range)` 这样的具体操作，而不是 `exec_sql(query)` 这类通用能力，否则等于把整个数据权限交给模型。**同时不要暴露过多工具** —— 工具一多会稀释模型注意力，建议按场景分组或做运行时裁剪。

## 第三步：写好工具描述与 schema

。这是**最影响效果**的一步。描述要说清"**这个工具做什么、什么时候该用、什么时候不该用**"；参数用 JSON Schema 声明类型、必填、枚举、范围；**名称要与实际行为一致**（描述与实现漂移是调用失败的头号原因）。

## 第四步：实现执行与错误处理

。每个工具函数要自己完成**业务逻辑 + 数据清洗 + 权限校验**。返回结果应当**结构化且裁剪好**（只给需要的字段、行数上限、附带总数说明）。**错误必须可诊断** —— 返回"参数 date 格式应为 yyyy-MM-dd"这类信息，让模型能自我纠正；不要把堆栈原样抛出。

## 第五步：处理认证与身份

。本地 stdio 场景通常不需要额外认证（靠进程边界）；远程部署则要接入 **OAuth**，并且**从验证过的令牌中取用户身份**，**绝不信任 Client 传来的 user_id**。**资源级鉴权在 Server 侧做** —— 令牌证明"这个用户是谁"，Server 决定"他能看哪些数据"。

## 第六步：写好资源与提示

。Resources 要有**稳定的 URI**（便于引用与缓存）；Prompts 要做成**带参数的模板**（如 `review_code({language, file_path})`），供用户显式触发。

## 第七步：本地调试

。用 MCP Inspector 之类的工具连上去，验证：工具列表是否正确、schema 是否被模型正确理解、错误信息是否可诊断、结果裁剪是否符合预期。**这一步能筛掉 80% 的问题。**

## 第八步：加固与上线

。加**超时、限流、并发上限**；对**写操作加幂等键**；**不可逆操作**（删除、发送、支付）要加二次确认或人工审批；加**完整审计日志**；对 Server 做**沙箱与依赖扫描**。

## 改造中最常见的坑

。**① 直接把 REST 接口一键转成工具** —— 语义不清、参数暴露过细；**② 忽略结果裁剪** —— 返回体巨大，模型被淹没；**③ 错误直接抛异常** —— 模型无法学习；**④ 工具数量失控** —— 选择准确率下降；**⑤ 权限只在 Host 做** —— 绕过 Host 直接调 Server 就失控，**Server 侧必须自己再校验**。

## 是否值得改造的判断

。如果你的应用**只服务一个自建 Agent**，MCP 的收益主要是标准化与可测试性，价值有限；如果是**多个应用/多个团队共享同一批能力**，或者要**接入生态工具生态**，那 MCP 的复用价值就非常明显 —— **Server 写一次，所有 Host 都能用**。
