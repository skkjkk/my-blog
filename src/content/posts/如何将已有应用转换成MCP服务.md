把已有应用改造成 MCP Server，本质是在现有能力外面加一层协议适配：把已经跑得通的业务函数，翻译成带描述与 schema 的工具、资源和提示模板。核心工作量不在协议实现上，而在把接口语义讲清楚——名字、参数、返回、错误、权限边界，都得让模型读懂并能自我纠正。

## 第一步：把能力按三类原语归位

先盘点应用的现有功能，按 MCP 的三类原语各归其位：

| 原语 | 是什么 | 典型例子 | 谁触发 |
| --- | --- | --- | --- |
| **Tools** | 可执行的动作 | 查询、创建、触发任务 | 模型主动调用 |
| **Resources** | 可读取的数据 | 配置、报表、日志文件 | 应用读取后拼进上下文 |
| **Prompts** | 可复用的提示模板 | 固定的分析模板 | 用户显式选择 |

判断标准只有一条：这个能力是被模型主动调用，还是被读取，还是给用户选。三类混在一个接口里，就没法分别做权限与二次确认。

## 第二步：定粒度，写清描述与 schema

工具要细粒度：用 `get_user_orders(date_range)` 这样的具体操作，而不是 `exec_sql(query)` 这类通用能力，否则等于把整个数据权限交给模型。同时不要暴露过多工具，工具一多会稀释模型注意力，建议按场景分组，或做运行时裁剪。

描述是最影响效果的一环：要说清这个工具做什么、什么时候该用、什么时候不该用；参数用 JSON Schema 声明类型、必填、枚举、范围；名称要与实际行为一致，描述与实现漂移是调用失败的头号原因。

```json
{
  "name": "get_user_orders",
  "description": "查询指定用户在时间区间内的订单列表。当用户问自己的订单、物流或退款进度时使用；涉及其他用户或全站统计时不要使用。",
  "inputSchema": {
    "type": "object",
    "properties": {
      "date_range": { "type": "string", "description": "起始到结束日期，格式 yyyy-MM-dd" },
      "limit": { "type": "integer", "minimum": 1, "maximum": 50 }
    },
    "required": ["date_range"]
  }
}
```

## 第三步：执行层自己做完业务、裁剪与鉴权

每个工具函数要独立完成三件事：业务逻辑、数据清洗、权限校验，不要指望宿主替你做。返回结果应当结构化且裁剪好——只给需要的字段、设行数上限、附带总数说明，让模型知道还有多少没返回。

资源级鉴权必须在 Server 侧做：令牌只证明「这个用户是谁」，由 Server 决定「他能看哪些数据」。如果权限只做在 Host，绕过 Host 直接调 Server 就失控了。

## 第四步：让错误可诊断

错误信息要对模型有用：返回「参数 date 格式应为 yyyy-MM-dd」这类能照着改的提示，让模型自我纠正；不要把堆栈原样抛出，堆栈对模型没有信息量，只会让它照着同样的方式再错一次。也不要用「操作失败」这种含糊说法，那等于把排障成本转嫁给模型。

## 第五步：处理认证、身份与两类只读原语

本地 stdio 场景通常不需要额外认证，靠进程边界隔离就够了；远程部署则要接入 OAuth，并且从验证过的令牌里取用户身份，绝不信任 Client 传来的 user_id。

Resources 要有稳定的 URI，便于引用与缓存；Prompts 要做成带参数的模板，例如 `review_code({language, file_path})`，供用户显式触发。这两类都不该有副作用，所以不需要像 Tools 那样逐次确认。

## 第六步：调试、加固与是否值得改造

先用 MCP Inspector 之类的工具连上去，验证四件事：工具列表是否正确、schema 是否被模型正确理解、错误信息是否可诊断、结果裁剪是否符合预期。这一步能筛掉 80% 的问题。

上线前再补齐：超时、限流、并发上限；写操作加幂等键；不可逆操作（删除、发送、支付）加二次确认或人工审批；完整审计日志；对 Server 做沙箱与依赖扫描。

是否值得改造看共享面：只服务一个自建 Agent 时，MCP 的收益主要是标准化与可测试性，价值有限；多个应用或多个团队共享同一批能力、要接入生态工具时，复用价值就很明显——Server 写一次，所有 Host 都能用。

## 常见追问

**Q：能不能用工具一键把 REST 接口全转成 MCP 工具？**
技术上转得动，但语义不清、参数暴露过细，模型既判断不出何时该调，也拿不到收敛过的结果。宁可少而准地手写几个语义明确的工具。

**Q：工具数量多了怎么控制？**
按场景分组，或按当前任务做运行时裁剪，只暴露这一轮真正用得上的工具。工具越多，模型的选择准确率越低。

**Q：鉴权只做在 Host 侧够不够？**
不够。Server 是独立进程，可以被绕过 Host 直接调用，所以资源级鉴权必须在 Server 侧再校验一次。

**Q：只有一个自建 Agent，还有必要改 MCP 吗？**
收益主要是标准化与可测试性，价值有限；等多方共享同一批能力、或要接入生态工具时再改更划算。

## 易错点

- **直接把 REST 接口一键转成工具**：语义不清、参数暴露过细，模型不知道该在什么时候用。
- **忽略结果裁剪**：返回体巨大，模型被无关字段淹没，反而漏掉关键信息。
- **错误直接抛异常**：模型学不到修正方向，只会反复重试同一个错误调用。
- **工具数量失控**：选择准确率下降，工具之间互相干扰。
- **权限只在 Host 做**：绕过 Host 直接调 Server 就失控，Server 侧必须自己再校验。

## 一句话记住

:::tip
MCP 改造的难点不在协议，而在把接口语义讲到模型能自己用对。
:::
