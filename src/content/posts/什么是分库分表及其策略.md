分库分表是把一份数据**按规则拆分到多个数据库或多个表**中，以突破单库单表的存储与性能上限。拆分的维度有两个：**纵向拆库**（把不同业务/不同数据分到不同库）和**横向拆表**（把同一张表的数据按规则分到多张表），实际方案通常是两者组合。

1) **垂直分库**。按业务模块把库拆开，比如用户库、订单库、商品库相互独立。优点是**业务解耦、故障隔离、可以按业务量独立扩容**，缺点是跨库 join 和分布式事务变复杂。适合业务模块边界清晰、模块间访问较少的系统。

2) **垂直分表**。把一张字段多、访问场景不同的宽表拆开，比如把用户表的常用字段放主表、低频字段放扩展表。适合字段访问倾斜明显的表。风险是**关联查询需要 join**，且扩展表的关联查询要额外处理。

3) **水平分表（分片）**。同一张表按规则拆成多张物理表，数据总量不变但单表变小。常见规则有四种：取模分片按 `user_id % N` 路由，分布均匀但**扩容需要迁移大量数据**；范围分片按时间或 ID 区间分片，**扩容只需新增一张表**，但容易数据倾斜；一致性哈希虚拟节点分片，扩容时只需迁移部分数据，是许多分片中间件的默认方案；基因分片把分片键的一部分编码进其他字段，解决**跨分片查询**问题。适合单表数据量过大、查询能带上分片键的场景。

4) **水平分库**。同一张表按规则拆到不同数据库实例上。它突破了**单机的存储与连接数上限**，可跨机扩展吞吐，是"分库"的核心价值。缺点是跨库事务与跨库 join 难度大。

5) **核心难点是分布式 ID**。分片后不能再依赖数据库自增，需要引入**全局唯一 ID 方案**：数据库号段模式（发号器批量取号，兼顾性能与数据库压力）、雪花算法（时间戳加机器号加序列号，趋势递增、分布式生成，但要注意**时钟回拨**和机器号冲突）、美团 Leaf、Redis 自增、或直接用 UUID（无序，不适合做聚簇索引主键）。

6) **分片键选择决定成败**。必须选**查询最高频的维度**作为分片键，否则大量查询会变成全分片扫描。分片键要尽量**避免跨分片查询与跨分片排序**，否则要引入多分片归并，或者做**异构索引库**（建一张映射表把非分片键查询路由到分片）。

7) **分页与排序是重灾区**。跨分片的 `LIMIT` 需要各分片取全量再归并排序，深分页性能极差。解决方案是**二次查询法**（第一次只查 id，内存归并后再批量回表）、**游标方式**（记录上一页最后一条的排序值）、或**搜索引擎**（ES）做二级索引。

8) **分布式事务**。跨库写需要处理一致性问题，方案包括**两阶段提交（2PC）**（强一致但性能差、阻塞）、**TCC**（Try-Confirm-Cancel，业务侵入大）、**可靠消息最终一致**（本地消息表或 RocketMQ 事务消息，最常用、侵入小）、**Seata 等框架**（封装 AT/TCC 模式）。实践中通常用**最终一致 + 对账补偿**替代强一致。

9) **什么时候该上分库分表**。不要过早分片。优先顺序是：**索引与 SQL 优化 → 缓存 → 读写分离 → 垂直拆分 → 最后才是水平分片**。单表超过千万级且写入量确实成为瓶颈、且已经无法通过以上手段解决时再考虑。

10) **中间件与代价**。常见方案有 ShardingSphere（应用层）、Mycat（代理层）、以及各云厂商提供的分布式数据库（屏蔽分片细节、支持弹性扩容）。分片带来的代价是**复杂度大幅上升** —— 跨片查询、分布式事务、全局 ID、扩容迁移、运维排查都要重新设计，并且**扩容期间的在线数据迁移本身就是一场大工程**。
