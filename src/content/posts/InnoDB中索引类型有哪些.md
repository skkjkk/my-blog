一句话答：InnoDB 的索引按用途分六种——聚簇、二级、多列（联合）、哈希、全文、空间，按底层结构只有 B+ 树、自适应哈希、R-Tree、倒排四类，高频考点全在 B+ 树家族。三条主线必须背下来：每张表有且仅有一个聚簇索引、叶子节点直接存整行；二级索引叶子只存「索引列值 + 主键值」，查其他列必须回表；用户无法在 InnoDB 上手动建哈希索引，能用的只有优化器自动维护的自适应哈希索引。

## 按底层结构归类：只有四种结构，B+ 树是绝对主力

面试时最容易答乱的，是把「用途分类」和「结构分类」混成一锅。先看结构，InnoDB 实际只用到四种：

| 底层结构 | 对应索引 | 在 InnoDB 里的地位 |
| --- | --- | --- |
| **B+ 树** | 聚簇索引、二级索引、联合索引、前缀索引 | **绝对主力**，普通索引全是它 |
| **自适应哈希** | 自适应哈希索引（AHI） | 引擎自动维护，用户建不出来 |
| **倒排** | 全文索引 FULLTEXT | 近似倒排，**不是 Lucene 那种完整实现** |
| **R-Tree** | 空间索引 SPATIAL | 专用于地理坐标、多边形 |

再按用途点名，就是常说的六种：**聚簇索引、二级索引、多列（联合）索引、哈希索引、全文索引、空间索引**，前缀索引算二级索引的一个变体，最后一节一起讲。顺便记住一条对照：**B 树是 MyISAM 主键索引的结构，InnoDB 不用 B 树**，只用 B+ 树。

## 聚簇索引：索引即数据，叶子节点存整行

聚簇索引（Clustered Index）是 InnoDB 的默认组织方式：**叶子节点存放整行数据**，数据与索引在**同一棵 B+ 树**上，找到索引键也就找到了整行。这决定了一个硬结论——**每张 InnoDB 表有且仅有一个聚簇索引**，因为行数据只能按一种顺序摆放一次。

聚簇索引不需要你显式声明，InnoDB 会按固定优先级自动挑一个：

1. **显式主键**（`PRIMARY KEY`）
2. 没有主键时，挑**第一个所有列都声明为 `NOT NULL` 的唯一索引**
3. 两者都没有时，内部生成一个 **6 字节隐藏列 `DB_ROW_ID`** 当聚簇索引键

非叶子节点只存索引键和页号，真正的行记录全部压在叶子层，所以一次等值查找就是「从根走到叶子，直接在叶子上拿到整行」。

:::caution
**不指定主键的代价**：走隐藏的 `DB_ROW_ID`（6 字节），这个值既不可见也不可控；二级索引的叶子要存主键值，等于每个二级索引都多背 6 字节；分库分表时更没有全局唯一性可言。
:::

## 二级索引：叶子只存主键，查非索引列要回表

二级索引（Secondary Index，也叫辅助索引）同样是 B+ 树，但**叶子节点存的是「索引列的值 + 主键值」**，不是整行。所以按二级索引定位到主键之后，还要**拿主键回到聚簇索引里取整行，这一步叫回表**。

回表的代价在于它是**随机 IO**：二级索引按自己的列有序，主键值在叶子里的顺序是散的，回表等于按这些散乱的主键去聚簇索引里东跳西跳。回表次数一多，可能比全表扫描的顺序 IO 还慢，这也是优化器偶尔宁愿放弃索引、走全表扫描的原因。

围绕回表有两条优化路线：

- **覆盖索引**：查询用到的列全部落在索引里（主键天然包含在内），就不需要回表，直接从二级索引返回结果
- **索引条件下推（ICP）**：把只用索引列就能判断的 `WHERE` 条件交给存储引擎层先过滤，砍掉一批记录再回表

## 联合索引：最左前缀与「范围截断」

多列索引就是**联合索引（Composite Index）**，由多个列按顺序组成，是最常用的类型，也是面试追问最多的类型。它只有两条规则，但错的人很多。

**规则一：最左前缀**。索引 `(a, b, c)` 相当于同时提供了 `(a)`、`(a, b)`、`(a, b, c)` 三个前缀索引，但 `WHERE b = ?` 或 `WHERE b = ? AND c = ?` 用不上它——索引第一层是按 `a` 排序的，跳过 `a` 就找不到入口。

**规则二：范围之后断档**。某一列用了范围条件（`>`、`<`、`BETWEEN`、`LIKE 'x%'`）之后，**它右侧的列无法继续用于索引定位**，不过这些列的完整值仍然存在索引里，可以拿来当覆盖索引或做 ICP 过滤。

```sql
-- 联合索引：列顺序决定能覆盖哪些查询
CREATE INDEX idx_user_status_time ON orders (user_id, status, created_at);

-- 走索引且可以完全覆盖：等值两列定位，范围列收尾
SELECT id, created_at FROM orders
WHERE user_id = 100 AND status = 'paid' AND created_at > '2026-01-01';

-- 走不了索引：跳过最左列 user_id
SELECT id FROM orders WHERE status = 'paid';

-- 条件书写顺序不影响使用：优化器按索引列顺序重排等值条件
SELECT id FROM orders
WHERE created_at > '2026-01-01' AND user_id = 100 AND status = 'paid';
```

最后一条容易被误判成「用不上索引」，其实不会：优化器会把 `user_id`、`status` 两个等值条件排到前面用满索引，`created_at` 只负责范围截断，断档发生在范围列的右侧而不是书写顺序的右侧。

## 哈希索引：InnoDB 里能用的只有自适应哈希

哈希索引按 key 的哈希值定位，**等值查询一次命中**，代价是彻底放弃顺序性。但 InnoDB 的哈希索引有个关键前提：**用户建不出来**。

InnoDB 提供的是**自适应哈希索引（Adaptive Hash Index，AHI）**：引擎自己盯着索引页的访问模式，发现某些页被反复用同一种方式等值查找，就**自动**在内存里为这些页建哈希索引，下次同样的等值查询直接命中，省掉 B+ 树的逐层下降。它是自适应的、活在内存里的，用户既不能针对某张表建，也不能精确控制，只能通过参数整体开关。

另一个高频误区是 `CREATE INDEX ... USING HASH` 这条语法。MySQL 8.0 确实接受这个写法，但 **InnoDB 会忽略它，实际仍然建成 B+ 树**，没有任何哈希加速效果。真正能手动建哈希索引的是 `MEMORY`、`NDB` 这类引擎。

哈希索引的短板很干脆：

- **不支持范围查询**：`>`、`<`、`BETWEEN` 全都用不上，哈希值的大小与 key 的大小无关
- **不支持 `ORDER BY`**：哈希索引本身无序，排不出顺序
- **不支持最左前缀**：联合 key 必须整体匹配，只给一部分列算不出哈希值
- **只适合纯等值查找**：等值且选择性高的场景才是它的主场

## 全文索引：MATCH AGAINST 与中文分词的坑

全文索引（`FULLTEXT`）解决的是「在长文本里找关键词」，用 `MATCH ... AGAINST ...` 检索，而不是 `LIKE '%关键词%'` 那种必然全表扫的写法。InnoDB 从 **MySQL 5.6 起**支持全文索引，在此之前只有 MyISAM 有。

两种检索模式：

- **自然语言模式**（`IN NATURAL LANGUAGE MODE`，默认）：按词的相关度给结果排序
- **布尔模式**（`IN BOOLEAN MODE`）：支持 `+词`（必须包含）、`-词`（必须排除）这类运算符

```sql
-- 建全文索引
ALTER TABLE articles ADD FULLTEXT INDEX ft_content (title, body);

-- 布尔模式：必须含 MySQL，排除 Oracle
SELECT id, title FROM articles
WHERE MATCH (title, body) AGAINST ('+MySQL -Oracle' IN BOOLEAN MODE);
```

真正的坑在**分词**：MySQL 默认的全文解析器**按空格和标点切词**，中文句子没有空格，一整句会被当成一个词，**中文几乎查不出东西**。两条出路：换 **ngram 解析器**（MySQL 5.7 起内置，按 N 个字符切分，建索引时加 `WITH PARSER ngram`），或者干脆把检索交给 Elasticsearch 这类专门的搜索引擎。线上做内容检索，基本都走后一条。

## 空间索引与前缀索引：两个补充类型

空间索引（`SPATIAL`）服务于地理数据，用 **R-Tree** 组织，适合「某点周围 N 公里内有什么」「多边形是否相交」这类查询。字段类型是 `POINT`、`LINESTRING`、`POLYGON`、`GEOMETRY` 及其集合；参与建索引的列**必须是 `NOT NULL`**，MySQL 8.0 里还要给列显式声明 `SRID` 属性把坐标锁定到某个空间参考系，否则优化器不会用这个空间索引。多维数据上 B+ 树无能为力，这正是 R-Tree 存在的理由。

前缀索引（Prefix Index）是对字符串列**只索引前 N 个字符**，写法是 `KEY idx_name (name(10))`，用于列很长（长 `VARCHAR`、`TEXT`）时把索引体积压下来。代价有三条：

- **不能用于覆盖索引**：索引里没有完整列值，拿不到原值
- **不能用于排序**：`ORDER BY name` 需要完整列值才能排
- **不能用于唯一约束**：前 N 个字符相同并不等于整列重复

还有一条容易被忽略：**区分度会下降**。`name(10)` 只截前 10 个字符，如果这 10 个字符的重复率很高，索引的过滤能力就废了。选 N 的正确顺序是先看数据，让前缀的选择性尽量接近整列的选择性，再定 N。

## 常见追问

**Q：为什么 InnoDB 推荐用自增主键？**
A：聚簇索引的叶子按主键顺序排列，自增主键的插入是**顺序追加**，只在树的最右侧页写；随机主键（比如 UUID）会把插入点散落到树中间，**页分裂**和随机写都躲不掉。另外主键值会复制进每一个二级索引的叶子，主键越长，所有二级索引一起变胖。

**Q：回表和覆盖索引怎么快速判断？**
A：看查询用到的列是否全在同一个二级索引里（主键天然算在内）。全在就是覆盖索引，不回表；只要有一个业务列不在索引里，就必须回表取整行，所以 `SELECT *` 几乎必然回表。

**Q：(a, b) 和 (b, a) 两个联合索引有区别吗？**
A：有，区别在能支撑哪些查询。`(a, b)` 能支撑 `a`、`a + b`；`(b, a)` 能支撑 `b`、`b + a`。建联合索引前先看 `WHERE` 的最左列是谁，等值列放前面、范围列放后面。

**Q：面试只给一分钟，怎么答？**
A：先点六种类型（聚簇、二级、多列、哈希、全文、空间），再强调两条硬结论：每表唯一聚簇索引、二级索引叶子存主键所以要回表。收尾补两个区分度最高的细节：自适应哈希索引不能手动建、前缀索引不能用于覆盖索引和唯一约束。

## 易错点

- **以为能用 `USING HASH` 给 InnoDB 建哈希索引**：语法不报错，但引擎忽略它，建出来的仍是 B+ 树。InnoDB 能用的哈希索引只有自动的自适应哈希索引。
- **以为 `(a, b)` 联合索引里单独查 `b` 也能走索引**：违反最左前缀，索引第一层按 `a` 排序，只给 `b` 就没有入口。
- **以为范围条件右侧的列还能继续定位**：范围列右侧不能再用于索引定位，值虽然在索引里，但只能用于覆盖索引或 ICP 过滤。
- **以为中文全文索引开箱可用**：默认解析器按空格切词，中文要换 ngram 解析器，或者直接交给 Elasticsearch。

## 一句话记住

:::tip
聚簇唯一且叶子存整行，二级索引存主键要回表，哈希只能自适应，其余全是 B+ 树。
:::
