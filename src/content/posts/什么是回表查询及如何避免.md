回表是指**通过二级索引查到主键值后，再回到聚簇索引中查一次完整行数据**的过程。因为二级索引的叶子节点只存「索引列 + 主键值」，所以只要查询需要的字段没有全部落在索引里，就必然多出一次按主键的查找，多出来的这次随机 IO 就叫回表。

## 回表的根因：两种索引的叶子节点存的东西不一样

InnoDB 的索引分两级，差别全在叶子节点里放什么。

### 聚簇索引

InnoDB 的**主键索引就是聚簇索引**，叶子节点直接存放**整行数据**。所以**按主键查询只需一次 B+ 树查找就能拿到完整行**，这是 InnoDB 最重要的性能优势。

### 二级索引

除主键外的所有索引都是二级索引。它的叶子节点存放的是**索引列的值 + 主键值**（⚠️ **不是行地址**，这一点与 MyISAM 不同）。

:::tip
**二级索引查到的只是「线索」，要拿到完整行必须用主键再查一次聚簇索引，这一步就叫回表。**
:::

## 什么情况下会回表

| 查询场景 | 是否回表 | 原因 |
| --- | --- | --- |
| 走聚簇索引（`WHERE id = ?`） | 否 | 叶子节点直接存放整行数据 |
| 走二级索引，`SELECT` 的字段全在索引中（覆盖索引） | 否 | 索引已包含所有需要的数据 |
| 走二级索引，`SELECT` 的字段不全在索引中 | 是 | 索引叶子只有索引列 + 主键，缺的字段必须回表取 |

一句话判断：**走了二级索引，且要的列不全在索引里 → 一定回表。**

## 回表的代价是随机 IO

二级索引里的主键值未必与聚簇索引的物理顺序一致，**每个主键都要去聚簇索引的 B+ 树里「再定位一次」**，这就是随机 IO。

- 回表 10 行 → 10 次随机 IO
- 回表 10000 行 → 10000 次随机 IO → **随机 IO 远慢于顺序 IO，可能比全表扫描还慢**

:::caution
**所以「用上了索引反而更慢」的典型场景就是：命中了索引，但要回表大量行。** 此时优化器会自己评估成本，必要时干脆放弃索引直接全表扫描。
:::

## 最有效的避免手段：覆盖索引

让查询用到的所有字段，都包含在**同一个**索引里。

```sql
-- 假设已有索引 idx_name_age(name, age)
SELECT name, age FROM user WHERE name = '张三';
-- 只用到 idx_name_age 一个索引，name 和 age 都在索引里
-- → 完全不用回表 → 这就是覆盖索引
```

:::caution
**「回表查询怎么避免」的标准答案就是这一句：让查询要用到的所有字段都落在同一个索引中。**
:::

代价也要说清楚：索引会变大，写入变慢、占用空间增加，所以不要为了覆盖把 `TEXT`、长 `VARCHAR` 这类大字段塞进索引。

## 另外三种减少回表的手段

| 手段 | 做法 | 注意 |
| --- | --- | --- |
| 索引下推（ICP） | MySQL 5.6+ 在**存储引擎层的索引上就完成过滤**，减少真正需要回表的行数 | `EXPLAIN` 的 `Extra` 显示 `Using index condition` |
| 延迟关联 | 深分页时先在索引上取主键 id 列表，再拿这批 id 回表取整行 | 只回表当前页需要的行 |
| 减少查询列 | 不写 `SELECT *`，只取真正需要的字段 | 本质是在主动构造覆盖索引 |

延迟关联的最小写法：

```sql
SELECT u.* FROM user u
JOIN (SELECT id FROM user WHERE name = '张三' ORDER BY id LIMIT 100000, 20) t
  ON u.id = t.id;
```

## 索引数量与最左前缀的连锁影响

### 一次查询只能走一个索引

每个索引都是一棵独立的 B+ 树，**一次查询只能走一个索引**。如果「过滤条件用 A 索引、排序用 B 索引」，InnoDB 只能**选一个**（通常选过滤性更好的那个），**另一个索引就白建了**。

### 最左前缀决定能不能用上索引

联合索引 `(a, b, c)`：

| 查询条件 | 索引命中情况 | 是否回表 |
| --- | --- | --- |
| `WHERE a=? AND b=? AND c=?` | 完全命中 | 取决于 select 列是否都在索引中 |
| `WHERE a=? AND b=?` | 命中 a、b，c 失效 | 取决于 select 列是否都在索引中 |
| `WHERE b=?` | 完全失效（违反最左前缀） | 走全表扫描或其它索引 |

## 用 EXPLAIN 确认到底回没回表

| `Extra` 字段 | 含义 |
| --- | --- |
| `Using index` | 覆盖索引，没有回表（好） |
| `Using index condition` | 索引下推过滤，仍然要回表 |
| `Using where` | 有额外过滤条件 |
| 没有 `Using index`，且 `key` 不是 `PRIMARY` | 大概率发生了回表 |

:::tip
**更精确的验证法：把 `SELECT` 列改成索引里已有的列，再看 `Extra` 是否变成 `Using index`。**
:::

## 常见追问

**Q：按主键查会回表吗？**
A：不会。主键索引就是聚簇索引，叶子节点就是整行数据，一次查找就到手。

**Q：覆盖索引为什么比回表快这么多？**
A：二级索引的叶子只存索引列 + 主键值，体积远小于整行，扫描时页更少、基本是顺序 IO，而且完全没有回表带来的随机 IO。

**Q：有了索引下推，是不是就不用管回表了？**
A：不是。ICP 只是把过滤条件下推到存储引擎，减少「过滤完仍需要回表」的行数；`SELECT` 出来的非索引列该回的表一次都省不掉。

**Q：回表多了，是不是多建几个索引就行？**
A：方向反了。索引越多，写入越慢、优化器选择空间越大反而更容易选错；正确做法是让**一个**联合索引尽量覆盖高频查询的字段。

## 易错点

- **把二级索引的叶子节点当成行地址。** 那是 MyISAM 的做法；InnoDB 二级索引叶子存的是**索引列 + 主键值**，所以才需要拿主键回聚簇索引。
- **以为 `Extra` 为空就代表没走索引。** 走了二级索引但需要回表时，`Extra` 往往就是空的，得结合 `key` 一起看。
- **以为加了索引查询一定变快。** 命中索引却要回表大量行时，随机 IO 累加起来可能比全表扫描更慢，优化器甚至会主动放弃索引。
- **以为覆盖索引万能。** `SELECT *` 基本不可能被覆盖，JOIN 里另一张表的字段也覆盖不到；这类查询要么收敛字段，要么接受回表。

## 一句话记住

:::tip
**二级索引只给线索，拿整行就得回表付随机 IO；字段都落在同一个索引里才免回表。**
:::
