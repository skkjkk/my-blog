三者的区别集中在**四个维度：是否删除数据、是否重置自增 ID、是否回收空间、是否可回滚**。`DELETE` 是 DML，逐行标记删除，可回滚，但不重置自增、也不归还空间；`TRUNCATE` 是 DDL，本质是重建表，清空快、重置自增、归还空间，但隐式提交、不可回滚；`DROP` 把表结构连同数据一起删掉。选型只看两件事：这次操作要不要能回滚，以及这张表以后还要不要。

## 对比总表

| | `TRUNCATE` | `DELETE` | `DROP` |
|---|---|---|---|
| 删数据 | ✅ 全部 | ✅ 可带 WHERE | ✅ 全部 |
| **重置 AUTO_INCREMENT** | ✅ **重置为 1** | ❌ 不重置 | ✅ 重置 |
| **回收存储空间** | ✅ **立即归还** | ❌ 不归还（留空洞） | ✅ 归还 |
| **删表结构** | ❌ 保留 | ❌ 保留 | ✅ **删除表定义** |
| **是否 DDL** | ✅ DDL | ❌ DML | ✅ DDL |
| **能否回滚** | ❌（**隐式提交**） | ✅ 可回滚 | ❌（**隐式提交**） |
| 触发器 | 不触发 | 触发 | 不触发 |
| 锁 | 短暂元数据锁 + 表级 MDL | 行级锁（逐行删） | 短暂元数据锁 |
| **执行方式** | **重建表**（最快） | 逐行标记删除（最慢） | 删元数据（快） |

## `DELETE` —— 逐行标记删除

- **是 DML**，在事务中，**可回滚**
- **⚠️ 不重置自增 ID** → 删完再插入，ID 从原来最大值继续
- **⚠️ 不立即回收空间** → 数据页里留下"空洞"，表空间不缩小；要回收需 `OPTIMIZE TABLE`
- **大事务 DELETE 会撑大 undo log、造成大量行锁、阻塞复制**

:::caution
**⚠️ 生产禁忌：不要 `DELETE FROM` 不带 WHERE 的千万行大表** → 应**分批删除**（`LIMIT 1000` 循环）避免长事务与主从延迟。
:::

## `TRUNCATE` —— 重建表（更快）

- 本质是 **DDL：丢弃旧表、创建同名空表**
- **重置自增 ID** → 删完再插入，ID 从 1 开始
- **立即归还空间** → 表文件重建，碎片清零
- **⚠️ 不可回滚、隐式提交** → 事务里的其他改动**会一并提交**（容易踩坑）
- **不触发 DELETE 触发器** → 它不是逐行删除，行级触发器不会被执行
- **会写 binlog** → 以 DDL 语句的形式记录，从库照着重放；它并不会"清空" binlog 里的历史记录
- **不能用于有外键被引用的表**（被外键引用时报错）

## `DROP` —— 删除表本身

- **删除表结构 + 数据**，表完全不存在
- **重置自增 ID**、**回收空间**
- **DDL、隐式提交、不可回滚**
- 后续再用需重新 `CREATE TABLE`（包括索引、约束、默认值、字符集），这些定义不会跟着残留
- 数据只能靠备份恢复，`DROP` 之后没有 `OPTIMIZE TABLE` 之类的补救手段

## 性能差异：为什么差几个量级

百万行表清空（InnoDB）：
- `TRUNCATE` → **秒级**（重建表，直接操作表空间文件）
- `DELETE` → **分钟级**（逐行删除 + undo log + binlog + 锁）

:::tip
**差距可达上千倍。** 所以清空大表必须用 `TRUNCATE`。
:::

## 生产使用的风险点

- **⚠️ `TRUNCATE` 会隐式提交事务** → 在事务中间执行 `TRUNCATE`，前面未提交的操作**会被一起提交** → **务必确认事务边界**
- **⚠️ 主从架构下的影响**：`TRUNCATE` 是 DDL，会以语句形式写进 binlog 让从库重放，大表重建期间**从库延迟可能飙升** → 尽量挑低峰执行
- **⚠️ 磁盘空间**：`TRUNCATE` 重建表空间并把空间归还给操作系统，但重建过程本身有短暂的 IO 峰值 → 执行前先确认磁盘余量

## 选型建议

| 场景 | 选择 |
|---|---|
| 清空整张大表 | ⭐ **`TRUNCATE`**（最快） |
| 删部分数据 | `DELETE ... WHERE` |
| 删表且不再需要 | `DROP` |
| **需要回滚** | 只能 `DELETE` |
| **表有外键被引用** | `TRUNCATE` 会失败 → 只能 `DELETE` |

## 常见追问

**问：清空一张大表，为什么用 `TRUNCATE` 而不是 `DELETE FROM`？**
**答：** `TRUNCATE` 走重建表，直接操作表空间文件，秒级完成；`DELETE` 逐行标记删除，要写 undo log 和 binlog、还要加行锁，是分钟级，而且在表里留下空洞。

**问：`TRUNCATE` 和 `DELETE` 在事务上的本质区别是什么？**
**答：** `DELETE` 是 DML，在事务里执行，没提交就能回滚；`TRUNCATE` 是 DDL，隐式提交，会把事务里前面那些未提交的改动一起提交，所以事务中间千万别夹一个 `TRUNCATE`。

**问：清空之后自增 ID 会怎样，为什么？**
**答：** `TRUNCATE` 重置为 1，因为它是丢弃旧表重建，AUTO_INCREMENT 计数器跟着表一起重建；`DELETE` 只删行不动表，计数器保留，新插入的 ID 继续从原来的最大值往上走。

**问：表被外键引用时为什么 `TRUNCATE` 会失败？**
**答：** 它走的是重建表而不是逐行删除，绕不过外键检查，MySQL 直接报错；这种表只能先处理外键约束，或者用 `DELETE` 逐行删。

## 常见易错点

- **直觉"`DELETE FROM` 不带 WHERE 就等于 `TRUNCATE`"** → 两者结果都是空表，但 `DELETE` 不重置自增、不回收空间、留一堆 undo log，是最慢的一种清空方式。
- **直觉"`TRUNCATE` 会触发删除触发器"** → 不会。触发器是行级事件，`TRUNCATE` 根本不逐行处理，只有 `DELETE` 才会触发。
- **直觉"删错了还能 `ROLLBACK`"** → `TRUNCATE` 和 `DROP` 都是隐式提交的 DDL，执行完就定了，回滚不了；只有未提交的 `DELETE` 能回滚。
- **直觉"`DROP` 只是把数据删了"** → 表定义、索引、约束、默认值、字符集全都一起没了，要重建得整条 `CREATE TABLE` 重写。

## 一句话记住

:::tip
`DELETE` 删行可回滚，`TRUNCATE` 重建表不可回滚，`DROP` 删表本身。
:::
