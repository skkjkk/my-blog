死锁是**两个或多个线程各自持有对方需要的锁，又都在等对方释放**，于是相关线程全部挂起、任务永远无法完成。它必须同时满足四个必要条件：互斥、持有并等待、不可剥夺、循环等待，**破坏其中任意一个就能避免死锁**。JVM **不会自动检测并解决**死锁，只能靠设计规避，出事后靠 `jstack` 定位。

## 死锁的四个必要条件（少一个就不成立）

四个条件必须同时满足才可能死锁，所以「破坏任意一个」就是所有避免手段的理论依据。

| 条件 | 含义 | 怎么破坏 |
| --- | --- | --- |
| 互斥 | 资源同一时刻只能被一个线程占用 | 改用不可变对象、无锁结构（CAS、原子类）、`ThreadLocal`，让状态不再共享 |
| 持有并等待 | 线程持有资源 A 的同时，还在等资源 B | 一次性申请全部所需资源；缩短临界区，不在持锁期间调用外部代码 |
| 不可剥夺 | 已获得的资源不能被强行剥夺，只能由持有者主动释放 | 用 `tryLock(timeout)`，超时就放弃并释放手上已持有的锁 |
| 循环等待 | 存在等待环：A 等 B 的锁、B 等 A 的锁 | 全局统一的加锁顺序（按 id 排序、按 hashCode 排序） |

四个条件里，最容易动手的是「循环等待」，因为互斥常常由业务本身决定（写共享状态天然要互斥），而「不可剥夺」在 `synchronized` 上根本做不到。

## 典型场景：反向加锁最典型，数据库与线程池各有变体

最典型的是两把锁、两个线程、反向加锁：线程 T1 先 `synchronized(lockA)` 再 `synchronized(lockB)`，线程 T2 反过来先拿 `lockB` 再拿 `lockA`。双方各持一把、互等对方那一把，等待环就此形成。**这段代码在语法上完全合法，编译器不会报错，只有运行时才会暴露。**

```java
Object lockA = new Object();
Object lockB = new Object();

// 线程 T1：先 A 后 B
synchronized (lockA) {
    // 若此刻 T2 已持有 lockB，T1 就停在这里等对方释放
    synchronized (lockB) { /* 业务逻辑 */ }
}

// 线程 T2：先 B 后 A，与 T1 的顺序相反
synchronized (lockB) {
    synchronized (lockA) { /* 业务逻辑 */ }
}
```

生产上真正会遇到的是四类场景：

- **嵌套锁获取顺序不一致**：就是上面的反向加锁，最常见的一类。
- **数据库层死锁**：两个事务以相反顺序更新两行（`SELECT ... FOR UPDATE` 的顺序不同），InnoDB 检测到环路后会**主动回滚其中一个事务**并抛出 `Deadlock found`，是否开启检测由 `innodb_deadlock_detect` 控制。生产上要**统一访问顺序**，并把这类异常当成**可重试失败**来处理。
- **线程池内的任务相互等待**：任务 A 把任务 B 提交到同一个线程池，然后同步等 B 的结果，而池中线程已被占满、B 根本排不进去执行，形成**线程饥饿死锁**。它比锁死锁更隐蔽，而且**不会被自动检测**。
- **类初始化死锁**：两个类的静态初始化块互相引用，在类初始化阶段形成等待环，较少见但真实存在。

## 避免手段：固定加锁顺序最有效，其余四条依次补

1. **固定加锁顺序（第一原则）**：所有线程按全局一致的顺序获取锁，比如按对象 hashCode 排序、按业务 id 大小排序。顺序一致，等待环就不可能形成，**这是实践中最有效也最容易落地的手段**。
2. **缩小锁的范围（第二原则）**：尽量只锁真正需要的那部分，减少同时持有多把锁的时间。「持有并等待」是必要条件之一，缩短临界区、避免在持锁期间调用外部代码（尤其是可能回调自己、再去加别的锁的代码），能大幅降低死锁概率。**最危险的做法是持锁期间调用第三方库或执行 RPC。**
3. **避免一次持有多把锁（第三原则）**：能用单锁保护全部共享状态，就不要用多锁；必须多锁时，改用一把大锁、分段锁（把不同数据段的写操作分开控制，`ConcurrentHashMap` 走的就是这个思路），或者干脆换成无锁数据结构（CAS、原子类、`LongAdder`）。
4. **使用带超时的锁（第四原则）**：`ReentrantLock.tryLock(timeout)` 在拿不到锁时**返回失败而不是无限等待**，等待环被打断。注意 `synchronized` **没有超时版本**，这是 `ReentrantLock` 相对它的重要优势。拿到失败后可以退避重试、换执行路径，或者直接放弃并上报。
5. **用更高层次的并发工具替代裸锁（第五原则）**：`BlockingQueue`、`ExecutorService`、`ConcurrentHashMap`、`CompletableFuture` 内部已经处理好了锁的顺序问题，**能不自加锁就不自加锁**。

这五条的顺序就是面试时的回答顺序：先讲固定加锁顺序，因为它投入最小、收益最大；最后讲替换成高级并发工具，因为它往往意味着改架构。

## 排查、预防与兜底：jstack 第一步，超时兜底最后一步

线上怀疑死锁，第一步就是 `jstack <pid>`（或 `jcmd <pid> Thread.print`）打印线程栈。**死锁的线程栈会明确打印 "Found one Java-level deadlock"，并列出各线程互相等待的锁**，这是最直接的证据；`jconsole` 和 VisualVM 里有「检测死锁」按钮，点一下就能看到等待环路；`jmap -histo` 可以辅助看对象分布。定位到之后按「jstack 定位 → 确认锁顺序 → 打破等待环」处理，重启是最后手段，因为可能丢失状态。

比事后救火更重要的是兜底：即使没提前避免，也要保证系统**不会永久卡住**，通过 `tryLock` 超时、任务超时、连接池获取超时，把死锁转化为**可重试的失败**。

预防层面有四件事：

- **代码规范**：规定锁顺序，禁止持锁期间调用外部代码，禁止持锁期间做 IO。
- **静态检查**：用 SpotBugs 的 `DL_SYNCHRONIZATION_ON_SHARED_CONSTANT`、`IS2_INCONSISTENT_SYNC` 等规则在 CI 阶段拦截。
- **压测与混沌测试**：故意制造并发场景，把问题在测试环境暴露出来。
- **监控告警**：对线程数、阻塞线程数、任务队列长度做告警。

## 常见追问

**Q：`synchronized` 也会死锁吗？它能不能超时？**

A：会死锁，而且 `synchronized` 没有超时版本，一旦等不到就只有一直等下去。想要「拿不到就返回」只能用 `ReentrantLock.tryLock(timeout)`，这也是从 `synchronized` 迁移到 `ReentrantLock` 的一个实际理由。

**Q：线程池怎么会死锁？**

A：任务 A 在池内执行时把任务 B 提交到同一个池并同步等结果，池中线程被 A 这类等待者占满，B 永远排不到线程执行，A 就永远等不到结果。这是饥饿死锁，线程栈里看不到「互相持锁」的环路，需要靠拆分线程池、避免同池嵌套提交、加等待超时来防。

**Q：数据库死锁和 Java 死锁有什么不同？**

A：数据库内核有死锁检测，检测到环路会主动回滚其中一个事务（抛 `Deadlock found`），所以表现为一个可捕获、可重试的异常；JVM 没有这层兜底，Java 层死锁只能靠外部工具发现。

**Q：死锁、活锁、饥饿三者的区别是什么？**

A：死锁是线程互相等待、谁也不动；活锁是线程都在跑，但状态来回切换、谁也没推进；饥饿是某个线程长期抢不到资源，别人一直插队。三者里只有死锁会形成稳定的等待环路。

## 易错点

- 以为「锁加了就没事、顺序无所谓」。反向加锁是线上最常见的死锁来源，编译器不报错，测试也常常测不出来。
- 以为死锁一定会被 jstack 报出来。线程池饥饿死锁和类初始化死锁不会打印 "Found one Java-level deadlock"，要看线程栈里的等待关系、任务队列和类初始化状态才能判断。
- 以为 `wait()` 和 `sleep()` 一样占着锁不放。`wait()` 会释放持有的 monitor 让别的线程进来，`sleep()` 不释放任何锁——说反了面试会直接扣分。
- 把 `tryLock` 当万能药。它只负责「拿不到就返回」，超时之后是退避重试还是放弃上报要自己决定；拿到锁的路径仍要在 `finally` 里释放，而且此时业务状态可能已经变了，不做二次校验照样出问题。
