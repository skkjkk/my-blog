悲观锁靠"数据库/框架真的加锁阻塞别人"，乐观锁靠"不锁，用版本号在提交时校验"。落到代码上，悲观锁通常是显式事务里的 `SELECT ... FOR UPDATE`，乐观锁通常是表加 `version` 字段、更新时带 `WHERE version = ?`，影响行数为 0 就重试或返回失败。两者的区别别处已有专篇，这里专注**"怎么落地实现"**。

## 乐观锁的三种实现路径

- **① 版本号（version）—— 最常用、最标准**
  - 表加 `version INT` 字段；更新时 `SET version = version + 1 WHERE id = ? AND version = ?`
  - 影响行数为 0 → 说明被别人改过 → **重试或返回失败**
- **② 时间戳（update_time）** —— 原理同版本号，⚠️ **时间戳精度可能不够**（秒级时间戳在同一秒内多次更新会误判），建议用版本号
- **③ CAS（应用层）** —— Java 的 `AtomicInteger` / `LongAdder`、Go 的 CAS、数据库的 `UPDATE ... WHERE stock = 原值`
  - **无锁、失败即重试**，适合**单变量**的并发修改

## 乐观锁的标准实现（Java 侧）

```java
// 实体加 @Version
@Version
private Integer version;

// 更新
int rows = userMapper.updateById(user);   // WHERE id=? AND version=?
if (rows == 0) {
    throw new ConcurrentUpdateException("更新冲突，请重试");  // 或重试
}

```
- MyBatis-Plus 的 `@Version` + `OptimisticLockerInnerInterceptor` **自动完成版本号自增与条件拼接**
- **必须保证"读-改-写"在同一个更新语句里**，不能先查再改再更新（否则校验失效）

## 悲观锁的三种实现路径

- **① 数据库行锁** —— `SELECT ... FOR UPDATE`（排他）/ `FOR SHARE`（共享）/ `LOCK IN SHARE MODE`
  - ⚠️ **必须在显式事务中**，否则语句结束即释放锁，**加锁形同虚设**
- **② 分布式锁** —— Redis（`SET NX EX` + Lua 释放）、Redisson、ZooKeeper 临时节点
  - 用于**跨服务、跨库**的资源互斥
- **③ JVM 锁** —— `synchronized` / `ReentrantLock`
  - ⚠️ **只能管单机**，多实例部署完全失效 → 分布式场景必须用分布式锁

## 悲观锁的标准实现（数据库侧）

```sql
BEGIN;
SELECT stock FROM product WHERE id = 1 FOR UPDATE;   -- 加排他行锁
-- 校验库存、做业务逻辑（保持事务短）
UPDATE product SET stock = stock - 1 WHERE id = 1;
COMMIT;

```
- **⚠️ 事务必须短** —— 锁持有到 `COMMIT` 为止
- **⚠️ 事务中禁止远程调用** —— 会把锁的时间放大到网络延迟级别
- 上面两条是同一个原因：行锁是**等 `COMMIT` 才放**的，事务里多待的每一毫秒，别的会话都在后面排队等锁，所以业务校验放在事务里，远程调用、发消息这些慢动作挪到事务外

## 实际首选：既不用显式锁，也不用版本号的"条件更新"

```sql
UPDATE product SET stock = stock - 1
WHERE id = 1 AND stock >= 1;

```
- **靠"条件"天然保证不超卖** —— **单条 SQL 原子完成**，不需要锁也不需要版本号
- `ROW_COUNT() = 0` → 库存不足
- **这是并发扣减场景的最优解**，比任何显式加锁都简洁
- 原因是"判断"和"扣减"被压进同一条语句，由数据库在执行时保证原子性：既没有线程阻塞，也没有版本号的重试开销

## 两种锁的代价对比

| | 悲观锁 | 乐观锁 |
|---|---|---|
| 冲突时行为 | **阻塞等待** | **失败重试** |
| 代价 | 上下文切换、线程挂起、可能死锁 | 重试浪费 CPU，极端情况活锁 |
| 适用 | **冲突频繁、必须串行** | **冲突少、读多写少** |
| 实现复杂度 | 低（数据库直接支持） | 高（要处理重试、版本号、幂等） |

## 选型决策树

- **能用条件更新/唯一索引解决** → **首选它们**（比锁更简洁、无死锁风险）
- **冲突概率低** → 乐观锁（版本号）
- **冲突概率高** → 悲观锁（`FOR UPDATE`），并保证**事务极短**
- **跨服务、跨实例** → 分布式锁（⚠️ 注意锁超时与看门狗续期）
- **高并发扣减** → 乐观锁重试 + **限流**；或直接用 **Redis 预扣减 + MQ 异步落库**

## 常见追问

**问：乐观锁和悲观锁分别有哪几种落地实现？**
**答：** 乐观锁是版本号（最常用、最标准）、时间戳、应用层 CAS；悲观锁是数据库行锁 `FOR UPDATE`、分布式锁、JVM 锁，其中行锁只在显式事务内才有效。

**问：为什么 `SELECT ... FOR UPDATE` 加了锁还可能等于没加？**
**答：** 它的锁跟着事务走，语句跑在自动提交或事务之外时，语句结束锁就释放了；同理 `synchronized` 只管单机，多实例部署下也挡不住并发。

**问：真实场景该按什么顺序选型？**
**答：** 先看能不能用条件更新或唯一索引解决，能就别上锁；冲突少用版本号乐观锁，冲突多才用 `FOR UPDATE` 并保证事务极短；跨服务、跨实例才上分布式锁。这条"能用条件更新就别加锁"最体现工程品味。

**问：乐观锁最容易踩哪些坑？**
**答：** 版本号必须交给数据库 `version = version + 1` 维护，应用自己算值写回会丢更新；重试要有上限和退避，且必须重新读最新数据再算；纯用值做校验还挡不住 ABA，版本号单调递增才能。

## 乐观锁的两个常见坑

- **① 版本号必须由数据库维护**（`version = version + 1`），不能由应用 `+1` 后写入（否则会丢更新）—— 直觉上"我在代码里加一也一样"，但你写回的是自己算出的值，别人先提交的更新就被直接覆盖
- **② 重试要有上限与退避** —— 无限重试会变成活锁；重试时**必须重新读取最新数据**再算，否则拿旧值重试只是白白再失败一次

:::caution
⚠️ **更根本的坑：乐观锁的 ABA 问题** —— 读到值 A → 别人改成 B 又改回 A → 你的校验通过，但基于的是**过期数据**。版本号能解决（版本号单调递增），**单纯用值做校验则不能**。
:::
