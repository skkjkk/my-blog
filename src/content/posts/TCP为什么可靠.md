TCP 的可靠性不是靠某一个机制，而是六个机制协同构成的体系：确认应答、超时重传、序列号与去重、校验和负责"数据不错"，流量控制与拥塞控制负责"不堵不炸"。它实际提供的是一条这样的字节流 —— 在连接未异常终止的前提下，按序、不重复、无差错地交付给对端应用，因此"可靠"两个字是有边界的。

## 六个机制总览：谁保证"数据不错"，谁保证"不堵不炸"

把六个机制按职责分成两组，是这道题最好记的骨架。前四个 —— 确认应答、超时重传、序列号与去重、校验和 —— 回答"数据到没到、对不对、有没有重复"；后两个 —— 流量控制、拥塞控制 —— 回答"能发多快"，让传输不把接收方或整个网络压垮。

| 机制 | 解决的问题 | 保护对象 |
| --- | --- | --- |
| 确认应答（ACK） | 发送方无法确认数据是否到达 | 交付的可确认性 |
| 超时重传 | 数据段或 ACK 本身丢失 | 数据最终到达 |
| 序列号与去重 | 乱序、重复 | 字节流的顺序与唯一 |
| 校验和 | 传输途中比特损坏 | 数据的正确性 |
| 流量控制（`rwnd`） | 发送太快冲垮接收缓冲 | 接收方 |
| 拥塞控制（`cwnd`） | 发送太快压垮链路 | 整个网络 |

六个机制不是并列罗列，而是层层兜底：校验和负责"发现错了"，重传负责"补回来"，确认号负责"知道补到哪了"，窗口负责"别发太快"。按这层因果串起来，被追问时才讲得下去。

## 确认应答与超时重传：可靠性的两条腿

TCP 是全双工的，每发送一个数据段，接收方都要回一个确认号（ACK），确认号的含义是"我已经收到第 N 号字节之前的全部数据"。发送方只有收到 ACK 才知道数据真的到了，而不是"发出去了"就算完 —— 这是可靠性唯一的事实来源，没有 ACK 就没有可靠可言。

超时重传补的是 ACK 本身也丢失的情形：发送方发出数据后启动重传定时器，规定时间内没等到对应 ACK 就重发该数据段；重传次数超过上限（如 6 次）则放弃连接并报错。这里有个关键认识 —— TCP 无法区分"数据段丢了"和"ACK 丢了"，因为两种情况下它看到的都是"没有 ACK"，索性用同一个超时机制统一覆盖。

RTO（重传超时时间）不是固定值，而是基于平滑的往返时间估计（RTT 平滑值加上偏差项）动态计算出来的，并随重传次数退避放大。超时重传是兜底手段，收到重复 ACK 时还有更快的快重传，那属于拥塞控制的一部分。

## 序列号与校验和：重排、去重与发现损坏

TCP 给每个字节编号，是字节序号而不是包序号。接收方按序号重排数据，保证交给应用的是有序字节流；已经收到过的序号直接丢弃，保证不重复。注意这两个能力由同一个字段实现：序列号不是分别对付乱序和重复，而是一次性把两个问题一起解决，这也是它最容易被低估的地方。

校验和是 16 位的，覆盖首部、数据和一个伪首部。接收方验证不通过就直接丢弃该段且不回 ACK，发送方因为等不到 ACK 才会超时重传。所以校验和是重传机制能够生效的前提 —— 它负责"发现损坏"，重传负责"修复损坏"，两者缺一不可。

## 流量控制与拥塞控制：一个保护接收方，一个保护网络

流量控制用滑动窗口实现：接收方在自己的 ACK 里通告接收缓冲区剩余空间（rwnd），发送方据此限制"已发出但尚未被确认"的数据量。它解决的是"发送方太快、接收方来不及处理导致丢包"，保护对象是接收方，防止其接收缓冲被冲垮。

拥塞控制用拥塞窗口（cwnd）限制发送速率。TCP 把丢包当成网络拥塞的信号，于是主动降速：慢启动阶段窗口快速增长以探测容量，进入拥塞避免后改为线性增长；真正丢包时用快重传加快补包、用快恢复避免吞吐锐减。它保护的是整个网络，而不是某一个接收方。

| 维度 | 流量控制 | 拥塞控制 |
| --- | --- | --- |
| 控制变量 | `rwnd`（接收窗口） | `cwnd`（拥塞窗口） |
| 数值来源 | 接收方在 ACK 中通告 | 发送方自己探测与调整 |
| 触发信号 | 接收缓冲区即将耗尽 | 丢包、重复 ACK 等拥塞信号 |
| 保护对象 | 接收方 | 整个网络 |

实际发送速率受 `min(cwnd, rwnd)` 约束，两个窗口谁小听谁的。所以被问"为什么慢"时要分清是哪一类限制：瓶颈在接收端时扩大缓冲区有用，瓶颈在网络链路时只能等拥塞控制慢慢恢复。

## 连接状态上的可靠性设计：握手、挥手与 TIME_WAIT

连接本身也是可靠性的一部分。三次握手同步双方的初始序列号，同时确认"我发得出、你收得到"和"你发得出、我收得到"这两件事都正常，顺带避免把旧连接残留的报文当成新连接的数据。

四次挥手是因为 TCP 全双工：一个 FIN 只能关闭一个方向，被动关闭的一方可能还有数据没发完，所以两个方向要各自关闭，确保双方数据都发完了才真正断开。

TIME_WAIT 状态保留 2MSL，作用有两个：一是最后那个 ACK 如果真的丢了，对方重传的 FIN 仍能被正确响应，不至于让被动方一直卡在 LAST_ACK；二是让本次连接在网络中迷途的旧报文自然消散，不去污染下一个恰好复用了相同四元组的新连接。

## 可靠性的边界：TCP 只是"尽力而为的交付"

必须区分一个层次：TCP 保证的是在连接未异常终止的前提下，把字节流按序、不重复地交付给对端应用。如果连接被强行断开（进程崩溃、网络中断、掉电），已发送但尚未被确认的数据会丢失 —— TCP 本身不提供任何持久化。

所以"绝对不丢"要靠应用层来补：ACK 在业务处理完成之后才发、数据真正落库之后才确认（配合业务幂等 + 去重表防重复投递）、用事务消息保证本地事务与消息发送一致，或干脆用 Raft/Paxos 这类共识协议做多副本。这是面试中区分层次的关键点：协议层的"可靠"不等于业务层的"不丢"。

## 代价与演进：为什么 QUIC 敢在 UDP 上重做一套可靠传输

可靠是有成本的。确认与重传引入了延迟，一个数据从发出到被确认至少要等半个往返（RTT 的一半）；滑动窗口、重传队列和整套连接状态机要持续占用内存；拥塞控制在丢包后主动退让，牺牲了带宽利用率，因为它宁可保守，也不愿把网络打满。

这正是 QUIC 敢在 UDP 上自己重做一套可靠传输的原因：把可靠性放进用户态、可以自己迭代，从而做更激进的拥塞控制（如 BBR 这类基于带宽估计的算法）、更快的连接建立（0-RTT）、更灵活的路径迁移（连接级加密让 NAT 重绑定不再打断会话）。换句话说，TCP 的可靠机制是几十年前在网络内核里定下来的，QUIC 是在同一个目标下换了一套更自由的实现空间。

## 常见追问

**问：ACK 里的确认号是"我收到了第 N 个包"吗？**
答：不是包序号，是字节序号，含义是"N 号之前的字节我全收到了"，也就是累计确认。正因为是累计的，中间某个 ACK 丢了通常不影响，后面的 ACK 会一并确认掉。

**问：为什么超时重传不能区分"数据丢了"和"ACK 丢了"？**
答：发送方只能观测到"没收到 ACK"这一个事实，两种丢失在它眼里完全一样，所以只能用超时加重传来统一覆盖；代价是可能重发对端其实已经收到的数据，这也正是需要序列号去重的原因。

**问：流量控制和拥塞控制都在限速，只留一个不行吗？**
答：保护对象不同。只留流量控制，网络拥塞时照样大量丢包；只留拥塞控制，接收慢的一方会被冲垮。发送速率取 `min(cwnd, rwnd)`，两道闸门各管一头。

**问：面试时这题怎么组织成三句话？**
答：第一句给六个机制的分工（确认应答 + 超时重传 + 序列号去重 + 校验和保数据可靠，流量控制 + 拥塞控制保传输可持续）；第二句给关键区分（流量控制保护接收方、拥塞控制保护网络，速率取 `min(cwnd, rwnd)`）；第三句给边界（TCP 的可靠是连接存活前提下的可靠交付，业务级不丢要靠应用层幂等与持久化）。第三点最能拉开差距，因为大多数人只会背六个机制。

## 易错点

- 把"发出去了"当成"送到了"。可靠性的起点是收到 ACK，不是 write 返回成功。
- 把序列号当成包序号。它是字节序号，所以同一个字段既能重排乱序、又能丢弃重复。
- 把流量控制当成拥塞控制。前者保护接收方（`rwnd`），后者保护整个网络（`cwnd`），混着答会直接暴露没理解。
- 以为 TCP 保证业务不丢。连接异常终止时，已发送未确认的数据照样丢，持久化和幂等是应用层要解决的问题。

## 一句话记住

:::tip
前四个机制保数据不错，后两个保网络不炸，可靠有边界。
:::
