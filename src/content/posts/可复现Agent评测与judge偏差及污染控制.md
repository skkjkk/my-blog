可复现的核心只有一句话：把所有非目标变量钉死，把剩下的不确定性交给统计。模型这一项要写具体快照标识，而不是会滚动的别名；温度与采样参数、系统提示词、工具实现版本、检索语料与依赖镜像摘要全部锁定并记录哈希，再靠多次采样报均值和置信区间。judge 的偏差按类型分别消解、上机前先用人工黄金集校准；评测污染则从数据集留出与运行隔离两侧掐断，并持续监控公开集与私有集的分数差。

## 可复现的第一原则：把所有非目标变量钉死

评测里唯一允许变化的是被测系统本身。除它之外的每一项都要显式锁定，并写进配置清单，否则两次运行的差异根本说不清来自哪里。

| 要锁定的对象 | 具体做法 | 不锁定的后果 |
| --- | --- | --- |
| 模型 | 写具体快照标识，不写会滚动更新的模型别名 | 上游一升级，两次评测就不是同一个系统 |
| 采样参数 | 温度、top-p、最大输出长度、停止序列全部显式写死 | 默认值一改，输出分布跟着变 |
| 提示词 | 系统提示词、工具描述、少样本示例、模板全部版本化 | 改一个标点就等价于换了一次实验 |
| 工具 | 工具实现版本与参数默认值 | 同名工具换了实现，行为完全变样 |
| 语料 | 检索语料拍快照并记录内容哈希 | 索引一变，召回就变，结果不可比 |
| 运行环境 | 依赖库锁版本，容器镜像锁摘要值，评测脚本自身也锁版本 | 环境漂移会被误读成模型进步 |
| 任务集 | 任务集版本化并记录哈希，任务内部的随机性用显式随机种子注入 | 依赖全局随机状态，重跑顺序一变结果就变 |

外部依赖同样属于「非目标变量」，冻结方式是四件事：

- 对第三方接口做录制回放，把调用当时的响应原样存下来，重跑时直接回放；
- 对系统时钟做冻结，凡是依赖当前时间的逻辑都要能被替换；
- 对文件系统使用快照，避免上一个用例的残留影响下一个；
- 对网络做隔离或走本地桩，禁止评测过程中访问真实线上服务。

把这四类不确定源全部固定下来，两次运行的差异才只剩下被测系统本身的变化。

## 单次结果不算结果：多次采样、配对比较与分桶

大模型输出本质上是随机的，同一配置只跑一次得到的数字没有统计意义。正确口径是重复运行若干次，报告均值和置信区间，而不是甩出一个单点分数。

比较两个系统时，要在同一批任务上做配对比较，再配合自助法（bootstrap）估计差异的区间，而不是各自跑一遍比较两个独立均值。原因很实际：任务之间难度的方差远大于两个系统之间的差距，不配对的话，少量样本根本分辨不出真实差异。

几条必须一起写死的判定规则：

- 任务成功与否的判定规则必须完全确定，并且写成可执行断言，不能靠人临场看输出判断；
- 必须分桶报告，按任务难度、任务类型、是否需要多轮交互分别统计，否则总分很容易掩盖某一类任务的塌陷；
- 必须把成本一并报告，即每任务的 token 数、费用和延迟，因为成本是选型时真正被权衡的量；
- 基线必须固化版本，比较时对照同一个基线快照，而不是每次重跑基线，否则上游漂移会被误读成被测系统的改进。

## 评测产物要能重放，回归门禁才立得住

每次评测产出一份清单：全部配置、每条任务的完整轨迹和最终结果，把它们作为制品归档。清单要细到任何人拿着它都能重跑一次并得到可比的结果。

```yaml
run_id: run-03
model: <provider>/<model>@<snapshot-id>   # 快照标识，不是滚动别名
sampling: { temperature: 0.0, top_p: 1.0, max_output_tokens: fixed }
prompt_version: system-prompt@<sha256>
tools: [search@<commit>, shell@<commit>]
corpus: { snapshot: kb-batch, sha256: <hash> }
seeds: [17, 29, 43]
task_set: { version: v3, sha256: <hash> }
```

回归门禁就建立在这套制品之上：先定义清楚哪些指标劣化超过多少阈值就阻断合入，再在持续集成里固定跑这些用例。没有可重放的产物，所谓「上次还能跑通」只是传说，门禁也无从判定。

## judge 的六类偏差，各有对应控制手段

LLM-as-judge 的偏差不是一种，控制手段也不能混着用，必须一类一类对着治。

| 偏差类型 | 表现 | 控制手段 |
| --- | --- | --- |
| 位置偏差 | 偏好第一个或最后一个候选 | 交换顺序后复测，要求两次结论一致；长文本和选择题要特别关注这一项 |
| 长度偏差 | 偏好更长更详尽的回答 | 改用成对比较而非绝对打分，相对判断比绝对打分稳定得多；同时对长度做匹配 |
| 自我偏好 | 偏爱与自己同族的模型输出 | 让 judge 使用与被评模型不同厂商的模型 |
| 格式偏差 | 偏爱带标题、加粗、Markdown 的结构化答案 | 统一格式，或者剥离格式后再评 |
| 提示敏感性 | 对措辞极其敏感，换个说法分数就变 | 评分细则版本化，给出可操作的判定项，并用少样本校准 |
| 确认偏差 | 倾向赞同参考答案 | 引入干扰样本，检查 judge 会不会因为候选看起来更完整就放过明显错误 |

## judge 要先校准、留痕、脱敏

judge 没过校准，它给出的模型排名就没有意义。校准的做法是维护一份人工标注的小规模黄金集，定期测 judge 与人的一致率；成对偏好用一致率和 Kappa 这类指标衡量，一致率不达标就先修 judge，再拿去评模型。

配套的三件事一样不能省：

- 留痕：judge 的调用参数、提示词版本、输出的理由都要保存，任何一次评分都能回溯到当时的具体输入；
- 脱敏：不能把被评模型的身份泄漏给 judge，也不能让它看到参考答案之外的提示线索；
- 分歧处理：判定有歧义时优先用多判官集成或多次采样取多数，并把 judge 与人类判断的差异当作一等公民持续监控。

## 污染的本质是测试信息泄漏进了被测系统

评测污染不是「模型太强」，而是答案通过某条渠道提前漏进了被测系统。常见的泄漏渠道有六条：

- 训练数据里混入了基准题目；
- 提示词里的少样本示例选自测试集；
- 检索库收录了测试文档；
- 模拟环境或工具的返回值里直接包含答案；
- 评测脚本与数据集同源，措辞和结构上互相泄漏；
- 公开数据集本身在互联网上被反复抓取，最终进入预训练语料。

污染是可以被观测的。典型信号是模型在某些样本上表现异常好，以及公开集与私有集之间的分数差距持续扩大；监控这个差距的变化趋势，比事后猜测可靠得多。

还要防另一种自我污染：在已有指标上反复试验直到某个指标好看。对策是预先登记评测协议和主要指标，事后不得更换判定口径和统计方法。

## 防污染：数据集留出与运行隔离两层一起做

数据集层面的重点是留出。用新鲜或私有的保留集，公开集只用于日常开发，私有集用于发布判定，两者定期轮换；并用时间切分保证测试样本晚于训练截止时间。发布前还要对训练语料做去污染清洗，靠三种方式交叉查：词法重叠、语义相似、标准答案匹配。

运行层面要切断泄漏通道：

- 每次评测生成独立的检索索引快照，剔除含有标准答案的文档；
- 少样本示例严格从训练池中抽取，绝不从测试集里选；
- 工具和桩服务不得携带答案信息，返回值里不能出现标准答案；
- 在私有评测集中植入可追踪的标记字符串，一旦它在外部数据里出现，就能定位泄漏源。

两层缺一不可：只做数据留出，运行时的检索库和工具返回值照样能把答案喂进去；只做运行隔离，公开集的样本早就在训练语料里了。

## 常见追问

**问：只固定温度不就够了吗？**
**答：** 不够。温度只是采样参数之一，模型快照、提示词模板、工具版本、语料哈希任何一项变了，两次运行的差异就不再只是被测系统的变化。

**问：为什么比较两个系统一定要配对比较？**
**答：** 因为任务难度带来的方差远大于系统之间的真实差距，不配对时这点差距会被任务方差吃掉。同一批任务上成对比较再配合自助法估计差异区间，样本量不大也能把差距和噪声分开。

**问：judge 直接拿一个强模型打分可以吗？**
**答：** 要先用黄金集测它跟人的一致率，通过才可用；还要注意自我偏好，judge 与被评模型同族时评分会偏高，最好换一个厂商的模型。

**问：换成私有数据集就一定能避免污染吗？**
**答：** 不能。私有集一旦被抄进少样本示例或检索库就已经污染了，所以运行层必须同时隔离；另外埋标记字符串，才好在外部数据里发现泄漏。

## 易错点

- 把模型别名当快照：配置里写的是会滚动的别名，上游一升级，前后两次评测就不是同一个系统，分数变化无法归因。
- 只报单点分数、不报置信区间：差两个点就宣称赢了，其实还在采样噪声范围内。
- judge 不做校准就上机：judge 自己都没和人工标注对齐，它给出的排名再整齐也没有说服力。
- 在测试集上反复调提示词：每改一版都在测试集上看效果，分数是被调出来的，不是能力涨了。

## 一句话记住

:::tip
非目标变量全钉死，judge 先校准再上岗，污染靠留出集加运行隔离掐断。
:::
