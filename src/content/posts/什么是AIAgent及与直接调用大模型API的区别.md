直接调用大模型 API 是「一问一答」：把提示词发过去，模型返回一段文本，这次调用就结束了，后续的解析、调工具、再把结果发回去，全由开发者自己的代码完成。AI Agent 是在这之上加了一个**能自主循环决策的运行时**：模型不只生成文字，而是围绕目标自己决定下一步做什么、调用哪个工具、观察结果再继续想，直到目标达成或触发终止条件。所以两者的分水岭不在模型强弱，而在**控制流归谁**。

## 本质区别是控制权的归属

直接调 API 时，**控制流在开发者代码里**：先取数据、再拼提示词、再解析返回、再判断要不要重试，每一步都被人预先写死，模型只是这条流水线上负责「生成文本」的一个环节。Agent 模式下，**控制流交给模型**，开发者只提供三样东西——目标、可用工具、边界条件——具体走哪条路径、调用几次、什么时候停，由模型在运行时动态规划。

这个差别会一路传导到工程上。同样是「查一下这个报错的原因」，直接调 API 的方案里，步骤是代码里写死的分支判断，出问题看堆栈；Agent 方案里，步骤是模型每次现编的，出问题只能看执行轨迹。前者确定、好测，后者灵活、难测，后面几节的取舍都从这一条长出来。

## Agent 比裸调 API 多出四个核心能力

这四个能力是它与裸 API 的分水岭：

- **感知**：读取环境与工具返回，把执行结果当成新的输入。
- **决策**：基于目标和已有观测，规划下一步动作。
- **执行**：调用工具并作用于环境，而不只是输出文本。
- **记忆**：跨步骤保留状态与历史经验，不必每次从零开始。

裸 API 调用只有「生成」这一项：给什么提示词就产出什么文本，它不知道上一步发生了什么，也没有能力让任何事情真的发生。所谓「加一个 Agent 层」，本质上就是把剩下三项能力补齐。

## 循环与状态管理是新增的负担

Agent 通过 Agent Loop 反复「思考 → 行动 → 观察」推进任务，循环本身不难写，难的是它带来两个裸 API 没有的问题：**上下文如何随步数增长而管理**（每一步的观测都往消息列表里堆，步数一多就可能撑爆窗口，需要裁剪、摘要或外置存储），以及**如何判断任务完成、防止无限循环**。

一个最小的 Agent Loop 骨架大致是这样（各家接口字段不同，结构类似）：

```text
messages = [system(目标 + 边界), user(任务)]
for step in range(MAX_STEPS):          # 终止条件之一：步数上限
    out = llm(messages, tools)         # 决策：模型选择下一步动作
    if out.final_answer:               # 终止条件之二：模型声明完成
        return out.final_answer
    result = run_tool(out.tool_calls)  # 执行：真正调用工具
    messages.append(result)            # 观察：结果回填进上下文
return fallback("超过步数上限，转人工")
```

注意最后那行兜底：循环必须留一条不依赖模型判断的退出路径，否则模型一旦「觉得自己还没做完」，就会一直转下去。

## 工具与副作用把工程问题带了进来

裸 API 调用通常只返回文本，最坏情况是答案不准；Agent 会真实调用数据库、文件系统、外部服务，一次误判就可能写坏数据或删掉文件。因此**超时、失败、权限、幂等、副作用**这些工程问题必须逐个处理：写操作要有幂等键，危险工具要有权限校验与人工确认，失败要能回滚或补偿。

这部分工作量往往比「接一个模型」大得多，也正是 Demo 与生产系统之间的实际差距。把 Agent 当成一个会自己行动的客户端来设计，比把它当成一个更聪明的聊天接口要安全得多。

## 自主性本身就是风险

正因为控制流交给了模型，同样的输入也可能走出不同的路径，于是带来三类裸 API 没有的风险：**可复现性下降**（今天跑通，明天换个措辞就偏了）、**成本不可预测**（步数不定，消耗跟着浮动）、以及**越权与提示注入风险**（工具返回的内容里如果藏着指令，模型可能当真执行）。

裸 API 调用的行为是确定的：同样的输入基本得到同样的输出，这三类风险几乎不存在。这也是为什么 Agent 系统必须额外配轨迹日志、权限隔离和预算上限——不是加保险，而是补上被移交出去的那部分可控性。

## 选型：先问步骤能不能预先确定

Agent 适合**步骤数无法预先确定、且需要与环境交互**的任务，典型如排障、深度检索、代码修改、运维操作——这类任务你事先写不出完整流程，只能给目标和工具。反过来，如果流程固定、步骤已知，**直接调 API 反而更好**：更快、更便宜、更可控、更易测试。这是选型时最重要的判断：把已知流程硬塞进 Agent，等于用不确定的东西替换确定的东西，只换来灵活性外加一堆新的失败模式。

| 维度 | 直接调用大模型 API | AI Agent |
|---|---|---|
| 控制流 | 在开发者代码里，步骤预先写死 | 交给模型，运行时动态规划 |
| 能力范围 | 只有生成 | 感知、决策、执行、记忆 |
| 交互形态 | 一问一答，单轮或多轮对话 | 思考 → 行动 → 观察的循环 |
| 副作用 | 通常没有，只产出文本 | 真实调用工具，可能改动数据 |
| 可复现性 | 高，行为确定 | 低，同输入可能走出不同路径 |
| 成本 | 按调用量可预估 | 步数不定，难以预估 |
| 调试方式 | 看输入输出与堆栈 | 只能看执行轨迹，需专门评测 |
| 适合场景 | 流程固定、步骤已知 | 步骤不定、需与环境交互 |

## 工程上该做的是分层混合

成熟做法是**混合式**：把确定性强的部分用普通代码写死（取数、校验、格式化、写库、重试策略），把需要灵活判断的部分交给模型做局部决策（这一步该查哪张表、这段报错像什么原因、要不要再补一次检索），而不是把整个流程都变成 Agent。

判断标准只有一条：**这一步是否真的需要自主推理**。需要，就交给模型；如果「按规则就能定」，就写进代码。模型参与的环节越少，系统越可控、越好测，也越省。

## 常见追问

**Q：Agent 是不是就是带工具调用的模型？**
A：不完全是。判断标准还是控制流归谁：如果每一步调用什么工具、调几次都由你的代码决定，那就是程序在编排，模型只是个被调用的工具；只有模型自己决定下一步做什么，才算 Agent。

**Q：直接上 Agent 框架是不是比手写 API 调用更强？**
A：不是。框架加的是循环、状态和工具管理，代价是延迟、成本和不可控性。流程固定的任务手写调用更快更稳，框架只在真的需要动态决策时才划算。

**Q：怎么防止 Agent 跑飞、成本失控？**
A：三件事：设硬性终止条件（步数、时间、预算上限），给工具加权限校验与幂等，把可确定的步骤留在代码里。不要指望用提示词约束住一个没有边界的循环。

**Q：为什么同一个任务两次跑出来的结果不一样？**
A：因为路径是模型运行时规划的，采样有随机性，观测到的内容也会变。要稳定就缩小模型决策的范围：固定流程前置、只把局部判断交给模型，同时记录轨迹便于复盘。

## 易错点

1. **把「用了大模型」当成「做了 Agent」**。单轮问答、固定几步的流水线，不管外面包几层，控制流仍在代码里，本质还是调 API。
2. **以为 Agent 一定比直接调 API 更强**。它换来的是灵活性，付出的是延迟、成本和可复现性；流程已知时它是负优化。
3. **只写循环不写终止条件**。没有步数或时间上限，模型可能在两个动作之间来回打转，账单和风险一起涨。
4. **把工具调用当成纯读操作**。写库、删文件、发消息都有副作用，缺权限校验和幂等，一次误判就是线上事故。

## 一句话记住

:::tip
直接调 API 是代码决定路径，Agent 是模型决定路径，选型看步骤能否预先确定。
:::
