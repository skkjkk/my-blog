Agent 的评估比模型评估复杂得多，因为**它评估的不只是「答得好不好」，而是「过程是否有效」**。所以标准答案要分两半说：指标上分四层，端到端效果、过程质量、效率与成本、安全与鲁棒性；方法上用四类，离线任务集、LLM-as-judge、轨迹评估、线上指标加故障注入。四层指标定义「评什么」，四类方法定义「怎么测」，两者合起来才算一套评估体系。

## 为什么要分四层：答对不等于系统好

模型评估面对的是单次输出，比答案准不准就够了。Agent 是「多步决策 + 工具调用 + 环境交互」，同一个任务往往有多条正确路径，于是出现三种只有 Agent 才有的失真：最终答案对了但过程绕了十倍的路；答案对了但把 token 和外部接口配额烧穿；答案对了但中途越权调用了不该调的接口。只看最终答案，这三种问题全都看不见。

| 层次 | 核心指标 | 回答什么问题 |
| --- | --- | --- |
| 端到端效果 | 任务成功率、部分完成率、首次成功率、人工满意度、业务指标转化 | 任务到底做成了没有 |
| 过程质量 | 步骤效率、工具调用准确率、冗余率、错误恢复能力、重规划次数、循环与目标漂移 | 做成的方式是否合理 |
| 效率与成本 | token 消耗（输入/输出分开）、单任务成本、端到端延迟 P50/P95/P99、工具调用的外部成本 | 这次成功值不值 |
| 安全与鲁棒性 | 越权与被拒调用次数、提示注入命中率、敏感信息泄露率、对抗样本下的性能下降幅度、故障恢复率 | 出问题时会不会造成伤害 |

## 端到端效果与过程质量：结果和过程都要评

端到端的核心指标是**任务成功率**，判定必须用客观标准——检查最终状态、关键产物、数据库里的实际变化，而不是让模型自述「我完成了」。配套指标包括**部分完成率**（长任务的分步达成情况）、**首次成功率**、**人工满意度**、以及**业务指标转化**（Agent 带来的实际业务价值）。

过程质量是 Agent 特有的一层，也是最容易被忽略的一层，具体看六项：

- **步骤效率**：完成任务的实际步数对比理想步数，差得越多说明规划越差；
- **工具调用准确率**：是否选对工具、参数是否正确、无效调用的比例有多高；
- **冗余率**：重复动作、无效绕路占了多少；
- **错误恢复能力**：工具报错后能否自行纠正，而不是原样重试；
- **重规划次数**：一条路走不通时，换方案的频率与代价；
- **是否出现循环或目标漂移**：绕回同一步，或者做着做着偏离了原始目标。

成功率相同的两个系统，过程指标可能完全不同，而过程指标才是下一步优化的入口。

## 效率与成本：只看成功率会低估优化价值

成本这一层容易被当成附属项，其实它经常是选型的决定性一票。要分开统计的是：**token 消耗**（输入与输出分开，输入涨多半是上下文管理有问题，输出涨多半是啰嗦或反复重试）、**单任务成本**、**端到端延迟**（看 P50/P95/P99，平均值会掩盖长尾）、以及**工具调用的外部成本**（数据库查询、第三方 API 配额这类不体现在 token 上的开销）。

这里的判断很直接：**只看成功率会低估优化价值**——同样 80% 的成功率，一个用 10 次调用换来，一个用 2 次调用换来，是完全不同的两个系统。

安全与鲁棒性则是成功率之外的兜底项，指标包括**越权调用与被拒调用次数**、**提示注入命中率**、**敏感信息泄露率**、**对抗样本下的性能下降幅度**、以及**故障恢复率**（依赖不可用时的降级表现）。这层不达标，前几层的分数再高也不敢上线。

## 方法一：固定任务集加客观判定器

这是最基础也最必要的一层：构建**固定任务集 + 客观判定器**，让「有没有做成」变成一个可执行断言，而不是一段人工评论。

要点有四条：

- 任务要**覆盖难度分层**：简单、中等、长程、多模态、边界各占一部分，避免用简单题刷出漂亮总分；
- 每条任务要有**明确的 pass/fail 判定规则**，写成可执行检查；
- 要有**对抗与陷阱样本**：含歧义的问题、缺失的信息、恶意内容；
- **必须多次采样取均值并给置信区间**，因为模型输出有随机性，单次结果没有统计意义。

一个任务用例大致长这样，判定逻辑全在 checks 里，不依赖模型自述：

```json
{
  "id": "long-task-07",
  "input": "（任务描述）",
  "checks": [
    { "type": "final_state", "expect": "订单状态为已退款" },
    { "type": "tool_sequence", "allow": ["query_order", "refund"], "forbid": ["delete_order"] },
    { "type": "step_budget", "maxSteps": 6 }
  ],
  "samples": 5
}
```

## 方法二：LLM-as-judge，重点是控偏差

开放式输出（文案、方案、解释是否到位）没有唯一答案，只能让模型来打分。真正难的不是打分这个动作，而是让打分不带偏。必须做的控制有五件：

- 用**成对比较而非绝对打分**，相对判断比绝对分数稳定得多；
- **交换顺序后复测**，检验并抵消**位置偏差**；
- judge 用**与被评模型不同厂商**的模型，规避**自我偏好**；
- 维护**人工标注的黄金集**持续校准 judge，并监控 judge 与人的一致率；
- **剥离格式**（标题、加粗、Markdown 结构）再评，规避**长度与格式偏差**。

结论要写清楚：**judge 是辅助手段，不能作为唯一依据**，它适合做排序和粗筛，不适合当发布门禁的唯一裁判。

## 方法三与方法四：轨迹评估、线上指标加故障注入

轨迹评估看的不只是最终答案，还有整个执行**过程**。三种做法：**规则校验**（步骤是否符合约束，比如禁止的动作有没有出现）、**反事实消融**（删掉某一步重跑，看结果是否变化，用来判断这一步到底有没有贡献）、以及**过程奖励模型（PRM）** 给中间步骤打分。轨迹评估的价值在于定位「哪一步错了」，而端到端指标只能告诉你「整体错了」。

线上方法看真实分布：成功率、延迟、成本、用户反馈、放弃率，这些是离线任务集替代不了的。同时配合**故障注入**——人为制造工具失败、依赖超时、上下文超限、模型异常，检验系统是真的降级了，还是直接崩掉。只有正常路径的评测，等于没测鲁棒性。

## 可信度工程与落地顺序

评测结果要可信，先处理**评测污染**：测试集泄漏进了训练语料、提示词里的少样本示例、或者检索索引里。对策是用**私有保留集做发布判定**、**时间切分**（测试样本晚于训练截止时间）、对训练语料做**去污染清洗**、并持续监控**公开集与私有集的分数差**。同时**预先登记评测协议与主指标**，防止事后挑选好看的那个指标。

还有一条容易被忽略的原则：**评估必须与线上目标对齐**。如果线上要的是「减少人工介入」，离线就该评「无需人工即可完成的任务比例」，而不是评回答的流畅度。**离线指标与线上指标不一致时，离线优化就是白做。**

落地顺序建议分三步：先建**小而硬的任务集**（几十道有明确答案的题）加**客观判定器**，把成功率与步数监控跑起来；再补**过程指标**与 **judge 校准**；最后做**红队与故障注入**。**不要一上来就追求完美的评估体系**——有一个能跑的基线，比有一个完美的设计更有价值。

## 常见追问

**问：任务成功率怎么才算客观判定？**
**答：** 用外部断言检查最终状态和关键产物，比如数据库里的记录、生成的文件、接口的返回，而不是让模型自述完成；长任务再用部分完成率兜住中间进度。

**问：为什么不直接全用人工评分？**
**答：** 人工成本高、没法高频回归，而且不同标注人的口径也不一致。人工更适合用来建黄金集、校准 judge，不适合当日常回归的主力。

**问：judge 分数高就说明 Agent 好吗？**
**答：** 不能这么推。judge 只看得到它被喂进去的输出和轨迹，本身还有位置、长度、自我偏好等偏差，必须和客观判定器、人工黄金集交叉验证后才能作为参考。

**问：离线分数涨了，线上没变化，问题出在哪？**
**答：** 最常见的是离线任务集和线上目标不一致，或者被测任务的分布不同；其次是评测污染。先对齐「线上真正优化的那个量」，再排查污染。

## 易错点

- 让模型自述「任务已完成」：这是最典型的假成功率，必须用外部可执行的判定器检查最终状态。
- 只报成功率、不报步数和成本：10 次调用换来的成功和 2 次调用换来的成功，不是同一个系统。
- 只测正常路径，不测失败路径：不注入工具失败、超时、上下文超限，就不知道系统是会降级还是会崩。
- 在测试集上反复调优直到分数好看：分数是被调出来的，属于自我污染，应该预先登记主指标，并用私有保留集做发布判定。

## 一句话记住

:::tip
先有客观判定器算成功率，再谈过程与成本指标；离线评测必须与线上目标一致。
:::
