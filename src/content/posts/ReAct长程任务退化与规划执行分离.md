ReAct 在长程任务上会退化，根因是它把思考和动作交织在同一条轨迹里，上下文既是记忆又是任务状态又是通信媒介，步数一多就必然出现上下文污染、错误级联、目标漂移和预算耗尽四类问题，而且完成与否只能靠模型自述。稳定的解法是把规划与执行解耦：规划器只维护目标、子任务依赖和验收标准，执行器只接收当前子任务的必要信息并返回结构化摘要，任务状态外置到存储，验收交给外部程序而不是模型自己。

## 为什么单条 ReAct 轨迹扛不住长程任务

ReAct 的原始形态是一问一答的短链条：模型交替产出思考和动作，环境返回 observation，所有这些拼回同一个 prompt 进入下一步。上下文里因此同时堆着目标、历史思考、历史动作、历史观测、中间产物和失败尝试，它们没有任何隔离手段。

- 上下文长度随步数单调增长，但其中有效信息的占比在下降，噪声占比在上升。
- 任务状态与对话历史绑死，任何一次摘要压缩都会连带损伤任务进度。
- 没有独立于对话的状态存储，重试和回滚只能靠重述历史。
- 没有独立的验收通道，"做完了"只能由执行模型自己宣布。

这四条合起来决定了：任务一旦长到几十步，单条轨迹的表现就会持续往下走，问题不在模型能力，而在承载结构。

## 四类退化是怎么发生的

长程任务里这四类退化往往同时出现，并且互相放大。

| 退化类型 | 触发机制 | 直接后果 |
| --- | --- | --- |
| 上下文污染 | 冗长的历史 observation、失败尝试和工具返回不断堆积，噪声把目标信息稀释掉 | 注意力被拉散，单步推理质量下降 |
| 错误级联 | 某一步的错误观测成为后续所有推理的前提，模型认知与环境事实逐渐脱节 | 错误被逐步固化、放大，越走越偏 |
| 目标漂移 | 长链条中模型只盯着当前局部子目标，逐渐忘掉原始目标和约束 | 子任务都完成了，却偏离了总目标 |
| 记忆与预算受限 | 窗口到达上限后早期关键信息被截断或被粗暴摘要；每步重述全量历史让成本和延迟随步数线性甚至超线性增长 | 失去全局进度感，同时逼近成本上限 |

还有一条容易被忽略：ReAct 缺少外部验证，完成与否基本靠模型自述，一旦早期自评出错，后面每一步都建立在错误前提上。这条正是错误级联最常见的起点。

## 解耦之后两者各自拥有什么

规划与执行分离的核心思路只有一句：让规划和执行各自拥有独立的上下文、独立的模型预算，并且都能被外部验证。拆开之后，脏 observation 只进执行器的局部上下文，进不了规划器的视野；执行器的自我声明也不直接推进状态，必须过验收关。

```text
plan  = [子任务1, 子任务2, ...]      # 每项带依赖关系和可判定的验收条件
state = { 已完成: [], 产物: {}, 进度摘要: "" }

while plan 未空 and 未超预算:
    task   = 取出一个依赖已满足的子任务
    ctx    = 当前子任务必要信息 + 进度摘要      # 不带全量历史
    result = 执行器(ctx, 预算上限=task.limit)
    ok     = 外部验收(task.验收条件, result)     # 程序化校验优先
    state  = 更新状态(task, result, ok)
    plan   = 只重规划受影响的子树(task, ok)
```

## 要点一：层次化分解与上下文隔离

高层规划器只负责拆解目标、维护子任务依赖图和验收标准，它不直接接触原始的脏乱 observation。执行器每次只接收当前子任务的必要信息和明确指令，执行完返回结构化摘要，规划器只接收这些契约化的结果。

这样切断的是噪声扩散的链路：一次工具调用返回的大段日志只污染那一个子任务的上下文，子任务结束就被压缩成一行结论，不会再影响后续几十步的决策。

## 要点二：用外部状态替代对话历史

任务树、子任务状态机、已完成产物统一存放在外部存储或文件系统里，上下文里只保留引用和进度摘要。

- 长程记忆不再受窗口长度限制，需要细节时按引用回查，而不是把全部历史塞回去。
- 状态可以被程序读写，因此可以被检查、被回滚、被并发更新。
- 换个执行模型甚至换个人接手，都能从外部状态继续跑。

## 要点三：外部验收替代模型自评

每个子任务都带有可判定的完成契约，优先使用程序化校验，比如运行测试、检查接口返回、校验数据约束；无法程序化判定时，再引入独立的验证模型或规则。

规划器依据验证结果而不是执行器的自我声明来推进状态，这是抑制错误级联最关键的一环。模型自评的问题不在于它一定说错，而在于它错了也没有任何机制能发现。

## 要点四：局部化重规划与失败恢复

为每个子任务设置检查点和幂等语义，失败时只重规划受影响的子树，而不是把全局重跑一遍。同时配合失败分类：

- 可重试错误：超时、限流、瞬时抖动，原样重试并做退避。
- 需要重规划的逻辑错误：子任务本身拆错了或验收条件写错了，回到规划器改子树。
- 不可恢复错误：前置条件不成立，直接中止并把原因写进外部状态。

不分类的后果是两种极端：一种是无脑重试陷进无效循环，另一种是一有小错就推翻全局重来。

## 要点五：预算与停止条件

为每个子任务和整体任务都设定步数、token 和时间的硬上限与软上限，并定义清晰的完成判据，防止无限循环。

硬上限负责兜底，触到就中止并把现场落盘；软上限负责提醒，到线后规划器要显式决策是继续、降级还是收尾。只有硬上限没有软上限，系统会在触线那一刻被直接砍断，既没有收尾决策也留不下现场。

## 要点六：模型分工与并行执行

规划属于高价值低频任务，适合推理能力更强的模型并配合思维链；执行往往是高频重复的，可以下发给更轻量更快的模型，从而在成本和稳定性之间取得平衡。

依赖图上互不冲突的子任务可以并行执行，既能压缩总步数，也能减少每个执行分支的上下文长度。并行时要注意写冲突：共享产物要么做分区，要么在合并点统一处理。

## 常见追问：拆分的边界在哪

- **问：所有任务都要拆成规划和执行两段吗？** 不必。任务步数短、反馈即时、错误代价低的场景，单条 ReAct 反而更简单也更省延迟。拆分解决的是长程、状态多、错误会级联的问题。
- **问：规划器怎么知道执行器做得对不对？** 靠子任务自带的验收契约，优先是程序化校验（测试、接口返回、数据约束），程序化判不了才上独立验证模型。绝不采信执行器的自我声明。
- **问：上下文隔离会不会让执行器缺信息？** 会缺冗余信息，不能缺必要信息。做法是让规划器显式写出这一步需要哪些输入，按需注入，而不是把整段历史丢过去。
- **问：规划器自己会不会漂移？** 会。所以原始目标、约束和验收标准要放在外部状态里反复回读，规划器每一轮都对着它们复核，而不是对着自己上一轮的措辞复核。

## 易错点：把解耦当成换提示词

- 只把 prompt 拆成两个角色，状态还是存在对话历史里。这只是换了说法，上下文污染和预算问题一个都没解决，真正的解耦必须配外部状态和外部验收。
- 让执行器自己判断是否完成。执行器天然倾向于报告成功，缺少独立验收时错误级联照样发生。
- 一出错就全量重跑。没有检查点和幂等语义，重跑既贵又会丢掉已经验证过的中间结果。
- 只设硬上限不设软上限。触到硬上限时任务是被砍断的，没有收尾决策也没有现场留存。

## 一句话记住

:::tip
规划器管目标和验收，执行器只管一个子任务，状态外置、验收外部化。
:::
