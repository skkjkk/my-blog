`start()` 和 `run()` 的分界线就是「有没有真的开出新线程」。`start()` 先做线程状态检查，再通过本地方法让 JVM 创建一条新线程，由这条新线程去执行 `run()`，它自己立即返回，调用方继续往下走；`run()` 只是一个普通的实例方法，谁调用它就在谁的线程里同步执行，不产生任何新线程，也没有异步效果。所以 `run()` 定义的是任务内容，`start()` 才是真正开启并发的那个开关。

## 两个方法各自做了什么

`start()` 的第一件事是校验线程状态：只有还没启动过（NEW）的线程才允许启动，否则直接抛 `IllegalThreadStateException`。校验通过后它调用内部的本地方法，把「创建一条操作系统线程」这件事交给 JVM，新线程随后进入就绪状态等待调度，拿到 CPU 后回调自己的 `run()`。整个过程对调用方来说是异步的，`start()` 不会等 `run()` 跑完才返回。

`run()` 则是 `Thread` 类里一个普通的方法，方法体就是留给子类重写或者由构造时传入的任务对象来实现的内容。它没有任何状态校验，也没有调用次数限制，执行效果完全等于一次普通方法调用：压一个新栈帧到当前线程上，跑完再返回。真正决定「在哪条线程上跑」的从来不是 `run()` 自己，而是调用它的那条线程。

## 为什么非要把任务和线程拆成两个方法

`Thread` 里 `run()` 的默认实现是把调用转交给构造时传入的 `Runnable` 目标对象，也就是说 `run()` 的职责被明确限定为「描述要做什么」，而 `start()` 单独负责「找一条线程来做」。这种拆分让同一份任务可以被不同的线程对象甚至线程池复用，也让「任务」这个概念可以脱离 `Thread` 继承体系独立存在。

反过来看，如果只有 `run()`，就没有启动并发的入口；如果只有 `start()`，任务内容无处安放。两个方法的分工，正是把「任务描述」和「线程调度」这两件本来可以独立演化的事情解耦。

## 关键差别一览

| 对比项 | `start()` | `run()` |
| --- | --- | --- |
| 是否创建新线程 | 是，交给 JVM 创建 | 否，完全不开线程 |
| 代码在哪个线程执行 | 新建的那条线程 | 调用它的那条线程 |
| 调用后是否阻塞调用方 | 否，立即返回 | 是，同步执行完才返回 |
| 能否重复调用 | 只能一次，第二次抛 `IllegalThreadStateException` | 可以任意次调用 |
| 能否被子类重写 | 不能，是 `final` 方法 | 能，本来就是设计给子类重写的 |
| 主要职责 | 启动线程、参与调度 | 定义任务内容 |

## 关键要点

- **`start()` 才开线程**：它向 JVM 申请创建新线程，由新线程执行 `run()`，调用后立即返回，主线程继续往下走。
- **`run()` 就是普通方法**：谁调用就在谁的线程里同步执行，不产生新线程、没有异步效果，多线程的并发收益一点都拿不到。
- **`start()` 只能调一次**：线程状态一旦离开 NEW 就不能再启动，重复调用抛 `IllegalThreadStateException`；`run()` 没有这个限制。
- **`start()` 是 `final`**：它涉及线程启动的底层逻辑，不允许重写；`run()` 是留给子类实现任务内容的扩展点。
- **任务与启动分离**：`run()` 描述做什么，`start()` 负责什么时候、在哪条线程上做，这也是 `Runnable` 加线程池能替代继承 `Thread` 的原因。

## 代码示例

```java
public class StartVsRun {
    public static void main(String[] args) {
        Thread t = new Thread(() ->
                System.out.println("跑在：" + Thread.currentThread().getName()));

        // 错误用法：直接调 run()，等同于一次普通方法调用
        t.run();      // 输出「跑在：main」

        // 正确用法：start() 才会创建新线程，任务在新线程里执行
        t.start();    // 输出「跑在：Thread-0」

        // t.start(); // 再来一次会抛 IllegalThreadStateException
    }
}
```

两次输出的线程名不一样，就是这段代码全部的说服力：`t.run()` 里打印的仍然是 `main`，说明它只是被主线程顺手调用了一下；`t.start()` 之后才出现新的线程名。注释掉的那一行说明线程对象是一次性的，启动过一次就作废，想再跑一遍只能新建线程对象，或者干脆交给线程池。

## 常见追问

**Q：既然 `run()` 里的代码也能执行，为什么不能直接调它？**
A：能执行，但没有任何并发。直接调 `run()` 只是主线程多压了一层栈帧，`run()` 里耗时多久主线程就阻塞多久，`Thread` 对象白创建了。面试里说「直接调 run 等于没用多线程」，就是这个意思。

**Q：`start()` 调两次会怎样，能不能复用线程对象？**
A：第二次抛 `IllegalThreadStateException`，因为线程状态已经不是 NEW 了。`Thread` 对象不可重启，需要再跑一次任务就新建线程对象；真实项目里更常见的做法是把任务交给线程池，由池子管理线程的复用。

**Q：为什么 `start()` 是 `final`，`run()` 却允许重写？**
A：`start()` 承载的是「创建线程并让其进入调度」这套 JVM 层面的约定，允许重写就可能绕过状态校验、把线程状态搞乱；`run()` 只是任务内容的入口，本来就该由子类或 `Runnable` 填充，所以开放重写。

**Q：`start()` 之后还能再调用 `run()` 吗？**
A：可以，`run()` 不看线程状态。但那时它只是在你当前调用的线程上又跑了一遍任务方法，和那条已经启动的线程毫无关系，通常会带来重复执行和状态错乱。

## 易错点

- **以为调了 `run()` 就是多线程**：错。线程数还是 1，`run()` 内的耗时操作会原样阻塞调用方，这是初学者最常见的一处。
- **以为 `start()` 会立刻执行 `run()`**：不对。`start()` 只是让新线程进入就绪状态，什么时候真正拿到 CPU 由调度器决定，所以启动顺序不等于执行顺序。
- **以为线程对象可以重复 `start()`**：错。第二次必然抛 `IllegalThreadStateException`，想重复执行得新建对象或用线程池。
- **重写 `run()` 时顺手把 `start()` 也「重写」**：`start()` 是 `final`，编译器直接拦下；真正该做的是重写 `run()`，或者干脆用 `Runnable` 加 `Thread` 组合。

## 一句话记住

:::tip
**`run()` 是任务内容，`start()` 是启动开关：一个同步执行，一个异步开线程。**
:::
