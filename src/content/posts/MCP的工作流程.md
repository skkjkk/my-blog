MCP 的工作流程可以按"**一次工具调用**"和"**一次完整会话**"两个尺度来看。一次完整会话是：Client 与 Server 建立传输通道，`initialize` 完成**能力协商**，`tools/list` 等接口**动态发现工具**，会话结束时显式关闭。一次工具调用则是：Host 把工具目录交给模型，模型返回结构化的 `tool_call`，Client 先做本地校验，再经 **JSON-RPC** 发 `tools/call`，Server 真正执行，结果回填后模型继续推理，**直到模型不再返回 tool_call**。

## 建立连接与能力协商

Client 启动后先与 Server 建立传输通道：本地场景用 **stdio**，跨网络部署用 **SSE / Streamable HTTP**。通道建好后，Client 发起 `initialize` 请求，双方交换**协议版本**与**能力声明**——Client 声明自己支持哪些特性，Server 返回自己支持哪些，这一步就是**能力协商**。协商结果决定了后续哪些方法可用，这也是协议能向前兼容演进的关键：新特性只对声明过的一方启用，老客户端不会被新字段打断。

## 能力发现：工具目录是拉出来的

协商完成后，Client 依次调用 `tools/list`、`resources/list`、`prompts/list`：前者拿到工具目录（含名称、描述、参数 JSON Schema），后两者分别拿到可读资源与提示模板。**工具是动态发现的**——Server 侧新增一个工具，客户端无需改代码，重新拉取目录就能看到。所以工具目录属于"运行时数据"，不是写死在客户端里的常量。

## Host 组装提示与模型决策

Host 是用户实际交互的应用，它先把工具目录整理成模型能理解的格式，随请求一起发给模型。**这一步是 MCP 与 Function Calling 的结合点**——MCP 提供工具定义，模型接口负责结构化表达调用意图。模型判断需要调用工具时，返回**结构化的 tool_call**（工具名 + JSON 参数）。注意：**模型不执行任何动作**，它只产出"我想调哪个工具、传什么参数"这段结构化数据。

## 调用执行：Client 校验后转给 Server

Client 收到 tool_call 后，**先做本地校验**（参数是否符合 schema），再通过 **JSON-RPC** 向 Server 发送 `tools/call` 请求。Server 在这里**真正执行**这个动作——访问数据库、调外部 API、读写文件。三方的边界很清楚：模型只表达意图，Client 负责转发与校验，带副作用的操作全部发生在 Server 侧。

## 结果回填与继续迭代

Server 返回执行结果（成功数据或错误信息），Client 把它按 `tool_call_id` 组织成 tool 消息，追加进消息列表，回传给 Host。**关键做法：失败也要把可诊断的错误回传**，别把异常吞掉，这样模型才能读到错误原因并自我纠正。模型基于结果继续推理，可能再调工具（多轮），也可能直接给出最终答案；**当模型不再返回 tool_call 时，一轮工具调用就结束了**。

## 一次完整时序

```
Host 决定使用某 Server
  → Client 建立连接 + initialize（能力协商）
  → Client tools/list（动态发现）
  → Host 组装提示（工具目录 + 用户输入）→ 模型
  → 模型返回 tool_call
  → Client 校验参数 → JSON-RPC tools/call → Server
  → Server 真正执行 → 返回结果
  → Client 回填 tool 消息 → 模型
  → 模型给出最终答案（循环结束）
```

两个尺度的区别可以对照着看：

| 尺度 | 起点 | 主要对象 | 结束标志 |
| --- | --- | --- | --- |
| 一次完整会话 | Client 建立传输通道 | 连接、能力协商、工具发现 | 会话显式关闭 |
| 一次工具调用 | 模型返回 tool_call | 校验、`tools/call`、结果回填 | 模型不再返回 tool_call |

## 反向通道：Sampling 与 Roots

协议不只允许 Client 调 Server，也允许 Server 反过来请求 Client，这是常被忽略的一半：

- **Sampling**：Server 请求 Client 代为调用 LLM，Server 无需自带模型即可获得智能能力。
- **Roots**：Server 请求 Client 暴露文件系统等上下文根目录，用于明确自己的操作范围。

**这两者体现了 MCP 的双向性**——它是一套双向的会话协议，而不是单向的"客户端调工具"。

## 会话关闭与资源释放

会话结束时要**显式关闭**，Server 侧的临时状态随之清理，例如订阅与缓存。这些状态只在本次会话内有效，不显式关闭就会一直被 Server 持有，连接和订阅都释放不掉。工程上把关闭放在连接的生命周期钩子里，比依赖进程退出更可靠。

## 工程上要注意的三点

- **Server 侧要做数据清洗**：把原始数据裁剪成适合模型消费的形式，这是 MCP Server 的核心价值之一，不是把上游接口原样透出。
- **认证只在远程部署时需要**：本地 stdio 靠进程边界隔离，走 SSE / Streamable HTTP 的远程 Server 才需要补认证与授权。
- **错误语义要标准化**：不同 Server 的错误表达方式不同，Client 侧要有归一化层，否则模型无法从错误中学习。

## 常见追问

**Q：每次请求都要调 `tools/list` 吗？**
A：不必，一次会话内拉一次即可，目录可以缓存；Server 侧工具变了要重新拉取才可见。

**Q：MCP Server 是不是就是把一堆 API 包一层？**
A：不是。它的核心价值之一是把原始数据清洗、裁剪成适合模型消费的形式，而不是把上游接口原样透出。

**Q：模型都按 schema 生成参数了，Client 为什么还要再校验一次？**
A：schema 只能约束格式，模型输出是概率性的，本地校验能拦住明显不合法的调用，避免无效请求打到 Server。

**Q：Host、Client、Server 三者谁在干活？**
A：Host 组装提示并管界面，Client 维护与 Server 的会话、转发 JSON-RPC，Server 真正执行副作用；模型只负责决策。

## 易错点

- **把"模型调用工具"当成模型在执行**：模型只产出 tool_call，执行发生在 Server 侧，正确说法是"模型表达调用意图，Client 转发，Server 执行"。
- **以为工具目录是写死的**：工具由 `tools/list` 动态发现，Server 加工具客户端不用改代码。
- **只回传成功结果、把错误吞掉**：失败也要把可诊断的错误回传，否则模型无法自我纠正，只会反复重试同样的错。
- **以为本地 stdio 也要配认证**：认证只在远程部署时需要，本地靠进程边界隔离。

## 一句话记住

:::tip
Client 负责协商与转发，模型只出 tool_call，Server 才是真正执行的一方。
:::
