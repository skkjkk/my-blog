SQL 调优是一个**自上而下**的过程，顺序很重要：先用慢查询日志和 `pt-query-digest` 定位最消耗资源的 SQL，再用 `EXPLAIN` 看清访问路径，然后才谈加索引、改 SQL，最后才考虑调参数、改 schema 与架构。顺序颠倒了，要么把时间花在不痛不痒的语句上，要么用「加个索引」掩盖真正的写法问题。

## 先定位问题，别盲改

开启慢查询日志（`slow_query_log`）和 `performance_schema`，用 `pt-query-digest` 把慢日志做归类统计，拿到**消耗资源最多的 top SQL** 列表。调优的收益高度集中在少数几条 SQL 上，优化不痛不痒的语句没有意义。

排序时不要只看「单次最慢」。一条单次耗时不高、但每秒调用上千次的语句，累计消耗常常更大：先按**总耗时**排一遍，再按**执行次数**和**扫描行数**各看一遍，才知道该动哪一条。

## 看执行计划，把「慢」落到具体算子

用 `EXPLAIN` 或 `EXPLAIN ANALYZE` 分析具体的访问路径，这一步是所有优化的起点。要回答的其实是四个问题：是全表扫描吗（`type` 出现 `ALL`）、索引失效了吗（`key` 为 `NULL`，或预估 `rows` 远大于实际返回行数）、有没有额外的排序与临时表（`Extra` 出现 `Using filesort`、`Using temporary`）、join 顺序对不对（驱动表选错时，被驱动表会走 `Using join buffer`）。

`EXPLAIN` 给的是优化器的估算，`EXPLAIN ANALYZE` 会真正执行并给出实际耗时与实际行数；两者偏差大，通常说明统计信息过期或优化器选错了索引。

```sql
EXPLAIN ANALYZE
SELECT id, title, created_at
FROM orders
WHERE user_id = 10086
  AND status = 1
ORDER BY created_at DESC
LIMIT 20;
```

这条 SQL 要验证的是：`user_id` 和 `status` 有没有走联合索引，`created_at` 的排序能不能顺着索引顺序出来而不再出现 `Using filesort`。

## 索引优化：收益最高的一步

原则是**为查询条件建立合适的索引**，几条硬要求：

- **区分度高的列才值得做索引**：性别、状态这类只有几个取值的列，建了也筛不掉多少行。
- **联合索引遵循最左前缀匹配**：`(a, b, c)` 能服务 `a`、`a,b`、`a,b,c`，跳过 `a` 只查 `b` 就用不上。
- **索引列上不要做函数运算，也不要让类型发生隐式转换**：`WHERE DATE(created_at) = '...'`，或者拿数字去比较 `varchar` 列，索引会直接失效。
- **避免以 `%` 开头的模糊匹配**：`LIKE '%关键字'` 用不上 B+ 树的有序性，只能扫。
- **用覆盖索引减少回表**：查询用到的列都在索引里，就不必再回主键索引取一次整行。

## 改写 SQL

同样的语义，换一种写法执行路径可能完全不同：

- **大表 join 小表时让小表作驱动表**：小结果集驱动、被驱动表走索引，避免大表被反复扫描。
- **用 `UNION ALL` 替代 `UNION`**：`UNION` 要额外做去重排序，两边结果确定不重复时这份开销纯属浪费。
- **`NOT IN`、`NOT EXISTS` 换成更适合的写法**：`NOT IN` 的子查询结果里只要有 `NULL`，整个条件就查不出任何行，这种情况用 `NOT EXISTS` 或 `LEFT JOIN ... IS NULL` 更稳。
- **避免 `SELECT *`**：少传无用列，也更容易做成覆盖索引。
- **把复杂查询拆成多条简单查询**：有时比一条巨型 SQL 扫描的行数更少。

| 写法 | 代价 | 更省的做法 |
| --- | --- | --- |
| `UNION` 合并两个已知不重复的结果 | 多一次去重排序 | 换成 `UNION ALL` |
| 大表驱动小表 join | 大表被反复扫描 | 小表作驱动表，大表走索引 |
| `SELECT *` 取全部列 | 多传数据，多半还要回表 | 只取需要的列，凑成覆盖索引 |

## 控制查询规模与存储参数

查询侧先把「一次要处理多少行」压下来：深分页用**延迟关联**（先在索引上定位主键 id，再 join 回表取详情）替代大 offset 的 `LIMIT`；用 `LIMIT` 限制返回行数，别让接口一次拉走整张表；大批量写入要**分批提交**，避免大事务导致锁持有时间变长、binlog 膨胀。

存储与参数侧：选择合适的存储引擎（InnoDB 支持事务与行锁）；把 `innodb_buffer_pool_size` 调到能让索引和热点数据常驻内存的规模，减少磁盘读；在可以接受持久性损失时调整 `innodb_flush_log_at_trx_commit` 提升写入性能；数据按时间或维度做分区，让查询能裁剪掉不相关的分区。

## schema、架构与事务边界

schema 层：避免过度范式导致一条查询要 join 十几张表，必要的冗余字段可以换取查询性能。架构层：读写分离把查询压力分流到从库，但要处理**主从延迟**导致的读不到最新数据；引入缓存（Redis）扛住热点读；单表数据量过大时做分库分表水平拆分。

事务与锁单独看：缩短事务持有锁的时间，把大事务拆小；避免在事务中做远程调用，外部接口一慢锁就一直不放；统一访问顺序减少死锁；使用间隙锁时先评估影响范围，范围条件实际加锁的区间往往比想象的宽。

## 优化后必须量化验证

用 `pt-query-digest`、慢查询日志、`EXPLAIN ANALYZE` 和压测对比优化前后的**耗时、扫描行数、逻辑读**，而不是凭感觉判断「应该快了」。优化完必须回归验证：新加的索引可能把写入拖慢，也可能让优化器换了执行计划，把另一条原本正常的 SQL 变慢。

## 常见追问

**Q：加了索引为什么还是慢？**
A：先看 `EXPLAIN` 里的 `key` 和 `rows`。索引可能根本没被用上（函数运算、隐式转换、`%` 前缀、不满足最左前缀），也可能用上了但选择性太差、回表太多，这时要考虑调整索引列顺序或做成覆盖索引。

**Q：深分页 `LIMIT 1000000, 20` 怎么优化？**
A：延迟关联，先用覆盖索引把主键 id 查出来，再按 id 回表取详情；或者改成游标分页，记住上一页最后一条的排序值，用 `WHERE id > ?` 往下翻，避免扫描并丢弃前面的大量行。

**Q：是不是所有慢 SQL 都能靠加索引解决？**
A：不是。索引只解决「按条件找行」的效率；要扫的行本来就多、循环里查库这类 N+1、锁等待、返回数据本身太大，加索引都不解决，索引加多了还会拖慢写入、占用 buffer pool。

**Q：这些手段的优先级怎么排？**
A：先用慢日志锁定最耗资源的那几条，再按「改索引、改 SQL → 控制查询规模 → 参数与存储 → schema 与架构」推进，越往后的手段成本越高、副作用越多。

## 易错点

- **「慢就是缺索引」**：不一定。先比一比扫描行数与返回行数的比值，比值接近 1 说明索引其实是有效的，慢因在别处。
- **把 `EXPLAIN` 的预估行数当成实际行数**：那是优化器的估算，偏差大就用 `EXPLAIN ANALYZE` 看真实执行数据。
- **无脑把 `UNION` 换成 `UNION ALL`**：两边可能重复、业务又要求去重时，换完会多出重复行。
- **索引建得越多越好**：每个索引都要在写入时维护，还占内存，低区分度列上的独立索引基本是负收益。

## 一句话记住

:::tip
先 EXPLAIN 看清路径，再改索引与 SQL，最后才动参数和架构。
:::
