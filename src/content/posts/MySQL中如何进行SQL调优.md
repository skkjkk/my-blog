SQL 调优是一个**自上而下**的过程，顺序很重要：先看执行计划找问题，再改 SQL 或索引，最后才考虑改架构。常见的手段有以下几类。

1) **先定位问题，别盲改**。开启慢查询日志（`slow_query_log`）和 `performance_schema`，用 `pt-query-digest` 做归类统计，拿到**消耗资源最多的 top SQL** 列表。调优的收益高度集中在少数几条 SQL 上，优化不痛不痒的语句没有意义。

2) **看执行计划**。用 `EXPLAIN` 或 `EXPLAIN ANALYZE` 分析具体的访问路径，定位是全表扫描、索引失效、排序临时表还是 join 顺序不对。这是所有优化的起点。

3) **索引优化**。这是收益最高的手段。原则是**为查询条件建立合适的索引**：区分度高的列适合做索引，联合索引要遵循**最左前缀匹配**，避免对索引列做函数运算或类型隐式转换（那会让索引直接失效），避免以 `%` 开头的模糊匹配，用覆盖索引减少回表。

4) **改写 SQL**。包括：把大表 join 小表时让小表作驱动表；用 `UNION ALL` 替代 `UNION` 去掉去重开销；把 `NOT IN`、`NOT EXISTS` 改成更适合的写法；避免 `SELECT *` 减少无用列传输与回表；把复杂查询拆成多条简单查询，减少全表扫描次数。

5) **控制查询规模**。深分页用**延迟关联**（先在索引上定位 id 再 join 回表）替代大 offset；大批量写入分批提交，避免大事务导致锁与 binlog 膨胀；用 `LIMIT` 限制返回行数。

6) **调整存储与参数**。选择合适的存储引擎（InnoDB 支持事务与行锁），合理设置 `buffer_pool` 大小让索引和热点数据常驻内存，调整 `innodb_flush_log_at_trx_commit` 在可接受持久性损失时提升写入性能。分区表可用于按时间或维度裁剪扫描范围。

7) **schema 设计与架构层面**。避免过度范式导致的过多 join，必要的冗余字段可以换取查询性能；读写分离把查询压力分流到从库；引入缓存（Redis）扛住热点读；分库分表在单表数据量过大时做水平拆分。注意读写分离带来的主从延迟问题。

8) **事务与锁的优化**。缩短事务持有锁的时间，把大事务拆小；避免在事务中做远程调用；统一访问顺序减少死锁；使用间隙锁时评估影响范围。

9) **用工具做量化验证**。用 `pt-query-digest`、慢日志、`EXPLAIN ANALYZE` 和压测对比优化前后的**耗时、扫描行数、逻辑读**等指标，而不是凭感觉判断。优化完必须回归验证，防止新索引反而拖慢写入。
