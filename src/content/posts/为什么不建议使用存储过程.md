存储过程是一段**预编译并存储在数据库中的 SQL 逻辑**。它在单体/小系统中确有价值，但在现代（尤其是微服务与高并发）架构下**被普遍不推荐**。核心理由：**把业务逻辑放进数据库，换来的是可维护性、可扩展性与可观测性的全面下降。**

1) **⭐ 头号理由：业务逻辑与业务代码分离 → 可维护性崩塌**
业务规则一半在 Java、一半在数据库 → **改一个逻辑要同时改两个地方、两套发布流程、两套版本管理**。
> **表现**：需求变更时数据库逻辑改动无法灰度、无法单测、无法回滚，**只能靠数据库变更脚本上线**，风险与协调成本极高。

2) **⭐ 第二个理由：数据库成为性能瓶颈，无法独立扩容**
数据库通常是**单点、有状态、最难扩容**的组件；而**应用层可以无状态水平扩容**。
> **把业务逻辑放数据库 = 把 CPU 密集型计算压到最难扩容的地方。** 复杂逻辑在库里执行 → 数据库 CPU 打满 → **所有查询一起变慢**。

3) **⭐ 第三个理由：难以版本管理与灰度**
- 存储过程的变更**不受 Git 管理**（或依赖额外的迁移工具）
- **无法灰度**：数据库是共享状态，A 实例和 B 实例可能连着不同的库版本 → **行为不一致**
- **回滚困难**：回滚应用版本容易，**回滚数据库过程要单独处理**
> **这在多实例、多版本并存的灰度发布中是硬伤。**

4) **⭐ 第四个理由：可观测性与调试困难**
- **执行计划不透明**：存储过程内部发生了什么，只能靠慢日志看到整体耗时，**无法定位到内部哪一步慢**
- **难以做链路追踪**：APM 埋点通常在应用层，库内逻辑**成了监控盲区**
- **调试体验差**：不像应用代码有 IDE 断点、单元测试、代码审查

5) **⭐ 第五个理由：连接数放大（高并发下的致命问题）**
调用存储过程时**只占用一次连接**，但**过程内部的每条 SQL 都会独占连接资源** → 过程内做大量循环查询时，**单次调用就可能长时间占用连接** → **连接池被耗尽**。
> **应用层做循环查询会频繁释放连接（可复用），库内做则是长时间独占。** 在高并发下这是压垮连接池的常见原因。

6) **第六个理由：数据库选型绑定**
存储过程是**厂商特有语法**（T-SQL / PL/SQL / MySQL 存储过程），迁移到其他数据库（TiDB、OceanBase、PolarDB、云原生数据库）需要**重写**。
> **而应用层的 SQL 基本可跨库** → 用 SQL 规范（如 SQLAlchemy、JPA）即可保持可移植。

7) **第七个理由：安全与权限边界模糊**
- 存储过程里可能藏着**只有高权限才能执行的敏感操作**（改数据、读敏感表），但应用只需 `EXECUTE` 权限 → **权限模型失真**
- **难以审计**：无法精确知道是哪个业务调用了它、传了什么参数

8) **⭐ 什么时候存储过程仍然合理（不要一刀切）**
- **数据一致性要求极高、必须与写入同事务**的逻辑（如复杂的账务分摊、批量 ETL）
- **数据库内部的运维/统计任务**（定时汇总、清理归档）
- **遗留系统改造期的临时方案**
> **判断标准：如果这段逻辑是"数据处理"而非"业务决策"，放数据库里是合理的；如果是业务规则，就该留在应用层。**

9) **⭐ 面试答法建议**。三点：**① 核心矛盾（业务逻辑下沉到最难扩容、最难版本化的组件）；② 三个最硬的痛点（版本与灰度、连接数放大、数据库成为瓶颈不可独立扩容）；③ 给出边界判断（数据处理 vs 业务决策）+ 迁移时选型绑定**。**第二点的"连接数放大"是最容易被忽略但最能体现实战经验的点。**
