存储过程是一段**预编译并存储在数据库中的 SQL 对象**，它把一段逻辑搬到数据库进程里执行。在单体系统、小型系统里它确实有价值，但在现代（尤其是微服务与高并发）架构下**被普遍不推荐**，根本原因是把业务逻辑放进数据库，换来的是可维护性、可扩展性与可观测性的全面下降。面试时按「一条核心矛盾 + 三个最硬的痛点 + 一条边界判断」作答，就是完整答案。

## 头号理由：业务逻辑与业务代码分离，可维护性崩塌

业务规则一半写在 Java 应用里、一半写在数据库里，是最难维护的形态：

- **改一处逻辑要动两个地方**：应用代码一处、存储过程一处，两套发布流程、两套版本记录
- **无法灰度**：数据库逻辑的变更没有「先放百分之一流量」这种手段，只能整体切换
- **无法单测与代码审查**：存储过程很难纳入单元测试、Code Review 和静态检查，改错了没人拦得住
- **只能靠数据库变更脚本上线**：出问题时也无法像应用那样把版本切回去

:::caution
需求变更时，数据库逻辑的改动既不能灰度、又不能单测、也难回滚，只能靠变更脚本直接上线，**风险与协调成本都极高**。
:::

## 第二个理由：数据库成为性能瓶颈，无法独立扩容

数据库通常是**单点、有状态、最难扩容**的组件：想提性能往往只能升配，或者做分库分表。而**应用层是无状态的**，加机器就能水平扩展。

把复杂计算放进存储过程，等于**把 CPU 密集型的工作压到整个系统里最难扩容的地方**：过程里的循环、聚合、临时表都会消耗数据库 CPU，而这份 CPU 是所有业务共享的，**一处打满，所有查询一起变慢**。

:::tip
应用层加机器能线性扩容，数据库加机器几乎没有廉价办法，所以**把业务逻辑放进数据库，等于把扩容压力集中在最贵也最难扩的那一层**。
:::

## 第三个理由：难以版本管理与灰度

- **存储过程的定义不受 Git 管理**：没有 diff、没有 blame、没有提交历史，除非额外引入迁移工具才能勉强补上
- **无法灰度**：数据库是共享状态，A 实例和 B 实例可能连着不同版本的库，同一个接口在不同实例上**行为不一致**
- **回滚困难**：回滚应用版本只是换一个镜像，回滚存储过程要单独写逆向脚本，还要考虑已经写进去的数据
- **多环境漂移**：开发、测试、生产的存储过程版本很容易悄悄不一致，排查问题时先得确认「你那边是哪个版本」

:::tip
**这在多实例、多版本并存的灰度发布中是硬伤**：应用可以同时跑新旧两个版本，存储过程做不到。
:::

## 第四个理由：可观测性与调试困难

- **执行计划不透明**：慢日志只能看到整个调用的总耗时，**定位不到过程内部究竟哪一步慢**
- **难以做链路追踪**：APM 埋点通常在应用层，库内逻辑**成了监控盲区**，一次慢调用在链路图上只是一个黑盒节点
- **调试体验差**：没有 IDE 断点、没有单元测试、没有本地复现，改错一次的成本远高于改应用代码
- **变更影响面说不清**：一个存储过程可能被多个系统调用，改动前很难查清到底谁在依赖它

## 第五个理由：连接数放大（高并发下的致命问题）

一次存储过程调用只从连接池借**一条连接**，但这**一条连接要在整个过程执行期间一直被占着**：过程内部顺序执行的每条 SQL 都复用同一条连接，中途不能把连接还给池子。

应用层做循环查询是另一种形态——每轮查询是**独立的短事务**，查完立刻归还连接、下一轮再借，同一条连接在多个线程之间反复复用。而过程里的循环是**在同一条连接上长时间串行执行**，一个慢过程就把一个连接钉死了。

:::tip
**应用层做循环查询会频繁释放连接（可复用），库内做则是长时间独占。** 高并发下连接池被耗尽，往往不是因为某条 SQL 太慢，而是因为慢逻辑占着连接不放。
:::

## 第六个理由：数据库选型绑定

存储过程用的是**厂商特有语法**：SQL Server 的 T-SQL、Oracle 的 PL/SQL、MySQL 的存储过程各有一套，异常处理、游标、动态 SQL 的写法都不通用。

一旦业务要迁到 TiDB、OceanBase、PolarDB 这类云原生数据库，或者要做多库并存，存储过程基本**只能重写**。而留在应用层的 SQL 大多是标准写法，换库主要是换驱动和少量方言；再叠一层持久层框架（JPA、MyBatis、SQLAlchemy 等），可移植性会更好。

:::tip
**能被迁移工具搬走的是表结构和数据，搬不走的是库里的过程逻辑**——这部分永远是人工重写。
:::

## 第七个理由：安全与权限边界模糊

- **权限模型失真**：存储过程里可能藏着改数据、读敏感表这类只有高权限才能执行的操作，而应用只需要 `EXECUTE` 权限，等于把高危操作包装成一个低权限入口
- **难以审计**：日志里只看到调用了某个过程，无法精确知道是哪个业务、哪个用户、传了什么参数
- **注入面并未消失**：过程内部若用字符串拼接动态 SQL，注入风险照旧存在，反而更难被代码扫描发现
- **责任边界不清**：出问题时应用团队和 DBA 团队容易互相说「不是我改的」

## 逐项对比：逻辑放应用层还是放数据库

| 维度 | 放应用层 | 放存储过程 |
| --- | --- | --- |
| 版本管理 | Git 全流程管理，有 diff 和 blame | 需额外迁移工具，多环境容易漂移 |
| 发布与回滚 | 可灰度、可蓝绿、可快速回滚 | 变更脚本整体上线，回滚要写逆向脚本 |
| 扩容方式 | 无状态水平扩容，加机器即可 | 受限于数据库，通常只能升配或分库分表 |
| 测试 | 单元测试加集成测试，覆盖容易 | 缺少成熟测试框架，分支难覆盖 |
| 可观测性 | 日志、指标、链路追踪齐全 | 慢日志只给总耗时，内部是盲区 |
| 连接占用 | 短查询，连接快速复用 | 整段过程独占一条连接 |
| 移植性 | 标准 SQL 为主，基本可跨库 | 厂商专有语法，换库要重写 |

## 什么时候存储过程仍然合理（不要一刀切）

- **必须与写入同事务、一致性要求极高的逻辑**：复杂的账务分摊、批量 ETL、跨多表的原子调整
- **数据库内部的运维与统计任务**：定时汇总、清理归档、历史数据修复
- **数据量极大、需要把计算推到数据旁边**：避免把海量数据搬到应用层再算一遍
- **遗留系统改造期的临时方案**：先不动，等业务整体迁移时一起收口

:::tip
**判断标准：如果这段逻辑是「数据处理」而非「业务决策」，放数据库里是合理的；如果是业务规则，就该留在应用层。**
:::

## 面试怎么答

1. **先给核心矛盾**：业务逻辑被下沉到了整个系统里最难扩容、最难版本化的组件
2. **再点三个最硬的痛点**：版本管理与灰度、连接数放大、数据库成为瓶颈不可独立扩容
3. **最后给边界判断**：数据处理放库里可以，业务决策留在应用层，再补一句迁移时的选型绑定

其中「连接数放大」是最容易被忽略、也最能体现实战经验的点：多数人能说出「数据库不好扩展」，但说不出「慢逻辑会把连接钉死」。

## 常见追问

**问：存储过程不是能减少网络交互、性能更好吗？**
答：确实少了几次网络往返，但省下的只是一点网络开销，付出的是可维护性、灰度能力和扩容能力。除非是数据量极大、必须在库内批量处理的任务，这笔交易通常不划算。

**问：业务逻辑放应用层，不也会出现多实例行为不一致吗？**
答：不会。应用是无状态的，同一个镜像部署到所有实例，行为天然一致；灰度靠流量比例控制，出问题按实例回滚。数据库是共享状态，两个应用版本连同一个库时，库里的逻辑没办法「只对百分之一的请求生效」。

**问：把存储过程也纳入 Git，用迁移工具统一管理，问题不就解决了？**
答：版本管理这一项能补上一部分，但灰度、单测、可观测性、连接占用这几项补不上——它们是「逻辑不在应用进程里」带来的结构性代价，工具抹不平。

**问：用了 ORM 之后 SQL 都由框架生成，还谈什么移植性？**
答：ORM 的作用是让换库时主要改方言和少量手写 SQL，而不是重写整套逻辑；存储过程则是整套逻辑重写，工作量根本不在一个量级。

## 易错点

- **以为存储过程「预编译所以更快」**：省下的只是解析开销，重复执行的 SQL 在应用层用预编译语句一样能复用执行计划；真正决定性能的是索引和执行计划，与「是不是存储过程」无关
- **以为存储过程能减少连接占用**：恰恰相反，它把一条连接被占用的时间拉长了，高并发下更容易耗尽连接池
- **以为「不用存储过程」就等于「不用数据库算」**：批量导入、定时汇总这类数据处理交给数据库完全合理，被反对的是把业务规则塞进去
- **以为「逻辑放数据库就绕过了注入」**：过程内部拼动态 SQL 一样有注入风险，而且权限被收敛成一个 `EXECUTE`，谁用什么参数调用更难审计

## 一句话记住

:::tip
存储过程不是不能写，而是别把业务规则塞进最难扩容、最难回滚的地方。
:::
