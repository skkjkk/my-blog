两者的定位是**纵向与横向互补**：MCP 让 Agent 拥有"工具"，A2A 让 Agent 拥有"同事"。一个成熟的多 Agent 系统里，**每个 Agent 同时扮演两个角色** —— 作为 MCP Client 使用工具与数据，作为 A2A Server 对外暴露自己的专业能力。架构上就体现为：编排层用 Agent Card 做路由，跨域协作走 A2A，每个 Agent 内部用 MCP 接工具与数据，共享状态外置到记忆层，全链路统一追踪。

## 四层架构：谁决策、谁干活、谁提供能力

分层的目的是把三件事分开：**谁决策**（编排层）、**谁干活**（专业 Agent）、**谁提供能力**（MCP Server），否则所有逻辑都会堆在一个巨型 Agent 里。最上层是**用户与编排层**（Orchestrator），负责与用户对话、拆解任务、决定把哪些子任务交给哪个专业 Agent。第二层是**专业 Agent 集群**，每个 Agent 是一个独立部署的服务，暴露 A2A 接口（持有自己的 Agent Card）。第三层是**工具与数据层**，通过 MCP Server 提供（数据库、代码执行器、搜索、文件系统、内部业务 API）。第四层是**共享基础设施**（记忆库、审计、密钥、预算守卫），它属于横切能力，四层共用同一套，而不是每个 Agent 各建一份。

| 层 | 角色 | 对外用什么 | 主要职责 |
| --- | --- | --- | --- |
| 用户与编排层 | Orchestrator | A2A Client | 对话、拆解任务、按 Agent Card 选路、汇总结果 |
| 专业 Agent 集群 | 独立部署的服务 | A2A Server（持 Agent Card） | 承接领域任务，内部再用 MCP 干活 |
| 工具与数据层 | MCP Server | MCP | 数据库、代码执行器、搜索、文件系统、内部业务 API |
| 共享基础设施 | 横切能力 | 供各层调用 | 记忆库、审计、密钥、预算守卫 |

## 两种协议的分工：MCP 管工具、A2A 管同事

两个协议解决的是两个方向的问题：**MCP 是纵向的**，解决"Agent 怎么访问自己下面的工具与数据"；**A2A 是横向的**，解决"Agent 怎么把一件事委托给平级的另一个 Agent"。区分标准其实只有一条：对面是一个**没有自主性的工具**，还是一个**有自己一摊事的独立主体**。工具只需要"调用 - 返回"，主体需要"委托 - 跟进 - 交付"。所以两者不能互相替代：把工具用 A2A 包一层，只会多出网络开销与鉴权复杂度；把 Agent 用 MCP 直接接进来，又丢掉了任务生命周期与信任边界。

| 维度 | MCP | A2A |
| --- | --- | --- |
| 方向 | 纵向：Agent → 工具与数据 | 横向：Agent → Agent |
| 对面主体 | 无自主性的工具 | 有自己业务与部署的独立 Agent |
| 交互模型 | 调用 - 返回 | 任务委托，有状态、有生命周期 |
| 怎么找到对方 | 拉取工具列表 | Agent Card 语义匹配 |
| 结果交付 | 直接回填结果 | Artifact 交付，常需摘要 + 引用 |
| 主要工程难点 | 权限最小化、结果清洗 | 跨组织认证、长任务、降级 |

## 一个具体例子：分析开源项目并产出技术报告

假设要做"分析某个开源项目并产出技术报告"。编排 Agent 拆出四个子任务：检索项目资料、执行代码验证依赖、绘制架构图、撰写报告。落成架构是这样：

```text
编排 Agent（A2A Client，内部另持自己的 MCP Client 集合）
  ├─ A2A → 检索 Agent        ── MCP → 搜索服务
  ├─ A2A → 代码验证 Agent    ── MCP → 代码执行沙箱、文件系统
  ├─ 本地完成：绘制架构图
  └─ 本地完成，或内容足够多时 A2A → 写作 Agent：撰写报告
```

检索与代码验证由两个专业 Agent 通过 **A2A** 承接，它们各自在内部通过 **MCP** 调用搜索服务、代码执行沙箱、文件系统；报告撰写可由编排 Agent 自己完成，也可在内容足够多时委托给"写作 Agent"。注意这个例子里每个 Agent 的身份都是双重的：对上游它是 A2A Server，对下游它是 MCP Client，这也是"两种协议协同"的真正含义。

## 协作链路：从 Agent Card 匹配到 Artifact 回收

一次跨 Agent 协作要走完下面这条链路，缺任何一步都会在联调时暴露出来：

1. 编排 Agent 读取所有候选 Agent 的 **Agent Card** 做语义匹配，选出执行方。
2. 按 Card 声明的输入输出 schema 构造请求，避免"我以为你会收这个格式"。
3. 通过 A2A 发起 Task，拿到任务标识与初始状态。
4. 接收流式中间产物与状态更新，长任务期间持续跟踪，而不是干等一个最终返回。
5. 任务完成后回收 Artifact，大产物走"摘要 + 引用"。
6. 把结果汇总进主轨迹，必要时写回共享记忆，供后续子任务复用。

这条链路上每一跳都要能对上同一个 trace id，否则跨边界排查会非常痛苦。

## 两侧的工程要点：A2A 侧与 MCP 侧

### A2A 侧：任务不是一次请求

任务是**有状态、有生命周期**的，需处理长任务、异步完成、失败与重试，还要支持取消。跨组织调用要处理**认证（OAuth 委托令牌）与信任边界**，对方的 Card 只是能力声明，不代表它的内部实现。Artifact 常常很大，**同样需要走"摘要 + 引用"的策略**，大产物外置、只回摘要与可寻址引用，不能整包塞进上下文。

### MCP 侧：工具要按角色发

每个专业 Agent 内部维护自己的 MCP Client 集合，不共用一把万能凭证。MCP Server 应当**按 Agent 的角色最小化暴露**（写作 Agent 不需要数据库写权限）。Server 返回结果要**清洗成适合模型消费的形式**，别把原始日志直接灌进上下文。MCP Server 还应当做**权限与配额控制**，防止某个 Agent 通过工具越权，或把下游服务压垮。

## 边界要划清：能用 MCP 解决就别上 A2A

**不要用 A2A 做本可以用 MCP 的事** —— 同一组织内、同一团队维护的工具，统一走 MCP 更简单、更安全。**A2A 应用于跨团队、跨厂商、能力边界清晰、且需要独立演进与独立部署的协作**。过度使用 A2A 会带来网络调用开销、鉴权复杂度与调试难度，所以判断标准不是"能不能拆成 Agent"，而是"这块能力是不是真由别人维护、需要独立演进"。反过来，把另一个团队的 Agent 硬塞进自己的 MCP 工具列表，同样会把信任边界糊掉。

## 共享状态、统一追踪与降级容错

跨 Agent 的共享上下文不建议靠"互相传消息"来维持，而应**外置到共享的记忆存储**（向量库、任务库、对象存储），各 Agent 按需检索。这与单 Agent 系统的记忆设计完全一致，只是作用域从"单个 Agent"变成"系统级"。

编排层还需要一条**贯穿 A2A 与 MCP 的统一 Trace**：从编排 Agent 发起、到跨 Agent 调用、到最终的 MCP 工具执行，全链路用同一个 trace id 串起来。

跨 Agent 调用要设置超时、重试与熔断，并准备**降级路径**：远端 Agent 不可用时，编排 Agent 自己把活干完，或切换到备选 Agent —— 前提是编排层缓存了 Agent Card 列表并能重新匹配。

## 常见追问

**Q：为什么不让 Agent 直接调对方的 MCP 工具，非要用 A2A？**
A：因为工具没有主体。跨团队、跨厂商时对方不会把自己的 MCP Server 暴露给你，它的内部工具权限也不该由你持有。A2A 把对方当独立主体，只交换能力声明与产物，信任边界清楚。

**Q：编排 Agent 自己也能调工具，还需要专业 Agent 吗？**
A：只有当子任务需要独立演进、独立部署、独立权限，或由别的团队维护时，拆成 A2A 协作方才划算；否则编排层自己用 MCP 做完更简单。

**Q：Artifact 很大怎么办？**
A：摘要 + 引用，大产物放共享存储，上下文里只留摘要和可寻址引用，和 MCP 返回大结果时的处理方式一致。

**Q：跨 Agent 的共享上下文放哪？**
A：放系统级共享记忆（向量库、任务库、对象存储），各 Agent 按需检索，不要靠互传消息同步状态。

## 易错点

- **把 A2A 当远程函数调用用**：Task 有状态、有生命周期，长任务要处理异步完成、重试与取消，不能按请求-响应一把梭。
- **以为 Agent 越多越"多 Agent"**：过度使用 A2A 会带来网络调用开销、鉴权复杂度与调试难度，同团队维护的能力统一走 MCP。
- **给所有 Agent 发同一套工具权限**：MCP Server 要按角色最小化暴露，写作 Agent 不该有数据库写权限。
- **只给自己这一段埋 Trace**：A2A 与 MCP 的边界必须共用同一个 trace id，否则跨边界排查会断链。

## 一句话记住

编排层用 Agent Card 路由，跨域走 A2A，Agent 内部走 MCP。
