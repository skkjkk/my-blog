两者是处理并发修改冲突的两种相反思路：**悲观锁假设冲突会发生，先锁住再操作**；**乐观锁假设冲突很少发生，不加锁，提交时再校验**。

## 悲观锁

。在读数据之前先加锁，常见实现是 `SELECT ... FOR UPDATE`（行级排他锁）或 `LOCK IN SHARE MODE`（共享锁），也可以用 `synchronized` 或分布式锁。拿到锁的线程修改数据并提交，其余线程阻塞等待。适合**写冲突频繁、必须串行化**的场景，比如账户余额扣减、库存扣减、秒杀下单。

## 乐观锁

。读数据时不加锁，而是在数据中增加一个**版本号字段**（或时间戳），更新时带上读到的版本号作为条件：更新时检查版本号是否仍是自己读到的那份，是则更新并把版本号加一，不是则说明被别人改过，**更新失败并重试或返回失败**。对应到 SQL 就是 `UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?`。适合**读多写少、冲突概率低**的场景，比如点赞计数、商品浏览量、库存充足时的扣减。

## 锁的粒度与影响

。悲观锁的 `FOR UPDATE` 会持有行锁直到事务提交，长事务会显著扩大锁范围，影响并发；而在 MySQL 中，**行锁只在事务生效**，如果没显式开启事务，语句结束即释放，实际上就失去了加锁的意义。

## 两者的失败代价

。悲观锁的代价是**等待与阻塞**，冲突多时线程大量挂起、上下文切换开销大；乐观锁的代价是**冲突时的重试开销**，冲突极其频繁时重试会浪费大量 CPU 甚至活锁，因此冲突率很高时反而不如悲观锁。

## 实现方式差异

。悲观锁通常依赖数据库的锁机制或应用层的分布式锁；乐观锁**不依赖任何锁**，只需要一个版本字段，是纯粹的乐观并发控制。

## 实践建议

。优先考虑**用数据库约束或原子语句替代显式加锁** —— 比如把"先查库存再更新"改成 `UPDATE stock SET count = count - 1 WHERE id = ? AND count >= 1`，靠条件更新天然保证不超卖，这往往比任何一种锁都更简洁高效。其次才是按冲突率选择：冲突少用乐观锁（版本号），冲突多用悲观锁（`FOR UPDATE`），并且要保证**悲观锁的事务足够短**。
