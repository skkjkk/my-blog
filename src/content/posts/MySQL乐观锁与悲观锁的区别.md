两者是处理并发修改冲突的**两种相反思路**。**悲观锁假设冲突一定会发生**，动手之前先把数据锁住，没抢到锁的线程排队等待；**乐观锁假设冲突很少发生**，读的时候完全不加锁，只在提交时用版本号校验这份数据有没有被别人改过，改过就失败重试。选哪个不取决于哪个更先进，而取决于**冲突率**：冲突频繁的写场景该用悲观锁，读多写少的场景用乐观锁更划算。

## 悲观锁：动手之前先锁住

它在读数据之前就加锁，拿到锁的线程才能修改并提交，其余线程阻塞等待。最常见的是数据库层实现：`SELECT ... FOR UPDATE` 加的是**行级排他锁**，别人读写同一行都得等；`LOCK IN SHARE MODE` 加的是**共享锁**，多个读可以并存，写操作要等读锁释放。也可以脱离数据库，用应用层的 `synchronized` 或者分布式锁达到同样的"互斥"效果。它的适用场景是**写冲突频繁、必须串行化**的场合，比如账户余额扣减、库存扣减、秒杀下单——这些地方一次并发写错就是真金白银的损失，宁可让线程排队也不能乱。

## 乐观锁：不加锁，提交时校验版本号

读数据时它不加任何锁，而是在表里加一个**版本号字段**（也可以用时间戳）。更新时带上自己读到的那个版本号作为条件：版本号仍是自己读到的那份就更新，并把版本号加一；不是就说明中途被别人改过，**本次更新失败，由应用决定重试还是直接返回失败**。落到 SQL 上就是 `UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?`，看影响行数是 1 还是 0 就知道有没有抢到。它适合**读多写少、冲突概率低**的场景，比如点赞计数、商品浏览量、库存充足时的扣减——绝大部分请求都会一次成功，加锁反而是浪费。

## 行锁只在事务里才算数

悲观锁不是加完就完事，`FOR UPDATE` 拿到的行锁会**一直持有到事务提交**，所以事务越长，锁覆盖的范围和持有时长就被放大得越多，别人排队越久，整体并发能力明显下降。更关键的是 MySQL 的**行锁只在事务中生效**：如果没有显式开启事务（自动提交开着），语句一执行完锁就释放了，**加锁形同虚设**，等于什么都没防住。所以悲观锁从来不是一个开关，它是一整套约束——先 `BEGIN`，短事务，尽早 `COMMIT`，事务里别夹远程调用。

## 谁更划算，取决于冲突率

| | 悲观锁 | 乐观锁 |
| --- | --- | --- |
| 冲突时的行为 | 阻塞等待别人释放锁 | 本次更新失败，重试或报错返回 |
| 主要代价 | 线程挂起、上下文切换开销大，长事务放大锁范围 | 重试浪费 CPU，冲突极密集时可能活锁 |
| 适用场景 | 写冲突频繁、必须串行化 | 读多写少、冲突概率低 |
| 实现依赖 | 数据库锁机制，或应用层分布式锁 | 不依赖任何锁，只要一个版本字段 |

两边代价的形状完全不同：悲观锁把成本花在**等待与阻塞**上，冲突越多，挂起的线程越多；乐观锁把成本花在**冲突时的重试**上，冲突少时几乎免费，可一旦冲突极其频繁，大量更新反复失败重试，浪费 CPU 甚至形成活锁，这时候它反而**不如悲观锁**。另外从实现上看，乐观锁不依赖任何锁机制，只需要一个版本字段，是纯粹的乐观并发控制；悲观锁则必须依赖数据库的锁或一把分布式锁。

## 实践建议：先想能不能不用锁

真正该排在第一位的不是二选一，而是**用数据库约束或原子语句替代显式加锁**。把"先查库存再更新"改成一条带条件的更新：

```sql
UPDATE stock SET count = count - 1
WHERE id = ? AND count >= 1;
```

条件本身就保证了不会超卖，单条语句原子完成，影响行数为 0 就代表库存不足。这往往比任何一种锁都更简洁高效，也没有死锁风险。只有在条件更新表达不了业务逻辑时，才回到按冲突率选锁：**冲突少用乐观锁（版本号），冲突多用悲观锁（`FOR UPDATE`）**，并且务必保证悲观锁的事务足够短。

## 常见追问

**Q：乐观锁是 MySQL 提供的一种锁吗？**
A：不是。MySQL 里没有名为"乐观锁"的机制，它就是一条普通的 `UPDATE` 加上版本号条件，全程不产生锁等待，本质是应用层约定的一种 CAS 式并发控制。

**Q：既然乐观锁不加锁，为什么不会丢更新？**
A：因为判断和修改在同一条语句里完成，`WHERE id = ? AND version = ?` 是原子的，两个请求只有一个能把版本号推进，另一个影响行数为 0、直接被识别为冲突。

**Q：冲突很频繁时为什么不能继续用乐观锁？**
A：每次冲突都要重试，重试又要重新读一遍最新数据，冲突率越高无效功越多，极端情况下大量线程互相打断形成活锁，此时让它们排队（悲观锁）反而更稳定。

**Q：用了 `FOR UPDATE` 却感觉没锁住，通常是什么原因？**
A：最常见是没在显式事务里执行，语句结束锁就释放了；其次是 `WHERE` 条件没走索引，扫描到的行都会被加锁，锁范围远大于你以为的那一行。

## 易错点

- **把乐观锁当成数据库的一种锁**：它不产生任何锁等待，只是"条件更新 + 检查影响行数"，说它"加锁"会答错。
- **以为写了 `FOR UPDATE` 就锁住了**：自动提交模式下等于没锁；`WHERE` 没走索引时锁的范围还会扩大到一大批行。
- **悲观锁的事务里做远程调用、等用户输入**：锁持有到 `COMMIT` 为止，事务一长锁范围就被放大，前面的排队全部白等。
- **重试不设上限、不退避**：乐观锁的重试必须重新读取最新数据并限制次数，否则冲突高时就是活锁。

## 一句话记住

:::tip
悲观锁排队，乐观锁重试；先看能不能用条件更新把两者都省掉。
:::
