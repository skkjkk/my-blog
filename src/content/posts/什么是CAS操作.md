CAS（Compare-And-Swap，比较并交换）是一条 **CPU 级别的原子指令**：它先读一下内存位置的当前值，和调用方给的预期值比较，相等就把这个位置改成新值并返回成功，不相等就什么都不动并返回失败。比较和写回在一条指令里完成，中间不会被别的线程插进来，所以它是无锁并发的基石——`AtomicInteger` 的自增、`Unsafe` 暴露的底层方法、AQS 里对 `state` 的修改，追到最下面都是这条指令。

## CAS 的比较和交换具体比什么

它有三个操作数：内存位置（可以理解为变量地址）、预期值 A、新值 B。执行时取该位置的当前值，与 A 比较，相等则写入 B 并报告成功，不等则原值保持不变并报告失败。

和普通赋值最大的差别就在这里：普通赋值是无条件覆盖，CAS 是**条件写**——只有当前值和预期值一致时才写入，判断和写入是不可分割的一步。成功与否通过返回值交给调用方，所以失败之后怎么办由调用方自己决定（通常是重读再试）。

JDK 里这套语义由 `Unsafe` 提供的 `compareAndSwapInt`、`compareAndSwapObject` 这类本地方法撑起来，参数是目标对象、字段偏移量、预期值、新值；`java.util.concurrent.atomic` 包下的原子类全部建立在它们之上。

## 为什么要它：用乐观重试替代阻塞加锁

没有 CAS 时，多线程更新共享变量只能加锁，拿不到锁的线程会被挂起，等锁释放再被唤醒，这一挂一醒是两次线程上下文切换。如果临界区其实只改了一个 `int`，这点调度开销比业务本身还贵。

CAS 走的是另一条路——**乐观地假设没人抢**，直接试一次，成功就走。成功路径上没有任何加锁、解锁、唤醒动作；只有真的发生竞争（别人抢先改了值）才失败一次，失败后重新读值再试。所以它的收益集中在无竞争或低竞争的场景，竞争一激烈收益就被重试成本吃掉。

## 落地写法是自旋重试

单次 CAS 只保证"这一次写入没被插手"，要完成"读-改-写"这种复合操作，必须把 CAS 套进循环：读当前值 → 算新值 → CAS → 成功退出、失败重读再来。`AtomicInteger` 的 `incrementAndGet` 内部就是这个结构，下面是对应的手写版本，可以直接对照理解：

```java
public static void addAndGet(AtomicInteger counter, int delta) {
    while (true) {
        int current = counter.get();                 // 读当前值
        int next = current + delta;                  // 在本地算新值
        if (counter.compareAndSet(current, next)) {  // 当前值仍等于 current 才写回
            return;                                  // 成功即退出
        }
        // 失败说明有人抢先改过：回到循环顶部重新读，再算一次
    }
}
```

这段代码里没有一句加锁，"重试"本身就是它的同步手段。也正因为是循环，失败次数直接决定开销：竞争越激烈，失败越多，循环转得越多。

## ABA：值没变，但中间已经被改过

CAS 只比较值是否相等，不关心这个值中途被改过几次。线程 A 读到 0，线程 B 把 0 改成 1 再改回 0，A 执行 CAS 时比较仍然通过，可它以为自己拿到的还是最初那个状态，实际中间已经发生过变化；如果这个值代表"栈非空""锁空闲"这类状态，判断就错了。

解决办法是给值配一个**版本号**，把"值 + 版本"打包成一对一起 CAS：每次修改版本号加一，A 的 CAS 就会因为版本对不上而失败。JDK 里现成的实现是 `AtomicStampedReference`，它的 `compareAndSet` 要同时比对引用和 stamp。

## 自旋的代价：线程数超过核数时会互相抢 CPU

自旋不阻塞线程，代价转嫁给了 CPU：失败了不睡觉，继续占着时间片重试。线程数没超过 CPU 核数时这很划算，总有线程能真正跑起来；一旦线程数超过核数，多个线程在同一份资源上空转，抢不到的就白白烧掉时间片，整体吞吐反而下降。

所以 CAS 适合竞争不激烈、临界区极短的场景，不适合把长逻辑塞进自旋里。反过来，阻塞式的锁也在朝自旋靠：`synchronized` 现在的实现会先短暂自适应自旋一段，抢不到再挂起线程，用少量自旋换掉一次线程调度。

## 常用实现类：从 AtomicXxx 到 LongAdder

`java.util.concurrent.atomic` 包按数据类型分了一组：`AtomicInteger`、`AtomicLong`、`AtomicBoolean`、`AtomicReference`，以及数组版的 `AtomicIntegerArray` 等。它们都是"一个变量 + CAS 循环"的封装，适合单变量计数、状态位切换、无锁栈或队列里的指针更新。

JDK 8 又补了 `LongAdder` 和 `DoubleAdder`。高并发计数时所有线程抢同一个变量，CAS 会大量失败；`LongAdder` 改成**分散热点**——内部维护一组 Cell，不同线程更新不同的 Cell，取结果时把各个 Cell 累加，冲突被摊开，失败率自然下降，是 `AtomicLong` 计数场景更优的选择。代价是 `sum()` 不是一次原子读，只保证最终一致，需要精确的即时值时不合适。

## 和锁怎么取舍

选型看四点：竞争程度、临界区长短、是否要同时保证多个变量、是否需要公平性或条件等待。

- 竞争低、只改一个变量、临界区就几行 → 优先 CAS，省掉线程挂起与唤醒；
- 临界区里有多个变量必须一起保持一致 → 用锁，一次 CAS 表达不了；
- 需要公平排队，或需要 `Condition` 按条件精确唤醒 → 用锁；
- 高并发纯计数 → 用 `LongAdder`，而不是让一堆线程在 `AtomicLong` 上死磕。

| 维度 | CAS（无锁） | synchronized / ReentrantLock |
| --- | --- | --- |
| 竞争时的动作 | 失败就地重试，不挂起线程 | 拿不到就阻塞挂起，等唤醒 |
| 适合的临界区 | 极短，通常只改一个变量 | 较长，可能包含多步逻辑 |
| 保证的粒度 | 单个位置的一次写入 | 一整段代码块 |
| 附带能力 | 无公平性、无条件等待 | 公平锁、`Condition` 多条件等待 |
| 主要风险 | 自旋烧 CPU、ABA | 上下文切换开销、可能死锁 |

这两者不是对立的两派，实际代码里经常混用：`LongAdder` 的计数靠 CAS 更新 Cell，而 Cell 数组的扩容仍然用 `synchronized` 保护——低频但结构复杂的部分交给锁，高频但极短的部分交给 CAS。

## 常见追问

**Q：CAS 和 `volatile` 是一回事吗？**
A：不是。`volatile` 保证可见性和有序性，但"读-改-写"三步之间仍可能被别的线程插进来；CAS 保证的正是这三步整体原子。原子类里的 `value` 字段本身带 `volatile`，可见性靠它，原子性靠 CAS。

**Q：有了 CAS，`synchronized` 是不是可以不用了？**
A：不能。一次 CAS 只能原子地改一个位置，临界区里有两三个变量要一起改、或者要等某个条件成立再继续，CAS 都表达不出来；高竞争下自旋也比阻塞更浪费 CPU。

**Q：`AtomicInteger` 一定比加锁快吗？**
A：只在低竞争时通常如此。竞争一起来，大量线程在同一变量上反复失败重试，CPU 全花在无用功上，这时分段计数（`LongAdder`）或者直接加锁可能更划算。

**Q：为什么 `LongAdder` 的 `sum()` 拿不到绝对准确的值？**
A：计数被拆在多个 Cell 里，`sum()` 是逐个读再相加，读的过程中别的线程还在改，所以只保证最终一致；需要快照式的精确值就用 `AtomicLong` 或加锁。

## 易错点

- **以为 CAS 读一次就够**：单次 CAS 只保护一次写入，复合操作必须自己套循环（或直接用原子类的现成方法），否则中间那步计算依然是竞态的。
- **以为值相等就没问题**：值相等不代表中途没变过，ABA 就是这么漏过去的，要版本号（`AtomicStampedReference`）兜住。
- **以为不阻塞就等于没开销**：CAS 是拿 CPU 换阻塞，线程数超过核数时自旋互相抢时间片，吞吐可能比加锁更差。
- **以为 CAS 能原子地改多个字段**：一次 CAS 只认一个内存位置，多个字段要么合成一个对象用 `AtomicReference` 整体替换，要么回到锁。

## 一句话记住

:::tip
CAS 是"值没变才写回"的原子指令：无锁靠自旋，防 ABA 靠版本号。
:::
