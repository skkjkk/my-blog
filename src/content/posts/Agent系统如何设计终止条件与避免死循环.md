终止条件是 Agent 系统中**防止资源失控的最后一道闸门**。设计良好的终止条件应当是**多重、异构、可归因**的 —— 单一条件（比如"看模型是否说完成了"）几乎必然出问题。

1) **第一类：完成类（成功终止）**。模型给出最终答案；或**验收条件被程序化校验通过**（这是最可靠的一种，因为不依赖模型自述）；或子任务清单全部标记为已完成。**优先使用程序化验收而非模型自述**，因为模型经常在没做完时就宣称完成。

2) **第二类：预算类（硬性上限）**。最大步数、最大 token、最大金额、最大墙钟时间、最大工具调用次数。**这些必须是硬上限**，超限即熔断，并且要能**提前预警**（比如走到 80% 预算时触发降级），而不是撞墙才停。

3) **第三类：停滞类（无进展检测）**。连续 N 步任务状态或环境状态**没有变化**；连续 N 步动作签名重复；工具错误率上升；连续 N 次同类失败。这是防死循环最有效的一类。

4) **第四类：循环检测**。对最近 K 步的动作与观测做归一化签名，检测滑窗内的**重复模式**；或用语义相似度识别"签名不同但实质重复"的循环。检测到后可**注入引导**（告知已尝试的方案、要求换路径）而不是直接终止。

5) **第五类：外部信号**。用户取消、超时、熔断信号、依赖方不可用。

6) **避免死循环的六条策略**。一是**给每类重复动作设上限**，同一工具连续失败 N 次即升级；二是**强制多样性** —— 连续两步动作相同时强制要求换工具或换参数；三是**注入扰动** —— 重复出现时在上下文中写入"已尝试过 X、Y，请换思路"；四是**重规划降级** —— 从微调参数升级为重新分解任务，再升级为换更大模型；五是**子 Agent 隔离** —— 把可疑任务交给独立的子 Agent 用干净上下文重试，避免污染主上下文；六是**熔断并升级人工** —— 确认无法自动恢复时果断停下并上报，而不是无限重试。

7) **降级链是设计重于检测**。与其追求"永不循环"，不如设计一条明确的降级链：正常执行 → 强制换路径 → 重新规划 → 换强模型 → 缩小任务范围 → 输出阶段性结论并转人工。**每一级都要有明确的触发阈值。**

8) **可观测性要求**。所有终止都要**记录终止原因分类**（成功/预算耗尽/停滞/循环/人工取消/异常），这些分类数据是线上分析"Agent 为什么没做完"的核心依据。只记"任务失败"是没有诊断价值的。
