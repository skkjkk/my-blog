外键（`FOREIGN KEY`）能保证**引用完整性**，但在国内互联网的实践中**基本被禁用**，尤其是**分库分表后更是完全不能用**。核心理由是：**外键把"跨表的一致性约束"下沉给数据库，而这套约束在分布式和高并发场景下代价极高。**

## 头号理由：外键与分库分表互斥

一旦分库分表，父子表往往在**不同的库甚至不同的实例**上 → **跨库的 FOREIGN KEY 在 MySQL 里根本不支持**（同实例跨库也不行，必须同一 schema）。

:::tip
**这意味着：一旦你用了外键，将来想分库分表就必须先全部拆掉外键 —— 相当于给架构演进上了枷锁。**
:::

## 第二个理由：性能代价（写放大）

- 每次 `INSERT`/`UPDATE`/`DELETE`，数据库都要**检查外键约束**：子表写完要查父表、父表删改要查子表
- **锁范围扩大**：父表删除一行时，数据库需要**锁住子表相关行**（`SELECT ... FOR SHARE`）才能防止并发写入产生"孤儿数据" → **锁等待与死锁概率明显上升**
- **触发隐式 SQL**：某些级联操作会触发额外的内部 SQL → 慢查询日志里会出现"看不见"的语句

## 第三个理由：级联删除（CASCADE ON DELETE UPDATE）风险极高

`ON DELETE CASCADE` 一句就能删掉一整条业务链上的数据 —— **删错了无法挽回，且日志里看不出是级联删的**。

:::tip
**互联网业务更倾向"软删除 + 状态标记"，而不是物理级联删除。**
:::

## 第四个理由：分库分表后约束无法保证，且"最终一致"才是现实

跨服务的数据一致性靠**分布式事务、可靠消息、幂等 + 对账补偿**来解决，而不是靠数据库外键。**外键给的是"强一致"幻觉 —— 在分布式下它既保证不了，也拖慢了整体。**

## 替代方案：应用层保证（业界主流做法）

- **写入时校验**：插入子表前先 `SELECT` 父表确认存在（配合缓存）
- **⭐ 幂等 + 唯一索引兜底**：用**业务唯一键 + 唯一索引**代替外键的"不重复"约束
- **⭐ 定时对账**：定期扫描孤儿数据并修复（这是大厂标准动作）
- **兜底保护**：对**强一致性的关键外键关系**，改用**应用层分布式锁 + 串行化写入**

## 必须分清：不是"外键功能没用"，而是"在特定架构下不适用"

- **小单体、内部管理系统、数据一致性要求极高** → **外键完全合理**，能省掉大量应用层校验代码
- **分库分表、微服务、高并发写** → **禁用外键**

:::tip
**面试时把判断标准说清楚（是否分库分表、是否高并发写）比一味说"外键不好"更有说服力。**
:::

## 特别提醒：外键与"隐式加锁"是隐蔽的性能杀手

很多人不知道：**外键约束会在父表行上加共享锁（`S` 锁）直到子表事务结束** → 高并发写入同一父记录时容易出现**锁等待甚至死锁**，而且**从慢日志看完全看不出是外键引起的**。

## 面试怎么答

1. 首要理由是"分库分表互斥"（跨库不支持外键 → 架构演进被锁死）
2. 性能代价（写放大 + 隐式锁 + 锁范围扩大导致死锁）
3. 给出正确替代（应用层校验 + 幂等唯一索引 + 定时对账 + 关键关系用分布式锁），并说明"小单体用外键反而合理"。第三点的"看场景而非一刀切"最能体现工程判断力
