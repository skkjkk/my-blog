外键（`FOREIGN KEY`）能保证**引用完整性**，但在国内互联网的实践中**基本被禁用**。首要理由是它与**分库分表天然互斥**：MySQL 的外键不能跨库，一旦分片就必须先把外键全部拆掉。其次是写路径上的代价——每次写入都要检查父表、并在父表行上加**共享锁**，锁范围扩大、死锁概率上升；再加上**级联删除不可回滚**。跨服务的一致性业界改用应用层校验、幂等唯一索引与定时对账来解决，而不是靠数据库外键。

## 头号理由：外键和分库分表天生互斥

InnoDB 的外键只支持**同一个 schema（库）内部**的父子表，跨库、跨实例都不支持，同实例但不同库也不行。而分库分表之后，父子表往往正好被切到不同的库甚至不同的实例上，外键直接失效。

于是演进顺序就变成：先建了外键 → 后来数据量上来要分片 → 必须**先拆掉所有外键**、再补上应用层校验与对账脚本，一次架构升级被拖成两次改造。很多团队从第一天就不建外键，就是为了保留这张"随时可以分片"的牌。

还有两个连带约束常被忽略：父表的被引用列必须有索引（主键或唯一索引），子表的外键列 InnoDB 会自动建索引。这些在建表、改表、做数据迁移时都是额外的检查项，分片中间件和数据同步工具也往往不认它们。

## 第二个理由：写路径上的代价（写放大 + 隐式加锁）

外键的检查是**同步**的，落在写入的关键路径上：

- 子表 `INSERT`/`UPDATE` 时，数据库要确认父行存在 → 对**父表对应行加共享锁（`S` 锁）**，并持有到子表所在事务结束。
- 父表 `UPDATE`/`DELETE` 时，数据库要确认子表是否还有引用 → 反向检查子表的相关行，同样要加锁。
- **锁范围因此扩大**：高并发写同一批热点父行时，大量共享锁与业务上的排他锁（`X` 锁）互相等待 → **锁等待与死锁概率明显上升**。
- 检查与级联动作都由存储引擎在内部完成，**不产生独立的 SQL 文本**，所以慢查询日志里看不到它们 → 从慢日志完全看不出是外键引起的，只能从执行耗时、锁等待时间侧面推断。

这是最容易踩的坑：很多人以为外键只是"多一次逻辑判断"，实际上它把一致性校验的成本变成了**行锁竞争**，在热点行上代价最高。

## 第三个理由：级联删除是不可回滚的批量事故

`ON DELETE CASCADE` / `ON UPDATE CASCADE` 一句 DDL 就能删掉一整条业务链上的数据：执行者是存储引擎，不走应用代码、不经过业务校验、不写入可审计的独立 SQL，**删错了只能靠备份恢复**，事后翻日志也看不出是谁连带删的。

```sql
-- 危险写法：删掉一条订单，订单明细整条链跟着消失，且不留独立 SQL 轨迹
ALTER TABLE t_order_item
  ADD CONSTRAINT fk_item_order
  FOREIGN KEY (order_id) REFERENCES t_order (id)
  ON DELETE CASCADE ON UPDATE CASCADE;
```

所以互联网业务更倾向**软删除 + 状态标记**：删除只改状态，物理清理收敛到少数可控的后台任务里，分批执行、可暂停、可核对。

## 第四个理由：外键给的是"强一致"的幻觉

外键只在**同一个库、同一个事务、同一份数据**范围内有效。一旦数据被拆开——分库分表、多副本、加缓存、走异步消息——它既保证不了引用完整性，又把强制检查的开销永久留在了写入路径上。

跨服务的数据一致性靠**分布式事务、可靠消息、幂等 + 对账补偿**来解决，而不是数据库外键。结论不是"外键是更强的保障"，而是"外键只是**单库范围内**的局部保障"，而现代业务的边界早就跨出了单个库。

## 替代方案：把约束搬到应用层，并接受最终一致

| 要保证的事 | 外键的做法 | 应用层的做法 |
| --- | --- | --- |
| 引用完整性（子表引用的父行必须存在） | 数据库在每次写入时强制检查 | 写入前校验父行存在（可先查缓存）+ 定时对账扫孤儿数据 |
| 不重复（幂等） | 外键本身并不负责这件事 | 业务唯一键 + 唯一索引，冲突就按幂等返回 |
| 删除父数据时的连带处理 | `ON DELETE CASCADE` 物理级联 | 软删除 + 状态标记，后台任务分批清理 |
| 强一致的关键关系 | 事务内加锁 | 分布式锁 + 串行化写入，把并发收窄 |
| 架构演进空间 | 分库分表前必须全部拆掉 | 无数据库层耦合，按分片键切分即可 |

其中两条最常被问到：

- **幂等 + 唯一索引兜底**：把"重复写入"变成可安全重试的操作，靠数据库的唯一约束兜住并发；注意它管的是**不重复**，不是引用完整性，别把两件事混为一谈。
- **定时对账**：定期扫描孤儿数据并修复，这是业界普遍的标准动作，也是最终一致的兜底。

真要求强一致的关键外键关系，还有一招是把它们收进**同一个聚合、用同一个分片键放在同一张表**里，用"同库同事务"换回外键那种保障；必须跨片时，才上应用层分布式锁 + 串行化写入。

## 什么情况下外键反而是对的

外键不是"功能没用"，而是"在特定架构下不适用"，判断标准只有两条：

- **单库单表的小系统、内部管理系统、数据一致性要求极高** → 外键完全合理，能省掉大量应用层校验代码，还能挡住误删和脏数据。
- **分库分表、微服务、高并发写热点行** → 禁用外键，把约束交给应用层与对账。

面试时把"是否已经或即将分库分表、是否高并发写同一批父行"这个标准说清楚，比一味说"外键不好"更有说服力——它体现的是**看场景、不一刀切**的工程判断力。

## 面试怎么答

1. 首要理由：**分库分表互斥**（跨库不支持外键 → 架构演进被锁死）。
2. 性能代价：**写放大 + 父表行上的隐式共享锁 + 锁范围扩大导致死锁**，而且慢日志里看不出来。
3. 正确替代：**应用层校验 + 幂等唯一索引 + 定时对账**，关键关系再加分布式锁。
4. 补一句场景判断：**小单体里外键反而合理**，禁用它是架构选择而非技术缺陷。

## 常见追问

**Q：外键和唯一索引是一回事吗？**

A：不是。外键保证"子表引用的父行确实存在"（引用完整性），唯一索引保证"这一列的值不重复"。禁用外键之后，唯一索引正好补上"不重复 + 幂等"这一半，引用完整性则交给应用层校验与对账。

**Q：已经用了外键，后来要分库分表怎么办？**

A：必须先把外键全部拆掉，否则分片后建表、数据迁移都会失败。顺序是：拆外键约束 → 补齐应用层校验与唯一索引 → 上线对账任务 → 再动分片。所以这笔改造最好在项目早期就做掉。

**Q：不用外键，怎么防止子表写入不存在的父 id？**

A：写入前校验父行存在（热点父数据放缓存），配合唯一索引挡住重复提交；遗漏的脏数据靠定时对账扫出来修掉。极端要求强的链路，用分布式锁把同一业务键的写入串起来。

**Q：外键会自动在子表建索引，这不是白捡的优化吗？**

A：索引该建还是自己建，但要清楚这个索引是为了**外键检查**而建的，未必符合你的查询模式；把一致性交给应用层后，索引用不用建、建成什么形状，完全由查询决定。

## 易错点

- 以为外键能防重复数据。外键管的是引用完整性，"同一个业务键只能有一条"要靠唯一索引；说反了会被追问到答不上来。
- 以为外键只是"多一次判断"，不影响并发。它会在父表行上加共享锁并持有到事务结束，热点父行上是实打实的锁竞争与死锁来源。
- 以为级联删除能在慢日志或 binlog 里查到来龙去脉。级联由存储引擎内部执行，不产生独立 SQL 文本，删错只能靠备份恢复。
- 把"禁用外键"说成绝对结论。单库小系统里外键是省代码的好工具，面试里说清适用边界才是加分项。

## 一句话记住

:::tip
外键锁死分库分表、把校验变成行锁竞争；小单体才值得留。
:::
