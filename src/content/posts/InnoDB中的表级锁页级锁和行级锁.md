InnoDB 的锁**按粒度分三层：表级锁（意向锁为主）、页级锁、行级锁**。核心结论：**InnoDB 的并发能力来自行级锁；表级锁是"表结构层的锁"，不是"数据行的锁"** —— 这也是最容易被误解的地方。

## 核心区分：表级锁 ≠ 锁整张表的数据

InnoDB 的"表级锁"主要是**意向锁（Intention Lock）** —— 它标记的是"**这个表上有某些行已被加锁**"，**本身不锁数据行**，只是给别的会话一个信号。真正的数据锁仍是行锁。

## 意向锁（Intention Locks）—— 表级锁的主角

意向锁也是**加在表对象上**的，但它**只表达意图，不限制别的会话去碰具体的行**：一个事务持着 IX，别的会话照样可以给同一张表的**其他行**加锁，只要它不去申请整张表的锁。

- **IS（意向共享锁）**：事务要**读**该表的某些行 → 在表上加 IS
- **IX（意向排他锁）**：事务要**写**该表的某些行 → 在表上加 IX
- **S / X（真正的表级共享/排他锁）**：要锁**整张表**时才加

## 为什么需要意向锁（作用）

**目的是让"表级锁"与"行级锁"兼容，且不必逐行检查**：
- 事务 A 要给 id=1 的行加 X 锁 → 先在表上标记 IX，再在行上加 X
- 事务 B 想给**整张表**加 S 锁 → 只需检查表上的 IX → **发现有 IX（不兼容）→ 等待**
- **如果没有意向锁**，B 就得**逐行扫描**检查有没有 X 锁 → 性能灾难

:::tip
**一句话：意向锁是"行锁与表锁之间的信号灯"，让表锁申请能 O(1) 判断是否冲突。**
:::

## 意向锁的兼容性规则

- IS 与 IS、IX、S **兼容**
- IX 与 IX、IS **兼容**，与 **X 不兼容**
- S 与 S、IS 兼容，与 **IX、X 不兼容**
- X 与**任何**意向锁都不兼容

记法很简单：**意向锁之间（IS 与 IX 互相）永远兼容**，多个事务可以同时对同一张表的不同行加锁；冲突只发生在"**有人想锁整张表**"或"**有人想锁同一行**"的时候。

## 页级锁（Page Lock）

- 粒度在**表锁与行锁之间**，锁住**整个数据页**（InnoDB 默认页大小 16KB）
- **InnoDB 中基本不使用** —— 行锁已足够细，且页锁会严重影响并发
- 面试里常被追问"**有没有锁升级**"：流传的说法是，对同一行的**更新次数过多、涉及列过多**时，为避免空间碎片，InnoDB 会把**行锁"提升"为页锁**
- **准确的说法**：页级锁在 MySQL 官方文档里是 **BDB 引擎**支持的粒度，**InnoDB 并没有"行锁自动升级为页锁/表锁"的机制**；行锁的覆盖范围只由**索引访问范围**决定，不会因为更新次数多而自动变大

:::tip
**"页级锁 / 锁升级"这个追问能接住很加分** —— 大多数人只知道"有行锁有表锁"，不知道还有页锁这一层，也不知道 InnoDB 其实不做锁升级。
:::

## 行级锁（Record Lock）—— 并发的主力

InnoDB 的行锁**加在索引上**（不是数据行上）：
- **记录锁（Record Lock）**：锁住某条索引记录
- **间隙锁（Gap Lock）**：锁住索引记录**之间的间隙**，阻止插入
- **临键锁（Next-Key Lock）**：记录锁 + 间隙锁的组合，**RR 隔离级别下的默认加锁单位**

:::tip
**所以"行锁"细分下来才是面试常问的间隙锁与临键锁**（另一份笔记详述）。
:::

## 最重要的一个结论：行锁加在索引上

- 查询**走索引** → 锁**精确的行**（并发高）
- 查询**没走索引** → 锁**扫描过的所有行**（**退化为近似表锁**）

:::tip
**这是"用了 InnoDB 并发还是上不去"的经典原因。** 索引缺失 → 全表扫描 → 锁住整张表。
**同时它也是"加了索引能减少死锁"的真正原因** —— 锁范围从全表缩小到了少量行。
:::

## 锁与隔离级别的关系

| 隔离级别 | 间隙锁 | 说明 |
|---|---|---|
| **RC（读已提交）** | **基本不用** | 只有记录锁 → **幻读风险** → 但并发好 |
| **RR（可重复读）** | ✅ **用** | 临键锁默认加锁 → 防幻读 → **但并发下降、死锁概率上升** |
| **Serializable** | 全部加 | 基本退化为表锁 |

## 避免死锁的实用建议（基于锁机制）

- **统一加锁顺序**（按 id 升序）
- **缩短事务**（锁持有到提交）
- **让 WHERE / JOIN / ORDER BY 的列都有索引**（避免锁范围扩散到全表）
- **RC 级别 + 业务可接受时**，可减少间隙锁带来的冲突

## 常见追问

**问：InnoDB 的表级锁是不是就是"锁住整张表的数据"？**
**答：** 不是。InnoDB 的表级锁主要是意向锁，它只在表上标记"这个表里有行被加了锁"，本身不锁任何数据行；要真正锁整张表得显式 `LOCK TABLES`，或者撞上 DDL 的元数据锁。

**问：既然有行锁了，为什么还要意向锁？**
**答：** 为了让表锁申请能 O(1) 判断冲突。有了表上的 IX，想加整表 S 锁的事务看一眼表级标记就知道要等；没有意向锁，它只能逐行扫描找 X 锁，等于性能灾难。

**问：为什么说"行锁加在索引上"，这对线上有什么影响？**
**答：** InnoDB 锁的是索引记录。走索引就只锁精确的几行，没走索引就会锁住扫描过的全部行，退化成近似表锁——这既是"用了 InnoDB 并发还是上不去"的原因，也是"加了索引能减少死锁"的真正原因。

**问：行锁会不会升级成页锁或表锁？**
**答：** 流传的说法是同一行更新太频繁、涉及列太多时行锁会提升为页锁；但 InnoDB 并没有自动锁升级机制，页级锁是 BDB 引擎的粒度。锁范围真正变大的原因只有一个：没走索引。

## 易错点

- 把"表级锁"理解成锁住整张表的数据。正确说法：InnoDB 的表级锁主要是意向锁，只做标记、不锁数据行，真正的数据锁仍然是加在索引上的行锁。
- 以为意向锁会互相阻塞。正确说法：IS 与 IX、IX 与 IX 都兼容，多个事务可以同时给同一张表的不同行加锁；只有申请整表 S/X 时才会和意向锁冲突。
- 以为"没走索引只是慢一点"。正确说法：扫描范围就是加锁范围，缺索引的 UPDATE/DELETE 会锁住扫过的所有行，并发骤降、死锁概率上升。
- 以为 InnoDB 会像某些数据库那样自动锁升级。正确说法：InnoDB 不做行锁到页锁/表锁的自动升级，粒度只由索引访问范围决定。

## 一句话记住

:::tip
**表级锁只是意向信号，真正的并发靠加在索引上的行锁。**
:::
