Google ADK（Agent Development Kit）是 Google 2025 年开源的 **Agent 开发框架**，也是 Google Cloud 与 Gemini 生态里 Agent 体系的核心组件。它把「定义 Agent、编排多个 Agent、驱动执行、调试与部署」收进一套 SDK，并且**原生实现 A2A 协议、同时支持 MCP**，让 ADK 构建的 Agent 既能被别人当独立主体调用，也能调用外部的工具与数据 —— 这是它最独特的定位。

## 它到底是什么：一个 SDK 加一个协议位置

ADK 要解决的不是「怎么调一次模型」，而是「怎么把一个 Agent 从定义写到上线」：用声明式配置描述身份、指令、工具与模型，用 Runner 驱动会话执行，用 Session 保存多轮状态，用事件流把过程暴露出来，最后接上调试、评估与部署链路。

两件事把它和大多数框架区分开。一是它**原生支持 A2A 协议**：ADK 构建的 Agent 可以直接暴露为 A2A Server，供其他厂商、其他框架的 Agent 调用。二是它**同时是 MCP 的支持方**：可以作为 MCP Client 去使用外部的工具与数据。一个向内取能力，一个向外接任务，这让 ADK 天然处在「多 Agent 互操作」的枢纽位置。

## 四个核心抽象：Agent、Runner、Session、Tool

| 抽象 | 职责 | 关键点 |
| --- | --- | --- |
| Agent | 具备身份、指令、可用工具与模型配置的智能体 | 身份与指令决定它的行为边界 |
| Runner | 驱动 Agent 执行会话的运行时 | 管理事件流、状态与插件 |
| Session | 承载对话历史与状态 | 多轮上下文与跨轮状态存在这里 |
| Tool | Agent 的能力出口 | 分函数工具、Agent 工具、MCP 工具、内置工具 |

把这四个摆在一起，分工是清楚的：Agent 是「配置加决策策略」，Runner 是「执行引擎」，Session 是「状态容器」，Tool 是「外部能力入口」。面试时能讲清这层分工，比背 API 名字有用得多。尤其注意 Tool 的四种形态 —— **Agent 工具**指的是把另一个 Agent 直接当一个工具来调用，这是 ADK 编排能力的支点。

## 多 Agent 编排：工作流型 Agent 与 Agent-as-Tool

ADK 的多 Agent 体系有两个方向。一个是**确定性的工作流型 Agent**：Sequential（顺序）、Parallel（并行）、Loop（循环），负责把子 Agent 按明确的拓扑串起来，适合步骤可枚举、流程稳定的任务，行为可预测、成本可估算。

另一个是**模型驱动的形态**：LlmAgent 由模型自己决定下一步调用哪个工具或哪个子 Agent，AutoFlow 等形态也在这一侧，并且允许通过**自定义 Agent** 自由扩展，把特殊逻辑写成自己的执行单元。两条路线可以混用：主干流程用 Sequential 固定下来，某个需要临场判断的节点挂一个模型驱动的子 Agent。

最值得记住的设计是「**把 Agent 当工具来用**」。一个子 Agent 被包装成父 Agent 的一个 Tool 后，父 Agent 像调函数一样调它，输入输出都是普通参数，内部的多轮推理被封装起来。它让不同角色的组合非常自然，也让「编排」从硬编码流程变成了可组合的积木。

## 事件流：整套工程能力的底座

Runner 对外输出的不是「一段最终文本」，而是以**事件（Event）**为单位的流：模型文本、工具调用、工具结果、状态变更、错误，全是同一类对象，按发生顺序流式吐出。

好处是下游只需要消费一种数据流：**流式 UI、SSE 接口、审计日志、链路追踪**都能基于同一套事件模型实现，不必为不同场景各写一套采集逻辑。这也是为什么 ADK 的调试与可观测能力不像事后补的补丁 —— 事件流本来就是运行时的第一等公民。

## 一个最小例子

```python
from google.adk.agents import LlmAgent

def get_weather(city: str) -> dict:
    """查询指定城市的天气。"""
    return {"city": city, "weather": "sunny"}

root_agent = LlmAgent(
    name="weather_helper",
    model="<受支持的模型>",      # Gemini，或其他受支持的模型
    instruction="你是天气助手，需要时调用工具。",
    tools=[get_weather],        # 普通函数即函数工具
)
```

按官方约定，在 `agent.py` 里暴露 `root_agent`，之后用 ADK 自带的命令行工具就能起本地 Developer UI 做交互调试，也可以直接跑命令行对话。这段只是结构示意：模型名、目录组织与命令行参数请以官方文档为准，面试里说清「Agent 是配置对象、工具是普通函数、Runner 负责跑」这三件事就够了，别硬背字符串。

## Developer UI：能看清「它当时为什么这么做」

ADK 自带可视化的调试界面，能看到**每一步的模型调用、实际发出的提示、工具调用与返回结果**，并且支持**回放**一次完整执行。这在生产调优 Agent 时价值极高：Agent 出错时最贵的成本是「不知道为什么」，而一次可回放的完整轨迹把定位问题从「猜」变成「看」。

回放还让一件事变得可操作 —— 把线上的一次失败案例固定下来，改一版指令或工具描述再跑一遍，比较两次执行的差异。**能看清它当时为什么这么做，比什么提示词技巧都管用。**

## 与 Google 生态的绑定，以及它的代价

ADK 深度集成 Gemini 模型，同时也支持其他模型与 Vertex AI；向上有 ADK 与 A2A 的组合（自己既当编排方，也当被调用方），向下有通往 Google Cloud 的部署链路；企业级能力上关注可观测性、评估、安全与部署，与 Google Cloud 的 Trace、评测服务、Agent Engine 打通。这也是它与「轻量个人项目型框架」最大的区别。

代价要说清楚：**它对 Google 生态有偏好**，最顺的路径、最完整的集成都在 Gemini 与 GCP 上。但 ADK 本身是开源的、可自行部署，绑定的是「默认路径」而不是「运行前提」—— 选型时把这一点分开讲，比一句「绑定 Google」准确得多。

## 多语言是一把双刃剑

ADK 提供 **Python、Java、Go、TypeScript** 四种语言实现，这在主流 Agent 框架里比较少见，对已有 Java 或 Go 技术栈的团队是实打实的加分项 —— 不必为了用 Agent 框架而引入一门新语言。

但多语言会摊薄框架的「深度」：**各语言实现的功能深度并不完全一致**。所以选型时必须先确认目标语言那套实现的完整度，**尤其是插件、评估与可观测这几块**，它们往往是最晚补齐、又最先被生产环境用到的部分。这是 ADK 选型里最容易踩的坑，也是面试里最能体现你读过文档的一句话。

## 与其他框架的对比定位

| 框架 | 强在哪 | 什么情况选它 |
| --- | --- | --- |
| LangGraph | 图式状态机与复杂编排 | 流程复杂、需要对分支与状态做显式控制 |
| AutoGen / CrewAI | 多角色对话与分工 | 主要靠角色协作推进，流程不那么刚性 |
| ADK | 多语言覆盖 + A2A/MCP 协议支持 + Google Cloud 集成 | 需要跨厂商 Agent 互操作，或已在 Google 生态内 |

一句话收束对比：LangGraph 强在「怎么把流程画对」，AutoGen 与 CrewAI 强在「怎么让多个角色聊明白」，ADK 强在「怎么让 Agent 之间、Agent 与工具之间按标准协议互通，并且落到云上」。**如果你的系统需要跨厂商 Agent 互操作，ADK 的 A2A 支持就是它最独特的优势。**

## 常见追问

**Q：ADK 和 MCP、A2A 分别是什么关系？**
A：方向不同。MCP 解决「我的 Agent 怎么用外部工具与数据」，ADK 在这里是 MCP Client；A2A 解决「我的 Agent 怎么被别的 Agent 当独立主体调用」，ADK 在这里能把 Agent 暴露成 A2A Server。取能力和接任务，是两条链路。

**Q：多语言支持是不是意味着四种语言功能一样强？**
A：不是。各语言实现深度不一致，插件、评估、可观测与部署链路的齐备程度要用目标语言逐个核对。这是 ADK 最常被追问、也最容易答错的一点。

**Q：用了 ADK 是不是就必须上 Google Cloud？**
A：不必。它是开源的、可自行部署；GCP 集成是加分项而非前置条件，只是默认路径更偏 Google 生态。

**Q：为什么说调试界面比提示词技巧更重要？**
A：Agent 的失败往往不是提示写得不够好，而是某一步选错工具、拿错上下文、或多轮后状态被覆盖。能看到每一步的模型调用与工具结果，才谈得上针对性修改。

## 易错点

- **把它当成「提示词框架」**：ADK 的重心是运行时（Agent + Runner + Session + 事件流）和工程链路（调试、评估、部署），提示词只是 Agent 配置里的一项，只谈 instruction 会答不到点上。
- **以为多语言就等于功能对齐**：四种语言实现深度不同，尤其插件、评估、可观测部分，选型必须按目标语言单独确认。
- **把 A2A Server 和 MCP Server 混为一谈**：A2A 是 Agent 之间的任务委托协议，MCP 是应用取工具与数据的协议，ADK 在两个方向上扮演的角色不同。
- **以为事件流只是日志**：事件流是 Runner 的对外接口，UI、SSE、审计、追踪都靠它；把它当附属产物，就理解不了 ADK 为什么能一套模型支撑多种消费场景。

## 一句话记住

:::tip
ADK 的价值不在写 Agent，而在编排、互操作与工程化一次给全。
:::
