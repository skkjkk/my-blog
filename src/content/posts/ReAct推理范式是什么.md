ReAct 是 "Reasoning + Acting" 的缩写，指让模型**交替进行推理和行动**：先想一步（Thought），再做一个动作（Action，比如调用工具），拿到观察结果（Observation）后接着想，如此往复，直到给出最终答案（Final Answer）。它的价值在于把"想"和"做"交织在同一条轨迹里，让每一步动作都基于最新的真实反馈，而不是靠模型内部一次性规划到底。因此它既能压低幻觉，也能在观测与预期不符时当场改方向，这就是"更可靠"的具体来源。

## 一条 ReAct 轨迹由哪三种元素构成

轨迹只有三种基本元素，交替出现：Thought 是模型对当前状态的自然语言判断，写清"我已知什么、下一步要做什么、为什么"；Action 是一次结构化的外部操作，通常是工具调用，带明确的工具名和参数；Observation 是环境返回的结果，由外部灌回上下文，不是模型自己编的。三者循环若干轮，最后以 Final Answer 收尾。

这个格式的真正作用是**可读、可审计、可回放**：每一步想什么、做什么、拿到什么都留下了记录，失败时能定位到具体是哪一步开始跑偏，而不是对着一个错误答案猜原因。面试时讲清这点，比背名词有说服力得多。

## 为什么要它：纯 CoT 和纯 Act 各缺一半

两种极端做法都有硬缺口。只推理（纯 CoT）容易**产生幻觉**——推理链条再自洽，也与真实世界脱节，因为它的全部依据都是模型参数里的记忆；只行动（纯 Act）缺乏规划能力，动作是反射式的，做完一步不知道下一步该去哪。

ReAct 的解法是让模型**用真实观测来纠正推理**，把"事实来源"从模型参数转移到环境反馈，从而降低幻觉、提升事实准确率。换句话说，它不是在提示词层面把推理写得更长，而是给推理接上了一个可以被检验的外部世界。

| 范式 | 有没有显式推理 | 有没有外部反馈 | 典型失效方式 |
| --- | --- | --- | --- |
| 纯 CoT | 有 | 没有 | 链条自洽但事实错误，无从发现 |
| 纯 Act | 没有 | 有 | 动作碎片化，缺全局规划 |
| ReAct | 有 | 有 | 步数一多，噪声累积与错误级联 |

## 一条典型轨迹长什么样

下面的轨迹是格式示意，重点看 Thought 与 Observation 怎么接力：

```text
问题：杭州今天的最高气温比北京高几度？

Thought 1：需要两个城市的气温，先查杭州，用 weather 工具。
Action 1：weather(city="杭州")
Observation 1：{"city": "杭州", "high": 26}

Thought 2：拿到 26℃，还差北京，继续查。
Action 2：weather(city="北京")
Observation 2：{"city": "北京", "high": 19}

Thought 3：两个数都来自工具返回，可以做减法，26 - 19 = 7。
Final Answer：杭州比北京高 7℃。
```

这里的关键不是代码本身，而是每一步 Thought 都只承诺"下一步做什么"，然后用 Observation 兑现。如果 Observation 1 返回的是"城市不存在"，下一轮 Thought 就会改成先做城市名纠错，而不是继续算减法。

## 它让 Agent 更可靠，体现在四点

- **事实性提升**：答案里的关键事实都锚定在真实观测上，不是模型凭记忆补的。
- **可纠错**：当观察与预期不符时，模型能在下一轮 Thought 中修正方向，而不是把错误一路带到结尾。
- **可验证**：每一步动作与结果都留痕，失败时可以逐段回放，定位问题环节。
- **可分解**：长任务被切成多个小步，每步难度降低，单步出错的影响面被限制住。

这四点合起来解释了"更可靠"到底可靠在哪：不是模型变聪明了，而是每一步都有外部事实参与裁决。

## 局限：什么任务不适合硬套 ReAct

ReAct 的代价同样明确，而且都随着步数放大。**上下文污染**——噪声随步数累积，早期有效信息被稀释；**错误级联**——早期错误成为后续推理的前提，越走越偏；**目标漂移**——长链条中模型只盯当前子目标，忘掉原始目标；**成本与延迟**——步数线性甚至超线性增长。

所以 ReAct 适合**中等长度、步数可预期**的任务；长程任务应改用**规划-执行分离**，把规划和执行拆成各自独立的上下文与验收环节。判断标准很直接：任务短、反馈即时、错误代价低，用 ReAct；任务长、状态多、错误会级联，先规划再执行。

## Reflexion 类方法可以叠加在 ReAct 之上

ReAct 的纠错只发生在当前这条轨迹内，任务结束轨迹就丢了，下个类似任务从零开始。Reflexion 在它外面加一个"复盘"环节：任务结束后生成失败原因的分析并存入记忆，下次遇到类似任务时把这段经验带进上下文，从而**跨任务改进**。

两者是叠加关系，不是替代关系。执行循环照旧是 ReAct，多出来的是"把这次的教训写成一条可检索的文字"，让第二次尝试开局就带着第一次的信息。

## 工程实现上的三条约束

**格式约束越严格，模型遵循越好。**工具名、参数结构、Thought 与 Action 的分界都要固定成解析器能吃下的形状，格式一松，模型就会把半截工具调用写进自然语言里。

**工具失败时要把可诊断的错误回填。**不要只丢一个堆栈或 "error"，而是给出模型能据此改参数的信息，比如"字段 user_id 不存在，请改用 id"，这样下一轮 Thought 才有修正的依据。

**每步都应能独立重放。**否则出现错误级联时无法定位是哪一步开始跑偏，重试也只能整条重跑，既贵又丢掉已验证的中间结果。

## 常见追问

- **问：ReAct 和 CoT 的本质区别在哪？** CoT 只在模型内部写推理，链条再长也拿不到新信息；ReAct 每一步推理后面都跟一次真实的 Action 与 Observation，事实依据来自环境而不是参数记忆。
- **问：Action 一定得是工具调用吗？** 泛指任何能读取或改变环境状态的操作，检索、查库、执行代码都算。没有可用的外部动作时，ReAct 就退化成 CoT，纠错的事实来源也就没了。
- **问：为什么它比一次性长链推理更准？** 因为中间结论被观测校验过。观测与预期不符时下一轮就能改方向；而一次性推理只要中间某步想错，后面整条链都建在错误前提上。
- **问：生产上怎么防止它跑飞？** 三件事：把输出格式约束死并限定工具白名单，给步数和 token 设硬上限，把工具报错回填成可诊断信息；再加一步留痕，保证每步可重放。

## 易错点

- 把 ReAct 等同于"多轮工具调用"。区别在于 Thought 有没有被显式写出来并参与下一步决策；只循环调工具、不做显式推理的状态机不是 ReAct。
- 以为推理写得越细越好。Thought 太长会挤占上下文、放大噪声，反而加剧上下文污染，写清"下一步做什么、依据是什么"就够。
- 忽视格式约束。Action 的格式一旦松动，解析器拿到的是半截调用，轨迹当场断掉，后面的纠错能力全部落空。
- 拿 ReAct 硬扛长程任务。几十步之后上下文污染、错误级联、目标漂移会同时出现，这类任务应该换成规划-执行分离。
