ReAct 是 "Reasoning + Acting" 的缩写，指让模型**交替进行推理和行动**：先想一步（Thought），再做一个动作（Action，比如调用工具），拿到观察结果（Observation）后继续想，如此往复，直到给出最终答案。核心思想是把"想"和"做"交织在同一条轨迹里，让每一步动作都基于最新的真实反馈，而不是靠模型内部一次性规划到底。

1) **它解决了什么问题**。纯 CoT（只推理）容易**产生幻觉** —— 推理链条与真实世界脱节；纯 Act（只行动）缺乏规划能力。ReAct 让模型**用真实观测来纠正推理**，把"事实来源"从模型参数转移到环境反馈，从而大幅降低幻觉、提升事实准确率。

2) **典型轨迹格式**是 Thought → Action → Observation 的交替，最终以 Final Answer 收尾。这个格式让轨迹**可读、可审计、可回放** —— 面试时讲清这点很重要。

3) **它让 Agent 更可靠，体现在四点**。一是**事实性提升**，答案中的关键事实都锚定在真实观察上；二是**可纠错**，当观察与预期不符时，模型能在下一轮 Thought 中修正方向；三是**可验证**，每一步动作与结果都留痕，便于定位失败环节；四是**可分解**，长任务被切成多个小步，每步难度降低。

4) **它也有明确的局限**，这是高分答法的关键。**上下文污染**（噪声随步数累积）、**错误级联**（早期错误成为后续前提）、**目标漂移**（长链条中忘记原始目标）、**成本与延迟**（步数线性甚至超线性增长）。因此 ReAct 适合**中等长度、步数可预期**的任务；长程任务应改用**规划-执行分离**。

5) **Reflexion 类方法可以叠加在 ReAct 之上**，增加一个"复盘"环节：任务结束后生成失败原因的分析并存入记忆，下次遇到类似任务时把这段经验带进上下文，从而**跨任务改进**。

6) **工程上的注意点**：格式约束越严格，模型遵循越好；工具失败时应把**可诊断的错误**回填让模型自我纠正；每步都应能**独立重放**，否则出现错误级联时无法定位是哪一步开始跑偏。
