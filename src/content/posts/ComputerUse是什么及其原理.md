Computer Use 是让模型**直接操作图形界面**（浏览器、桌面软件）的一类能力：模型接收屏幕截图，输出 `click(x, y)`、`type("text")`、`scroll(dx, dy)` 这类结构化动作，由外部执行器在真实屏幕上落地，再截图回传，靠这个闭环代替人完成点击、输入与滚动。它把 AI 的能力边界从"API 空间"扩展到"整个操作系统"，代价是引入了视觉定位误差、状态假设错误与提示注入三类新风险。

## 原理：感知—动作闭环，以及为什么必须每步验证

模型接收**屏幕截图**作为视觉输入，输出**结构化动作**，动作自己不执行，而是交给外部的**执行器（Actor）**在真实屏幕上执行；执行完再截图回传，**如此循环**，直到任务完成或触发终止条件。**这是一个闭环，不是一次性的输出。**

一轮迭代大致是这样：

```text
截图 → 模型输出 {"action": "click", "x": 450, "y": 320}
     → 执行器点击 → 重新截图
     → 模型判定"菜单已展开" → 输出 {"action": "type", "text": "报销单"}
```

闭环里最容易出错的地方不是"想不出动作"，而是**状态假设错误**：模型以为页面已经刷新、以为点击生效了，实际并没有。因此**每个动作后都必须重新观察并验证**（确认提示出现了、页面内容真的变了），不能凭一次输出连续执行多个动作而中间不回头看一眼。

## 模型侧三个核心能力，空间定位是最大难点

模型侧要同时具备三件本事：**视觉理解**——识别界面元素、读出文字、理解布局；**空间定位**——把"那个蓝色的按钮"对应到具体坐标；**动作规划**——判断当前状态下该做什么、下一步做什么。

三者里**空间定位是最大的难点**：纯视觉模型的坐标精度有限，差几十像素就点空。主流实现因此在截图上叠加 **Set-of-Mark（SoM）**这类标注技术，先把可交互元素框出来并编号，让模型输出**元素 ID 而非裸坐标**，定位精度大幅提升。

## 动作空间：从裸坐标到语义化元素引用

早期方案是纯坐标驱动（`click(450, 320)`），现在主流转向**语义化动作**：基于可访问性树（accessibility tree，也叫无障碍树）或 DOM 的元素引用表达"点哪个东西"。**可访问性树尤其适合 Web 场景**——稳定性远高于像素坐标，而且天然带元素角色与名称。

| 维度 | 裸坐标动作 | 语义化动作 |
| --- | --- | --- |
| 表达形式 | `click(450, 320)` | 引用元素 ID / 可访问性树节点 |
| 稳定性 | 分辨率、缩放、主题一变就可能失效 | 布局微调仍可命中 |
| 元素信息 | 只有一个点，没有角色与语义 | 天然带角色、名称与层级 |
| 适用场景 | 画布、绘图、缺少可访问性信息的界面 | Web 与可访问性良好的桌面应用 |

语义化动作不是万能的，一旦界面没有可访问性信息，工程上仍要回退到坐标动作，所以两套动作空间通常是并存的。

## 「看屏幕」这一步的工程优化

截图看似最简单，其实是最贵的一步：每次都要传图、都要推理，成本和延迟都压在这里。常见优化有四条。

- **只截取变化区域**，避免整屏重复上传。
- **降采样与裁剪**，把分辨率压到够用为止。
- **文字用 OCR 提取**，避免让视觉模型去啃界面上的小字。
- **保留上一步的标注图**，避免每轮重新做一遍 SoM 标注。

这几条直接决定单步成本与延迟，而一个真实任务往往要走很多步，所以它们是 Computer Use 能否落地的**决定性因素**。

## 安全：双重确认、白名单、沙箱与提示注入

这类 Agent 能点击**任意按钮**，一次误操作的代价可能是转账、删数据、发错消息，所以安全不是加分项而是前置条件。

- **双重确认机制**：高风险动作执行前必须人工确认。
- **动作白名单与区域限制**：只允许在指定应用、指定区域内操作。
- **沙箱环境隔离**：跑在虚拟桌面或容器里，出问题不波及真实环境。
- **禁止访问生产数据与凭证**：不给它真账号、真密钥、真客户数据。

Anthropic 官方明确把**提示注入**列为最大风险：网页上的一段恶意文本就可能诱导 Agent 泄露数据或执行越权动作。这一点是纯视觉方案绕不开的——模型看到的屏幕内容本身就是不可信输入，界面上任何文字都可能冒充指令。

## 与 RPA、普通工具调用的本质区别

RPA 靠**确定性规则与选择器**：流程写死，稳定但僵化，界面一改版就可能全挂。Computer Use 靠**模型理解界面**，能应对界面变化，代价是**引入不确定性与不可复现性**——同一个任务跑两次，走的路径可能不一样。工程上常见的做法是**两者结合**：固定高频的流程用 RPA，界面多变、需要"看懂"的部分交给 Computer Use。

普通工具调用则是**结构化、精确、可枚举**的：参数有 schema，结果有约定。Computer Use 的"工具"是**整个 GUI**——状态空间巨大、动作语义模糊、失败原因多样。所以它**不是普通 Function Calling 的一个变体，而是一类需要专门工程方法的技术**：视觉定位、状态验证、沙箱，缺一不可。

| 维度 | RPA | Computer Use | 普通工具调用 |
| --- | --- | --- | --- |
| 决策依据 | 确定性规则与选择器 | 模型理解当前界面 | 预定义 schema |
| 界面变化 | 容易失效 | 能适应 | 不涉及 |
| 状态空间 | 有限、可枚举 | 整个 GUI，巨大 | 有限、可枚举 |
| 可复现性 | 高 | 低，路径可能不同 | 高 |
| 主要失败原因 | 选择器失效 | 定位错、状态假设错、提示注入 | 参数错、接口错 |

## 典型代表与成熟度判断

代表实现有 Anthropic 的 **Claude Computer Use**（参考架构，跨桌面与网页）、**OpenAI 的 Operator / CUA**、**Google 的 Project Mariner**，以及各类 RPA 与 GUI 智能体产品。Anthropic 的官方实现采用**虚拟桌面 + 截图循环**，并强调**不依赖特定系统、纯视觉**，以便跨平台复用同一套策略。

成熟度上，它已经能完成相当复杂的网页与桌面任务：表单填写、跨应用数据搬运、后台系统操作。但**长链条任务的累积误差**、**提示注入**、**细致操作（拖拽、画图、复杂表格编辑）**仍是显著瓶颈。**目前最可靠的定位是"有人监督的自动化"，而不是完全自主。**

## 常见追问

**Q：为什么不让模型一次输出十个动作批量执行？**
A：因为每个动作都会改变界面状态，批量执行等于在没看到结果的前提下赌后续动作的前提都成立，出错后也无法定位是哪一步偏的；正确做法是一步一观察，最多把无副作用的连续输入合并。

**Q：没有可访问性树的界面（画布、游戏、部分原生软件）怎么办？**
A：只能回退到纯视觉路线：截图加 SoM 标注、输出坐标动作，再靠动作后的截图验证与失败重试兜住定位误差。

**Q：它和 Agent 里的工具调用是什么关系？**
A：是工具调用的一种极端形态——工具不再是几个带 schema 的函数，而是整个图形界面；因此它额外需要视觉定位、状态验证和沙箱这些工程手段，不能照搬函数调用的那套可靠性假设。

**Q：企业里最先能落地在什么场景？**
A：没有 API、只能人肉点界面的后台流程，比如表单录入、跨系统对账搬运；这类场景价值明确，而且天然适合配一个人在边上盯着。

## 易错点：四句最容易说错的话

- **把 Computer Use 当成"更聪明的 RPA"**：RPA 的稳定来自写死流程，Computer Use 的灵活来自模型判断，两者是互补关系，别指望它天然比 RPA 稳。
- **用单步成功率评估可靠性**：单步成功率再高，几十步连乘下来也会明显下降；长链条任务要看端到端成功率，并补上每步验证与失败重试。
- **只做截图理解，不做状态验证**：模型说"已经点了"不等于真点上了，必须用下一张截图确认弹窗出现、内容变化。
- **忽略提示注入**：屏幕上的一切文字都是不可信输入，网页里的恶意文本可以冒充指令，只能靠白名单、沙箱与人工确认兜底。

:::tip[一句话记住]
Computer Use 是一个必须每步验证的截图闭环，不是一次性的动作预测。
:::
