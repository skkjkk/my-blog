MCP（Model Context Protocol，模型上下文协议）是一套开放协议，用于标准化 AI 应用与外部资源（数据、工具、提示模板）之间的连接方式：它规定了客户端与服务器的通信规范、资源暴露方式、工具描述格式和提示模板机制，让不同的 AI 应用能够以统一方式接入各种数据源与工具，不必为每个数据源单独写集成代码。它真正解决的问题是集成碎片化——把 N 个应用与 M 个数据源之间的 N×M 套适配，收敛成 N+M 套。

## 它到底是什么

MCP 是一份协议规范，不是框架也不是 SDK。它规定了三层角色：**Host**（宿主应用，如 Claude Desktop、IDE）内嵌多个 **Client**；每个 Client 与一个 **Server** 建立**独立会话**；Server 侧实现具体的 MCP 协议并对接真实系统（文件系统、数据库、内部 API）。

通信层基于 **JSON-RPC 2.0**，消息就是请求、响应、通知三种形态，所以任何能收发 JSON 的进程都能当 Server，不需要额外绑定某种语言或运行时。协议只规定「工具怎么被描述、发现、调用、返回」，不规定工具的业务实现。

```json
{"jsonrpc": "2.0", "id": 1, "method": "tools/call",
 "params": {"name": "read_file", "arguments": {"path": "README.md"}}}
```

## 它解决的问题：集成碎片化

在没有 MCP 之前，每个 AI 应用要接一个数据源就得写一套适配，每接一个工具就多一套代码，N 个应用 × M 个数据源就是 N×M 的工作量，而且每套适配都锁死在自己的框架里，无法复用。MCP 把**数据源与工具抽象成统一的 Server**，应用只做一次 MCP Client 适配，复杂度降到 N+M。**这是它最大的价值。**

| 维度 | 没有 MCP | 有 MCP |
| --- | --- | --- |
| 适配工作量 | N×M 套 | N+M 套 |
| 新增一个数据源 | 每个应用各改一遍 | 只新增一个 Server |
| 新增一个应用 | 重写全部集成 | 只实现一次 Client |
| 工具描述格式 | 各家自定义 | 协议统一的 schema |
| 复用边界 | 绑定某个框架 | 跨宿主复用 |

## 它统一了上下文供给的三类资源

MCP 把「模型能看到什么、能做什么」拆成三类语义不同、取用方式也不同的资源，客户端可以按需取用：

| 资源类型 | 是什么 | 典型例子 | 谁来触发 |
| --- | --- | --- | --- |
| **Tools** | 可被调用的动作 | 查库、发请求、写文件 | 模型决定何时调用 |
| **Resources** | 可读取的上下文数据 | 文件、数据库记录 | 应用按需读取后拼进上下文 |
| **Prompts** | 可复用的提示模板 | 固定的分析模板 | 通常由用户显式选择 |

三类分开的意义是：**动作有副作用、数据没有、模板是给人选的**，混在一个接口里就没法做权限和确认。

## 传输方式

标准传输是 **stdio**（本地进程，适合本地工具）：Host 把 Server 作为子进程拉起，走标准输入输出，不经过网络，天然不需要认证。另有 **SSE** 和 **Streamable HTTP** 用于远程部署，此时必须考虑**认证与授权**——协议标准化了消息格式，但不会替你把鉴权、租户隔离和审计做好。

## 关键能力：能力协商与动态发现

Client 初始化时与 Server 交换**协议版本与能力声明**，双方据此确定能用哪些特性；之后可以调用 `tools/list`、`resources/list` 拉取可用能力列表。**这意味着工具是动态发现的** —— 新增工具无需改客户端代码，Server 侧加一个工具，所有宿主下次拉列表就能看到。

## 反向能力：Sampling 与 Roots

协议不只允许 Client 调 Server，也允许 Server 反向请求 Client：

- **Sampling**：Server 请求 Client 代为调用 LLM，复用宿主的模型能力与配额，这样 Server 不必自己绑定模型。
- **Roots**：Server 请求 Client 暴露文件系统等根目录上下文，明确自己可操作的范围边界。

## 它与 Function Calling 的关系

这两者经常被混为一谈，其实是**互补的上下层**：**Function Calling 是模型接口层面的机制**（模型输出结构化的调用意图）；**MCP 是应用与工具之间的协议层**（规定工具怎么被描述、发现、调用、返回）。MCP 内部完全可以用 Function Calling 来实现 LLM 侧的推理。

| 维度 | Function Calling | MCP |
| --- | --- | --- |
| 层次 | 模型接口层 | 应用与工具之间的协议层 |
| 规定什么 | 调用意图与参数 schema | 工具的发现、描述、调用、返回 |
| 谁来实现 | 模型厂商与 SDK | Host 与 MCP Server |
| 关系 | 下层机制 | 上层协议，内部可复用前者 |

## 生态意义与边界风险

MCP 推动生态从「框架竞争」转向「标准竞争」：它已被主流 IDE 与 Agent 框架广泛支持，工具作者只需实现一次 Server，就能在多个宿主中使用，**这是它快速普及的根本原因**。但它标准化了「怎么接工具」，**没有解决**工具越权、提示注入、结果可信度这些问题。

:::caution[边界]
MCP Server 引入的第三方代码，本质上扩大了攻击面。权限隔离、信任分级、脱敏与审计仍然需要宿主侧自己做。
:::

## 常见追问

**Q：有了 MCP，是不是就不用为每个工具写对接代码了？**
不是。MCP 标准化的是「怎么接」，Server 内部对接真实系统的适配仍然要写，区别是**写一次就能被多个宿主复用**，不必按应用重写。

**Q：远程部署 MCP Server 最容易漏掉什么？**
认证与授权。stdio 是本地子进程模型，天然没有网络暴露；换成 SSE 或 Streamable HTTP 之后，鉴权、限流、租户隔离都得宿主和部署方自己补齐。

**Q：MCP 会不会让工具调用变安全？**
不会。协议只统一了描述与调用格式，越权访问、提示注入、返回结果不可信这些问题依旧存在，要靠宿主侧的权限隔离与审计。

**Q：MCP 和 A2A 有什么区别？**
MCP 是「调用本地或远程的一个工具」，本质是函数调用；A2A 是「把一件事交给另一个独立 Agent」，需要考虑任务生命周期与产物交付。前者接工具，后者接主体。

## 易错点

- **把 MCP 当成 Function Calling 的替代品**：它是上层的协议层，不是替代，两者可以叠加使用。
- **以为 Server 必须自带模型**：Sampling 让 Server 反向借用宿主的模型能力与配额，Server 自己不必绑定模型。
- **以为新增工具要改客户端**：能力是动态发现的，调用 `tools/list` 即可拿到最新列表。
- **以为协议自带安全保证**：越权、注入、结果可信度都不在协议范围内，第三方 Server 反而扩大了攻击面。

## 一句话记住

:::tip
MCP 把 N×M 套工具集成，收敛成一套标准协议的 N+M。
:::
