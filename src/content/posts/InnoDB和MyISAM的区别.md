InnoDB 是 MySQL 5.5 之后的**默认存储引擎**，MyISAM 是遗留引擎。两者的核心差异可以概括为一句话：**InnoDB 面向"写入与并发"，MyISAM 面向"只读与查询"。**

## 事务支持 —— 最大的分水岭

InnoDB **支持 ACID 事务**（`BEGIN`/`COMMIT`/`ROLLBACK`），具备 undo log（回滚）、redo log（崩溃恢复）、MVCC 多版本并发控制；MyISAM **完全不支持事务**，一条 SQL 要么全部成功要么全部失败，没有回滚能力。**凡是需要事务的业务（转账、下单、扣库存）只能用 InnoDB。**

差别不只是语法：MyISAM 缺的是**回滚的能力**。转账扣了 A 的余额、还没来得及加 B 的余额就报错，MyISAM 只能把半截结果留在库里等人手工修；InnoDB 用 undo log 把这条语句改过的行全部还原。

## 锁粒度 —— 并发能力的决定因素

InnoDB 用**行锁 + 间隙锁 + 临键锁**（精确到索引记录），并发写能力高；MyISAM 只有**表级锁** —— 一旦有写操作，**整张表全部锁死**，读也不能进。

:::tip
**这是最容易被面试官追问的点**：MyISAM 表 A 在读的同时，表 B 想写 → **写必须等所有读释放表锁**。所以 MyISAM 的"读多写少"优势本质是**用写的代价换读的高并发**。
:::

## 索引结构

InnoDB 聚簇索引（**数据和索引在同一个 B+ 树**，主键即数据存放位置），**二级索引叶子节点存主键值**，回表需要再查一次聚簇索引；MyISAM 是**非聚簇索引**（数据和索引分离），二级索引叶子节点**直接存数据地址**，查完即得。

两边的主键也有区别：InnoDB 的表必须有聚簇索引，没显式主键就找唯一非空索引，再没有就隐式生成一个行 ID；MyISAM 允许没有主键的表，数据按插入顺序存放。

:::tip
副作用：InnoDB 的二级索引查询**可能回表**，非覆盖索引场景比 MyISAM 多一次查找。
:::

## 崩溃恢复能力

InnoDB 有 **redo log**（WAL 预写日志）→ 断电后可恢复已提交事务；MyISAM **只有 `CHECK TABLE` 手动修复**，断电后数据可能损坏且**无法自动恢复**。

WAL 的意思是先写日志再改数据页：事务提交时 redo log 已经落盘，重启时重放日志补齐没来得及写回的数据页，未提交的事务再用 undo log 回滚。MyISAM 写数据是直接改文件，没有这层日志，断电时正在写的表可能整张损坏，只能靠 `CHECK TABLE` / `REPAIR TABLE` 这类手动检查去捞，捞不回的部分就永久丢了。

## 外键与约束

InnoDB **支持外键**（会建索引并触发级联检查）；MyISAM **不支持外键**，外键只在应用层校验。

具体说，InnoDB 建外键时会在子表对应列上自动建索引，插入、更新、删除都要过一遍级联检查（`CASCADE`、`SET NULL` 等）。MyISAM 遇到 `FOREIGN KEY` 语法不报错，是**直接忽略**——所以从 InnoDB 换到 MyISAM，约束会静默失效，脏数据照样写得进去。

## 全文索引

MyISAM **原生支持 FULLTEXT 全文索引**；InnoDB 从 **MySQL 5.6 起**也支持了（但中文分词仍需应用层处理，如用 Elasticsearch）。

这条常被当成"MyISAM 还有独特优势"的例子，其实早就不是了：InnoDB 的 FULLTEXT 在事务表上可用，不用为了全文索引把整张表退回 MyISAM；真要中文分词，两边都得额外配分词器，正经的搜索还是交给 Elasticsearch 这类外部引擎。

## COUNT 性能

`COUNT(*)` 在 MyISAM 上走索引统计，**几乎瞬间返回**；InnoDB 必须扫描（InnoDB 用 MVCC 无法保存精确行数），大表上差距明显。

差距的根源是可见性：MyISAM 把表的精确行数存在元数据里，不带 `WHERE` 时直接读这个数；InnoDB 的同一张表在不同事务眼里行数可能不同，缓存一个全局数字就是错的，只能挑一棵最小的索引从头数。不过条件一旦加上 `WHERE`，MyISAM 也得老老实实扫表，这个优势立刻消失。

## 行锁的额外代价

InnoDB 的行锁是加在**索引**上的，若 SQL **没走索引就会退化成表锁**，看起来像 MyISAM 的问题 —— 这是"明明用了 InnoDB 还是并发上不去"的常见原因。

更细一层：锁的真正对象是扫过的那些索引记录，索引失效时全表扫一遍就锁住全部记录；间隙锁、临键锁还会把区间也锁上，让相邻位置的插入被挡住。所以排查这类问题第一步是 `EXPLAIN` 看有没有走索引，第二步才是看有没有长事务一直不提交、把锁攥在手里。

## 对比一览表

| 维度 | InnoDB | MyISAM |
| --- | --- | --- |
| 事务 | 支持 ACID，可回滚 | 不支持，无回滚能力 |
| 锁粒度 | 行锁、间隙锁、临键锁 | 表级锁，写锁全表 |
| 索引结构 | 聚簇索引，二级索引存主键需回表 | 非聚簇索引，叶子存数据地址 |
| 崩溃恢复 | redo log 自动恢复 | 只能手动 CHECK / REPAIR |
| 外键 | 支持，级联检查 | 不支持，语法直接忽略 |
| 全文索引 | MySQL 5.6 起支持 | 原生支持 |
| COUNT(*) | 需扫描索引计数 | 读元数据，瞬时返回 |
| 典型场景 | 增删改多的业务表 | 只读归档、日志类历史表 |

## 易错点

- "MyISAM 查询快" → **只在纯读场景成立**。一旦有写，并发急剧下降；且现代版本 InnoDB 经 B+ 树缓存优化，纯读性能已与 MyISAM 接近。
- "MyISAM 更省空间" → **不准确**。MyISAM 有固定大小的行指针（因为索引存地址），InnoDB 聚簇索引虽存主键但无额外指针行开销，两者空间差异不大。
- "MyISAM 支持表级锁所以更简单" → 简单的是**开发**，代价是**并发与可靠性**。
- "用了 InnoDB 就一定高并发" → **错**。行锁加在索引上，SQL 不走索引、或者长事务不提交，照样会堵成一团。

## 选型结论

:::tip
**新项目一律用 InnoDB，没有例外。** MyISAM 只在"只读归档、极端低写入、需要 FULLTEXT 而不想升级版本"这类遗留场景里保留。**从 MyISAM 迁移到 InnoDB 用 `ALTER TABLE ... ENGINE=InnoDB`**，迁移前务必备份（表锁定时间长、大表需预留充足磁盘空间做双份副本）。
:::

## 常见追问

**问：面试时这条该怎么组织答案？**
**答：** 主线打事务 + 锁粒度（InnoDB 行锁支持事务、MyISAM 表锁无事务 → 写并发天差地别），再补聚簇索引 vs 非聚簇索引对回表与 COUNT 性能的影响，最后落到"新项目无脑选 InnoDB + 迁移注意大表锁表"。其中"二级索引要回表"最能体现对索引结构的理解。

**问：MyISAM 读更快，为什么还选 InnoDB？**
**答：** 只在纯读场景成立。一旦有写，MyISAM 的表锁会让读也排队等锁；InnoDB 的行锁配缓冲池，读写混合下综合吞吐更高，现代版本纯读已经和 MyISAM 很接近。

**问：已经用了 InnoDB，为什么并发还是上不去？**
**答：** 行锁加在索引上，SQL 不走索引就退化成锁全表，表现得和 MyISAM 一样。先 EXPLAIN 确认走了索引，再查有没有长事务一直持锁不放。

**问：从 MyISAM 迁移到 InnoDB 要注意什么？**
**答：** ALTER TABLE ... ENGINE=InnoDB 会重建整张表并且锁表，大表要预留磁盘做双份副本、迁移前务必备份；原先依赖 COUNT(*) 秒回和 FULLTEXT 的查询也要重新评估。

## 一句话记住

:::tip
新项目一律选 InnoDB，MyISAM 只留给只读归档。
:::
