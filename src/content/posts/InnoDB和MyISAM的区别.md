InnoDB 是 MySQL 5.5 之后的**默认存储引擎**，MyISAM 是遗留引擎。两者的核心差异可以概括为一句话：**InnoDB 面向"写入与并发"，MyISAM 面向"只读与查询"。**

1) **⭐ 事务支持 —— 最大的分水岭**
InnoDB **支持 ACID 事务**（`BEGIN`/`COMMIT`/`ROLLBACK`），具备 undo log（回滚）、redo log（崩溃恢复）、MVCC 多版本并发控制；MyISAM **完全不支持事务**，一条 SQL 要么全部成功要么全部失败，没有回滚能力。**凡是需要事务的业务（转账、下单、扣库存）只能用 InnoDB。**

2) **⭐ 锁粒度 —— 并发能力的决定因素**
InnoDB 用**行锁 + 间隙锁 + 临键锁**（精确到索引记录），并发写能力高；MyISAM 只有**表级锁** —— 一旦有写操作，**整张表全部锁死**，读也不能进。
> **这是最容易被面试官追问的点**：MyISAM 表 A 在读的同时，表 B 想写 → **写必须等所有读释放表锁**。所以 MyISAM 的"读多写少"优势本质是**用写的代价换读的高并发**。

3) **索引结构**
InnoDB 聚簇索引（**数据和索引在同一个 B+ 树**，主键即数据存放位置），**二级索引叶子节点存主键值**，回表需要再查一次聚簇索引；MyISAM 是**非聚簇索引**（数据和索引分离），二级索引叶子节点**直接存数据地址**，查完即得。
> 副作用：InnoDB 的二级索引查询**可能回表**，非覆盖索引场景比 MyISAM 多一次查找。

4) **崩溃恢复能力**
InnoDB 有 **redo log**（WAL 预写日志）→ 断电后可恢复已提交事务；MyISAM **只有 `CHECK TABLE` 手动修复**，断电后数据可能损坏且**无法自动恢复**。

5) **外键与约束**
InnoDB **支持外键**（会建索引并触发级联检查）；MyISAM **不支持外键**，外键只在应用层校验。

6) **全文索引**
MyISAM **原生支持 FULLTEXT 全文索引**；InnoDB 从 **MySQL 5.6 起**也支持了（但中文分词仍需应用层处理，如用 Elasticsearch）。

7) **COUNT 性能**
`COUNT(*)` 在 MyISAM 上走索引统计，**几乎瞬间返回**；InnoDB 必须扫描（InnoDB 用 MVCC 无法保存精确行数），大表上差距明显。

8) **行锁的额外代价**
InnoDB 的行锁是加在**索引**上的，若 SQL **没走索引就会退化成表锁**，看起来像 MyISAM 的问题 —— 这是"明明用了 InnoDB 还是并发上不去"的常见原因。

9) **⚠️ 常见误区**
- "MyISAM 查询快" → **只在纯读场景成立**。一旦有写，并发急剧下降；且现代版本 InnoDB 经 B+ 树缓存优化，纯读性能已与 MyISAM 接近。
- "MyISAM 更省空间" → **不准确**。MyISAM 有固定大小的行指针（因为索引存地址），InnoDB 聚簇索引虽存主键但无额外指针行开销，两者空间差异不大。
- "MyISAM 支持表级锁所以更简单" → 简单的是**开发**，代价是**并发与可靠性**。

10) **选型结论**
> **新项目一律用 InnoDB，没有例外。** MyISAM 只在"只读归档、极端低写入、需要 FULLTEXT 而不想升级版本"这类遗留场景里保留。**从 MyISAM 迁移到 InnoDB 用 `ALTER TABLE ... ENGINE=InnoDB`**，迁移前务必备份（表锁定时间长、大表需预留充足磁盘空间做双份副本）。

11) **面试答法建议**。三点：**① 事务 + 锁粒度是主轴**（InnoDB 行锁支持事务，MyISAM 表锁无事务 → 写并发天差地别）；② 补充**聚簇索引 vs 非聚簇索引**（影响回表与 COUNT 性能）；③ **落到"新项目无脑选 InnoDB + 迁移注意大表锁表"**的实践结论。**第二点的"二级索引要回表"最能体现对索引结构的理解。**
