JVM 的内存结构决定了"对象在哪、什么时候被回收"，GC 机制决定了"怎么回收"，而监控与调优则是"怎么知道它健康、出问题怎么治"。

1) **运行时数据区（JVM 内存结构）**
- **堆（Heap）**：**线程共享**，存放几乎所有对象实例与数组。**唯一会被 GC 重点回收的区域**，也是 OOM 最常发生的地方。
- **虚拟机栈（VM Stack）**：**线程私有**，每次方法调用压入**栈帧**（局部变量表、操作数栈、动态链接、方法返回地址）。**栈帧的生命周期与方法调用同步** —— 方法返回即弹出，**不需要 GC**（但栈溢出会 `StackOverflowError`）。
- **程序计数器（PC Register）**：**线程私有**，记录当前执行的字节码位置。
- **本地方法栈**：线程私有，服务于 Native 方法。
- **方法区（Metaspace）**：JDK 8 起**从堆中独立出来，用本地内存实现**（`-XX:MetaspaceSize` 控制），存放**类元信息、运行时常量池、方法数据**。**它才是真正的"永久代"替代者**（永久代 PermGen 已在 JDK 8 被移除）。
- **直接内存**：不属于 JVM 规范，但 NIO 常用（`DirectByteBuffer`），**不受堆大小限制**，是 OOM 排查时的隐藏坑。

2) **内存溢出（OOM）的常见类型与对应原因**
| 错误 | 原因 |
|---|---|
| `Java heap space` | 堆不够 —— 内存泄漏、一次性大对象、数据量过大 |
| `GC overhead limit exceeded` | GC 时间占比超阈值（默认 98%）仍回收不了多少 —— **通常是内存泄漏** |
| `Metaspace` OOM | 类加载过多（动态代理、脚本、热部署） |
| `Direct buffer memory` | 直接内存耗尽 |
| `unable to create native thread` | 线程数过多、内存不足、或系统层面限制 |
| `StackOverflowError` | 递归过深、栈深度不足 |

3) **GC 机制：如何判断对象"死了"**
- **可达性分析（GC Roots）**：从 **GC Roots**（**线程栈中的引用、静态字段、JNI 引用**）出发遍历对象图，**不可达即被判定为垃圾**。这是**准确的**（不会误杀），但**要暂停所有线程（STW）**。
- **可达性分析 ≠ 引用计数**：引用计数无法处理**循环引用**（a 引用 b、b 引用 a，双方计数都不为 0 却都不可达）→ 所以 Java 用可达性分析。
- **对象晋升**：Minor GC 存活的少数对象 → ** Survivor 区** → 熬过多次 GC → **晋升老年代**；大对象直接进老年代（**大对象阈值**）。**老年代回收成本高得多**，所以要尽量让对象在年轻代就死掉。

4) **GC 算法的核心思想**
- **分代假设**：**绝大多数对象都是朝生夕死的**（朝生夕死的是新生代），**少数对象会长期存活**（老年代）→ **分代收集**。
- **新生代（复制算法）**：`Eden + 2 个 Survivor`（8:1:1 默认）。Minor GC 时把存活对象**复制**到 Survivor（**无需处理死对象、内存连续、分配快**）。代价是** Survivor 空间不足时对象直接晋升老年代**。
- **老年代（标记-清除 / 标记-整理 / 标记-复制）**：先**标记**出存活对象，再**清除**其余；**标记-整理**会压缩内存消除碎片（但需要移动对象，成本高）。
- **写时复制（COW）**：如 `CopyOnWriteArrayList`、`CopyOnWriteArraySet` —— 写时复制整个数组，**读无锁**。适合**读远多于写**的场景。

5) **垃圾收集器的演进与选择**
- **Serial**：单线程，适合小应用与客户端。
- **Parallel Scavenge**（JDK 8 默认）：多线程的**新生代复制 + 老年代标记-整理**，**吞吐优先**。搭配 **Parallel Old** 组成"吞吐优先"组合。**适合批处理、后台计算**。
- **CMS**（JDK 8 默认，**JDK 14 已移除**）：**低延迟优先**，并发标记，但**碎片多**、**CMS 阶段失败会退化为 Full GC**。
- **G1**（**JDK 9+ 默认**）：**把堆划分为 Region**，**每个 Region 独立管理**（Eden/Survivor/Old 不再物理分区），**可预测的停顿模型**（按目标停顿时间挑选回收区域），**支持并发标记**。**兼顾吞吐与延迟**，是当前主流选择。
- **ZGC**（JDK 15+ 正式，**JDK 17 转正**）：**超低延迟**（亚毫秒级停顿），用**染色指针 + 读屏障**实现并发标记与转移，**与堆大小无关**。适合**大堆 + 严苛延迟要求**。
- **Shenandoah**（OpenJDK）：同样追求超低延迟，**支持压缩指针**（ZGC 早期不支持）。

6) **GC 的关键参数（现代 JDK 以 G1 / ZGC 为主）**
| 参数 | 作用 |
|---|---|
| `-Xms` / `-Xmx` | 初始堆 / 最大堆。⭐ **生产环境务必设为相等**，避免运行期反复扩缩 |
| `-XX:MaxGCPauseMillis` | G1 的**目标停顿**（如 200ms），**它通过调整年轻代大小来达成** —— **设小会让 GC 更频繁但单次更快** |
| `-XX:G1HeapRegionSize` | G1 Region 大小（默认按堆大小自动推算，1~32MB） |
| `-XX:InitiatingHeapOccupancyPercent`（IHOP） | G1 **何时启动并发标记**（默认 45%） |
| `-XX:MaxGCPauseMillis` + `-XX:InitiatingHeapOccupancyPercent` | 两者配合决定 G1 的行为，是 **G1 调优的主战场** |
| `-XX:+UseZGC` | 启用 ZGC |
| `-Xss` | 线程栈大小（影响 StackOverflow） |
| `-XX:MaxMetaspaceSize` | 元空间上限（**不设则无上限，动态类加载易 OOM**） |
| `-XX:+HeapDumpOnOutOfMemoryError` | **OOM 时自动 dump 堆快照** ⭐ 必开 |

7) **监控：先建立基线，再看趋势**
- **基础指标**：`jstat -gcutil <pid> 1s`（看 **S0/S1/E/O/MCS** 各区使用率、**YGC/FGC 次数与耗时**、**GCC/OS 占比**）。**GC 占比 > 5%~10% 就要警惕**，接近 98% 就是"GC overhead limit exceeded"的前兆。
- **GC 日志** ⭐ **最重要的手段**。开启 `-Xlog:gc*,safepoint:file=gc.log:time,uptime,level,tags:filecount=10,filesize=64M`（JDK 9+ 统一日志框架；JDK 8 用 `-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:`）。**JDK 8 与 9+ 的日志参数完全不同，务必区分。**
- **GC 日志分析工具**：**GCViewer**、**GCEasy**（可视化分析，最易上手）、**jstat**、**JMC**（Java Mission Control，官方可视化工具）。
- **运行时诊断**：**jcmd**（`jcmd <pid> GC.heap_info`、`Thread.print`、`VM.flags`）、**jmap**（`-histo:live` 看对象分布、**`dump` 打堆快照**）、**jstack**（线程栈）、**jstat**。
- **性能剖析**：**Arthas**（`dashboard`、`trace`、`profiler`、`thread`、`watch`）—— **无需重启即可在生产观测**，是最实用的诊断工具。
- **APM**：SkyWalking、Pinpoint、Elastic APM —— 提供**调用链、火焰图、慢查询**。
- **GC 事件与告警**：注册 `NotificationListener` 监听 GC 事件，**GC 停顿 > 阈值直接告警**（比看平均利用率更有用）。

8) **调优的第一步：定位问题类型**
**① 内存泄漏（持续增长）** —— 现象：老年代使用率**只增不减**，Full GC 后也降不下来。
排查：dump 堆快照 → 用 **MAT（Memory Analyzer Tool）** 分析 → 看 **Dominator Tree**（谁支配了最多内存）→ 看 **Leak Suspects** 报告 → 定位到具体对象与持有链。
**常见泄漏源**：**静态集合无限增长**（用 Map 缓存却从不清理）、**监听器未注销**（内部类/匿名类持有外部引用）、**ThreadLocal 未 remove**（线程池复用 → **数据串号 + 内存泄漏**）、**未关闭的连接与流**、**第三方 SDK 内部缓存**。

**② 内存不足但无泄漏（瞬时大对象）** —— 现象：Full GC 后能降下来，但频繁 Full GC。
处理：**增大堆**、**调小大对象阈值**（`-XX:PretenureSizeThreshold`）、**改用 G1 的大 region 策略**、**减少一次性大数组**、**流式处理替代全量加载**。

**③ 停顿时间过长（延迟问题）** —— 现象：P99 延迟高但平均正常。
处理：**换 G1（默认）或 ZGC（超低延迟）**、**调 `MaxGCPauseMillis`**、**调 IHOP 提前并发标记**、**减少大对象**、**避免频繁 Full GC**。

**④ 吞吐优先场景** —— **Parallel GC + 增大堆**。

9) **调优原则**
- **优先换收集器，而不是调参数** —— 从 CMS 换 G1、从 G1 换 ZGC 的收益远大于精细调参。
- **调参前必须有监控数据**，**没有 GC 日志就调参 = 盲调**。
- **优先增大堆**：大多数"GC 频繁"其实是**堆太小**，而不是收集器不行。
- **优先减少对象分配**：对象分配速率（Allocation Rate）是 GC 频率的根因。**减少临时对象、避免不必要的大对象、复用对象**比调参更根本。
- **`-Xms` = `-Xmx`**：避免堆动态伸缩带来的抖动。
- **每次只改一个变量**，用**相同负载压测**对比，**看 P99 而不是平均值**。
- **不要迷信"调优参数"** —— 很多"GC 问题"的根因是**代码层面的对象管理问题**（无界缓存、不必要的装箱、大量临时集合）。

10) **排查流程（可直接照做）**
```
① 看 GC 日志 → 判断类型：老年代只增不减(泄漏) / 能降但频繁(内存不足) / 停顿长(延迟)
② 泄漏 → dump 堆快照 → MAT → Dominator Tree → 定位持有链 → 修代码
③ 非泄漏 → 扩大堆 + 换 G1/ZGC + 调 MaxGCPauseMillis / IHOP
④ 压测验证 → 对比 P99、GC 占比、分配速率
```

11) **面试答法建议**。四点：**① 内存结构（堆共享、栈线程私有、Metaspace 已独立出堆、直接内存是隐藏坑）；② GC 机制（可达性分析 + 循环引用 + 分代假设 + 复制算法 + 晋升）；③ 收集器选型（Parallel 吞吐 / G1 均衡可预测 / ZGC 超低延迟）与关键参数；④ 监控与调优流程（GC 日志 → 分型 → MAT 定位泄漏 / 调堆与收集器 → 压测验证），并强调**"优先减少分配与增大堆，而非盲目调参"**。** 第四点的"分型判断"是最能体现实战经验的部分。
