子 Agent 模式指：**主 Agent（父）把某个子任务整体委托给一个独立的 Agent（子）执行**，子 Agent 有自己独立的上下文、提示和工具集，只把**结论**返回给父 Agent。这本质上是用"**上下文隔离**"换取"**结构复杂度**"。

1) **核心优势是上下文隔离**。子 Agent 的中间过程（试错、原始数据、大段工具返回）留在自己的上下文里，父 Agent 只拿到**精炼结论**。这直接缓解了主上下文的膨胀问题 —— 这是子 Agent 模式最主要的收益。

2) **第二个优势是专业化与并行**。子 Agent 可以有**专属的提示、工具集与模型**，比如"代码审查 Agent"只带静态分析工具、"数据清洗 Agent"只带 SQL 工具；互不依赖的子任务**可并行执行**，压缩总延迟。

3) **第三个优势是权限与故障隔离**。子 Agent 天然是**权限边界**（只给它完成任务所需的最小工具集），且某个子 Agent 出错或被攻击，**不会污染主上下文**，爆炸半径可控。

4) **第四个优势是可复用与可替换**。子 Agent 是独立可测的单元，可以单独评测、单独优化模型与提示、单独灰度。

5) **挑战一：上下文交接处的信息损失**。这是最核心的问题。父 Agent 传给子 Agent 的任务描述可能**不完整**（父不知道子需要的某个上下文），子返回的结论可能**丢失关键前提**（父看不到子踩过的坑）。**解法**：定义**结构化的任务交接契约**（明确输入、明确输出 schema、明确成功标准、明确不可做的事），并让子 Agent 返回**结论 + 依据 + 未决问题**三部分，而不只是一个答案。

6) **挑战二：委派决策本身的可靠性**。父 Agent 要判断"这个任务该不该委派、交给谁"。委派判断错误（该自己做却外包、或不该外包却自己做）会显著降低效率与质量。**解法**：给委派规则设**明确判据**（如"需要独立上下文且输出可验证"才委派），并**记录委派决策的正确率**作为指标。

7) **挑战三：错误传播与归因困难**。子 Agent 失败时，父 Agent 看到的是一句"失败"，难以定位是任务描述不清、子能力不足、还是工具出错。**解法**：子 Agent 必须返回**结构化失败原因**（分类），并保留**可追溯的子轨迹**。

8) **挑战四：成本与延迟叠加**。子 Agent 有自己的系统提示、工具定义、至少一次模型调用，**固定开销不小**；串行委派会累积延迟，并行委派会推高并发与成本。**解法**：只在**上下文隔离收益确实大于开销**时使用；小任务直接父 Agent 做。

9) **挑战五：循环委派（乒乓）**。父把任务给子，子又把子任务委派出去，形成无限递归或互相推诿。**解法**：**限制委派深度**（如最多 1~2 层）、子 Agent **不允许再委派**、设置**总预算与总步数**跨父子共享。

10) **边界问题的完整清单**。**深度与递归**（最多几层）；**权限继承**（子只拿到任务必需的子集权限，**不继承父的全部权限**，且父对子有**权限收窄**而非放大）；**预算共享**（父子共用同一份 token/时间预算，防止子无限消耗）；**结果契约**（子返回什么、什么格式、什么算成功）；**失败语义**（子失败是返回错误让父重试、还是父接管）；**可观测性**（父子调用需统一 trace id）；**幂等与副作用**（子产生的外部副作用如何回滚与补偿）；**共享状态**（父子通过外部存储共享状态，而不是靠传消息）。

11) **实践建议**。**子 Agent 最适合"脏活"** —— 大量数据处理、深度检索、多轮试错、独立领域任务。**不适合"需要全局判断"的核心决策**，因为父 Agent 恰恰失去了这些细节。同时**一定要给子 Agent 一个干净但完整的上下文**，并**把子返回的结论当成不可信输入做校验**（子也可能被注入）。
