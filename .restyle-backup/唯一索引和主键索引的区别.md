两者**都是索引**，但定位完全不同：**主键索引 = 唯一 + 非空 + 聚簇（数据的物理组织方式）**；**唯一索引 = 只保证"不重复"，不改变数据存储方式**。

1) **⭐ 最本质的区别：是不是聚簇索引**
- **主键索引必然是聚簇索引**（InnoDB）—— 叶子节点存放**整行数据**，数据与索引在**同一棵 B+ 树**上
- **唯一索引默认是非聚簇**（二级索引）—— 叶子节点存放**索引列值 + 主键值**，查完可能还要**回表**
> **这是最容易答错的点**：很多人以为"唯一索引和主键索引只是约束不同"，其实**连存储结构都不同**。

2) **⭐ 唯一索引的真正价值：把"业务唯一性"下推到数据库**
主键只能有一列、且必须非空自增；而"手机号唯一""身份证唯一""订单号唯一"这类**业务唯一约束**，只能靠唯一索引实现。
- **没有唯一索引** → 并发下会插入重复数据，只能靠应用层加锁校验（**有并发窗口，不可靠**）
- **有唯一索引** → 数据库直接拒绝，**是并发场景下的最后一道防线**
> **典型场景：并发创建用户，同一个手机号 —— 靠应用层"先查再插"必然有并发问题，靠唯一索引才能真正兜住。**

3) **约束严格度对比**
| | 主键索引 | 唯一索引 |
|---|---|---|
| 唯一性 | ✅ | ✅ |
| **非空** | ✅ **NOT NULL** | ⚠️ **可为 NULL**（MySQL 中 NULL 不参与唯一性判断，可有多行 NULL） |
| 数量 | 每表 **仅 1 个** | **多个** |
| 聚簇索引 | ✅ 必然是 | ❌ 默认不是 |

4) **⭐ NULL 的特殊语义（高频细节）**
MySQL 的唯一索引**允许多行 NULL**（因为 `NULL <> NULL` 判定为"不相等"）。
> **所以如果业务要求"该字段唯一且不能为空"，必须同时写 `NOT NULL`**，否则会出现多条 NULL 记录。

5) **性能对比**
- 主键查询 → **不回表**，一次 B+ 树查找直接拿到整行
- 唯一索引查询 → 若查询列不在索引中 → **需要回表**（多一次随机 IO）
> **所以等值查询用唯一索引定位后，仍需回表拿其他列；而主键查询不需要。** 但如果查询只需要索引列，**两者性能几乎一致**（都是一次索引查找）。

6) **⭐ 二级唯一索引的"锁"特性（高频追问）**
在 RR 隔离级别下，**对唯一索引做等值查找（`WHERE uk = ?`）会加记录锁（不加间隙锁）**；而对**非唯一索引**或**范围查询**会加**间隙锁/临键锁** —— 这直接影响并发插入能否被阻塞。
> **典型区别**：唯一索引上的 `WHERE uk = 'x'` 能**并发插入不同值**；普通索引的范围查询会**锁住间隙，阻塞插入**。

7) **⚠️ 唯一索引不是越多越好**
- 每个唯一索引都是一棵独立 B+ 树 → **写入时都要维护**
- 唯一索引**太严格会拖慢写入**（要加唯一性校验、并发冲突时还会阻塞等待）
- 常见优化：**业务上允许重复但希望"去重"**的场景，用**普通索引 + 应用层去重**比唯一索引更灵活

8) **主键的选择建议**
- **聚簇索引决定了数据的物理顺序** → 主键应**尽量短**（`BIGINT` 优于 `UUID CHAR(36)`），因为**所有二级索引的叶子节点都存主键值** → 主键越长，**所有索引都会膨胀**
- **⚠️ 强烈不推荐用 UUID 字符串做主键**（36 字符 + 无序 → 页分裂 + 全索引膨胀）→ 用 **雪花算法（有序 BIGINT）** 或 **有序 UUID**

9) **面试答法建议**。三点：**① 本质区别是"是否聚簇索引"**（数据物理组织方式不同，不是简单的约束差异）；② **唯一索引的真正价值 = 把业务唯一性下推到数据库、作为并发下的最后防线**（并强调 NULL 可重复的坑）；③ **锁行为差异（唯一索引等值查找用记录锁，普通索引范围查询加间隙锁）**。**第三点的锁粒度差异最能体现对 InnoDB 锁机制的掌握。**
