MCP（Model Context Protocol，模型上下文协议）是一套**开放协议**，用于标准化 AI 应用与外部资源（数据、工具、提示模板）之间的连接方式。它定义了客户端与服务器之间的通信规范、资源暴露方式、工具描述格式和提示模板机制，让不同的 AI 应用能够以统一方式接入各种数据源与工具，而不必为每个数据源单独写集成代码。

1) **它解决的核心问题是"集成碎片化"**。在此之前，每个 AI 应用要接一个数据源就得写一套适配，每接一个工具就多一套代码，N 个应用 × M 个数据源就是 N×M 的工作量。MCP 把**数据源与工具抽象成统一的 Server**，应用只做一次 MCP Client 适配，复杂度降到 N+M。**这是它最大的价值。**

2) **它统一了"上下文供给"的三类资源**。**Tools**（可被调用的动作）、**Resources**（可读取的上下文数据，如文件、数据库记录）、**Prompts**（可复用的提示模板）。这三类以不同语义暴露，客户端可以按需取用。

3) **它基于 JSON-RPC 2.0**，采用 **Client-Server 架构**。Host（宿主应用，如 Claude Desktop、IDE）内嵌多个 Client，每个 Client 与一个 Server 建立**独立会话**；Server 侧实现具体的 MCP 协议并对接真实系统。

4) **传输方式**。标准传输是 **stdio**（本地进程，适合本地工具）；另有 **SSE** 和 **Streamable HTTP**（远程部署）。远程部署时必须考虑**认证与授权**。

5) **关键能力：能力协商与动态发现**。Client 初始化时与 Server 交换协议版本与能力声明，之后可以调用 `tools/list`、`resources/list` 拉取可用能力列表。**这意味着工具是动态发现的** —— 新增工具无需改客户端代码。

6) **采样（Sampling）与 Roots 的反向能力**。Server 可以反向请求 Client 代为调用 LLM（让 Server 复用宿主的模型能力与配额），也可以请求 Client 暴露文件系统等根目录上下文。这让 Server 不必自己绑定模型。

7) **它与 Function Calling 的关系**。**Function Calling 是模型接口层面的机制**（模型输出结构化调用意图）；**MCP 是应用与工具之间的协议层**（规定工具怎么被描述、发现、调用、返回）。两者是**互补的上下层**，MCP 内部完全可以用 Function Calling 来实现 LLM 侧的推理。

8) **它推动生态从"框架竞争"转向"标准竞争"**。MCP 已被主流 IDE 与 Agent 框架广泛支持，工具作者只需实现一次 Server，就能在多个宿主中使用。**这是它快速普及的根本原因。**

9) **需要注意的边界与风险**。它标准化了"怎么接工具"，但**没有解决**工具越权、提示注入、结果可信度这些问题 —— 这些仍然需要宿主侧自己做**权限隔离、信任分级、脱敏与审计**。MCP Server 引入的第三方代码，本质上扩大了攻击面。
