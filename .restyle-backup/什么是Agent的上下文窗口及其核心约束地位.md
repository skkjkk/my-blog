上下文窗口是模型在单次推理中能"看到"的 token 总量上限，包含系统提示、工具定义、历史消息、检索到的资料、工具执行结果和当前输出预留。Agent 工程里几乎所有难题，最终都能追溯到**这个窗口是有限且昂贵的**这一事实。

1) **它同时是容量约束和成本约束**。窗口满了就必须丢弃或压缩历史，而丢弃意味着丢失信息；同时每个 token 都要付费，且每轮都要**重发全部历史**，所以成本随步数呈超线性增长。**上下文管理是 Agent 系统最主要的成本项和性能瓶颈。**

2) **它是"记忆"必须外置的根本原因**。Agent 往往需要记住几十步之前的事实、用户的偏好、历史决策，这些放不进窗口。解决办法是把状态外置到外部存储（文件系统、向量库、KV 存储、任务树），上下文里只保留**当前决策必需的最小信息 + 引用**。

3) **它是长程任务退化的根源**。步数增加后，窗口里堆满冗长 observation、失败尝试和工具返回，噪声占比上升、关键目标被稀释，注意力被拉散；同时早期关键信息在窗口触顶后被截断或粗暴摘要，导致**目标漂移**与**错误级联**。

4) **它决定了"上下文压缩"成为必备工程能力**。常见策略有四种：**截断**（保留最近 N 轮，最简单但会丢早期约束）、**摘要**（用模型把历史压成摘要，损失细节）、**外置**（结果存外部、上下文只留引用，最稳但增加了检索依赖）、**结构化保留**（只保留实体、数值、决策点、未决事项等结构化片段）。生产中通常**分层组合**使用。

5) **它带来"位置效应"这一隐含约束**。长上下文中间部分的信息容易被忽略（所谓 lost in the middle），所以**重要内容应放在提示的靠前或靠后位置**，而非埋在中间。

6) **它倒逼工具返回结果的设计**。工具返回一大段 HTML 原文会瞬间吃满窗口，因此工具层应当**主动裁剪与摘要** —— 例如只返回与问题相关的片段、只返回前 N 条并注明总数、或只返回结构化字段。**工具结果的裁剪策略往往比换模型更能提升 Agent 表现。**

7) **它与上下文工程（Context Engineering）的区别**。Prompt Engineering 关注单次提示怎么写；**Context Engineering 关注"每一轮该往窗口里放什么"** —— 检索什么、压缩什么、隔离什么、丢弃什么。这是 Agent 时代的核心能力，也是"上下文窗口是最核心约束"的深层含义。
