分布式锁要解决的是"多个服务实例并发操作同一份共享资源时的互斥"，实现上有三条主流路线，选哪条取决于对可靠性、吞吐和运维复杂度的取舍。

1) **基于数据库实现**。利用数据库的主键唯一约束或 `select ... for update` 行锁来保证互斥，常见做法是建一张锁表，以资源标识作为主键，插入成功即拿到锁，删除记录即释放锁。实现最简单、无需额外组件，适合并发量不高、对可靠性要求一般的场景。

2) **基于 Redis 实现**。用 `SET key value NX EX seconds` 这条命令原子地完成"不存在才设置 + 设置过期时间"，释放锁时用 Lua 脚本比对 value 再删除，避免误删他人持有的锁。因为 Redis 是内存数据库，吞吐高、延迟低，是目前最主流的选择。Redisson 提供了成熟的实现，支持可重入、看门狗自动续期、锁等待与多种数据结构。

3) **基于 ZooKeeper 实现**。在 `/lock` 节点下创建**临时顺序节点**，靠"序号最小者获得锁"的规则实现互斥，节点会话断开时自动删除。相比 Redis，它的**一致性语义更强**，因为临时节点与会话绑定、会话失效即自动释放，不会出现死锁。但部署与运维更重，写性能也低于 Redis。

4) **三种方案的关键对比**。数据库实现简单但并发能力弱；Redis 性能最好但属于 AP 模型，极端故障切换时可能丢失锁，需要业务侧做兜底；ZooKeeper 属于 CP 模型，强一致但可用性与性能有代价。生产上常见的选择是：并发高、允许极小概率的锁丢失场景用 Redis；强一致要求高、规模不大的核心场景用 ZooKeeper。

5) **必须处理的三个工程细节**。第一是**锁超时**。锁一定要带过期时间，防止持有者宕机后形成死锁；但业务执行时间可能超过超时，所以要用**看门狗机制定期续期**（Redisson 默认会自动续期）。第二是**误删锁**。释放锁时必须校验锁的持有者标识（如随机 UUID），否则 A 的锁超时后被 B 拿到，A 恢复后执行删除就会误删 B 的锁，这需要用 Lua 脚本保证"比对 + 删除"的原子性。第三是**重入**。业务可能嵌套加锁，需要记录持有者线程标识和重入次数，保证同一线程可重入、不同线程互斥。

6) **更完善的方案需要补齐什么**。生产级的分布式锁还应支持：锁的**自动续期**、**可重入**、**公平性**（FIFO 排队）、**看门狗**（续期与超时接管）、以及**多模式**（读锁、写锁、红黑锁）。Redisson 基本覆盖了这些能力。

7) **除了锁本身还要考虑的事**。很多场景下真正的瓶颈不是互斥而是并发度限制，因此生产上常配合**分布式信号量**（限制并发数）、**分布式限流**、**幂等控制**一起使用。另外如果操作本身是幂等的，引入分布式锁的收益可能远小于它带来的复杂度与故障风险。

8) **协调服务与方案选型的补充**。除了 Redis 和 ZooKeeper，近年也出现了基于 etcd 的实现，etcd 提供强一致与租约机制，是 Kubernetes 生态的天然选择。趋势上是从"各家自研锁"走向"使用成熟中间件或云厂商提供的托管锁服务"，以降低自研带来的正确性风险。
