这三个是**并发读取时由于隔离级别不足导致的数据异常**。先给结论：**脏读 < 不可重复读 < 幻读**，严重程度递增（幻读的影响面最大）。

1) **⭐ 脏读（Dirty Read）**
一个事务**读到了另一个事务尚未提交的数据**。
> 场景：A 事务把余额从 100 改成 0（**未提交**）→ B 事务读到了 0 → **A 事务回滚** → B 读到的 0 是**根本不存在的数据**。
> **最危险**：B 基于脏数据做了决策（如"余额为 0，库存不足，拒绝下单"），而实际数据是 100 → **业务决策错误**。

2) **⭐ 不可重复读（Non-Repeatable Read）**
一个事务在**两次读取同一行数据**之间，**别的事务修改并提交了它**，导致**前后两次读到的值不同**。
> 场景：A 事务读余额 = 100 → B 事务改成 50 并提交 → A 事务再读 = 50。
> **⚠️ 关键限定：针对的是"UPDATE"（修改已存在的行）**，影响的是**单行数据的值**。

3) **⭐ 幻读（Phantom Read）**
一个事务在**两次执行相同的范围查询**之间，**别的事务插入/删除了符合条件的新行**，导致**前后两次查询返回的"行数"不同**。
> 场景：A 事务 `SELECT * FROM orders WHERE amount > 100` 查到 10 行 → B 事务插入 1 条 amount=200 的订单并提交 → A 事务再查 → **11 行**，多出来的那行就是"幻影行"。
> **⚠️ 关键限定：针对的是"INSERT / DELETE"**，影响的是**结果集的"行集合"**。

4) **⭐ 三者的本质区别（表格对比）**
| | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| **读到了什么** | **别的事务未提交**的数据 | **别的事务已提交**的修改 | **别的事务已提交**的新增行 |
| **触发操作** | 读 | **UPDATE**（改值） | **INSERT / DELETE**（改行数） |
| **影响对象** | 值的**正确性** | 同一行的**值不一致** | 结果集的**行数不一致** |
| **严重程度** | 最高 | 中 | 中（但影响面最广） |

5) **⭐ 四种隔离级别与三种异常的对应关系**
| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| **读未提交（RU）** | ❌ 可能 | ❌ 可能 | ❌ 可能 |
| **读已提交（RC）** | ✅ 避免 | ❌ 可能 | ❌ 可能 |
| **可重复读（RR）** | ✅ 避免 | ✅ 避免 | ⚠️ **基本避免**（有例外） |
| **串行化（Serializable）** | ✅ 避免 | ✅ 避免 | ✅ 完全避免 |

6) **⭐ MySQL 的 RR 并不完全解决幻读（高频陷阱）**
InnoDB 在 RR 下通过**MVCC + 间隙锁 + 临键锁**避免了大部分幻读，但有两个例外：
- **① 当前读（Current Read）仍会幻读**
  - **快照读**（普通 `SELECT`）→ 读 MVCC 快照版本 → **看不到别的事务新提交的行** → 不幻读
  - **当前读**（`SELECT ... FOR UPDATE` / `FOR UPDATE` / `UPDATE` / `DELETE` / `LOCK IN SHARE MODE`）→ **读最新版本 + 加锁** → **会看到新插入的行** → **可能幻读**
- **② MVCC 的"快照"是事务第一次读时建立的** —— 同一事务内**后续的快照读**都用同一个快照 → 这就是"可重复读"的实现

7) **⭐ 间隙锁是防幻读的核心机制**
InnoDB 在 RR 下对**范围查询加锁**时用**临键锁（Next-Key Lock）= 记录锁 + 间隙锁** → **锁住"记录之间"的空隙** → **阻止其他事务插入新行** → 从源头消除幻读。
> **⚠️ 但间隙锁是双刃剑**：它会**阻塞插入**，在高并发下**显著增加锁等待与死锁概率** → 这也是很多系统用 **RC 级别换取并发**的原因。

8) **⭐ 解决幻读的三个务实选项**
- **① 用 RC 隔离级别**（放弃部分一致性，换并发与较少死锁）—— **互联网高并发场景的常见选择**
- **② 保持 RR + 接受当前读的幻读**，**在业务层做唯一性约束兜底**（如用唯一索引防重复下单）
- **③ 需要严格一致时用 Serializable**（⚠️ 性能代价大，基本只在极少数场景用）

9) **⭐ 实战中的真实风险排序（与教科书不同）**
实际系统里，**最常遇到的不是"幻读"，而是"不可重复读"带来的业务错误**：
- **读-改-写场景**：先查库存再扣减 → 中间被别人改了 → **超卖**
- **判断-执行竞态**：`if (containsKey) put` → 并发下重复插入
> **这些问题的正解不是加隔离级别，而是用条件更新、唯一索引、乐观锁版本号** —— **靠数据库的原子操作，而不是靠隔离级别**。

10) **⭐ 一句话记忆**
> **脏读 = 读到不该存在的（未提交）；不可重复读 = 同一行前后值不一致（被改）；幻读 = 结果集前后行数不一致（被增删）。**

11) **面试答法建议**。四点：**① 三者的定义与触发操作差异（脏读=未提交、不可重复读=被 UPDATE、幻读=被 INSERT/DELETE）；② 四种隔离级别的对应关系；③ MySQL RR 的两个例外（当前读仍会幻读 + MVCC 快照在首次读时建立）；④ 落地观点（间隙锁防幻读但增加死锁，实际问题应靠条件更新与唯一索引而非堆隔离级别）**。**第三点的"当前读仍幻读"和第四点的"别靠堆隔离级别"最能拉开差距。**
